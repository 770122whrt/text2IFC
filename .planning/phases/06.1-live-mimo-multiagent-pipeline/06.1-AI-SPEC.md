# Phase 6.1 AI Design Contract

## Provider

- Protocol: Anthropic-compatible Messages API
- Model source: `TEXT2IFC_MIMO_MODEL`
- Acceptance model: `mimo-v2.5-pro`
- Authentication: environment variable only
- Base URL: environment variable only; never persisted
- `max_tokens`: `131072`
- Transport: streaming SSE for live acceptance
- Accepted terminal reason: `end_turn`

The exact raw provider response is evidence. The extracted text is a derived
artifact and cannot replace the envelope.

## Agent Call Contract

Every semantic call records:

- run ID, case ID, role, attempt number, and timestamps
- prompt template ID/hash and structured renderer input paths/hashes
- rendered prompt
- redacted request body
- every SSE event in order
- reconstructed exact response envelope
- response ID, model, `stop_reason`, and usage
- untouched text content and any non-text content block metadata
- normalization diagnostics
- parsed object or parse error
- schema/semantic/gate feedback
- route and artifact paths

Provider endpoint, token, authorization headers, and `.env` content are never
recorded.

## Design Brief Agent

### Inputs

- original Chinese request
- immutable conversation transcript
- Design Brief JSON Schema
- relevant BIM JSON 2.0 schema fragments
- relevant IFC2X3 generation capability records
- relevant few-shot examples and their IDs
- prior deterministic diagnostics, when rerunning after a format failure

### Output

Exactly one Design Brief object. The schema must distinguish:

- known facts and their user/source evidence
- corrections and superseded facts
- missing facts and why they matter now
- ambiguities and whether they block generation
- unsupported intent
- readiness status
- one to three clarification questions when clarification is required

Every missing fact/question must cite an evidence path present in the supplied
schema/capability/example context. This is evidence grounding, not a global
field whitelist.

### Evaluation

- schema validity
- question count and mapping
- evidence-path validity
- unsupported-question rate
- user-fact preservation
- correction preservation
- readiness consistency
- human review of question relevance on the live matrix

## BIM JSON Generator

### Inputs

- original request and transcript
- ready Design Brief
- full canonical Formal BIM JSON 2.0 schema
- full canonical Draft Envelope 1.0 schema
- supported generation capability profile
- relevant geometry/relationship few-shots
- exact output discriminator rules

### Output

Exactly one JSON object and no Markdown/prose:

- Formal: `schema_version == "bim-json/2.0"`; or
- Draft: `draft_version == "bim-json-draft/1.0"` and
  `target_schema_version == "bim-json/2.0"`.

Unknown versions are blocked, not repaired by migration.

### Evaluation

- whole-response parse success
- exact discriminator classification
- schema and semantic validity
- user-fact coverage and contradiction rate
- compiler/reopen success for Formal output
- Phase 4 geometry/relationship/structure metrics

## Repair Mode

Repair uses the Generator prompt family with an explicit repair mode and one
attempt maximum. Inputs include the immutable original evidence and exact
deterministic diagnostics. The fact-delta gate rejects newly invented facts.

Eligible examples include a wrong enum, missing required wrapper field already
derivable from the supplied canonical contract, or inconsistent reference ID
that can be resolved from the candidate. Missing dimensions or unsupported user
semantics are not repairable; they route to Draft/clarification.

## Audit Agent

Audit runs after deterministic terminal status. It receives references and
bounded content for the user request, transcript, Design Brief, final candidate
or Draft, validation, routing, IFC/geometry metrics, and artifact manifest.

Output is exactly one audit JSON object containing verdict, findings, evidence
paths, intent coverage, contradictions, residual uncertainty, and deterministic
gate status. The Audit verdict cannot be `pass` when any mandatory deterministic
gate failed.

## Prompt Versioning

Behavior-changing prompts are new registry entries, initially:

- `design-brief.v2`
- `bim-json-generator.v2`
- `bim-json-generator-repair.v2`
- `audit.v2`

Historical v1 files and hashes remain immutable evidence. A candidate prompt is
promoted only after recorded live comparison on the acceptance matrix. Prompt
iteration must report both improvements and regressions.

## Few-shot and Retrieval Policy

Few-shots demonstrate conditional behavior, schema shape, geometry semantics,
and failure routing. They cannot contain hidden defaults presented as universal
requirements. Retrieval returns only versioned source records and persists the
selected IDs/hashes so a call can be reproduced.

Initial retrieval may be deterministic keyword/capability selection. A vector
RAG system is not required until measured retrieval failures justify it.

## Human and Observer Roles

The user supplies or corrects semantic facts. The Observer may pause, diagnose,
classify, and report. Neither the Observer nor a developer-authored fixture may
substitute semantic content inside a live acceptance trace.
