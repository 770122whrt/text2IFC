# Phase 6.2-fix: Real-time REPL CLI UAT - Specification

**Created:** 2026-06-26
**Updated:** 2026-06-28
**Ambiguity score:** 0.06 (gate: <= 0.20)
**Requirements:** 20 locked
**Status:** Revised after real UAT defect 005

## Goal

Replace the Phase 6.2 scripted/file-style acceptance gap with a true
Chinese-first terminal REPL where a human can type a request, see Mimo's
clarification questions immediately, answer them turn by turn, and receive a
validated IFC2X3 artifact plus a DB-backed review report.

## Background

Phase 6.2 successfully built a real Mimo-backed backend pipeline: shared
SQLite sessions, Design Brief calls, Generator calls, Audit calls,
deterministic validation, IFC compilation, report generation, and query/export
commands. However, its final acceptance did not match the intended product
experience. The accepted run relied on UTF-8 file/scripted input as practical
automation evidence, and `scripts/agent/run_phase6_2_cli.py` still behaves
like a pipeline entrypoint that prints a final JSON summary rather than a
human-facing conversation loop.

The missing behavior is not another provider integration and not a new model
architecture. The missing behavior is a product boundary: the user must be able
to run one command, type Chinese text in a terminal, see each Mimo-authored
question before entering the next answer, and inspect the resulting artifacts.
Regression tests may still use fake providers and scripted input, but the
final acceptance must prove a real REPL session rather than a preloaded answer
stream.

Real UAT on 2026-06-27 exposed a third acceptance defect. The rectangular-room
session `f2a8cdea36b88997` reached Formal BIM JSON, `no_repair_needed`, real
Audit `accepted`, IFC compile/reopen success, and then failed the final
geometry gate with `WALL_ORIENTATION_MISMATCH` and `ROOM_ENCLOSURE_OPEN`.
The root cause was a stage-order contract mismatch: Audit saw validation and
repair-route evidence, but the geometry feedback was produced only after Audit
had already accepted. The next fix must move deterministic gate evidence in
front of decisive Audit and route confirmed failures back to repair/generation
instead of letting the REPL end as "Audit accepted, final gate blocked".

The follow-up live UAT session `d462b95089755d47` proved the ordering fix can
produce a real accepted IFC, but post-review exposed a fourth acceptance
defect. Some checks were still too self-referential: wall geometry expectations
could be derived from the generated candidate itself, so they proved compiler
faithfulness to the candidate rather than candidate faithfulness to the user's
Design Brief. The same run also showed an explicit user fact,
`door.opening_direction: "into_space"`, preserved in the Design Brief but not
represented in current BIM JSON/IFC support. Phase 6.2-fix must therefore add a
semantic fidelity boundary: every explicit user fact must be represented,
compiler-generated, marked unsupported/Draft, waived by the user, or blocked.
Unsupported facts must not be hidden in custom properties and counted as IFC
support.

Real UAT on 2026-06-28 exposed a fifth acceptance defect in session
`3aa55eb71f464ff8`. The Design Brief was `ready`, and Mimo returned parseable
JSON, but the Generator output was contract-invalid: `IfcDoor` lacked required
semantic geometry and the model emitted unsupported explicit relationships
`IfcRelAggregates` and `IfcRelContainedInSpatialStructure`. The current
pipeline saved the parseable output only as `generator/parsed-output.json`;
`repair` only accepts `generator/candidate.json` as its previous candidate, so
the bounded repair loop saw `previous_candidate=None` and immediately recorded
`blocked_failure`. This is a loop-contract defect: actionable, parseable
invalid Formal output must enter bounded repair/regeneration or Draft routing
with evidence instead of ending as an unrepairable pipeline block. The same run
also showed that Design Brief normalized `walls.placement` to Chinese `"外侧"`
rather than the canonical support value `outside_boundary`, which can prevent
semantic gates from consistently applying explicit user geometry intent.

## Requirements

1. **One-command REPL entrypoint**: A user can start a live chat-style text2IFC
   session without `--scripted-stdin`, prewritten answer files, or a hidden
   answer list.
   - Current: `scripts/agent/run_phase6_2_cli.py` supports live Mimo calls but
     is pipeline-shaped and commonly invoked with `--scripted-stdin`,
     `--stop-after`, and explicit output flags.
   - Target: A command such as
     `.venv\Scripts\python scripts\agent\run_text2ifc_chat.py --live`
     opens a Chinese-first REPL, prompts for the initial request, and owns the
     full Design Brief -> BIM JSON -> IFC route.
   - Acceptance: Running the REPL command with no scripted input source starts
     with a visible Chinese prompt for the user's building request and creates
     a session row with `interaction_mode: "human_repl_live"`.

2. **Turn-by-turn Mimo clarification**: The REPL prints Mimo's 1-3
   Design-Brief clarification questions before reading the user's next answer.
   - Current: `run_design_brief_clarification_loop` accepts an iterable of
     `user_answers`; it persists transcript turns but does not expose a
     question-then-wait conversational boundary to the user.
   - Target: A stepwise controller invokes Mimo, persists the assistant turn,
     prints the Chinese questions, then blocks for user input. The answer is
     appended only after the question is visible and persisted.
   - Acceptance: A RED/GREEN test proves the answer reader is not called until
     after the assistant question has been printed and an assistant turn/event
     has been recorded.

3. **Human-facing Chinese terminal UX**: The REPL displays the process in
   readable Chinese instead of only dumping final JSON.
   - Current: The live CLI returns a machine JSON result at the end and keeps
     intermediate outputs mainly in artifacts.
   - Target: The terminal shows concise Chinese status lines for session
     creation, Mimo thinking/call completion, clarification questions, BIM JSON
     validation, IFC generation, report/export writing, Draft/blocking status,
     and final artifact paths. Raw JSON is shown only under an explicit debug
     option.
   - Acceptance: Tests over fake providers assert visible strings for initial
     prompt, Mimo question display, validation progress, final IFC path, report
     path, and session hash.

4. **Same evidence-rich pipeline after readiness**: Once Design Brief reaches
   `ready`, the REPL reuses the Phase 6.2 Generator, deterministic gates,

   - Current: The pipeline exists but is driven by a backend-oriented CLI.
   - Target: The REPL does not create a parallel BIM JSON model or second
     compiler path; it routes the ready session into the existing verified
     Phase 6.2 flow.
   - Acceptance: The REPL final Formal run writes and reopens
     `dataset/processed/agent-demo/phase6.2-fix-repl/runs/<session_hash>/output.ifc`

5. **Shared session DB and query/export compatibility**: REPL sessions remain
   first-class records in one shared SQLite DB and can be queried, resumed, and

   - Current: Phase 6.2 has a shared session DB and query/export commands.
   - Target: REPL sessions use the same DB schema and query/export surface,

   - Acceptance: `query_phase6_2_sessions.py list/show/turns/calls/artifacts/export`

6. **Generated report proves interaction mode**: The generated `report.md`

   - Current: Phase 6.2 report is DB-backed and artifact-linked, but it does

   - Target: The report includes original input, terminal transcript summary,

   - Acceptance: Report completeness tests reject a report missing

   - Target: The pipeline produces a gate-evidence bundle before decisive

    - Current: Audit can accept a candidate because it never saw the later

    - Target: If deterministic gates fail, Audit must return a blocking route:

      accepted IFC through Audit wording.
    - Acceptance: Tests reject an Audit `accept` recommendation when geometry
      feedback contains blocking issues, and prove a gate dispute blocks for
      human/developer review instead of passing.

11. **Geometry feedback can drive bounded repair**: Confirmed geometry failures
    route back to the BIM JSON Generator repair path with exact issue evidence.
    - Current: Repair happens before final geometry feedback exists, so final

    - Target: A true-positive geometry failure creates a bounded repair attempt

      relationships.
    - Acceptance: A west/east wall orientation failure produces either a

12. **Trace, report, and terminal visibility for the gate-audit-repair loop**:
    The user must be able to see why a run was repaired, blocked, or accepted.
    - Current: The REPL now prints final-blocked paths, but the report does not
      yet express the corrected gate -> Audit -> repair sequence.
    - Target: Terminal status, session events, `report.md`, and

      attempts, attempt count, final gates, and final route.
    - Acceptance: Report completeness tests fail if geometry feedback,
      Audit classification, repair attempt evidence, or final route are
      missing from a run that encountered geometry issues.

13. **Design-derived geometry expectation**: Geometry gates for user-stated
    rectangular room boundary facts must derive expectations from the Design
    Brief and explicit user facts, not solely from the generated candidate's

    - Current: `_wall_geometry_expectation_from_candidate` can build expected
      wall bounding boxes from the same candidate it later checks. That proves
      compiler fidelity to the candidate, but it can miss candidate-level
      semantic drift from the Design Brief.
    - Target: For supported rectangular-room cases, the gate writes a

      as space net dimensions, wall thickness, wall outside/inside boundary
      intent, storey elevation, and wall closure. Candidate-derived geometry
      may remain as compiler-fidelity evidence, but it cannot be the only

    - Acceptance: A fixture where the Design Brief says "internal clear

      a 0.1m gap between wall inner faces and the space boundary fails with a
      stable semantic geometry issue before Audit can accept.

14. **Semantic capability contract for model prompts**: Generator and Audit
    must receive a machine-readable semantic capability profile that tells
    them which explicit facts can be represented in Formal BIM JSON/IFC today,
    which facts are compiler-generated, and which facts must remain Draft or
    unsupported.
    - Current: The pipeline exposes class-level capability states such as
      `IfcDoor` generate and `IfcDoorStyle` unsupported, but it does not expose
      a fact-level contract for requests such as inward door swing or window
      operation semantics.
    - Target: A versioned capability profile is rendered into prompt inputs and
      trace artifacts. It is not a second BIM JSON model and does not replace
      JSON Schema; it is a support-boundary contract for generation, audit, and
      Draft routing.
    - Acceptance: Prompt render inputs for Generator and Audit include the
      capability profile ID/hash and at least one test proves the model is told
      that current `door.opening_direction` semantics are unsupported unless a
      future compiler capability explicitly supports them.

15. **Unsupported explicit facts route to Draft/blocking state**: A Formal IFC
    cannot be accepted when an explicit user fact is unsupported by current
    BIM JSON/IFC generation capability unless the user explicitly waives that
    fact.
    - Current: A user can state "door opens inward"; Design Brief may preserve
      it, but the current Formal BIM JSON/IFC path can accept without encoding
      that semantic fact.
    - Target: Unsupported explicit facts are recorded in semantic coverage as
      `unsupported_draft`, `blocked_unknown_capability`, or `waived_by_user`.
      If not waived, the run remains Draft/blocked and writes no accepted IFC.
    - Acceptance: A live or deterministic fixture with
      `door.opening_direction: "into_space"` fails Formal acceptance under
      current capabilities and produces a Draft/blocking route with a Chinese
      explanation rather than an accepted IFC.

16. **Semantic coverage report and verifier**: The generated report and final
    verifier must expose whether every explicit Design Brief fact reached a
    terminal coverage state.
    - Current: Reports expose prompts, validation, geometry feedback, Audit,
      repair route, and artifact paths, but they do not contain a dedicated
      semantic coverage section. The verifier also has false negatives around
      no-clarification live sessions and `final-acceptance` metric naming.
    - Target: Each run writes `semantic-coverage.json` and `report.md`
      contains `## Semantic Coverage`. The verifier accepts valid
      no-clarification terminal sessions, resolves
      `--session-from final-acceptance.json` relative to the output root, and
      reads the actual final metrics stage.
    - Acceptance: The verifier rejects missing semantic coverage for Formal
      acceptance, rejects unwaived unsupported explicit facts, and passes the
      known no-clarification live REPL shape when all semantic coverage states
      are terminal.

17. **Parsed invalid Formal enters bounded repair/regeneration**: A parseable
    Generator output that declares Formal BIM JSON 2.0 but fails the contract
    must be treated as an actionable previous candidate when diagnostics map
    to supported editable BIM JSON paths.
    - Current: `run_generator_stage` writes invalid parseable output to
      `parsed-output.json` only. `run_repair_stage` looks only for
      `candidate.json`, so repair records `failure feedback has no previous
      candidate` and never calls the Repair Agent.
    - Target: The pipeline preserves an invalid Formal repair source, routes
      validation diagnostics into bounded repair/regeneration, and records
      before/after artifacts without treating the invalid object as an
      accepted candidate.
    - Acceptance: A fixture matching session `3aa55eb71f464ff8` triggers one
      repair/regeneration call, not `previous_candidate=None`; the repaired

18. **Repair eligibility distinguishes fixable contract errors from product
    decisions**: Contract-invalid outputs may be repaired only when the missing
    or unsupported part is a known generator-format error, not a missing user
    fact or unsupported product capability.
    - Current: Invalid Formal outputs are all blocked before eligibility is
      assessed against the parsed document.
    - Target: Missing `IfcDoor.Representation` and extra unsupported compiler
      relationships are repair/regeneration-eligible when door width/height
      and host are known. Unsupported facts such as door swing operation remain
      Draft/blocking unless waived.
    - Acceptance: Tests prove missing door representation is eligible for
      bounded repair, explicit unsupported door opening direction is not
      silently repaired into acceptance, and unknown required facts still route
      to Draft/question rather than invented values.

19. **Canonical Design Brief vocabulary for supported gates**: Design Brief
    known facts used by deterministic gates must use canonical support values
    or include a normalization layer before gates run.
    - Current: Mimo can preserve wall placement as Chinese `"外侧"`, while
      semantic geometry helpers expect `outside_boundary`.
    - Target: The Design Brief validator/normalizer or downstream gate adapter
      maps known synonyms such as `"外侧"` to `outside_boundary` while
      preserving the original text in provenance or source evidence.
    - Acceptance: A Design Brief with `walls.placement: "外侧"` activates the
      same semantic outside-boundary geometry expectation as
      `outside_boundary`, and the normalized value is visible in trace
      evidence without overwriting the original user request.

20. **Loop observability for invalid-generator recovery**: Terminal output,
    session events, report, and export must show whether invalid Generator
    output was repaired, regenerated, drafted, or blocked.
    - Current: The user sees `Generator: invalid` and `Repair:
      blocked_failure`, but not why the loop stopped or whether a repair agent
      was eligible.
    - Target: The run records an explicit route such as
      `repair_attempted_from_invalid_formal`, `draft_required`, or
      `blocked_nonrepairable_contract`, plus validation issue codes, attempt
      count, provider call count, and artifact paths.
    - Acceptance: `report.md` and `session-export.json` for an invalid
      Generator recovery contain the parsed invalid output reference,
      validation diagnostics, repair eligibility, repair/regeneration raw
      output, final route, and no accepted IFC unless all gates pass.

- Reordering or splitting existing deterministic gates so generated-IFC
  feedback reaches Audit before final acceptance.
- Passing geometry feedback into Audit and the conditional repair path.
- Bounded repair/retry routing for confirmed geometry failures.
- Blocking gate disputes for human/developer review instead of accepting them.
- A Design-Brief-derived semantic geometry expectation for supported
  rectangular rooms, especially clear internal dimensions, wall thickness,
  outside/inside boundary intent, and wall closure.
- A semantic capability profile that tells Generator and Audit which explicit
  user facts current BIM JSON 2.0 and IFC2X3 generation can faithfully carry.
- Draft-first handling for unsupported explicit facts such as inward door
  opening direction under current capabilities.
- A semantic coverage sidecar, report section, and verifier gate for explicit
  user facts.
- A bounded invalid-Formal recovery loop that can repair/regenerate parseable
  invalid Generator output when diagnostics are actionable.
- Canonical normalization for Design Brief support vocabulary used by
  deterministic gates.
- Report/session/terminal evidence for invalid-generator recovery attempts and
  terminal routes.

**Out of scope:**

- Public API or web UI - this phase is terminal-only.
- Broad multi-agent framework replacement - OpenAI Agents SDK remains a later
  architecture decision unless needed for the REPL, which is not assumed.
- RAG, fine-tuning, or dataset expansion - this phase only fixes interaction
  acceptance.
- Broad new geometry/fidelity features beyond supported rectangular-room
  semantic checks. This fix may add Design-Brief-derived expectations for the
  existing rectangular room scope, but it does not implement arbitrary
  topology, curved walls, complex openings, or high-fidelity source round-trip
  expansion.
- Implementing `IfcDoorStyle`, door operation type generation, swing arcs, or
  full opening-direction semantics. Under current capability this explicit
  fact routes to Draft/blocking unless the user waives it.
- Treating `custom:` property sets as proof of semantic IFC support. They may
  preserve text as evidence only when explicitly marked as non-satisfying.
- RAG, fine-tuning, or knowledge-base expansion for capability discovery.
  Those may improve future fact support, but they cannot override current
  unsupported capability in Phase 6.2-fix.
- Unbounded autonomous looping across Design Brief, Generator, Repair, and
  Audit. This phase allows one bounded recovery attempt for actionable invalid
  Formal output; broader planner-style multi-agent loop policies remain future
  architecture work.
- Silent deterministic patching of model output without trace. Any deterministic
  cleanup must be recorded as normalization/validation evidence and must not
  add user facts.
- Letting Audit, the Observer, or the supervisor override deterministic schema,
  compile, reopen, geometry, secret-scan, or report gates.
- Silent prompt-side "supervisor decisions" that reinterpret the user's
  geometry to force acceptance.
- Fully automated proof that a real human typed in a terminal - the verifier
  can prove no scripted input path was used by the accepted REPL run and can
  preserve transcript evidence, but a human UAT note remains part of the final
  acceptance record.

## Detailed Decision Rules

The following rules are normative for Phase 6.2-fix implementation and tests.
If code, prompts, or reports disagree with this table, the table wins and the
implementation must be corrected.

### Semantic Capability and Coverage Rules

Every explicit user fact extracted into the Design Brief must end in exactly
one of these coverage states before Formal acceptance:

- `represented`: the fact is explicitly represented in supported BIM JSON 2.0
  and survives validation/compile/reopen evidence.
- `compiler_generated`: the fact is not model-authored because the compiler
  deterministically generates it from supported higher-level BIM JSON facts.
- `unsupported_draft`: the fact is meaningful but current BIM JSON/IFC
  generation capability cannot faithfully carry it, so the run remains Draft or
  asks the user whether to waive it.
- `waived_by_user`: the user explicitly says the unsupported or unknown fact is
  not required for this run.
- `blocked_unknown_capability`: the system cannot prove whether the current
  stack supports the fact, so it blocks instead of accepting.

Formal acceptance is forbidden while any explicit fact is uncovered,
unsupported but unwaived, or assigned to custom text preservation only.

The capability profile is not a second BIM JSON schema. It is a prompt,
Audit, and verifier contract that says what the current generator/compiler can
support. JSON Schema remains the only structural truth for BIM JSON.

### Design-Derived Geometry Expectation Rules

For supported rectangular rooms, semantic geometry expectations must be derived
from Design Brief facts and explicit user intent, including:

- internal clear room dimensions,
- wall thickness,
- wall height and storey elevation when stated,
- whether walls sit outside, inside, or on the room boundary,
- required closure around the stated space boundary,
- door/window host wall and relative position when stated.

Candidate-derived wall bounding boxes may still be written as compiler
fidelity evidence, but they cannot be the only expectation used for semantic
acceptance. If the Design Brief says a room has internal clear dimensions
`6m x 4m` and walls sit outside the boundary with `0.2m` thickness, wall inner
faces must align with the corresponding space boundary within tolerance. A
candidate that places the walls outside with an unintended gap fails even if
the compiler faithfully produces that candidate.

### Minimum Audit Input Bundle

Decisive Audit must receive one evidence bundle for the exact candidate under
review. The bundle must include:

- Design Brief artifact path and parsed Design Brief status.
- Candidate BIM JSON path/hash and contract version.
- BIM JSON validation result and diagnostics.
- IFC compile result, or an explicit reason compile was skipped.
- IFC reopen result, or an explicit reason reopen was skipped.
- Geometry feedback path and summary, or an explicit reason geometry could not
  run.
- Current repair route and attempt count.
- Report/artifact paths available so far.

Missing gate evidence is itself a blocking pipeline defect. Audit must not
produce a final acceptance decision from an incomplete evidence bundle.

### Route Decision Matrix

| Candidate state | Gate state | Audit output | Required route | Accepted IFC allowed? |
|---|---|---|---|---|
| Design Brief is Draft/incomplete | Any | Any | `draft_required` or `blocked_failure`; do not call IFC compile | No |
| BIM JSON is invalid | Validation failed | `revise` or `block` | Repair if actionable and attempts remain; otherwise Draft/blocked | No |
| BIM JSON is invalid | Validation failed | `accept` | Reject as `audit_override_attempt` and block | No |
| IFC compile or reopen fails | Compile/reopen failed | `revise` | Repair if the failure maps to candidate BIM JSON and attempts remain | No |
| IFC compile or reopen fails | Compile/reopen failed | `gate_dispute` | `blocked_gate_dispute`; developer/human review required | No |
| Geometry feedback has blocking issues | Geometry failed | `revise` / true candidate issue | Bounded repair/generation retry with exact geometry feedback | No, until repaired candidate passes all gates |
| Geometry feedback has blocking issues | Geometry failed | `gate_dispute` | `blocked_gate_dispute`; preserve gate evidence and no acceptance | No |
| Geometry feedback has blocking issues | Geometry failed | `accept` | Reject as `audit_override_attempt` and block | No |
| All deterministic gates pass | Gates passed | `revise` or `block` | Respect Audit blocking reason; repair or block as recorded | No |
| All deterministic gates pass | Gates passed | `accept` | Final verifier and secret scan may run; accept only if they pass | Yes |
| Final verifier or secret scan fails | Final checks failed | Any | `blocked_failure`; never accepted | No |

### Invalid Formal Recovery Rules

Parseable Generator output with `schema_version: "bim-json/2.0"` and failed
validation is an invalid Formal candidate. It is not acceptance-eligible and
must not be copied to `candidate.json` as if it were valid. It may be copied to
an explicitly named recovery artifact such as `invalid-candidate.json` or
passed as `previous_candidate` to repair when all of the following hold:

- the JSON parsed successfully,
- diagnostics name editable BIM JSON paths,
- required user facts for the correction already exist in the Design Brief,
- the correction is expressible in current Formal BIM JSON 2.0,
- the issue is not an unsupported explicit product semantic requiring Draft.

The repair/regeneration loop must preserve:

- original `parsed-output.json`,
- validation diagnostics,
- repair source artifact path,
- allowed change paths,
- repair prompt and raw output when a model call is made,
- repaired candidate or Draft artifact when produced,
- issue delta or blocking reason.

For session `3aa55eb71f464ff8`, missing `IfcDoor.Representation` is eligible
because width, height, host wall, and opening evidence already exist. The extra
`IfcRelAggregates` and `IfcRelContainedInSpatialStructure` relations are
eligible for removal because current Formal profile treats them as
compiler-generated/unsupported explicit model output, not as user-authored
facts. Door operation semantics would not be eligible under current capability
unless waived.

### Repair Eligibility

A geometry issue is repair-eligible only when all of the following are true:

- The feedback has stable issue codes, affected entity IDs, and enough
  observed/expected geometry context for a model or deterministic repair prompt
  to target the issue.
- The required correction can be expressed in supported BIM JSON 2.0 fields.
- The correction does not require new user facts such as unknown room
  dimensions, wall thickness, opening size, host wall, storey, material, or
  relationship intent.
- The relevant fact is already present in the user transcript, Design Brief,
  candidate BIM JSON, schema/capability context, or deterministic geometry
  feedback.

For Phase 6.2-fix UAT, the default maximum is one repair attempt per candidate
route. A different limit is allowed only if the run records
`max_repair_attempts`, `attempt_index`, and the reason for changing the limit in
the report and session export.

### Gate Dispute Definition

`gate_dispute` means Audit has evidence that the deterministic gate may be
wrong or underspecified. It does not mean "accept anyway". A gate dispute must:

- Preserve the original gate feedback unchanged.
- Record why the gate result is disputed.
- Block final acceptance.
- Ask for developer/human review or a future test update before the same class
  can be accepted.

### Audit Authority

Audit may:

- Compare the user intent, Design Brief, BIM JSON, validation diagnostics,
  generated IFC metrics, and geometry feedback.
- Classify a failure as candidate issue, missing user fact, gate dispute, or
  blocked pipeline issue.
- Recommend repair, Draft clarification, or blocking.

Audit may not:

- Edit BIM JSON or IFC artifacts.
- Add dimensions, placements, openings, rooms, storeys, relationships, or
  properties.
- Override failed validation, compile, reopen, geometry, verifier, report, or
  secret-scan gates.
- Treat supervisor interpretation as a replacement for user facts.
