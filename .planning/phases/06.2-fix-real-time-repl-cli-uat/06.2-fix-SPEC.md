# Phase 6.2-fix: Real-time REPL CLI UAT - Specification

**Created:** 2026-06-26
**Ambiguity score:** 0.06 (gate: <= 0.20)
**Requirements:** 8 locked
**Status:** Planned for user review

## Goal

Replace the Phase 6.2 scripted/file-style acceptance gap with a true
Chinese-first terminal REPL where a human can type a request, see Mimo's
clarification questions immediately, answer them turn by turn, and receive a
validated IFC2X3 artifact plus a DB-backed review report.

## Background

Phase 6.2 successfully built a real Mimo-backed backend pipeline: shared
SQLite sessions, Design Brief calls, Generator calls, Audit calls,
deterministic validation, IFC compilation, report generation, and query/export
commands. However, its final acceptance did not match the intended product
experience. The accepted run relied on UTF-8 file/scripted input as practical
automation evidence, and `scripts/agent/run_phase6_2_cli.py` still behaves
like a pipeline entrypoint that prints a final JSON summary rather than a
human-facing conversation loop.

The missing behavior is not another provider integration and not a new model
architecture. The missing behavior is a product boundary: the user must be able
to run one command, type Chinese text in a terminal, see each Mimo-authored
question before entering the next answer, and inspect the resulting artifacts.
Regression tests may still use fake providers and scripted input, but the
final acceptance must prove a real REPL session rather than a preloaded answer
stream.

## Requirements

1. **One-command REPL entrypoint**: A user can start a live chat-style text2IFC
   session without `--scripted-stdin`, prewritten answer files, or a hidden
   answer list.
   - Current: `scripts/agent/run_phase6_2_cli.py` supports live Mimo calls but
     is pipeline-shaped and commonly invoked with `--scripted-stdin`,
     `--stop-after`, and explicit output flags.
   - Target: A command such as
     `.venv\Scripts\python scripts\agent\run_text2ifc_chat.py --live`
     opens a Chinese-first REPL, prompts for the initial request, and owns the
     full Design Brief -> BIM JSON -> IFC route.
   - Acceptance: Running the REPL command with no scripted input source starts
     with a visible Chinese prompt for the user's building request and creates
     a session row with `interaction_mode: "human_repl_live"`.

2. **Turn-by-turn Mimo clarification**: The REPL prints Mimo's 1-3
   Design-Brief clarification questions before reading the user's next answer.
   - Current: `run_design_brief_clarification_loop` accepts an iterable of
     `user_answers`; it persists transcript turns but does not expose a
     question-then-wait conversational boundary to the user.
   - Target: A stepwise controller invokes Mimo, persists the assistant turn,
     prints the Chinese questions, then blocks for user input. The answer is
     appended only after the question is visible and persisted.
   - Acceptance: A RED/GREEN test proves the answer reader is not called until
     after the assistant question has been printed and an assistant turn/event
     has been recorded.

3. **Human-facing Chinese terminal UX**: The REPL displays the process in
   readable Chinese instead of only dumping final JSON.
   - Current: The live CLI returns a machine JSON result at the end and keeps
     intermediate outputs mainly in artifacts.
   - Target: The terminal shows concise Chinese status lines for session
     creation, Mimo thinking/call completion, clarification questions, BIM JSON
     validation, IFC generation, report/export writing, Draft/blocking status,
     and final artifact paths. Raw JSON is shown only under an explicit debug
     option.
   - Acceptance: Tests over fake providers assert visible strings for initial
     prompt, Mimo question display, validation progress, final IFC path, report
     path, and session hash.

4. **Same evidence-rich pipeline after readiness**: Once Design Brief reaches
   `ready`, the REPL reuses the Phase 6.2 Generator, deterministic gates,
   conditional repair, Audit, report, session DB, and IFC compilation path.
   - Current: The pipeline exists but is driven by a backend-oriented CLI.
   - Target: The REPL does not create a parallel BIM JSON model or second
     compiler path; it routes the ready session into the existing verified
     Phase 6.2 flow.
   - Acceptance: The REPL final Formal run writes and reopens
     `dataset/processed/agent-demo/phase6.2-fix-repl/runs/<session_hash>/output.ifc`
     and the candidate passes `validate_v2_document` before compilation.

5. **Shared session DB and query/export compatibility**: REPL sessions remain
   first-class records in one shared SQLite DB and can be queried, resumed, and
   exported.
   - Current: Phase 6.2 has a shared session DB and query/export commands.
   - Target: REPL sessions use the same DB schema and query/export surface,
     with additional interaction metadata rather than a separate log format.
   - Acceptance: `query_phase6_2_sessions.py list/show/turns/calls/artifacts/export`
     can retrieve the REPL acceptance session by `session_id` or
     `session_hash`, and `session-export.json` contains every user and
     assistant turn in order.

6. **Generated report proves interaction mode**: The generated `report.md`
   must expose the REPL interaction evidence, not only final artifacts.
   - Current: Phase 6.2 report is DB-backed and artifact-linked, but it does
     not prove that final acceptance was a human REPL instead of scripted
     input.
   - Target: The report includes original input, terminal transcript summary,
     interaction mode, input-source classification, Design Brief questions,
     user answers, prompt/raw/parsed sidecars, validation feedback, route,
     Audit result, metrics, final IFC path, and session export path.
   - Acceptance: Report completeness tests reject a report missing
     `interaction_mode`, `input_source`, terminal transcript evidence, or
     final artifact paths.

7. **Scripted input cannot satisfy final acceptance**: The verifier blocks any
   final acceptance bundle that was produced by scripted stdin, prewritten
   answer files, replay output, or fake providers.
   - Current: Scripted stdin is useful for regression and was used as accepted
     practical evidence because direct Chinese piping in Codex PowerShell was
     unreliable.
   - Target: Regression may still use scripted stdin or fake providers, but
     the final acceptance verifier requires `interaction_mode:
     "human_repl_live"`, `input_source: "terminal"`, real Mimo evidence labels,
     and no scripted input artifact for the accepted session.
   - Acceptance: Negative tests prove `verify_phase6_2_fix_artifacts.py`
     rejects acceptance indexes with `scripted_stdin`, `input_source: "file"`,
     missing live provider response IDs, fake/replay evidence classes, or
     absent REPL transcript events.

8. **Windows UTF-8 guardrails**: The REPL preserves Chinese input/output on
   Windows terminals or reports an explicit encoding diagnostic before a live
   run can be accepted.
   - Current: Direct Chinese text piped through the Codex PowerShell command
     surface can corrupt text; UTF-8 files were used as a workaround.
   - Target: The REPL configures stdin/stdout to UTF-8 where possible, stores
     text as UTF-8 in DB/artifacts, and records terminal encoding metadata for
     acceptance review.
   - Acceptance: Tests cover UTF-8 Chinese round-trip through the REPL IO
     abstraction, and the live acceptance report includes terminal encoding
     metadata without leaking environment secrets.

## Boundaries

**In scope:**

- A new or clearly separated REPL entrypoint for real human terminal use.
- Stepwise Design Brief orchestration that prints questions before reading
  answers.
- Reuse of existing Phase 6.2 provider, session DB, Generator, repair, Audit,
  report, query/export, validation, compiler, and geometry gates.
- Additional DB events/metadata needed to distinguish human REPL acceptance
  from scripted regression.
- A stricter artifact verifier for Phase 6.2-fix acceptance.
- One real Mimo happy-path REPL acceptance that produces a reopenable IFC2X3.
- One Draft/quit path that proves the REPL exits without fabricating facts or
  writing IFC.
- Documentation and planning updates that explicitly record the Phase 6.2
  misunderstanding and the corrected acceptance boundary.

**Out of scope:**

- Public API or web UI - this phase is terminal-only.
- Broad multi-agent framework replacement - OpenAI Agents SDK remains a later
  architecture decision unless needed for the REPL, which is not assumed.
- RAG, fine-tuning, or dataset expansion - this phase only fixes interaction
  acceptance.
- New geometry/fidelity features - existing Phase 4/6.2 gates define IFC
  correctness for this fix.
- Fully automated proof that a real human typed in a terminal - the verifier
  can prove no scripted input path was used by the accepted REPL run and can
  preserve transcript evidence, but a human UAT note remains part of the final
  acceptance record.

  blocked outcomes write trace/report artifacts but no IFC.
