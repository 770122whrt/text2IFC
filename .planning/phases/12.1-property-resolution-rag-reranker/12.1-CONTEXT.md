# Phase 12.1: Property Resolution RAG and Reranker Correction - Context

**Gathered:** 2026-08-21
**Status:** Frozen for specification and planning
**Source:** Phase 12 real DeepSeek failure analysis and user design discussion

<domain>
## Phase Boundary

Replace manual reviewed-alias authorization for natural-language IFC property
claims with one common, evidence-bearing pipeline:

```text
Stage 1 property claim
  -> class-applicable authoritative candidate filter
  -> multilingual vector Top-K
  -> bounded Property Resolution Provider stage (Stage 1.5)
  -> deterministic admissibility gate
  -> program-constructed ExactPropertyIntent
  -> existing target/model binding, Stage 2 and atomic IFC authoring
```

This urgent correction is inserted before Phase 12 live acceptance can be
curated and before Phase 12 status can close. It owns property resolution only;
it does not reopen structural geometry, Type, material, Storey, Ground Truth,
Door/Window operation, or publication thresholds.

</domain>

<decisions>
## Implementation Decisions

### Authority and historical aliases

- **D-01:** `schemas/ifc/knowledge/property_aliases.json` remains immutable
  historical evidence for old artifacts. The active Phase 12.1 resolver neither
  loads it nor includes it in the active collection fingerprint, retrieval
  score, reranker prompt, admissibility gate, or authorization evidence.
- **D-02:** No new phrase-to-property dictionary, reviewed alias, family phrase
  branch, or output compatibility mapping may be added.
- **D-03:** An explicitly user-supplied canonical `Pset.Property` continues to
  use the exact Phase 10.1 path. Stage 1.5 is required only for
  `natural_language_property` claims.

### Stage responsibilities

- **D-04:** Stage 1 preserves target/operation, original property phrase, raw
  value/unit/scope and request provenance. It does not choose or authorize a
  canonical Pset/property.
- **D-05:** Stage 1.5 is a separate Provider call after deterministic target
  class resolution and vector retrieval. It is not folded back into Stage 1
  and is not a general analysis Agent.
- **D-06:** Stage 1.5 receives one claim and a bounded Top-K of public,
  class-applicable property records. It may select only an offered candidate or
  return clarification/unsupported. It cannot invent candidates, values,
  scopes, operations, or IFC objects.
- **D-07:** Stage 2 receives only exact typed semantic authority. It never
  receives embeddings, aliases, the full property corpus, Top-K payloads or
  reranker reasoning.

### Retrieval and semantic decision

- **D-08:** Multilingual vector retrieval plus bounded LLM reranking is the
  final natural-language property direction. Vector-only, LLM-only and
  alias-only selection are not executable authority.
- **D-09:** Candidate eligibility is deterministic and precedes vector search:
  checked-in IFC2X3 PSD/project-record provenance, target-class applicability,
  supported `TypePropertySingleValue`, scalar value type, operation scope and
  public-source constraints.
- **D-10:** Stage 1.5 output is a semantic decision claim. A deterministic
  admissibility gate then checks offered-candidate membership and hashes,
  registry authority, class/template/type/unit/scope compatibility, decision
  shape, conflict state and a versioned minimum retrieval-quality floor. Code
  never promotes vector Top-1 or a score margin into semantic authority. The
  Top-1/Top-2 margin remains recorded evidence for evaluation and diagnosis;
  close candidates are precisely what the bounded reranker must compare.
- **D-11:** The program, not the Provider, constructs `ExactPropertyIntent`
  from the selected authoritative record plus the user's original value/unit,
  scope and provenance. Existing Binder logic then binds it to operation,
  target, request hash and model fingerprint.

### Clarification, durability and evidence

- **D-12:** Stage 1.5 has at most two Provider attempts. Malformed or
  noncanonical output is preserved and corrected only by schema feedback; no
  key alias or normalizer is added.
- **D-13:** A selected candidate below the frozen retrieval floor, competing
  candidates that Stage 1.5 cannot resolve, Provider
  `clarification_required`, vector unavailability, stale candidate hashes and
  unsupported value/unit/scope fail closed before Stage 2. A small raw vector
  margin alone does not override a valid bounded reranker decision. A user
  answer resumes the same run lineage.
- **D-14:** Query, eligible set, Top-K, embedding/collection identity, prompt
  hash, Provider/model evidence, raw attempts, semantic decision, admissibility
  result and ExactPropertyIntent handoff are durable hash-bound artifacts.
- **D-15:** Synthetic, cached, prerecorded, hand-authored or injected Provider
  evidence cannot satisfy live acceptance. Offline tests may inject a transport
  only when the result is permanently marked non-live/non-acceptance-eligible.

### Family and closeout scope

- **D-16:** The new path is common to existing property-capable occurrences:
  Window, Door, Wall/WallStandardCase, Beam and Column. Wall remains
  property-only; no `add_wall` operation is introduced.
- **D-17:** Existing Window/Door repair workflows and their frozen geometry,
  Type, Storey, L1/L2 and transaction contracts must remain green. This phase
  changes no operation Prompt profile except where a property claim must be
  routed to Stage 1.5.
- **D-18:** The preserved Phase 12 live failure remains historical evidence.
  Phase 12.1 reruns a fresh zero-skip preflight and real DeepSeek matrix, curates
  only independently recomputed strict successes, and closes OPS-03/OPS-04 and
  Phase 12 only after all gates pass. Phase 13 remains unstarted.

### Implementation Discretion

- Exact internal class/function names for the vector lifecycle, reranker and
  admissibility modules, provided each boundary above remains independently
  testable.
- Whether Qdrant uses the existing local path or a configured local service,
  provided collection identity is versioned, reusable and fail-closed.
- The exact minimum retrieval-quality floor, provided it is derived from the
  frozen evaluation set, checked in as a versioned policy and never supplied
  by the Provider. Raw margins remain evaluation evidence, not a local
  phrase-to-property selector.

</decisions>

<specifics>
## Specific Ideas

- `外窗` should be resolved semantically as the combination of the resolved
  Window target and the external-property concept, by multilingual retrieval
  and reranker comparison against official candidate definitions, not by a
  phrase table.
- `IfcBeam + "load bearing" + true` and
  `IfcColumn + "load bearing" + true` must resolve through the same pipeline to
  their class-applicable `LoadBearing/IfcBoolean` records.
- The term "deterministic authorization" is replaced in this phase with
  "deterministic admissibility gate" so documentation does not pretend that
  program checks prove natural-language semantics. The semantic decision comes
  from vector plus bounded LLM; code proves only execution admissibility.

</specifics>
