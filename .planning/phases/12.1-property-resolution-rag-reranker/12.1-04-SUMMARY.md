# Phase 12.1 Plan 04: Property Admissibility and Exact Intent Summary

**A Stage 1.5 decision is now non-executable until code reopens the selected
record, checks concrete authoring risks and constructs an exact typed handoff.**

## Accomplishments

- Added immutable, separately replayable `PropertyAdmissibilityResult` evidence
  for passed, clarification, unsupported, project-confirmation and rejected
  outcomes.
- Rechecked offered-candidate membership, current query/corpus lineage,
  authoritative record identity, IFC-class inheritance, scalar-template
  support, value type, unit, occurrence-direct scope, conflicts and the frozen
  retrieval floor before exact intent exists.
- Kept vector Top-1 and vector margin non-authoritative: a valid offered rank-2
  selection can pass, while a high-score candidate still cannot skip Stage 1.5.
- Constructed `ExactPropertyIntent` only in code. Pset/property/value type come
  from the authoritative record; normalized user value/unit, scope and public
  provenance come from the original Stage 1 claim. Retrieval evidence and LLM
  reasoning do not enter the exact intent.
- Routed passed standard selections through the existing exact resolver and
  Binder. Project/custom records still require explicit confirmation.
- Closed a concrete production-boundary risk: matching provenance alone no
  longer permits an authorized property value to differ from the normalized
  original user value.
- Preserved IFC inheritance for `Pset_WallCommon.IsExternal` on
  `IfcWallStandardCase` without introducing a Wall creation operation.

## Concrete Risk Boundary

The gate exists only for named product failures: invented/off-run candidate,
wrong IFC family, unsupported property representation, incompatible value or
unit, shared-Type mutation, unresolved semantic conflict, stale query/corpus
evidence, below-floor retrieval, custom-property confirmation and substitution
of the user's requested value. It does not attempt to prove natural-language
meaning and introduces no hash/fingerprint gate.
