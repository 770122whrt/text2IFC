# Phase 12.1 Plan 01: Property Resolution Contract Summary

**The additive Stage 1.5 contract is now executable and bounded: LLM output can
express a semantic choice, but cannot author or override an IFC property.**

## Accomplishments

- Added closed JSON Schemas for the property query, maximum-five public
  candidate set, three-outcome reranker decision, concrete admissibility result
  and the future evaluated policy instance.
- Kept reviewed aliases out of every new schema and Prompt input. The historical
  `property_aliases.json` and policy 0.1 remain unchanged and readable.
- Registered a repair-only Prompt that processes one claim, selects only an
  offered ID and has no Window/Door/Wall/Beam/Column phrase-to-property example.
- Froze the Stage 1 boundary: natural-language claims retain original user facts
  and reject canonical property, candidate, value-type and authorization fields.

## Contract Boundary

- Query authority: original phrase/value/unit/scope, resolved target class and
  stable run/request/model/operation/claim IDs.
- Candidate authority: public record identity, canonical metadata,
  applicability, scalar template/value type/unit, source and retrieval rank/score.
- Provider authority: semantic decision over offered IDs only.
- Program authority: admissibility and later ExactPropertyIntent construction.
- Stage 2 authority: unchanged; it will receive only the exact typed fact in a
  later plan.

## Deviations from Plan

None. The implementation follows the user-amended no-new-hash/concrete-risk
contract. The repository's pre-existing Prompt Registry still records its
required content metadata; that value is not present in the new property query,
candidate, decision, admissibility or policy schemas and is not an execution
gate for property selection.
