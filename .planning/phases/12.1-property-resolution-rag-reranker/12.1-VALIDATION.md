## Quality Claim

A natural-language property request is publishable only when a ready,
versioned multilingual vector index retrieves a bounded candidate set, a
separate bounded Provider stage confirms one offered candidate, deterministic
code proves execution admissibility and constructs the exact typed property,
and reopened IFC verification independently matches that authority. Historical
aliases are neither active evidence nor an executable replay path. They may be
retained byte-for-byte as historical-only artifacts or an isolated evaluation
Baseline, but cannot make a current case acceptance-eligible.

## Validation Layers

### L0-A: Contract and public-boundary checks

- New query/candidate/decision/admissibility schemas validate exact versions,
  required fields, `additionalProperties=false` and bounded Top-K.
- Stage 1.5 Prompt has an immutable ID/version and contains no aliases, private
  canaries, full IFC, Gold, mutation mappings or Stage 2 authoring payload.
  Current execution uses additive Prompt `ifc-property-resolution.v0.2`; v0.1
  remains registered only so historical attempts stay reproducible.
- Reranker output can reference only offered candidate IDs and allowed decision
  enums; malformed/noncanonical output is preserved and receives schema
  feedback on at most one correction attempt.

### L0-B: Knowledge and retrieval checks

- Official/property-project records retain provenance and applicability.
- Active collection inputs exclude historical aliases and declare corpus,
  record schema, embedding model and document renderer versions.
- RepairAPI construction, public/offline/live runners and current Proof
  validation contain no default/fallback resolver that loads reviewed aliases.
- Build, reuse, configured-version drift, unavailable model/Qdrant and stale
  configuration are tested.
- Top-K is deterministic for a fixed index/query and contains no ineligible or
  private-derived record.
- Pre-retrieval eligibility enforces authority, authorability, class,
  supported scalar template and operation scope, but does not call
  request-specific value or unit normalization. Raw value/kind/unit remain in
  the public query evidence for later admissibility and are absent from the
  vector query representation used to resolve property identity.

### L0-C: Semantic decision and admissibility checks

- Offline Provider-seam tests cover `confirmed`, `clarification_required`,
  `unsupported`, malformed/truncated, selection of an unoffered candidate ID,
  changed candidate record and multiple selection.
- Focused boundary tests prove a related or nearest candidate cannot convert a
  vague repair goal into `confirmed`; meaningful underspecified requests may
  require clarification even when only one related candidate is offered.
- Focused taxonomy tests distinguish underspecified supported property edits
  and multiple plausible properties (clarification), explicit absent
  properties (`unsupported_property`), unsupported repair operations
  (`unsupported_operation`), and resolved properties with invalid values
  (post-resolution deterministic rejection and value correction).
- The admissibility gate independently reopens the candidate record and checks
  class/template/value/unit/scope/cardinality/minimum retrieval-quality policy.
- Five focused wrong-value cases prove `Window.FireRating`, `Door.FireRating`,
  `Column.LoadBearing`, `Beam.Reference` and `Wall.AcousticRating` remain
  retrievable, while deterministic admissibility rejects their incompatible
  Boolean/string/integer values after Stage 1.5 selection.
- Vector Top-1 and Top-1/Top-2 margin never auto-select a property; score, rank
  and margin remain retained evaluation evidence.
- ExactPropertyIntent copies canonical fields only from the record and user
  fields only from the original claim. Provider-supplied canonical/value fields
  are impossible by schema and ignored/rejected by code.

### L1/L2: IFC application checks

- Existing-occurrence property chains: Window, Door, Wall,
  WallStandardCase, Beam and Column.
- Created-occurrence property chains: add Window, add Door, add Beam and add
  Column where those operations already exist.
- Reopened IFC proves exact Pset/property, typed scalar, occurrence-direct
  ownership, no duplicate effective fact, unchanged shared Type and unrelated
  roots, plus each operation's frozen geometry/relationship L1.
- No Wall creation test or claim exists.

### Full-chain public API/CLI checks

- complete success;
- vector/LLM property clarification and same-lineage resume;
- unsupported/no candidate;
- malformed/truncated Stage 1.5 output and one schema correction;
- vector/model/Qdrant unavailable;
- configured candidate/record/policy/prompt version mismatch;
- atomic mixed Door+Window+Beam+Column rollback;
- source immutability and private-Gold isolation;
- crash after candidate, decision and admissibility persistence, then restart;
- idempotent terminal publication and no partial successful IFC.
- active runtime unavailable or incomplete fails closed without alias fallback.

### Independent Proof checks

The curator never trusts the runner aggregate. A separate process must recompute:

- source/damaged/public boundary and source immutability;
- query, eligible-set and Top-K membership/order;
- embedding/collection identity and ready health;
- Stage 1.5 prompt/schema/provider/model/usage/raw-attempt lineage;
- reranker decision and deterministic admissibility;
- ExactPropertyIntent and authorized fact binding;
- ChangeSet, reopened IFC L0/L1/L2/preservation/isolation;
- no fallback/cache/private leakage.

For each current Phase 12.1 property claim, the required public evidence group
is the persisted query, candidate set, rendered Prompt and Provider attempt,
parsed Stage 1.5 decision, admissibility result, program-constructed
ExactPropertyIntent and authored IFC fact. The validator may rerun deterministic
retrieval/admissibility/binding/IFC checks, but must not call the Provider or a
legacy alias resolver. Missing evidence, alias-derived candidate authority or a
retained `REVIEWED_ALIAS_EXACT` decision is a current-eligibility failure, not a
reason to reinterpret or normalize the case. Historical committed Proof remains
unchanged and readable, but is not replayed or counted as Phase 12.1 acceptance.

### Plan 06: retrieval capability

Plan 06 runs real local BGE-M3 embeddings and real Qdrant retrieval with zero
network. For each case it must first durably persist the public query and
offered Top-K candidate set; only then may the evaluator open the Gold label and
score retrieval.

Report:

- Top-K recall for supported standard positives;
- Window/Door/Wall/Beam/Column slices and uncertainty;
- empty-Top-K count and fail-closed behavior;
- retrieval-floor/policy behavior and runtime/model/collection readiness;
- alias/private leakage and ineligible-candidate counts;
- all failures retained in the denominator.

Machine- and human-readable output must state:

```text
retrieval_capability = "evaluated"
stage_1_5_semantic_evaluation_status = "not_evaluated_offline"
```

Plan 06 must not report confirmed-selection accuracy, clarification accuracy,
unsupported accuracy or false semantic authorization from a deterministic
answer source. Missing semantic scoring is not a Provider failure because no
genuine semantic Provider is evaluated in Plan 06.

Retrieval hard gates:

- every required Window/Door/Wall/Beam/Column positive has its canonical
  authoritative record in Top-K;
- empty Top-K never invokes Stage 1.5 or authorizes a property;
- every offered candidate satisfies the frozen retrieval floor/policy;
- zero alias runtime authority, private leakage or ineligible offered record;
- no Stage 1.5/system capability claim from Top-K Recall.

### Plan 06: Stage 1.5 contract and admissibility correctness

Hermetic seam/full-chain tests prove that the rendered Prompt contains only the
allowed public query/candidates/schema context; selection is limited to one
offered candidate, clarification or unsupported; malformed/unoffered outputs
fail closed under bounded retry; clarification lineage is durable; and empty
Top-K bypasses Stage 1.5. These tests also prove deterministic admissibility,
program construction of `ExactPropertyIntent`, Stage 2 isolation and IFC
application/reopen behavior.

Deterministic Provider doubles used here are plumbing evidence only. They do
not contribute semantic Candidate scores or capability metrics.

### Plan 07: genuine Stage 1.5 semantic capability

Before the four end-to-end UAT cases, Plan 07 runs a separate genuine Provider
evaluation over the unchanged 60 public queries and retrieval Gold identities
through the normal production route. The preserved genuine prediction ledger
uses Prompt/taxonomy v0.2. Final acceptance scoring uses the additive frozen
v0.3 taxonomy sidecar against those same immutable predictions with zero
Provider calls, regeneration, or modification.
Exact canonical requests retain `exact_bypass`; natural-language requests with
empty Top-K retain `not_invoked_no_candidates`; only authority/class/template/
scope-eligible natural-language cases with a nonempty offered Top-K render a
Stage 1.5 Prompt and call the approved Provider. Request value/type/unit
validity does not participate in this retrieval eligibility. For invoked
cases, the offered set, rendered Prompt, raw response, parsed decision, retry
lineage, Provider/model metadata, token usage and timing are durably persisted
before the evaluator opens Gold.

At minimum report:

- offered-set selection accuracy;
- separate clarification, unsupported, and deterministic-inadmissible accuracy;
- Window/Door/Wall/Beam/Column slices and uncertainty;
- false authorization count/rate and unoffered selection count;
- malformed-response/retry and final-unresolved counts;
- token usage, latency and Provider attempt count;
- retrieval failures separately from semantic-selection failures.

A correct property absent from Top-K is a retrieval failure. A correct property
present in Top-K but not selected is a semantic-selection failure. A genuinely
ambiguous case that requests clarification is a correct semantic outcome. A
meaningful but underspecified broader repair goal also requires clarification;
retrieval proximity alone cannot make it a confirmed property.

The complete 60-case route-faithful ledger is the system-outcome denominator.
The Stage 1.5 semantic denominator is the predeclared subset whose production
route actually invokes the Provider; exact bypass and empty-Top-K cases are
reported separately and never treated as semantic attempts.

The following Plan 07 gates are frozen before any Provider call:

- every case's final route/outcome matches its frozen evaluator label;
- offered-set selection accuracy is 1.0 for invoked cases whose frozen outcome
  is a confirmed standard property;
- clarification, unsupported, and deterministic-inadmissible accuracy are each
  1.0 for their frozen denominators;
- every family slice with a nonzero invoked denominator has strict outcome
  accuracy 1.0;
- false standard authorization, unoffered selection, private leakage and false
  publication counts are zero;
- every confirmed-standard case whose Gold record is present in Top-K has zero
  final unresolved outcomes;
- malformed responses may consume only the frozen bounded retry; exhausting it
  without the frozen correct terminal outcome fails the gate;
- token, latency, retry and Provider-attempt metrics are reported but have no
  post-hoc pass threshold in this phase.

Plan 07 preflight must compare the accepted Plan 06 query/Gold fixtures
byte-for-byte against their checkpoint using Git. The genuine run already
verified additive v0.2 before Provider prediction; the zero-Provider rescore
must verify the canonical v0.3 taxonomy hash and the immutable source
ledger/report hashes. This is evaluation-dataset immutability, not a production
property hash or authorization gate.
