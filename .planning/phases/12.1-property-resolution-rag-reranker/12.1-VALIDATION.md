# Phase 12.1: Property Resolution RAG and Reranker Correction - Validation

**Created:** 2026-08-21
**Status:** Frozen
**Requirements:** RAG-05, RAG-06, RAG-07, OPS-03, OPS-04

## Quality Claim

A natural-language property request is publishable only when a ready,
fingerprinted multilingual vector index retrieves a bounded candidate set, a
separate bounded Provider stage confirms one offered candidate, deterministic
code proves execution admissibility and constructs the exact typed property,
and reopened IFC verification independently matches that authority. Historical
aliases are not active evidence.

## Validation Layers

### L0-A: Contract and public-boundary checks

- New query/candidate/decision/admissibility schemas validate exact versions,
  required fields, `additionalProperties=false`, bounded Top-K and hash syntax.
- Stage 1.5 Prompt has an immutable ID/hash and contains no aliases, private
  canaries, full IFC, Gold, mutation mappings or Stage 2 authoring payload.
- Reranker output can reference only offered candidate IDs and allowed decision
  enums; malformed/noncanonical output is preserved and receives schema
  feedback on at most one correction attempt.

### L0-B: Knowledge and retrieval checks

- Official/property-project records retain provenance and applicability.
- Active collection fingerprint excludes historical aliases and includes
  corpus, record schema, embedding model/weights and document renderer version.
- Build, reuse, corpus drift, model drift, unavailable model/Qdrant and stale
  collection are tested.
- Top-K is deterministic for a fixed index/query and contains no ineligible or
  private-derived record.

### L0-C: Semantic decision and admissibility checks

- Offline Provider-seam tests cover `confirmed`, `clarification_required`,
  `unsupported`, malformed/truncated, candidate injection, changed candidate
  record, multiple selection and changed request/model hash.
- The admissibility gate independently reopens the candidate record and checks
  class/template/value/unit/scope/cardinality/minimum retrieval-quality policy.
- Vector Top-1 and Top-1/Top-2 margin never auto-select a property; score, rank
  and margin remain retained evaluation evidence.
- ExactPropertyIntent copies canonical fields only from the record and user
  fields only from the original claim. Provider-supplied canonical/value fields
  are impossible by schema and ignored/rejected by code.

### L1/L2: IFC application checks

- Existing-occurrence property chains: Window, Door, Wall,
  WallStandardCase, Beam and Column.
- Created-occurrence property chains: add Window, add Door, add Beam and add
  Column where those operations already exist.
- Reopened IFC proves exact Pset/property, typed scalar, occurrence-direct
  ownership, no duplicate effective fact, unchanged shared Type and unrelated
  roots, plus each operation's frozen geometry/relationship L1.
- No Wall creation test or claim exists.

### Full-chain public API/CLI checks

- complete success;
- vector/LLM property clarification and same-lineage resume;
- unsupported/no candidate;
- malformed/truncated Stage 1.5 output and one schema correction;
- vector/model/Qdrant unavailable;
- candidate/record/policy/prompt fingerprint drift;
- atomic mixed Door+Window+Beam+Column rollback;
- source immutability and private-Gold isolation;
- crash after candidate, decision and admissibility persistence, then restart;
- idempotent terminal publication and no partial successful IFC.

### Independent Proof checks

The curator never trusts the runner aggregate. A separate process must recompute:

- source/damaged/public boundary and hash bindings;
- query, eligible-set and Top-K membership/order/hashes;
- embedding/collection identity and ready health;
- Stage 1.5 prompt/schema/provider/model/usage/raw-attempt lineage;
- reranker decision and deterministic admissibility;
- ExactPropertyIntent and authorized fact binding;
- ChangeSet, reopened IFC L0/L1/L2/preservation/isolation;
- collection FILES hashes and no fallback/cache/private leakage.
