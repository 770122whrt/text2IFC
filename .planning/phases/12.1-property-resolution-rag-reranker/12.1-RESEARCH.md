# Phase 12.1: Property Resolution RAG and Reranker Correction - Research

**Date:** 2026-08-21
**Mode:** Codebase-grounded planning research; no external dependency search

## Current Architecture

### Knowledge records and vector support already exist

`src/text2ifc_knowledge/property_search.py` already provides:

- versioned standard/project `PropertyKnowledgeRecord` construction;
- checked-in IFC2X3 registry provenance and applicability;
- `BgeM3EmbeddingProvider` with lazy local model loading;
- deterministic test `InMemoryVectorIndex`;
- local/service `QdrantVectorIndex` with collection reuse;
- query, candidate and decision dataclasses;
- value/unit normalization.

The current collection-reuse key includes reviewed aliases, which is
incompatible with D-01. Phase 12.1 needs a declared collection identity based
on record schema/corpus, embedding model and query-document renderer versions,
not historical phrase mappings. This identity is operational configuration,
not an authorization condition.

### Vector is not wired into the public production constructor

`create_default_property_resolver()` defaults `vector_index=None`.
`RepairAPI.from_environment()` and `run_phase12_live_uat.py` call that default.
Only `run_phase10_2_live_uat.py` explicitly constructs BGE-M3, Qdrant, builds or
reuses a collection and injects the resolver.

This explains why the Phase 12 live resolution evidence has an empty candidate
set. Enabling the existing vector seam alone would not complete the target
design because current policy rejects vector-only authorization and no LLM
reranker exists.

### Current Window live evidence used alias exact

The Phase 10.2 `外窗` decision artifact records
`reason_code=REVIEWED_ALIAS_EXACT`. Qdrant health was ready but the resolver
returned before vector search. That run remains valid evidence for exact alias
and downstream authoring, but not for vector semantic selection.

### Resolution is currently synchronous and coupled

`resolution_flow.resolve_repair_intent()` calls
`property_knowledge_resolver.resolve()` synchronously while resolving each
operation. `PropertyKnowledgeResolver.resolve()` combines applicability,
exact/alias/keyword/vector retrieval, semantic decision, type normalization and
exact-intent production.

Stage 1.5 requires these responsibilities to separate:

1. eligible-record selection;
2. vector Top-K creation;
3. Provider semantic decision;
4. deterministic admissibility;
5. exact-intent materialization.

The Provider call should be owned by the public Repair API/run state rather
than hidden inside the vector resolver, because raw attempts, clarification and
crash recovery must be durable.

### Existing Provider and persistence seams are reusable

`OpenAICompatibleLiveProvider.generate_live()` already supplies public prompt,
JSON response, provider/model/usage/response ID and redacted evidence. Stage 1
and Stage 2 already implement versioned prompts, JSON-schema validation, at
most two correction attempts and append-only attempt artifacts.

`RepairAPI`, `RunStore`, `RunStage` and `continue_with_answer()` already provide
durable parameter/target/prototype/custom-property clarification. Phase 12.1
must add an explicit property-resolution stage/artifact binding instead of
pretending the new call belongs to Stage 1 or Stage 2.

## Recommended Module Boundaries

| Responsibility | Existing analog | Planned boundary |
|---|---|---|
| Eligible record filter | `PropertyKnowledgeResolver.resolve()` prefix | `property_retrieval.py` or a narrowed resolver method |
| Vector lifecycle | Phase 10.2 runner | production `PropertyKnowledgeRuntime` factory |
| Stage 1.5 prompt/schema/attempts | `request_stage.py`, `provider_stage.py` | new `property_resolution_stage.py` |
| Admissibility | exact-property registry checks | new pure `property_admissibility.py` |
| Exact intent construction | `ResolvedExactProperty` conversion | one pure constructor from passed decision + record |
| Durable orchestration | `RepairAPI._resolve_and_finish()` | explicit pre-Stage-2 property-resolution transition |
| Live evidence | Phase 12 transcript ledger | add stage `property_resolution` and count separately |

Names are discretionary; separation is not.

## Prompt Boundary

Stage 1.5 should receive only:

- original public phrase/value/unit/scope;
- resolved operation ID/type and target IFC class, without private identity
  beyond what the public operation already contains;
- bounded candidate IDs, canonical paths, official definitions,
  applicability, supported type/unit/template and retrieval scores;
- a strict output schema and prior validation feedback on attempt two.

It must not receive:

- pristine benchmark IFC, mutation manifest or Gold;
- full IFC STEP text or full property corpus;
- historical aliases;
- candidate values derived from private/current neighboring occurrences;
- Stage 2 ChangeSet schema or authoring internals.

## Evaluation Consequences

Because the target changes LLM behavior and property authority, regression
tests alone cannot support a system-level improvement claim. The phase needs:

- a preserved red-capable reproduction of `load bearing`;
- sibling positive/negative/boundary/cross-scene failure-family cases;
- a frozen Baseline-versus-Candidate evaluation with one evaluator;
- separate candidate recall and Stage 1.5 confirmed-selection precision reporting;
- zero false standard authorization and zero private leakage;
- offline Provider-seam and complete public API/CLI tests before live calls;
- a live run described as viability/reliability evidence, not as the sole
  proof of class-level improvement.

## Concrete Failure Scenarios

1. **Provider selects an unoffered ID:** block by membership in the persisted
   candidate set for the current run, operation and claim.
2. **Semantic overconfidence:** require calibrated policy, conflict detection
   and clarification; never use self-reported LLM confidence alone.
3. **Historical alias changes the new result:** active collection/query/prompt
   tests canary the old aliases and prove they are not runtime inputs.
4. **Cross-class property:** re-check applicability after LLM selection.
5. **Value invention:** copy value only from Stage 1/user claim and type-check
   against the selected record.
6. **Extra Provider call evidence drift:** extend attempt ledgers, preflight,
   curator and validator before accepting live results.
7. **Configured retrieval runtime is unavailable:** record explicit model,
   corpus, renderer and collection versions and fail before the Provider call
   when they cannot be prepared.
8. **Regression scope confusion:** Wall coverage means property-only existing
   occurrences, not Wall creation.

## Validation Architecture

Validation follows six independent layers:

1. schema/prompt and pure eligibility/admissibility unit tests;
2. deterministic vector lifecycle and retrieval evaluation;
3. Stage 1.5 Provider-seam tests with injected offline transport;
4. complete RepairAPI/CLI tests including clarification/restart/rollback;
5. historical Door/Window plus Wall/Beam/Column property non-regression;
6. zero-skip preflight, genuine DeepSeek UAT and separate Proof/IFCCompare.

Every live acceptance artifact must connect all six layers through stable run,
operation, claim, candidate and attempt IDs. No layer may trust the saved
aggregate result of another layer.
