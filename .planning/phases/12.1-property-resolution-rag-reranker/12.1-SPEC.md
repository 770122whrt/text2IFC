# Phase 12.1: Property Resolution RAG and Reranker Authority Correction - Specification

**Created:** 2026-08-21
**Status:** Frozen for planning
**Requirements:** RAG-05, RAG-06, RAG-07, OPS-03, OPS-04
**Depends on:** Phase 10.1, Phase 10.2, Phase 12 Plans 12-01 through 12-14,
and the current 12-15A/B/C correction baseline
**Blocks:** Phase 12 live Proof acceptance, Phase 12 closeout, Phase 13
**Ambiguity score:** 0.065 (gate: <= 0.20)

## Goal

Natural-language IFC property claims must resolve through a reusable,
class-applicable, multilingual vector retrieval and bounded LLM reranker stage.
No active runtime phrase dictionary may authorize a property. The Provider may
select only an offered authoritative candidate or request clarification; code
must independently decide whether that semantic choice is admissible and must
construct the exact typed property handoff from authoritative data.

The phase is complete only when the new path works for Window, Door,
Wall/WallStandardCase, Beam and Column property-capable occurrences, the
existing Door/Window repair workflows remain unchanged, a zero-skip public
preflight passes, real DeepSeek succeeds without fallback, and a separate
validator recomputes strict accepted Proof before Phase 12 closes.

## Trigger and Current Failure

The preserved Phase 12 real DeepSeek complete case produced valid Stage 1
claims for `IfcBeam` and `IfcColumn` with `property_phrase = "load bearing"`
and Boolean `true`. The default production resolver had no vector index and its
keyword path searched reviewed alias strings only, so it returned
`PROPERTY_NOT_RESOLVED` before Stage 2.

The earlier Phase 10.2 Window live case resolved `外窗` through
`REVIEWED_ALIAS_EXACT`; although BGE-M3/Qdrant was ready, that case did not use
vector retrieval to authorize the result. Therefore it is insufficient as
evidence for the target architecture.

## Requirements

### R1. Active resolver policy and alias retirement

- **Current:** Human-reviewed phrases in `property_aliases.json` can directly
  authorize a standard property and are included in the current collection
  inputs.
- **Target:** A new resolver/policy version excludes reviewed aliases from all
  active runtime inputs and authority. The file remains unchanged for
  historical artifact interpretation only. Explicit user-supplied canonical
  `Pset.Property` requests retain their exact no-RAG path.
- **Acceptance:** A runtime canary fails if alias records are loaded, embedded,
  prompted or cited by the new natural-language resolver; `外窗`
  still succeeds through vector plus reranker; old committed artifacts remain
  readable without relabeling.

### R2. Stage 1 property-claim boundary

- **Current:** Stage 1 emits `natural_language_property`, but tests allowed
  manually curated full alias phrases to stand in for semantic retrieval.
- **Target:** Stage 1 emits only target/operation identity, original phrase,
  raw value/unit/scope and request provenance. It neither translates the phrase
  into a canonical Pset nor emits reranker candidates.
- **Acceptance:** Prompt/schema tests reject Provider-selected Pset/property,
  value type, candidate ID and executable status in a natural-language claim;
  Window/Door/Wall/Beam/Column positive claims retain their original phrase.

### R3. Deterministic candidate eligibility

- **Current:** Applicability filtering exists inside the resolver, but it is
  coupled to exact alias/keyword/vector decision logic.
- **Target:** Eligibility is a separately testable pre-retrieval step using
  checked-in IFC2X3 PSD or current-project record provenance, target-class
  inheritance, supported scalar template/value type, operation scope and
  public-source constraints.
- **Acceptance:** Cross-class, non-scalar, unsupported-scope, private-derived,
  stale-corpus and incompatible-value candidates never enter Top-K. Project
  custom records remain candidates but cannot auto-authorize.

### R4. Production multilingual vector lifecycle

- **Current:** BGE-M3/Qdrant is wired only by the dedicated Phase 10.2 runner;
  `RepairAPI.from_environment` and Phase 12 live UAT create a resolver with
  `vector_index=None`.
- **Target:** The public production construction path prepares/reuses a
  versioned BGE-M3/Qdrant property collection without aliases, exposes a
  bounded search seam, records health and blocks natural-language resolution
  when vector evidence is unavailable or its declared configuration is stale.
- **Acceptance:** Offline lifecycle tests prove build/reuse/version/failure;
  production preflight records `knowledge_health.status=ready`, model and
  collection versions, record count and zero Provider calls before all
  local gates pass.

### R5. Bounded Top-K query and evidence

- **Current:** Vector search receives only the raw phrase and returns record
  IDs/scores; the Phase 12 production path has no vector evidence.
- **Target:** A versioned query binds the original phrase, resolved target IFC
  class, raw value kind, unit/scope, operation ID, run/request/model IDs and
  corpus version. Top-K contains only public candidate IDs,
  canonical names, definitions, applicability, template/value/unit metadata,
  scores and source provenance.
- **Acceptance:** Query and candidate-set schemas reject extra/private fields,
  duplicate/unoffered IDs and unbounded candidate counts; persisted evidence
  reproduces candidate membership and ordering.

### R6. Independent Property Resolution Provider stage

- **Current:** No LLM reranker exists; Phase 10.2 explicitly excluded one.
- **Target:** Stage 1.5 is a separate Provider call between retrieval and Stage
  2. It receives one public query plus Top-K and may output only `confirmed`,
  `clarification_required` or `unsupported`, with at most one offered selected
  candidate, bounded conflicting IDs and a bounded clarification question.
- **Acceptance:** The new schema/prompt rejects invented candidate IDs,
  Pset/property/value/type/scope/operation fields and private evidence. At most
  two attempts are preserved; malformed output receives schema feedback only,
  never a compatibility normalizer.

### R7. Deterministic admissibility gate

- **Current:** `PropertyKnowledgeResolver.resolve()` performs semantic
  retrieval and exact-intent construction in one decision method.
- **Target:** After the Stage 1.5 semantic decision, code verifies candidate-set
  membership, authoritative record identity, class/template/value/unit/scope
  compatibility, decision cardinality, conflict state and versioned
  minimum retrieval-quality policy. It records score/rank/margin but never
  turns vector Top-1 or a large margin into semantic authority; Stage 1.5 owns
  the bounded semantic comparison. This gate does not claim to prove language
  semantics.
- **Acceptance:** Tests reproduce concrete failures: the Provider selects an ID
  that was not offered; the selected record is not applicable to the resolved
  class; value type/unit/scope is incompatible; or an occurrence request would
  mutate a shared Type. Below-floor retrieval, multiple confirmed candidates,
  stale configured versions and alias-derived evidence also fail before exact
  intent or Stage 2.

### R8. Program-constructed ExactPropertyIntent

- **Current:** The local resolver can directly populate a resolved exact intent
  after exact/alias/hybrid logic.
- **Target:** Only a passed admissibility result can cause program code to copy
  canonical set/property/value type/unit metadata from the authoritative record
  and user value/scope/provenance into `ExactPropertyIntent`. Provider text
  cannot supply or overwrite those fields.
- **Acceptance:** Exact-intent provenance links the query, persisted candidate
  set, semantic decision, admissibility policy and authoritative record by
  stable IDs and versions. Stage 2 receives the exact typed fact and no
  retrieval payload.

### R9. Target/model binding and publication authority

- **Current:** Existing `authorize_standard_property()` and semantic Binder bind
  exact properties to operation, target, request and model.
- **Target:** The existing binding and atomic authoring path remains the sole
  executable authority after ExactPropertyIntent. No Stage 1.5 response is
  directly authorable.
- **Acceptance:** Wrong target/model/request reuse fails; reopened IFC L2 proves
  canonical property, typed value, occurrence-direct ownership, no duplicate
  effective fact, unchanged shared Type and preservation of unrelated roots.

### R10. Clarification and durable resume

- **Current:** The API supports parameter, target, prototype and custom-property
  clarification, but has no durable reranker decision/resume boundary.
- **Target:** Vector unavailable, below-floor retrieval, competing candidates
  unresolved by the reranker, reranker clarification and custom/project
  candidates produce a bounded
  clarification with the same run lineage. Restart/resume uses the persisted
  query and offered candidate set for that run and claim.
- **Acceptance:** Start/resume/restart/idempotency tests prove zero Stage 2 before
  answer, one bound answer, stale/replayed answers rejected, cancel publishes no
  IFC and successful resume preserves all attempts/evidence.

### R11. Family-neutral property scope

- **Current:** `set_occurrence_properties` supports existing Beam, Column, Door,
  Wall, WallStandardCase and Window occurrences; add Beam/Column/Window/Door
  operations may also carry property intents through common semantic authoring.
- **Target:** All natural-language property claims use the same Stage 1.5 path.
  Wall remains existing-occurrence property-only. Door/Window geometry, Type,
  Storey, thresholds and workflows are unchanged.
- **Acceptance:** Focused complete chains pass for `外窗 -> IsExternal`, Door
  property semantics, Wall property-only, Beam/Column `load bearing`, and mixed
  Door+Window+Beam+Column atomic publication. There is no `add_wall` claim or
  operation.

### R12. Frozen evaluation and no false authorization

- **Current:** The 40-case Phase 10.2 retrieval set measures the old
  alias/keyword/vector policy; Phase 12 offline tests hard-coded full reviewed
  alias phrases and missed the valid shortened Stage 1 claim.
- **Target:** A checked-in Baseline-versus-Candidate evaluation keeps failures in
  the denominator, re-scores both with one evaluator and adds group-isolated
  Window/Door/Wall/Beam/Column natural-language, ambiguous, wrong-class,
  unknown, malformed and boundary cases. Subagent opinion is not test evidence.
- **Acceptance:** Every supported standard positive has its canonical record in
  Top-K; all confirmed selections are correct; ambiguous/negative/custom cases
  have zero false standard authorization; capability slices and uncertainty are
  reported without promoting a single fixed case to system-level evidence.

### R13. Zero-skip preflight and genuine DeepSeek UAT

- **Current:** The Phase 12 preflight is green, but the real complete case failed
  before Stage 2 and the live runner does not count Stage 1.5 calls.
- **Target:** A fresh preflight covers every stage seam and the public API/CLI
  complete, clarification/resume, unsupported, malformed/truncated reranker,
  unoffered-candidate selection, vector failure, persistence/recovery, rollback,
  Gold isolation, reopen, L0/L1/L2/preservation and publication behavior. Real
  DeepSeek then runs only with the official endpoint/default SDK and ready
  vector evidence.
- **Acceptance:** Preflight has no failure, skip, substitution or timeout and
  records zero network calls. Live evidence records Stage 1/1.5/2 attempts,
  raw responses, prompts, profiles, tokens and correction lineage with every
  fallback/cache flag false.

### R14. Independent Proof and Phase 12 closeout

- **Current:** The failed live run is not acceptance-eligible and Phase 12 is
  open; accepted Proof remains the prior independently validated collection.
- **Target:** A separate process validates raw live evidence, vector/reranker
  binding, ExactPropertyIntent lineage, damaged/public boundary, reopened IFC,
  strict L0/L1/L2/preservation/isolation before curation.
  Phase 12.1 owns the deferred Phase 12 acceptance and closeout work.
- **Acceptance:** Only independently recomputed successes enter append-only
  Proof; the failed 2026-08-20 run stays unchanged; full regressions and
  IFCCompare pass; only then do REQUIREMENTS/ROADMAP/STATE close RAG-05..07 and
  OPS-03/04. Phase 13 has no artifact or execution.

## In Scope

- Versioned public query, candidate-set, reranker-decision and admissibility
  contracts.
- BGE-M3/Qdrant production lifecycle and public health evidence.
- One bounded Stage 1.5 Provider call per unresolved natural-language property
  claim, with at most two attempts.
- Program construction of ExactPropertyIntent and existing target/model Binder
  handoff.
- Durable clarification/resume and crash-safe run evidence.
- Window, Door, Wall/WallStandardCase, Beam and Column property paths.
- Offline evaluation, full public-chain preflight, real DeepSeek UAT,
  independent Proof, IFCCompare and Phase 12 status closure.

## Out of Scope

- New manual aliases or LLM-output compatibility mappings.
- Rewriting or deleting historical alias files and accepted evidence.
- Wall creation, structural analysis nodes or unregistered operations.
- Door/Window workflow, geometry, Type, Storey, Ground Truth or L1 threshold
  redesign.
- Shared-Type property mutation and complex property templates.
- Cross-encoder/second-reranker experiments or general Agentic retrieval loops.
- Phase 13 or 128k context work.
