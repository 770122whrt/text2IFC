# Phase 10.2: IFC2X3 Property Knowledge Retrieval and Resolution - Specification

**Created:** 2026-07-23
**Status:** Written specification awaiting user review
**Requirements:** RAG-01, RAG-02, RAG-03, RAG-04
**Depends on:** Phase 10.1
**Ambiguity score:** 0.07 (gate: <= 0.20)

## Goal

Given an IFC2X3 model and a Chinese or English property request that may not
name an exact IFC Pset/property path, resolve the phrase through a bounded,
evidence-bearing local knowledge pipeline, convert only an authorized result
into the exact typed Phase 10.1 property contract, author the property on the
target occurrence, and publish an IFC only after reopen, L1 and requested-
property L2 pass.

Phase 10.2 must prove one real `LargeBuilding.ifc` Window chain with DeepSeek
and a ready local vector service. It also introduces reusable occurrence
property authoring for Wall, Door and Window without introducing shared-Type
mutation or broad geometry operations.

## Why This Phase Exists

Phase 10.1 can safely execute an exact request such as:

```text
Pset_WindowCommon.IsExternal = true
```

It cannot safely interpret requests such as:

```text
把这个窗户标记为外窗。
Mark this window as external.
```

Sending the complete IFC2X3 property library to the Provider is wasteful and
does not establish authority. Allowing the Provider to invent a Pset path,
value type or unit is unsafe. Phase 10.2 therefore places property discovery
between Stage 1 and the existing exact-property Binder:

```text
IFC + user text
  -> Stage 1 RepairIntent 0.3 claims
  -> local Property Knowledge Resolver
  -> authorized ExactPropertyIntent
  -> existing Binder and Stage 2
  -> one bound ChangeSet
  -> atomic IFC authoring
  -> reopen + L1 + requested-property L2
  -> published IFC or honest failure
```

Target Wall/Type resolution remains the deterministic Phase 7/09.1 path. The
property knowledge resolver does not replace target retrieval, choose a
prototype, or inspect private Ground Truth.

## Locked Design

### 1. Authority model

| Layer | Role | Authority |
|---|---|---|
| Checked-in buildingSMART IFC2X3 PSD registry | Canonical Pset/property name, applicability, template, IFC data type and unit family | Authoritative standard source |
| Current IFC project facts | Existing project Pset/property spelling, observed type/unit/ownership and occurrence counts | Authoritative only for facts observed in that source IFC |
| Reviewed alias records | Approved Chinese/English terms pointing to a canonical record | Retrieval enrichment; may authorize only under the exact alias rule |
| Qdrant vectors | Semantic candidate recall | Rebuildable, non-authoritative index |
| Provider output | User-phrase and raw-value extraction | Claim only; never authorization |

bSDD is explicitly excluded. Qdrant is never a source of truth and can be
deleted and rebuilt from the authoritative records plus reviewed enrichment.

### 2. RepairIntent 0.3 property claims

RepairIntent 0.3 introduces a discriminated union. Existing 0.1 and 0.2
artifacts keep their original readers and meanings.

An `exact_property` claim preserves an explicitly named Pset/property:

```json
{
  "intent_kind": "exact_property",
  "set_name": "Pset_WindowCommon",
  "property_name": "IsExternal",
  "raw_value": true,
  "raw_unit": null,
  "requested_value_type": null,
  "scope": null,
  "source": {
    "source_kind": "user_request",
    "reference": "request:/text",
    "excerpt": "Pset_WindowCommon.IsExternal = true"
  }
}
```

A `natural_language_property` claim preserves the user's phrase without
inventing an IFC path:

```json
{
  "intent_kind": "natural_language_property",
  "property_phrase": "标记为外窗",
  "raw_value": true,
  "raw_unit": null,
  "scope": null,
  "source": {
    "source_kind": "user_request",
    "reference": "request:/text",
    "excerpt": "把这个窗户标记为外窗"
  }
}
```

Stage 1 may extract only the phrase, scalar value, unit, scope and provenance.
It cannot select a Pset, declare a property standard/custom, choose an IFC data
type, normalize a unit, or mark a claim executable.

### 3. Versioned knowledge records

The authoritative standard corpus indexes all IFC2X3 property definitions, not
only Window properties. Each standard record contains at least:

- stable record ID and record schema version;
- IFC schema version;
- canonical Pset and property names;
- applicable IFC classes;
- property template type;
- IFC value type and unit families;
- English definition text when present in the PSD source;
- authoritative source path and content hash;
- authorable/not-authorable classification.

All records may be retrieved, but Phase 10.2 authoring permits only
`TypePropertySingleValue` records with a known IFC scalar data type.
Enumerated, list, bounded, table, reference and complex definitions remain
searchable evidence but cannot produce an executable ChangeSet.

Applicability uses IFC inheritance. For example, a Pset applicable to
`IfcWall` may be valid for `IfcWallStandardCase` when the checked-in EXPRESS
declaration confirms that subtype relationship.

Project-property records are aggregated by source IFC hash and contain:

- exact observed Pset/property names;
- target IFC class;
- observed IFC value types and units;
- direct/inherited ownership;
- occurrence frequency and provenance references.

Actual property values are not included in embedding text. A project-only or
otherwise custom property always requires the existing hash-bound custom
confirmation, even when retrieval produces one unique project candidate.

### 4. Knowledge index lifecycle

The standard record store is built explicitly from the checked-in IFC2X3
registry and is reused by corpus hash. Project-property records are built or
reused by source IFC SHA-256. Neither is rebuilt during every Repair Run.

The vector collection identity includes:

- record schema version;
- authoritative corpus hash;
- reviewed-alias hash;
- embedding provider ID;
- embedding model fingerprint.

The first live implementation uses local BGE-M3 through a replaceable
`EmbeddingProvider` interface and local Qdrant. Unit tests use a deterministic
fake embedding provider and do not load the real model. Standard embeddings
are computed once for a matching collection fingerprint and then reused.

### 5. Bounded hybrid retrieval

The resolver uses four retrieval paths:

1. exact canonical Pset/property lookup;
2. exact reviewed-alias lookup;
3. deterministic token/keyword retrieval;
4. dense-vector retrieval from Qdrant.

No Elasticsearch, sparse/multi-vector retrieval, cross-encoder, LLM reranker
or agentic retrieval loop is introduced in this phase.

Every query is filtered by:

- resolved target IFC class and IFC inheritance;
- `TypePropertySingleValue`;
- known scalar IFC data type;
- supported value/unit compatibility.

Candidate output is bounded and records source ranks, scores, matched terms,
applicability evidence, authority and provenance. Full candidate evidence
remains local and is never copied into Stage 2.

### 6. Deterministic decision policy

Confirmation is exceptional rather than the default:

- A unique applicable canonical exact match is authorized automatically.
- A unique applicable reviewed alias is authorized automatically.
- A natural-language standard candidate is authorized automatically only when
  keyword and vector retrieval independently rank the same applicable record
  first, the keyword path has positive canonical/alias evidence, vector score
  and margin meet a versioned checked-in policy, and there is no tied or
  conflicting peer.
- A vector-only result is candidate evidence and cannot authorize a property.
- Low confidence, insufficient margin, retriever disagreement, applicability
  conflict, type/unit conflict and multiple plausible candidates produce one
  bounded local clarification.
- A project-only/custom candidate produces the Phase 10.1 custom preview and
  requires explicit confirmation.

The score and margin values are calibrated on the checked-in Phase 10.2
evaluation set, recorded in a versioned deterministic policy file, and cannot
be supplied or changed by the Provider.

Candidate selection and custom confirmation are local state transitions. They
do not call the Provider again. Stage 1 is rerun only when the user supplies
new free text, changes the value/unit, or changes the requested operation.

### 7. Value and unit normalization

The knowledge resolver, not Stage 1, supplies the standard IFC value type.
Phase 10.2 supports:

- `IfcLabel`/`IfcText`-compatible strings;
- `IfcBoolean`;
- `IfcInteger`;
- `IfcReal`;
- scalar IFC length measures with deterministic `mm`, `cm` and `m`
  normalization, including the corresponding Chinese unit terms.

Unit conversion uses the source model's declared project units. An absent unit
may be inferred only when the standard record and project unit make the
interpretation unique. Incompatible values, unsupported unit families and
ambiguous unitless measures require clarification and cannot be authored.

Relative or computed requests such as “increase by 20%”, “use the average on
this storey” or “copy every property from another Window” are outside this
phase. The value must resolve to one deterministic scalar.

### 8. Exact handoff and token boundary

A successful resolution emits the existing Phase 10.1
`ExactPropertyIntent`/authorized property fact. Stage 2 receives only the
final exact typed facts needed by the selected operation; it does not receive:

- the complete property registry;
- Top-K candidates;
- PSD definitions;
- aliases;
- embedding vectors or scores;
- Qdrant payloads.

This preserves the existing Binder as the only authorization boundary and
keeps Provider context proportional to the requested change rather than to the
IFC2X3 knowledge corpus.

Each claim writes local evidence under:

```text
property-resolution/
  claim-001/
    query.json
    candidates.json
    decision.json
```

The files contain hashes and provenance and are referenced by the Run
manifest. They are evidence, not Provider prompt content.

### 9. Generic occurrence property operation

Phase 10.2 adds `set_occurrence_properties` to the Operation Registry. The
operation:

- targets exactly one existing occurrence;
- supports `IfcWall`, `IfcWallStandardCase`, `IfcDoor` and `IfcWindow`;
- writes one or more authorized `IfcPropertySingleValue` facts atomically;
- changes no geometry, placement, containment, host/opening or shared Type;
- reuses the Phase 10.1 Binder, semantic authorer, transaction and dynamic L2
  extension.

`add_window_with_opening_to_wall` remains available and may attach authorized
properties to its newly created Window. The generic operation is for property-
only modification of an existing target. Future Beam, Column and Space
support expands the authoring whitelist and adapter-specific validation; it
does not require a new property knowledge architecture.

### 10. Safe occurrence upsert

The writer uses the following merge contract:

- If the target has one exclusive direct matching Pset/property, update it.
- If the matching direct Pset relationship is shared by multiple occurrences,
  use copy-on-write: detach only the target from that shared relationship,
  attach a cloned target-owned Pset, and change only the clone.
- If the fact exists only on the Type, leave the Type unchanged and add an
  occurrence override when the requested effective value differs.
- If the property is absent, add it to one target-owned direct Pset.
- Multiple conflicting direct Psets/properties fail closed; no heuristic merge
  is permitted.
- Unrelated properties in the selected Pset and all non-target objects remain
  unchanged.

One operation may contain multiple properties. Resolution and authoring are
all-or-nothing: any unresolved claim, write failure, reopen failure or
postcondition failure publishes no successful IFC.

### 11. L1 and L2 publication gates

For `set_occurrence_properties`, L1 verifies:

- target GlobalId and IFC class are preserved;
- placement and representation are unchanged;
- containment, host and Type relationships are unchanged;
- non-target occurrences are unchanged;
- the output reopens as IFC2X3.

Requested-property L2 verifies independently from the reopened IFC:

- exact Pset/property identity;
- normalized scalar value;
- IFC value type and unit;
- occurrence-direct ownership when an override/write was requested;
- no duplicate effective property;
- preservation of unrelated target properties;
- unchanged shared Type facts and non-target facts.

Private Ground Truth may be used only after production application to perform
benchmark comparison. It never supplies a retrieval candidate, expected
property or prompt input.

### 12. Failure and degradation behavior

- If Qdrant is unavailable, canonical exact, reviewed alias and keyword paths
  remain usable.
- A query that needs vector consensus while Qdrant is unavailable returns
  `PROPERTY_VECTOR_UNAVAILABLE`; it does not guess or silently downgrade to
  vector-free auto-authorization.
- Registry, alias, collection or model fingerprint drift prevents reuse and
  requires an explicit rebuild.
- Invalid source IFC, invalid produced IFC, stale target/model fingerprint,
  unresolved property, unconfirmed custom property and failed L1/L2 all
  suppress the successful IFC artifact.
- The real Phase 10.2 UAT must record knowledge health as `ready`; a degraded
  run cannot satisfy live acceptance.

## Boundaries

### In scope

- Full IFC2X3 property knowledge records and project-property observations.
- Reviewed aliases, simple keyword retrieval, BGE-M3 embeddings and Qdrant
  hybrid retrieval.
- Exact and natural-language RepairIntent 0.3 property claims.
- Deterministic candidate authorization/clarification/custom confirmation.
- Scalar `IfcPropertySingleValue` type and common length-unit normalization.
- Occurrence property authoring for Wall, WallStandardCase, Door and Window.
- Target-local copy-on-write, atomic application, reopen, L1 and dynamic L2.
- One real LargeBuilding Window DeepSeek UAT using
  `Pset_WindowCommon.IsExternal`, not `FireRating`.

### Out of scope

- bSDD and other remote knowledge authorities.
- Vector-only automatic authorization.
- Shared-Type property mutation or automatic propagation to all same-Type
  occurrences.
- Enumerated, list, bounded, table, reference or complex property authoring.
- Quantity, material or classification authoring redesign.
- Relative calculations, property-set cloning from a neighboring object or
  unrestricted batch repair.
- New Door/opening, Beam, Column, Space or geometry operations.
- L3 authoring exactness, curved-wall work and the 128k context experiment.

## Verification Strategy

### Retrieval evaluation

A checked-in set contains at least 40 cases:

- at least 12 Chinese standard-property expressions;
- at least 12 English standard-property expressions;
- at least 8 ambiguous, inapplicable, custom or unknown negative cases;
- the remainder covers aliases, spelling variation and mixed-language input.

The report separates candidate recall from automatic authorization. Automatic
authorization must have zero false positives. A low-recall result may ask for
clarification; an incorrect silent authorization fails the phase.

### Deterministic authoring tests

Fixtures cover:

- Wall, WallStandardCase, Door and Window property-only operations;
- create, exclusive update, inherited override and shared-Pset copy-on-write;
- multiple atomic property writes;
- duplicate/conflict failure with unchanged source bytes;
- standard auto-resolution, reviewed alias, hybrid consensus, ambiguity,
  custom confirmation and vector-unavailable behavior;
- unit normalization and incompatible value/unit rejection;
- non-target, geometry, relationship and shared-Type preservation.

### Real DeepSeek UAT

One `LargeBuilding.ifc` Window case runs:

```text
Chinese natural-language IsExternal request
  -> real DeepSeek Stage 1
  -> ready BGE-M3/Qdrant hybrid resolver
  -> exact authorized property fact
  -> real Stage 2
  -> bound ChangeSet
  -> IfcOpenShell apply and reopen
  -> L1 + requested-property L2
  -> published repaired IFC and complete evidence
```

The UAT uses no fake embeddings, synthetic Provider response, fallback
ChangeSet or private-Gold input. Provider failure remains an honest failed run.
Wall and Door require deterministic end-to-end integration tests in this phase
but do not require additional live Provider calls.

## Acceptance Criteria

- [ ] RepairIntent 0.3 round-trips discriminated `exact_property` and
  `natural_language_property` claims while 0.1/0.2 readers remain stable.
- [ ] Stage 1 cannot set canonical path, standard/custom status, IFC value
  type, normalized unit, confirmation or authorization for a natural-language
  claim.
- [ ] All IFC2X3 property records have version, provenance, applicability,
  template, type/unit and source hashes; all searchable records are separated
  from the authorable SingleValue subset.
- [ ] Project-property records are source-hash scoped and custom project
  candidates still require hash-bound confirmation.
- [ ] Local BGE-M3 and Qdrant adapters are replaceable, lazy-loaded and reused
  by deterministic collection fingerprint.
- [ ] Exact, alias, keyword and vector retrieval produce bounded evidence and
  enforce IFC-class, template, scalar-type and unit hard filters.
- [ ] Vector-only evidence cannot authorize a property.
- [ ] At least 40 retrieval cases report candidate recall and authorization
  accuracy with zero false automatic authorizations.
- [ ] A successful decision emits only the exact Phase 10.1 contract; Stage 2
  receives no Top-K list, definitions, aliases, vectors or retrieval scores.
- [ ] Local candidate selection/confirmation does not invoke the Provider
  again unless the user changes free text, value/unit or operation.
- [ ] Deterministic scalar and `mm`/`cm`/`m` normalization succeeds only when
  type and unit semantics are unambiguous.
- [ ] `set_occurrence_properties` supports one existing Wall,
  WallStandardCase, Door or Window occurrence and atomically writes one or more
  authorized scalar properties without geometry or shared-Type mutation.
- [ ] Shared occurrence Psets use copy-on-write and all non-target effective
  facts remain unchanged.
- [ ] Reopened L1 and requested-property L2 independently validate identity,
  preservation, exact typed value/unit, ownership and duplicate absence.
- [ ] Qdrant degradation is explicit; a vector-required query never guesses.
- [ ] The LargeBuilding real DeepSeek `IsExternal` Window chain records
  knowledge health `ready`, real Stage 1/2 traces, one bound ChangeSet, reopened
  L1/L2 success and a published IFC without synthetic fallback or Gold leakage.
- [ ] Focused/full tests, compileall, private-canary scan and
  `git diff --check` pass.
