# Phase 6.6 Spec: Cross-case Stability Testing and Failure Attribution

## Purpose

Phase 6.6 measures whether the real Chinese Text-to-IFC workflow is reliable
across three different difficulty levels. It uses fixed, provenance-linked
inputs and records failures before approving a repair. The phase does not call
a workflow stable merely because one easy prompt succeeds or because the same
prompt is repeated several times.

## Goal

Produce one accepted, independently reopenable IFC2X3 artifact for each of the
fixed Easy, Medium, and Difficult standard inputs, with correct semantic facts,
spatial relationships, geometry, failure ownership, and complete audit
evidence.

## Primary Stability Metric

The primary gate is cross-case coverage:

| Difficulty | Active case | Current result | Required result |
|---|---|---|---|
| Easy | `STD-E-RES-01` | Accepted session `d2f86855a9738b50` | Accepted and reopenable |
| Medium | `STD-M-OFF-03` | Accepted session `8c8ef9a111e326d7` | Accepted and reopenable |
| Difficult | `STD-D-MUL-01` | Historical Design Brief truncation | Accepted and reopenable |

All three rows must pass. This may be described as bounded cross-case
operational stability, not as a statistical success rate. Repeated runs become
a secondary metric only after all three difficulty rows pass once.

## Fixed Inputs and Truth Boundary

- Manifests must contain exact natural-language input, SHA-256 identity, and
  `model_output: null` before a provider call.
- `STD-M-OFF-01` remains historical ambiguity evidence. Its successor
  `STD-M-OFF-02` explicitly defines a closed 12 m by 6 m office perimeter and
  supersedes the input contract without rewriting old evidence.
- `STD-M-OFF-03` preserves the same geometry but replaces the unsupported
  double-leaf entrance semantic with one supported 1600 mm by 2200 mm entrance
  door. True IFC2X3 `IfcDoorStyle.OperationType` support remains future work.
- JSON Schema remains the only Formal BIM JSON structural truth.
- No test may silently add dimensions, walls, storeys, spaces, openings,
  relations, placements, or properties missing from the input.
- A workflow-internal error must not be routed to the user as missing BIM
  information.

## Runtime Baseline

- Provider: `deepseek-openai-compatible`.
- Model: `deepseek-v4-flash`.
- Phase 6.6 completion-token budget: `65536`.
- Generation strategy: staged ChangeSet composition.
- Trace level: compact, with redacted requests and retained response IDs.
- Provider credentials and base URLs remain local environment data and must not
  appear in artifacts, reports, commits, or logs.

The 64K value is a controlled runtime parameter, not evidence of success by
itself. Prompt, input, model, schema, and evaluator remain fixed when comparing
the 8K and 64K Medium observations.

## Per-case Acceptance

A case is accepted only when all applicable checks pass:

1. A real provider processes the frozen manifest input.
2. Every provider response required for acceptance finishes without
   truncation; partial JSON is never parsed as Formal.
3. The Design Brief contains addressable facts and no unresolved user question.
4. Formal BIM JSON 2.0 validates against the canonical schema.
5. Expected-fact counts, storey containment, shared-wall obligations, opening
   and fill relationships, semantic coverage, and preservation checks pass.
6. Global geometry gates pass after all packages are composed.
7. IFC2X3 compiles and reopens through IfcOpenShell.
8. Entity counts and spatial relationships match the natural-language input.
9. Audit is non-blocking and cannot override a failed deterministic gate.
10. The case result, report, response IDs, token usage, elapsed time, hashes,
    IFC path, and zero-finding secret scan are retained.
11. Human visual review finds no obvious missing enclosure, duplicate shared
    wall, detached host, incorrect storey, or incoherent placement.

## Stability Measurements

Each run records:

- final status and accepted/not-accepted result;
- stage reached and failure owner;
- provider response IDs and finish reasons;
- prompt, completion, reasoning, cached, and total token counts;
- elapsed time by Design Brief, generation, repair, gate, Audit, and compile;
- package count, attempts per package, and empty-package decisions;
- schema/gate issue codes and issue deltas between repairs;
- clarification fallback usage and question count;
- unrelated-component preservation rate;
- IFC schema, reopen result, entity inventory, relationship inventory, and
  artifact hash;
- secret-scan finding count.

## Failure Taxonomy

Failures must be classified before TDD begins:

- `input_ambiguity`: required BIM semantics are genuinely missing;
- `provider_truncation`: response ends with `finish_reason=length`;
- `provider_runtime`: connection, timeout, or provider API failure;
- `decomposition`: package ownership or package scheduling is wrong;
- `structured_output`: non-Draft output violates its contract;
- `schema_validation`: Formal BIM JSON violates the canonical schema;
- `relationship`: containment, shared wall, host, void, or fill is wrong;
- `geometry`: dimensions, placement, enclosure, intersection, or topology fails;
- `compile_reopen`: IFC cannot compile or reopen;
- `audit`: reviewer finds a supported defect after deterministic gates;
- `routing_attribution`: workflow/provider defects are assigned to the user;
- `evidence_persistence`: a failed run does not leave a normal machine-readable
  result.

## Experiment Log

### P66-EXP-001: Medium with the 8K default

- Input: unchanged `STD-M-OFF-02`, hash
  `86c737c2498d19013b52e7ad6a78d5dca411554e1146dde29c769aed2d27cce4`.
- Session: `d254ffd6ace08cea`.
- Result: Design Brief reached `ready`; first staged ChangeSet response ended
  with `finish_reason=length` at the 8192-token default.
- IFC: not generated.
- Classification: `provider_truncation` plus `evidence_persistence`, because the
  exception escaped before a normal campaign result was written.
- Decision: keep as baseline evidence; retry one variable at 64K.

### P66-EXP-002: Medium with 64K

- Same input, provider, model, prompt registry, schema, staged workflow, and
  evaluator as EXP-001.
- Session: `ce0eccf3c9d37f0e`.
- Result: no response truncation. The storey-local package produced a complete
  16,510-token response and passed its package gate.
- The manifest then scheduled `package-cross-storey` even though it owned zero
  components and zero relationships. Three provider attempts all finished with
  `stop`, but the package remained invalid.
- Final issue: `UNRESOLVED_DRAFT_PATH` for
  `/generation_package_manifest/packages/2/owned_component_ids`.
- The router assigned this internal path error to the user and selected
  `ask_user`; final status was `draft_or_blocked` after 247.5 seconds.
- IFC: not generated.
- Classification: `decomposition` and `routing_attribution`, not
  `input_ambiguity` and not `provider_truncation`.
- Decision: 64K removes the observed truncation but is insufficient for
  acceptance. Preserve the run and plan deterministic fixes before another
  live call.

### P66-EXP-003: First supported-scope Medium successor

- Input: `STD-M-OFF-03`, hash
  `eb9833500ffecce2a7c3e585bab032fc9f16483a601a53fccb7ae226572e0e50`.
- Session: `1d155f2003fcc419`.
- Result: BIM JSON validated and IFC2X3 compiled/reopened, but final Audit
  blocked acceptance.
- Root causes: the Design Brief put `floor_slabs` inside a storey despite the
  canonical top-level few-shot; it assigned three `host_centerline` windows to
  one continuous wall; and the staged ChangeSet placed the main door opening
  at local Z 1100, making its top exceed the wall height.
- Decision: do not add another slab dialect and do not weaken the alignment
  Gate. Reject non-canonical Design Brief facts, remove the prompt conflict,
  add focused slab/door examples, and rerun the same frozen input.

### P66-EXP-004: Canonical-contract Medium rerun

### P66-EXP-005: Frozen Difficult 64K observation

- Input: unchanged `STD-D-MUL-01`, hash
  `816b8f796c232595bbe0d031e824d9892f2b09d26bffd213dcca96a48f92a51e`.
- Session: `1524fc3a5071c348`.
- Provider evidence: two complete real-provider Design Brief responses;
  26,966 and 24,782 total tokens respectively. No provider truncation or
  runtime failure was observed.
- Result: the first response asked three Chinese clarification questions for
  door positions, window positions, and the atrium/void bounds. The
  observation harness supplied its non-inventing unknown answer, and the
  second response correctly stopped at `draft_required`. No Gate, Audit, BIM
  JSON candidate, or IFC compile stage was reached.
- Genuine input gaps: the frozen input does not define door/window offsets,
  exact stair footprint/run direction/riser-tread geometry, or a dedicated
  second-storey stair-arrival/opening zone.
- Layout conflict: all of the second-storey north-east 5 m by 3 m zone is
  assigned to bedroom two and all of the middle 12 m by 2 m zone is assigned
  to the corridor. The current truth-preserving Gate cannot place the required
  stair opening without overlapping a declared `IfcSpace` unless the user
  revises one of those space bounds or explicitly allocates a non-space stair
  landing/opening zone.
- Design Brief defects retained for diagnosis: it derived the void bounds as
  `x=6000..12000, y=0..3000` while simultaneously marking those bounds
  missing, and it emitted a different first-floor slab opening at
  `x=7000..12000, y=5000..8000`. These are Agent consistency defects, not
  permission to guess the final geometry.
- Classification: `input_ambiguity` plus `structured_output`; stair/railing
  generation, geometry Gates, compile/reopen, and visual correctness remain
  untested because the run stopped before Formal generation.
- Evidence root:
  `dataset/processed/agent-demo/phase6.6-difficult-live-64k-observation/`.
- Decision: preserve the frozen failure. Do not weaken the Gate or rewrite
  `STD-D-MUL-01`. Create a provenance-linked Difficult successor only after
  explicit user decisions resolve the stair-arrival zone and remaining
  placement facts.
