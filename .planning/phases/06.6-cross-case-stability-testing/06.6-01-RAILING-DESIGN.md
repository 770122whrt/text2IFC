# Phase 6.6-01 Design: Declarative Linear Products and IfcRailing

## Decision

Implement `IfcRailing` as the first consumer of a declarative linear-product
contract. Do not add a railing-only pipeline parallel to walls, doors, stairs,
or slabs. The contract belongs to orchestration expectations only; BIM JSON
2.0 JSON Schema remains the sole Formal output truth.

## Problem

The IFC2X3 capability registry marks `IfcRailing` as `generate`, the Formal BIM
JSON schema accepts the class, and the compiler can create represented IFC
products. The current Text-to-IFC workflow is nevertheless incomplete because:

- Design Brief `known_facts.railings` are not projected into expected facts;
- staged generation packages do not authorize railing IDs;
- total-count and storey-containment expectations omit railings;
- semantic geometry expectations do not preserve railing endpoints or height;
- no focused few-shot teaches a linear segment on a storey-local datum;
- no deterministic Gate checks boundary alignment and height;
- no Text -> BIM JSON -> IFC2X3 railing artifact has been reopened.

This is a workflow defect, not an IFC schema defect.

## Alternatives Considered

### A. Railing-only branches

Add `railings` beside every existing fixed collection in each module. This is
small initially but repeats the same projection, package, count, containment,
and geometry plumbing for every future product class. Rejected because it
creates a shallow interface and accumulating class-specific conditionals.

### B. Universal IFC product registry now

Replace all existing wall, door, window, slab, and stair handling with one
fully generic registry. This has long-term potential but is too broad for a
stability bugfix and would put accepted Easy/Medium paths at unnecessary risk.
Rejected for Phase 6.6.

### C. Additive linear-product contract

Keep established special workflows intact and add one small, declarative
interface for product families that share storey ownership and segment-based
geometry. Register only `known_facts.railings -> IfcRailing` now. Future
`IfcBeam` or `IfcMember` support may reuse the interface only after their own
requirements justify it. Selected.

## Interfaces

### Design Brief input

A confirmed railing record uses explicit facts:

```json
{
  "id": "railing-atrium-north",
  "ifc_class": "IfcRailing",
  "storey": "storey-2",
  "start_mm": [6000, 3000],
  "end_mm": [12000, 3000],
  "base_elevation_mm": 3300,
  "height_mm": 1100,
  "thickness_mm": 50,
  "alignment_target": "void-atrium:north-edge"
}
```

The live UAT must explicitly provide every numeric value. The Agent may derive
neither thickness nor endpoints from an unspecified word such as "standard".
Missing required geometry remains Draft.

### Expected-facts sidecar

`build_expected_facts` exposes a generic `products` collection. Each item
preserves stable identity, IFC class, owning storey, source facts, and one
supported geometry contract:

```json
{
  "id": "railing-atrium-north",
  "ifc_class": "IfcRailing",
  "storey": "storey-2",
  "geometry": {
    "kind": "linear_segment",
    "start_mm": [6000, 3000, 3300],
    "end_mm": [12000, 3000, 3300],
    "height_mm": 1100,
    "thickness_mm": 50
  }
}
```

This sidecar is orchestration evidence and does not redefine Formal BIM JSON.
The initial family registry contains exactly one mapping:
`railings -> IfcRailing -> linear_segment -> storey_local`.

### Generation package

The storey-local package owns each product ID. The package prompt receives the
explicit geometry contract and must generate a normal Formal BIM JSON entity
with `ifc_class: "IfcRailing"`, parent-relative `ObjectPlacement`, and supported
`Representation`. Compiler-generated containment remains outside model output.

## Geometry Convention

- Coordinates in the Design Brief and expected-facts sidecar are millimetres.
- `start_mm` and `end_mm` are global plan endpoints on the railing centerline.
- `base_elevation_mm` is the global bottom elevation.
- Formal `ObjectPlacement` is storey-local and performs the datum conversion
  exactly once.
- The first UAT uses a simple rectangular solid guard segment. Its plan length
  is the endpoint distance, plan thickness is explicit `thickness_mm`, and
  vertical extrusion depth is explicit `height_mm`.
- The railing centerline must coincide with the referenced void edge within
  the existing geometry tolerance.
- Zero-length, diagonal-without-supported-orientation, missing-height, missing-
  thickness, and unknown-storey records do not enter Formal generation.

## Generic Gates

The new behavior extends existing Gate interfaces rather than introducing a
standalone railing reviewer:

1. `dynamic_entity_completeness` reads arbitrary IFC counts and requires the
   expected number of `IfcRailing` entities.
2. `dynamic_storey_containment` resolves expected generic products and checks
   their actual storey.
3. Semantic geometry expectations expose generic product bounding boxes with
   stable issue code `LINEAR_PRODUCT_BBOX_MISMATCH`.
4. A linear-product alignment check compares centerline endpoints, base
   elevation, height, and thickness to explicit facts.
5. Audit may report additional defects but cannot override a failed Gate.

The Gate is driven by the geometry contract and IFC class carried in expected
facts. It does not contain a separate geometry algorithm named for railings.

## Prompt and Few-shot Policy

One few-shot teaches the `linear_segment` pattern using `IfcRailing`. It must
show:

- explicit source endpoints and dimensions;
- conversion from global facts to storey-local placement;
- a rectangle profile aligned along the segment;
- vertical extrusion to the required height;
- containment left to the compiler;
- no `IfcRailingType`, baluster spacing, handrail profile, or unstated default.

Future classes reuse this example only when their geometry contract is truly
the same. A unique relationship or decomposition pattern still earns its own
few-shot; class names alone do not.

## Scope

Included:

- straight horizontal or vertical railing segments;
- explicit storey, endpoints, base elevation, height, and thickness;
- BIM JSON generation, deterministic Gates, IFC2X3 compile/reopen;
- two railings on the Difficult atrium north and west edges.

Excluded:

- `IfcRailingType`;
- posts, balusters, handrail profiles, materials, corner joins, and curved
  paths;
- code support for `IfcBeam` or `IfcMember`;
- changing the canonical BIM JSON schema;
- weakening existing wall, slab, opening, or stair Gates.

## Acceptance

The step is complete only when:

1. A ready Design Brief with two explicit railings projects two generic
   products, `total_counts.IfcRailing == 2`, and two storey-owned package IDs.
2. Missing endpoints, height, thickness, or storey produce deterministic
   unresolved/Draft evidence before provider generation.
3. A candidate missing one railing, assigning it to the wrong storey, or
   shifting it away from the declared edge fails a deterministic Gate.
4. The focused few-shot and prompt registry pass drift checks.
5. A deterministic fixture compiles and reopens as IFC2X3 with exactly two
   `IfcRailing` entities and correct storey containment.
6. The revised Difficult live run retains real-provider evidence and produces
   an IFC only after all applicable Gates pass.
7. Artifact secret scan reports zero findings.

## Generalization Rule

Adding another IFC class does not automatically require a new end-to-end
pipeline. It requires:

- a registry entry when it matches an existing geometry/ownership contract;
- a new contract only when its geometry or relationship semantics are new;
- a focused few-shot per new pattern, not per class;
- one representative E2E case per pattern, plus class-specific E2E only when
  the class has unique compiler behavior.
