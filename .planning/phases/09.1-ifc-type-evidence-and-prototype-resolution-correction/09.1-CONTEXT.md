# Phase 09.1: IFC Type Evidence and Prototype Resolution Correction - Context

**Gathered:** 2026-07-20
**Status:** Ready for planning
**Source:** User discussion after Phase 9 live UAT

<domain>
## Phase Boundary

Correct the public index and production-evidence boundary so IFC Type facts are
distinguished from occurrence-direct facts, and make Prototype authorization
usable through names and clarification rather than requiring users to enter an
IFC GUID. This phase must let the LargeBuilding Window repair reach the real L2
comparator without the false `PROTOTYPE_TYPE_FACT_CONFLICT`.

This phase does not author missing Window Psets, quantities, Material,
Classification or `IsExternal`; those remain Phase 10.

</domain>

<decisions>
## Implementation Decisions

### Type and occurrence authority

- **D-01:** IFC2X3 `IfcWindowStyle` is the current Window Type representation;
  the public model must remain extensible to Door, Beam and Column Type objects.
- **D-02:** Occurrence-direct properties such as `Constraints.Level` and the
  current occurrence's sill height must never be promoted to Type facts.
- **D-03:** Type facts require explicit source provenance. The preferred
  authority is a first-class Type record; occurrence aggregation may only be a
  fail-closed compatibility fallback over facts proven inherited.
- **D-04:** Index schema/version changes invalidate and rebuild per-run SQLite
  indexes. Historical run directories and UAT evidence remain immutable.

### Human-facing Prototype resolution

- **D-05:** A normal user is not required to provide a GUID. A unique,
  explicitly named Type such as `M_Fixed:0915 x 1830mm` may bind
  deterministically to its internal GUID.
- **D-06:** A request containing only dimensions/category/similarity may
  retrieve deduplicated Type candidates but must ask for confirmation; it may
  not silently authorize the nearest, same-storey, name-similar or
  vector-similar object.
- **D-07:** Clarification candidates are Type-level records and display Type
  name, IFC class, dimensions, occurrence count/storeys and evidence. They do
  not repeat every occurrence as a separate Prototype choice.
- **D-08:** GUID remains accepted for API, expert and deterministic UAT usage,
  and remains visible in audit evidence after a name/selection is resolved.

### Evidence and phase handoff

- **D-09:** Production Evidence must read authorized Type facts without asking
  the LLM to decide inheritance or resolve conflicts.
- **D-10:** `Constraints.Level` is not fixed through an ignore list, majority
  vote, arbitrary value selection or LLM judgment.
- **D-11:** Phase 09.1 succeeds when the 41-occurrence LargeBuilding Window
  Style case builds production evidence and reaches L2 without the false Type
  conflict. L2 is allowed to report the real Phase 10 authoring gaps.
- **D-12:** Phase 10 remains responsible for authoring Window Psets,
  quantities, Material, Classification, labels and `IsExternal`, and for the
  final offline/live L1+L2 pass.

### Validation

- **D-13:** Tests cover direct-versus-inherited extraction, first-class Type
  persistence, unique-name binding, ambiguous candidate clarification,
  fail-closed unauthorized similarity, the 41-occurrence regression, index
  version invalidation and both offline and real-Provider pipeline paths.
- **D-14:** The phase must retain the Phase 9 publication rule: no successful
  IFC is published unless Evaluation 0.2 passes all mandatory gates.

### the agent's Discretion

- Exact `TypeRecord` Python class and SQLite table names.
- Whether the compatibility fallback is removed immediately or retained behind
  the new index schema version, provided first-class Type facts are preferred.
- Exact compact JSON shape for public Type candidates, provided all D-07 fields
  and provenance remain bounded and Gold-free.

</decisions>
