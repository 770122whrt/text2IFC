# Phase 09.1: IFC Type Evidence and Prototype Resolution Correction - Research

**Researched:** 2026-07-20
**Scope:** Local IFC2X3 indexing, Prototype resolution, production authority and validation

## Executive Summary

The LargeBuilding failure is an authority-classification defect, not a model,
LLM or ChangeSet defect. `indexer._properties()` calls IfcOpenShell with
`should_inherit=True` and marks every returned property `inherited=True`.
`production_evidence._type_prototype_facts()` then treats every such fact from
all 41 occurrences sharing a Type as a Type fact. Direct occurrence values
`Constraints.Level = Level 1/Level 2` therefore appear to conflict.

The durable correction is a versioned index model with first-class IFC Type
records plus inheritance-aware occurrence extraction. Prototype resolution and
production evidence must consume the Type record. Aggregating occurrences is
acceptable only as a legacy fail-closed fallback over facts independently
proven inherited.

## Observed Facts

- The shared object is IFC2X3 `IfcWindowStyle`, GlobalId
  `2cXV28XOjE6f6irhu0CO_c`, Name `M_Fixed:0915 x 1830mm`.
- Forty-one surviving `IfcWindow` records reference that Type.
- Every occurrence has a direct `Constraints.Level`; values legitimately differ
  between Level 1 and Level 2.
- Direct IfcOpenShell extraction of the Window Style has no `Constraints` set,
  proving that `Constraints.Level` is not a Type fact.
- `semantic_facts.extract_ifc_semantic_facts()` already implements the correct
  merged-versus-direct comparison and is the closest reusable pattern.
- Index schema and extractor are both version `0.1`; resolution explicitly
  rejects mismatched versions, so a `0.2` bump provides deterministic rebuild
  behavior without migrating historical run databases.
- Type-name resolution already exists, but it scans occurrence records and
  clarification candidates are occurrence-level rather than deduplicated
  Type-level records.

## Recommended Architecture

### 1. Versioned Type model

Add a frozen `TypeRecord` public model with at least:

- `record_id = type:<GlobalId>`;
- `ifc_global_id`, `identity_reliable`, `ifc_class`, `name`;
- `applicable_occurrence`, `predefined_type`, `element_type` when present;
- bounded aliases and provenance;
- direct Type `PropertyFact` values;
- registered material/classification relationship facts when supported;
- occurrence summary (`occurrence_count`, sorted distinct storeys) computed by
  repository query, not stored as semantic Type authority.

Extend `IndexRepository` with `put_type_record`, `get_type_by_global_id`,
`iter_type_records` and Type alias lookup. Use dedicated `type_objects`,
`type_aliases` and `type_properties` tables rather than overloading editable
element rows. Only Types referenced by registered indexed occurrences need to
be indexed in v0.2, which preserves bounded scope.

### 2. Correct occurrence property provenance

Replace `_properties(entity)` with an inheritance-aware extractor using both:

```python
merged = get_psets(entity, should_inherit=True, verbose=True)
direct = get_psets(entity, should_inherit=False, verbose=True)
```

A fact is inherited only when the set/property is absent from `direct`.
Centralize this logic with the semantic extractor helper so indexing and direct
evaluation cannot drift again. Extract Type properties from the Type object
itself with `should_inherit=False`.

### 3. Human-readable Type resolution

Resolve explicit `type_name` against Type records. A unique exact normalized
name binds deterministically and records the resulting GUID in
`authorized_semantics`. GUID lookup remains supported.

`selection_required` and ambiguous names return one public candidate per Type,
not one candidate per occurrence. Candidate fields should be bounded to:
`token`, `type_global_id`, `ifc_class`, `type_name`, dimensions approved by the
public capability policy, `occurrence_count`, sorted storeys and evidence.
Candidate tokens must bind operation ID plus Type GUID. A stored affirmative
answer is still required before an inferred/dimension-matched candidate becomes
authority.

### 4. Production evidence authority

Replace occurrence-proxy Type extraction with direct TypeRecord facts. Keep
`PROTOTYPE_TYPE_FACT_CONFLICT` for genuine contradictory Type authority, but do
not manufacture it from occurrence-direct values. Formal current Type binding
and explicit user-approved Prototype remain separate provenance kinds.

Do not treat Revit-exported text such as `Materials and Finishes.Glass Pane
Material = Glass` as an IFC material relationship without policy. Phase 09.1
preserves and labels evidence; Phase 10 decides which authorized facts must be
authored and compared.

## Compatibility and Data Lifecycle

- Bump `INDEX_SCHEMA_VERSION` to `text2ifc/ifc-index/0.2` and
  `EXTRACTOR_VERSION` to `text2ifc/ifc-indexer/0.2`.
- Update resolution version guards and tests atomically.
- Existing immutable run indexes remain readable only through their historical
  artifacts; new runs detect `INDEX_SCHEMA_VERSION_MISMATCH` and rebuild.
- No in-place migration of evidence directories.
- Keep public DTO versions explicit if candidate shape changes; persisted
  clarification answers must bind the offered Type token and current run
  revision.

## Security and Failure Modes

- Private original/Gold remains forbidden from Type indexing and Prototype
  resolution.
- Never authorize a Type from nearest, same-storey, name similarity, vector
  similarity or LLM assertion alone.
- Duplicate/unreliable Type GUIDs are diagnostic and cannot become authority.
- Candidate payloads remain top-K/bounded; raw full Type Psets do not go to the
  Provider or CLI.
- A missing, ambiguous or stale Type remains clarification/failure, not a silent
  untyped fallback.
- Publication remains solely controlled by Evaluation 0.2.

## Validation Architecture

Use existing pytest infrastructure and deterministic LargeBuilding fixture.
TDD red tests must first reproduce:

- direct `Constraints.Level` is incorrectly inherited;
- one Type appears as repeated occurrence candidates;
- two legitimate occurrence Level values trigger the current Type conflict.

Then verify:

- unit: direct/inherited extraction and TypeRecord round trip;
- contract: stale v0.1 index rejects/rebuilds under v0.2;
- resolution: unique name, ambiguous name, selection authorization, token
  tampering and forbidden automatic similarity;
- evidence: direct occurrence facts excluded, genuine Type conflict still
  fails closed, public/private authority boundary preserved;
- integration: both Phase 9 complete-input and feedback paths reach L2;
- benchmark: LargeBuilding no longer raises
  `PROTOTYPE_TYPE_FACT_CONFLICT`, L1 remains passed, L2 reports real authoring
  categories and no false successful IFC is published;
- live: one unique Type-name case and one candidate-confirmation case with
  secrets redacted and results retained as additive UAT evidence.

Quick feedback commands should target the touched unit suites; every wave and
final verification should run `tests/ifc_repair` completely.

## Planning Risks

1. Adding Type rows to `elements` would make target mutation resolution treat
   non-occurrence Types as editable targets; use separate storage.
2. Fixing only the `inherited` boolean removes the observed conflict but leaves
   resolution coupled to occurrence proxies and repeats the design debt for
   Door/Beam/Column.
3. Expanding candidate payloads with every Type Pset would break bounded public
   context and possibly expose unrelated project data.
4. Reusing existing v0.1 SQLite files after semantic changes would create
   non-reproducible evidence; version bump and rebuild are mandatory.
5. Phase 09.1 must not make Phase 10 tests green by suppressing mandatory L2
   facts or weakening publication policy.
