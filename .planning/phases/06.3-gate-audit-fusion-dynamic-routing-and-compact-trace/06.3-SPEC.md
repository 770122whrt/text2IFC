# Phase 6.3: Gate-Audit Fusion, Dynamic Routing, and Compact Trace - Specification

**Created:** 2026-07-02
**Ambiguity score:** 0.08 (gate: <= 0.20)
**Requirements:** 12 locked
**Status:** Drafted for user review

## Goal

Add scalable complex-building reliability to the live text2IFC pipeline by
fusing deterministic gates with dynamic Audit reasoning, routing failures back
to the correct stage, and reducing default trace artifacts enough to speed up
normal generation runs without losing auditability.

## Background

Phase 6.2-fix delivers the true Chinese REPL path and already handles simple
and two-room cases well enough for smoke coverage. A later live DeepSeek run
with a complex two-storey residential request exposed a different class of
problem: the system generated parseable, schema-valid BIM JSON and a reopenable
IFC, but the result omitted important facts such as second-floor doors and
window opening/fill relationships. Geometry feedback also showed that some
gate logic is too rigid for multi-storey layouts: candidate-derived geometry
expectations can mis-handle parent-relative storey elevation and wall-axis
conventions.

The failure was correctly blocked as `audit_blocked`, so the pipeline did not
false-accept the IFC. However, the route after blocking is not yet mature. The
system cannot consistently decide whether the issue belongs to Design Brief
extraction, BIM JSON generation, local repair, missing user facts, or a gate
dispute. The current run also writes many JSON sidecars by default, which slows
normal experimentation and makes human review harder.

This phase is not Phase 7 and not a schema redesign. It extends the existing
Phase 6.2-fix pipeline so complex multi-storey requests can be audited and
routed safely. It may add sidecar contracts such as `expected-facts.json`,
`gate-summary.json`, and `route-decision.json`, but it must not silently change
the BIM JSON 2.0 schema or add a second structural truth.

## Requirements

1. **Complex-building benchmark capture**: The two-storey residential live
   failure class must become a repeatable regression fixture focused on
   dynamic auditing, not on hard-coded two-storey success.
   - Current: The complex run is preserved as run artifacts, but no phase-level
     fixture defines the exact missing facts, gate limitations, and route
     expectations.
   - Target: The phase records a complex multi-storey fixture with expected
     facts derived from the user request or Design Brief, including storeys,
     spaces, doors, windows, host relationships, opening/fill expectations,
     slabs, roof, stair, and containment.
   - Acceptance: A test can load the fixture and prove that omitted second-floor
     doors, unembedded windows, wrong containment, or unsupported geometry
     cannot be accepted as a successful IFC.

2. **No hard-coded building shape assumptions**: Gate, Audit, routing, and
   expected-fact logic must not special-case one floor count, room count, wall
   count, or the exact two-storey residential sample.
   - Current: Some geometry checks and examples are more reliable for simple
     rectangular rooms than for multi-storey building graphs.
   - Target: New logic derives counts and facts from Design Brief / BIM JSON /
     capability sidecars, and all explicit fixed numbers in tests are fixture
     data rather than product rules. Non-two-storey coverage must exercise
     expected-fact extraction, dynamic gates, and route decisions, not only
     sidecar extraction.
   - Acceptance: Tests cover at least one non-two-storey synthetic fixture,
     such as a three-storey simplified building, through gate failure and
     route decision paths without changing gate or route code.

3. **Gate-Audit evidence bundle**: Deterministic gate evidence and Audit
   reasoning must be reviewed as one coherent bundle for the same candidate.
   - Current: Gate outputs, Audit prompt inputs, repair route, and final report
     are spread across many files and can be hard to relate.
   - Target: Each decisive Audit receives a `gate-summary.json` / evidence
     bundle containing schema validation, semantic coverage, compile/reopen,
     geometry applicability and result, containment checks, opening/fill
     checks, repair history, artifact hashes, expected-facts path/hash, and
     current candidate identity.
   - Acceptance: Audit prompt-render inputs include the same candidate hash,
     expected-facts hash, gate summary path, and gate summary hash that the
     final report displays. If any decisive artifact hash does not match the
     current candidate, the route must block before acceptance.

4. **Gate applicability instead of blind hard failure**: Every nontrivial gate
   must state whether it is applicable, not applicable, inconclusive, passed,
   or failed.
   - Current: Some gates behave as if one geometric convention applies to all
     generated buildings.
   - Target: Gate results include `applicability`, `scope`, `basis`, and issue
     evidence. If a gate cannot prove its premise for a complex layout, it
     returns `inconclusive` or `gate_dispute_candidate` instead of inventing a
     pass/fail meaning.
   - Acceptance: A fixture with unsupported arbitrary topology blocks as
     inconclusive/gate-dispute rather than passing or applying a room-specific
     geometry rule incorrectly.

5. **Expected facts from Design Brief**: The system must build dynamic expected
   facts from Design Brief and transcript evidence before scoring BIM JSON.
   - Current: Semantic coverage mainly classifies known facts as represented or
     unsupported by path, but does not fully materialize expected counts and
     relation obligations.
   - Target: `expected-facts.json` captures explicit user intent such as
     number of storeys, named spaces per storey, doors, windows, host walls,
     relative placement phrases, slabs, roof, stairs, and required containment
     relationships.
   - Acceptance: The two-storey fixture expects four second-floor doors and
     nine windows, and a candidate missing those items fails before acceptance.

6. **Dynamic completeness and relationship gates**: Formal acceptance must
   verify dynamic entity counts, containment, and opening/fill obligations.
   - Current: Schema-valid BIM JSON can omit requested doors or include
     windows without opening/fill relationships while still compiling.
   - Target: Gate checks verify requested IFC class counts, storey membership,
     space membership when available, door/window host wall relationships, and
     `IfcOpeningElement` plus `IfcRelVoidsElement` / `IfcRelFillsElement`
     consistency when the compiler profile requires embedding.
   - Acceptance: A candidate with nine `IfcWindow` entities but zero window
     opening/fill relations fails with stable issue codes.

7. **Audit route decisions**: Audit must output a route decision, not only
   `accept` / `revise` / `reject`.
   - Current: Blocked outcomes can identify broad audit failure but do not
     always say which upstream stage should be corrected.
   - Target: Audit classifies issues into `design_revision_required`,
     `generator_regeneration_required`, `local_repair_required`,
     `draft_required`, `blocked_gate_dispute`, or `blocked_failure`.
     `route-decision.json` must bind to the same candidate and gate evidence
     by recording `candidate_hash`, `gate_summary_hash`,
     `expected_facts_hash`, and source issue codes.
   - Acceptance: Missing facts in Design Brief route to Design Brief; missing
     entities or relationships in BIM JSON route to Generator; small
     placement/relationship corrections route to repair; uncertain gate
     semantics route to gate dispute. A route decision with stale or mismatched
     hashes blocks as evidence mismatch.

8. **Back-routing to Design Brief is allowed and bounded**: If the Design
   Brief is the source of failure, the pipeline may rerun Design Brief with
   structured feedback instead of forcing Generator repair.
   - Current: Repair is mainly generator/candidate oriented.
   - Target: The route controller can send feedback to Design Brief, Generator,
     or Repair depending on issue ownership, while preserving transcript and
     never adding supervisor-authored user facts.
   - Acceptance: A fixture where Design Brief omits an explicit second-floor
     window fact reruns Design Brief or blocks as design revision evidence
     rather than attempting wall geometry repair.

9. **Bounded revision loops with stall detection**: Automated retry loops must
   be finite, observable, and stopped when issue counts do not improve.
   - Current: Recovery is bounded in selected paths, but there is no unified
     loop policy across Design Brief, Generator, Repair, and Gate-Audit routes.
   - Target: Route attempts record `stage`, `attempt_index`,
     `input_issue_count`, `output_issue_count`, `issue_delta`, and stop after
     configured limits or non-decreasing issues.
   - Acceptance: A non-improving generator-regeneration fixture stops as
     blocked with evidence instead of looping.

10. **Compact trace for generation speed**: Normal runs must avoid writing the
    full prompt/raw/metrics sidecar set unless requested or needed for failure
    analysis.
    - Current: Every run writes many stage-local JSON and text files by
      default, slowing generation and making review noisy.
   - Target: CLI supports `--trace-level compact|debug|full`, defaulting to
     `compact`. Compact mode writes the human report, final candidate, IFC
     when accepted, `gate-summary.json`, `route-decision.json`,
     `session-export.json`, and `trace-manifest.json`; bulky prompt/raw files
     are deferred into `trace/` or a bundle when debug/full is enabled or the
     run fails in a way that requires deep evidence. Every non-accept route
     must remain recoverable from `trace-manifest.json` through hashes, linked
     artifacts, or a generated trace bundle; compact mode may reduce eager
     writes but must not destroy failure evidence.
   - Acceptance: A compact smoke run writes fewer default top-level artifacts
     than the current debug-style run, and still lets a verifier find every
     required evidence item through `trace-manifest.json`. Design Brief
     omission, Generator omission, local repair, gate dispute, and
     `blocked_failure` outcomes all retain enough redacted provider and
     diagnostic evidence to audit the owning stage.

11. **Complex-building acceptance is no false accept**: Complex multi-storey
    runs may still block, but they must not be reported as accepted unless all
    applicable gates and Audit pass.
    - Current: The complex two-storey case blocked, which is correct, but the
      failure report did not yet produce a precise stage route.
    - Target: The hard-case report explains whether the candidate needs Design
      Brief revision, Generator regeneration, local repair, Draft questions, or
      gate-dispute review.
    - Acceptance: The complex two-storey fixture produces either a verified
      accepted IFC or an accurate blocked route with missing/failed facts listed
      in `report.md` and `gate-summary.json`.

12. **BIM JSON schema boundary is preserved**: Phase 6.3 may add orchestration
    sidecars but must not silently change the BIM JSON 2.0 schema or introduce
    a second BIM JSON model.
    - Current: JSON Schema is the single structural truth.
    - Target: Sidecars describe expectations, gates, routes, and traces only.
      If implementing scalable generation proves that BIM JSON 2.0 cannot
      represent required facts, Phase 6.3 must block and recommend a separate
      schema phase rather than patching the schema ad hoc.
    - Acceptance: No Phase 6.3 code path accepts a BIM JSON field absent from
      the schema unless a formal schema migration phase has been approved.

## Boundaries

**In scope:**

- Gate-Audit evidence bundle and shared candidate identity.
- Dynamic expected-facts sidecar derived from Design Brief / transcript facts.
- Dynamic completeness, containment, host-wall, and opening/fill checks.
- Gate applicability states and gate-dispute blocking.
- Route decisions that can return to Design Brief, Generator, local repair,
  Draft, blocked failure, or gate-dispute review.
- Bounded revision attempt policy and stall detection.
- Compact trace mode designed to reduce normal generation overhead.
- Complex multi-storey regression fixture and UAT matrix.
- Single-room and two-room cases only as smoke regression.

**Out of scope:**

- Phase 7 multi-agent product expansion - this phase stabilizes Phase 6.x.
- Changing BIM JSON 2.0 schema - schema changes require a separate phase.
- Full layered generation architecture that changes the first Design Brief /
  JSON interface - this phase may research or document it, but not adopt it as
  the primary implementation path.
- RAG, fine-tuning, or dataset expansion - not needed for the Gate-Audit fix.
- Full arbitrary topology, BRep, tessellation, curved walls, or advanced MEP
  generation - unsupported content must block or Draft honestly.
- Re-optimizing single-room and two-room generation as primary milestones -
  they remain smoke tests because they already basically work.
- Audit overriding failed deterministic gates. Audit may dispute applicability,
  but dispute means blocked review, not acceptance.

## Constraints

- All work happens only in
  `C:\Users\rt do believe\.codex\worktrees\a542\bimnet`; the E-drive working
  tree is not edited.
- TDD is mandatory for eligible behavior.
- JSON Schema remains the only BIM JSON structural truth.
- No hard-coded production assumptions about storey count, room count, wall
  count, door/window count, or the two-storey test case.
- Non-two-storey coverage must reach gate and route behavior, not stop at
  `expected-facts.json` extraction.
- No silent defaults for dimensions, placements, openings, relationships,
  storeys, rooms, or properties.
- Provider secrets, private URLs, headers, and token values must not appear in
  prompts, traces, reports, commits, or final answers.
- Compact trace must improve normal generation speed or file count without
  destroying reproducibility; debug/full trace remains available, and all
  non-accept routes must preserve or link to sufficient failure evidence.
- If gate applicability is uncertain, the safe outcome is blocked dispute,
  not acceptance.

  where applicable.
- [ ] Hash mismatch between route decision and gate summary blocks acceptance
  with an evidence-mismatch issue code.

- [ ] Compact trace mode writes fewer default top-level artifacts than debug
