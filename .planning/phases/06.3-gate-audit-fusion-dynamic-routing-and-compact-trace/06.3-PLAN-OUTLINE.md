## Non-negotiable Phase Boundary

- Phase 6.3 improves complex multi-storey reliability and gate routing inside
  the current pipeline.
- It does not introduce Phase 7 product scope.
- It does not silently change BIM JSON 2.0 schema.
- It does not hard-code the two-storey residential prompt as production logic.
- It does not stop non-two-storey coverage at expected-fact extraction; at
  least one non-two-storey fixture must exercise dynamic gates and route
  decisions.
- It does not let Audit override failed deterministic gates.
- It does not make single-room or two-room demos the primary success target.

## Corrected Gate-Audit Model

Gate and Audit are one review system with different strengths:

1. Deterministic gates provide hard evidence when their premises are valid.
2. Every nontrivial gate declares applicability and evidence basis.
3. Audit receives the same gate summary and candidate identity that the report
   shows.
4. Gate summary, Audit input, route decision, manifest, and report bind to the
   same candidate through hashes. A stale or mismatched hash blocks acceptance.
5. Audit may classify a failure as candidate issue, design issue, missing user
   fact, local repair, or gate dispute.
6. Audit cannot turn a failed applicable gate into acceptance.
7. Gate dispute blocks for human/developer review.

## Target Route Order

1. Design Brief reaches `ready`, Draft, or blocked.
2. Expected facts are derived from Design Brief and transcript evidence.
3. Generator emits Formal BIM JSON 2.0 or Draft.
4. Dynamic semantic/completeness/relationship gates evaluate the candidate.
5. Compile/reopen and applicable geometry gates run.
6. `gate-summary.json` is produced for the same candidate.
7. Audit reviews the gate summary and returns a route decision.
8. The route controller chooses:
   - `accept`
   - `design_revision_required`
   - `generator_regeneration_required`
   - `local_repair_required`
   - `draft_required`
   - `blocked_gate_dispute`
   - `blocked_failure`
9. Bounded retry runs only when evidence says the target stage can improve.
10. Compact report and trace manifest expose the final route.

## Trace Strategy

Default: `--trace-level compact`

Compact top-level artifacts:

- `report.md`
- `output.ifc` when accepted
- `candidate.json` when Formal candidate exists
- `expected-facts.json`
- `gate-summary.json`
- `route-decision.json`
- `session-export.json`
- `trace-manifest.json`

Compact mode may reduce eager file writes, but every non-accept route must
remain auditable. `trace-manifest.json` must locate or reconstruct redacted
provider request/response evidence, prompt-render input hashes, diagnostics,
route evidence, and candidate/gate hashes for Design Brief omissions,
Generator omissions, local repair routes, gate disputes, and blocked failures.

Debug/full artifacts:

- rendered prompts
- redacted requests
- raw responses
- parsed outputs
- provider usage/response IDs
- validation and repair sidecars
- stage metrics
- optional `trace-bundle.zip`

## Primary Test Cases

- Hard case: complex two-storey residential run from the real DeepSeek/Mimo
  class of prompts.
- Scalability case: non-two-storey simplified building that reaches
  expected-fact extraction, dynamic gate failure/pass assertions, and route
  decisions to prove no two-floor hard-coding.
- Smoke only: current simple-room and two-room cases.

## Completion Criteria

- The hard case cannot false accept.
- The hard case either produces an accepted IFC with all applicable facts
  covered, or produces a precise blocked route.
- A non-two-storey fixture proves gate and route behavior is data-driven, not
  a second-floor special case.
- Route decisions reference the same `candidate_hash`,
  `expected_facts_hash`, and `gate_summary_hash` as the report and manifest.
- Compact trace is the default and writes fewer top-level artifacts than debug.
- Compact non-accept routes and debug/full trace remain sufficient for
  provider, prompt, route, and gate audit.
- Roadmap, state, requirements, summaries, and final verification are updated.
