# Phase 5: Multi-turn Clarification Agent - Context

**Gathered:** 2026-06-15
**Status:** Ready for planning
**Source:** Phase 5 user discussion, Phase 3 handoff, and `05-SPEC.md`

<domain>
## Phase Boundary

Phase 5 builds the first runtime clarification layer for text2IFC:

Natural language -> multi-turn clarification -> formal BIM JSON 2.0 -> IFC2X3.

The Agent exists because one-shot Text-to-JSON can only succeed when the user
already supplies all required building facts. When facts are missing, the Agent
must ask targeted questions, preserve state, and keep the work as Draft until
the formal BIM JSON 2.0 document is complete enough to compile.

The final acceptance artifact for this phase is an IFC2X3 file generated by the
Agent demo. A conversation that remains Draft is a valid intermediate state,
but Phase 5 is not complete until the scripted simple-room demo produces a
formal BIM JSON 2.0 document and a reopenable IFC file.
</domain>

<spec_lock>
## Locked Requirements

The requirements, boundaries, and acceptance criteria in `05-SPEC.md` are
locked. Planning must not weaken:

- Chinese-first interaction.
- 1-3 user-facing questions per turn.
- no silent defaults when the user does not know.
- Draft separation from formal BIM JSON.
- formal validation before IFC compilation.
- no raw IFC/STEP output from the model layer.
- no low-level IFC implementation objects in model output or user questions.
- no committed secrets or provider URLs.
</spec_lock>

<decisions>
## Implementation Decisions

### Interaction policy

- **D-01:** The first Agent version is Chinese-first. Internal diagnostics may
  use stable English codes, but user-facing questions are Chinese by default.
- **D-02:** Each clarification turn asks 1-3 key questions. If more facts are
  missing, the remaining facts stay queued in Agent state.
- **D-03:** If the user says they do not know a required fact, the Agent keeps
  the conversation in Draft and does not apply a default template in Phase 5.
- **D-04:** Questions must be about building-level semantic facts: storeys,
  rooms, dimensions, placement, openings, relationships, and supported
  properties. The Agent must not ask users for `IfcCartesianPoint`,
  `IfcDirection`, `IfcOwnerHistory`, STEP IDs, or compiler bookkeeping.

### BIM JSON and IFC boundary

- **D-05:** BIM JSON Schema remains the only structural truth. Agent state can
  reference schema paths and Draft paths, but it cannot define a second BIM JSON
  model.
- **D-06:** The language model emits or edits semantic BIM JSON facts only. The
  compiler owns low-level IFC helper entities and STEP serialization.
- **D-07:** `validate_v2_document` is the formal gate before compilation. Draft,
  invalid, and missing-fact states must not create or overwrite IFC output.
- **D-08:** The final Phase 5 demo must write an IFC2X3 file and reopen it with
  the existing compiler verification path.

### Agent state and provenance

- **D-09:** Agent state records the original user request, every asked question,
  every user answer, accepted facts, rejected/unknown facts, diagnostics, and
  candidate document state.
- **D-10:** Answer merging appends new facts and preserves original user text.
  Existing explicit facts may be changed only when the user explicitly corrects
  them.
- **D-11:** Draft state must list missing facts with stable IDs, user-facing
  question text, source path or validator path, status, and rationale.
- **D-12:** Agent transcripts and diagnostics are reproducible artifacts, but
  must redact or omit credentials, headers, and provider URLs.

### Provider policy

- **D-13:** Deterministic fake/file providers are required for TDD, CI, and
  replay. Live providers are optional smoke tests, not unit-test dependencies.
- **D-14:** The live Mimo adapter uses an Anthropic-compatible provider boundary
  configured only by environment variables and CLI flags. Environment variable
  names may appear in docs and diagnostics; secret values must not.
- **D-15:** If live credentials are absent or the provider fails, the Agent must
  produce a clear diagnostic and preserve local deterministic testability.
- **D-16:** RAG over IFC documentation is out of scope unless the Phase 5 live
  smoke results show recurring class/property knowledge errors that cannot be
  solved by the prompt, schema, or deterministic validators.

### Demo scope

- **D-17:** The first scripted demo starts from an incomplete Chinese request
  for a one-storey rectangular room with four walls, one door, and one window.
- **D-18:** The demo may use scripted answers to prove the loop deterministically.
  It should still exercise the same Agent state, question planner, merger,
  validation, compilation, and artifact-writing paths as a live run.
- **D-19:** Later BIMNet-like complexity is deferred. Phase 5 should leave
  extension seams for more classes and richer geometry, but must not block the
  simple-room IFC demo on Phase 4 fidelity.

### the agent's Discretion

- Exact Python package names, provided Agent code is isolated from Phase 3
  dataset/baseline code and reuses validators/compiler directly.
- Exact state serialization shape, provided it is deterministic JSON and covers
  the decisions above.
- Exact Chinese wording for questions, provided tests check language, count,
  target fact, and absence of low-level IFC jargon.
- Exact live provider implementation detail, provided fake/file modes remain
  deterministic and live mode never persists secrets.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `FakeProvider` and `FileProvider` already prove the provider boundary pattern.
- `build_prompt` and the Phase 3 prompt contract already forbid raw IFC/STEP
  and low-level IFC helper output.
- `validate_v2_document` produces field-level diagnostics that can seed
  missing-fact records.
- `validate_draft` verifies incomplete Draft envelopes.
- `compile_document` rejects Draft input and writes IFC atomically for valid
  formal documents.
- `evaluate_prediction_cases` can score validity and compile/reopen outcomes.

### New Integration Points

- Agent code should live under `src/text2ifc_agent/`.
- Agent CLIs should live under `scripts/agent/`.
- Agent tests should live under `tests/agent/`.
- Demo artifacts should live under `dataset/processed/agent-demo/simple-room/`.
- The final IFC file should be written as
  `dataset/processed/agent-demo/simple-room/output.ifc`.
</code_context>
