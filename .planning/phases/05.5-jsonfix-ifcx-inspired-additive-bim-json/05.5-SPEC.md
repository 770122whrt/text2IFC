# 05.5 SPEC: jsonfix IFCx-Inspired Additive BIM JSON

## Status

Specified on 2026-06-20.

## Objective

Build a conservative jsonfix phase that improves the text2IFC JSON boundary
without replacing the current IFC2X3 pipeline.

The phase explores and implements an IFCx-inspired additive repair layer for
BIM JSON:

```text
source BIM JSON 2.0 base document
+ user or Agent semantic patch layer
+ validation or repair patch layer
= composed candidate BIM JSON
-> validate_v2_document
-> IFC2X3 compiler
-> reopen and quality gates
```

The first acceptance demo is a missing-piece repair path: an existing BIM JSON
2.0 model is missing a simple semantic component, a patch adds the missing
facts, the composed result validates, and the result compiles to a real
reopenable IFC2X3 file.

## Locked User and Project Decisions

- The final output target remains IFC2X3 because the authorized BIMNet dataset
  is IFC2X3.
- IFCx and IFC5 alpha are research inputs, not replacement output standards.
- BIM JSON remains a model-friendly semantic contract. The model must not
  output raw IFC, STEP text, `IfcCartesianPoint`, `IfcDirection`,
  `IfcOwnerHistory`, STEP IDs, or compiler-only objects.
- IFCx layer, path, inheritance, and namespaced attribute ideas may be borrowed
  only when they improve traceability, additive repair, or missing-piece
  completion.
- Start with an independent `bim-json-patch/1.0` envelope. Do not immediately
  replace BIM JSON 2.0 with a new top-level `layers[]` formal document.
- A patch must preserve provenance and must not silently overwrite source IFC
  facts.
- Deletion is not a normal first-version operation. If deletion is needed, it
  must be represented as a review-required tombstone, not silent removal.
- Composed output must pass formal BIM JSON validation before IFC compilation.
- Unsupported source geometry or unsupported classes remain explicit losses or
  Draft content. They are not replaced with fabricated boxes or proxy objects.

## Current State

- BIM JSON 2.0 already represents IFC2X3 semantic entities, relationships,
  placement, selected geometry, materials, types, topology, and provenance.
- BIM JSON 2.0 already compiles to reopenable IFC2X3 through IfcOpenShell.
- Phase 4 added generated-IFC correctness gates and high-fidelity source loss
  accounting.
- Phase 5 added a Chinese-first multi-turn Agent that can reach valid formal
  BIM JSON and compile a simple-room IFC.
- Two IFCx research notes exist:
  - `docs/research/ifcx-hello-wall-structure-reading.md`
  - `docs/research/ifcx-vs-bim-json-jsonfix-strategy.md`
- IFC5-development is alpha. Its IFCx examples are useful for JSON
  organization, but they are not stable enough to become this project's schema
  authority.

## In Scope

- A documented `bim-json-patch/1.0` envelope for additive semantic repairs.
- A JSON Schema for the patch envelope, while keeping BIM JSON structural truth
  in the existing BIM JSON schema.
- Patch operations for a small safe set:
  - `add_entity`
  - `set_attribute`
  - `set_property`
  - `add_relationship`
  - `set_material`
  - `mark_missing`
  - `mark_unsupported_loss`
  - review-required tombstone records for deletion-like intent
- A patch validator that rejects raw IFC/STEP, compiler-only objects, missing
  provenance, ambiguous targets, and unsupported operations.
- A deterministic patch composer that combines a base BIM JSON 2.0 document
  with ordered patches without mutating the base document.
- Stable target addressing by semantic `id`, with optional `global_id` and
  source provenance. STEP line numbers are not stable target identities.
- A missing-piece json2IFC demo that writes text input, patch JSON, composed
  BIM JSON, diagnostics, report, and IFC2X3 output.
- A read-only external-sample audit that may select a small IFC2X3 subset from
  `dataset/external/bim-whale-ifc-samples` and
  `dataset/external/ifc-bench` for extraction and compatibility checks. Raw
  external datasets remain untracked and are never mixed into BIMNet splits.
- A strict final IFC2X3 artifact gate. Acceptance requires the parsed STEP
  `FILE_SCHEMA` section to contain exactly one identifier, `IFC2X3`,
  IfcOpenShell to reopen the file with
  `model.schema == "IFC2X3"`, full IFC validation to report no errors, and the
  Phase 4 generated-IFC quality gate to pass for the supported demo scope.
- A decision report for whether a future BIM JSON 3.0 should adopt patch
  layers, `types[]` / `type_ref`, namespace attributes, or space-boundary
  objects as first-class structures.

## Out of Scope

- Replacing BIM JSON 2.0 with IFCx.
- Targeting IFC5 output.
- Runtime remote schema resolution against `ifcx.dev`.
- Asking a language model to output OpenUSD mesh vertices, face indices, or
  arbitrary 4x4 transform matrices as the normal text2IFC path.
- Full BIM JSON 3.0 migration in this phase.
- Fine-tuning, deployment, service packaging, or production provider routing.
- Solving broad BRep, mapped geometry, tessellation, boolean, or surface-model
  reconstruction.
- Silent repair of invalid Agent output. Repairs must be explicit patch facts
  with provenance.

## Decision Questions and Recommended Locks

| Question | Recommended jsonfix lock | Reason | Phase 5.5 handling |
|---|---|---|---|
| Should BIM JSON 3.0 directly use top-level `layers[]`? | No. Start with independent `bim-json-patch/1.0`. | It protects the working BIM JSON 2.0 compiler and validator while testing additive repair. | Build patch envelope and composer first. Decide 3.0 later from evidence. |
| Should patches delete source facts? | Not by default. Use review-required tombstone records only. | Silent deletion could corrupt source IFC provenance and training truth. | Validator rejects destructive deletion as a normal op. |
| How should patches address targets? | Semantic `id` first, optional `global_id` and source map. Never STEP IDs. | BIM JSON `id` is stable in this project; STEP line numbers are file-local and fragile. | Composer resolves `id` and reports ambiguous or missing targets. |
| Should namespace properties enter Formal BIM JSON now? | Patch layer first. Formal migration is a future decision. | Namespace attributes help patches, but Formal BIM JSON should stay compiler-friendly. | Allow namespaced facts only where composer maps them to existing Formal structures or reports loss. |
| Should type reuse become `types[]` / `type_ref` now? | Explore through report and limited patch fixtures, not mandatory Formal migration. | Phase 4 already supports selected IFC type relationships. A new first-class type model needs evidence. | Record candidate shape and compile only what current validation supports. |
| Should space boundaries become boundary objects? | Research and fixture only unless a safe IFC2X3 mapping is implemented. | IFCx suggests boundary objects, but IFC2X3 output still needs deterministic relationships. | Keep current relationships as compiler truth; document future boundary-object option. |
| Should complex geometry move into JSON patch layers? | No for normal generation. Keep unsupported complex geometry as explicit loss. | Mesh/BRep patches are too low-level for the model and too easy to fabricate. | `mark_unsupported_loss` is in scope; geometry generation expansion is not. |

## Requirements

### 1. Patch envelope contract

- Current: BIM JSON 2.0 supports Formal and Draft documents, but not ordered
  additive patch layers.
- Target: Define `bim-json-patch/1.0` as a separate envelope that targets BIM
  JSON 2.0 and contains ordered provenance-bearing layers and operations.
- Acceptance: Positive and negative patch fixtures validate deterministically.

### 2. No competing BIM JSON model

- Current: BIM JSON 2.0 schema is the structural truth for Formal documents.
- Target: Patch schemas describe transformations, not a second Formal BIM JSON
  shape.
- Acceptance: The composer output is validated by `validate_v2_document`; patch
  validation alone is never enough for IFC compilation.

### 3. Provenance-preserving composition

- Current: Source extraction and Agent artifacts preserve provenance, but full
  document replacement can obscure who added or changed a fact.
- Target: Base facts, user patch facts, Agent patch facts, validation repair
  facts, and compiler-generated facts remain distinguishable.
- Acceptance: The missing-piece demo report lists facts by source layer and
  never mutates the base input file.

### 4. Safe patch operations

- Current: No operation-level repair contract exists.
- Target: Support the minimum safe operation set needed for semantic missing
  piece repair and property completion.
- Acceptance: Unsupported operations, destructive deletes, raw IFC/STEP text,
  low-level helper objects, and missing provenance are rejected with stable
  diagnostics.

### 5. Deterministic composer

- Current: No BIM JSON composition engine exists.
- Target: Ordered patches compose with explicit conflict rules, diagnostics,
  and stable output.
- Acceptance: Tests prove later allowed operations win only where explicitly
  permitted, conflicts are reported, and base documents remain byte-for-byte
  unchanged.

### 6. Missing-piece json2IFC demo

- Current: The project can generate IFC from complete BIM JSON and Agent
  outputs, but not from an auditable patch repair path.
- Target: A demo starts from a base BIM JSON missing a wall or similarly simple
  component, applies a semantic patch, validates the composed document, compiles
  IFC2X3, reopens it, and runs generated-IFC quality checks.
- Acceptance: The demo writes
  `dataset/processed/jsonfix/missing-piece-repair/output.ifc` plus text,
  patch, composed JSON, diagnostics, metrics, and report artifacts.

### 7. BIM JSON 3.0 decision report

- Current: The project has research notes but no decision gate for promoting
  IFCx-inspired ideas into the core JSON contract.
- Target: Phase 5.5 closes with a written recommendation on whether BIM JSON
  3.0 should adopt patch layers, type refs, namespace attributes, or boundary
  objects.
- Acceptance: The report separates implemented facts from future design
  options and lists residual blockers.

## Acceptance Checklist

- [ ] `bim-json-patch/1.0` schema and examples exist.
- [ ] Patch validation rejects unsafe, ambiguous, or compiler-level content.
- [ ] Patch composition is deterministic and does not mutate base documents.
- [ ] Composed candidates pass `validate_v2_document` before compilation.
- [ ] A missing-piece repair demo produces a real reopenable IFC2X3 file.
- [ ] The final artifact is rejected if its parsed declared or reopened schema is
      IFC4, IFC4X3, unknown, or inconsistent; the report records both schema
      observations and the IFC validation result.
- [ ] External samples, when used, are selected only after license/source and
      IFC schema inventory; non-IFC2X3 samples are excluded from jsonfix
      extraction checks rather than converted silently.
- [ ] The demo report separates source, patch, validation, and compiler facts.
- [ ] Unsupported geometry or classes remain explicit losses or Draft facts.
- [ ] A BIM JSON 3.0 decision report records what should and should not be
      promoted from the patch experiment.
