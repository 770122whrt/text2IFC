## Findings

### IFC5-development is alpha

The repository and examples are preliminary. They are useful for research and
architecture, but they should not replace the project's IFC2X3 EXPRESS and PSD
registries.

### IFCx top-level shape

IFCx uses:

```json
{
  "header": {},
  "imports": [],
  "schemas": {},
  "data": []
}
```

The important part for jsonfix is `data[]`, where each node fragment can have:

```json
{
  "path": "node-address",
  "children": {},
  "inherits": {},
  "attributes": {}
}
```

### IFC class identity is an attribute in IFCx

IFCx does not use BIM JSON's `ifc_class` field. Instead, examples use a
namespaced attribute such as `bsi::ifc::class`.

jsonfix conclusion: keep BIM JSON `ifc_class` for model and compiler clarity.
Do not force the model to learn namespaced IFC class facts as the primary
Formal shape.

### IFCx supports additive layers

The Hello Wall fire-rating examples show that a later layer can add or override
a property by using the same path.

jsonfix conclusion: adopt the additive idea, but express it as a project-owned
patch envelope with explicit operations and provenance.

### IFCx composition has clear phases

The core composition code describes:

```text
Federation -> Flattening -> Composition
```

jsonfix conclusion: use a similar mental model:

```text
Validate patch -> compose candidate -> validate BIM JSON -> compile IFC
```

### IFCx geometry examples are too low-level for normal text2IFC output

Hello Wall uses OpenUSD-style mesh points, face indices, and transforms.

jsonfix conclusion: do not make mesh or generic matrices the normal model
output. Keep semantic placement and extrusion profiles as the formal route.

### IFCx boundary objects are promising but not immediately portable

Hello Wall represents a space boundary as an object-like attribute. IFC2X3
output still needs deterministic relationship mapping.

jsonfix conclusion: document boundary objects as a BIM JSON 3.0 candidate, but
do not require them for the first patch implementation.

## Research-Based Constraints

- The patch system must be offline and deterministic.
- IFC2X3 registries remain schema truth.
- IFCx remote schema layers are not runtime dependencies.
- The language model emits semantic repair facts only.
- Any borrowed IFCx idea must improve traceability, repair, or auditability.
- Any borrowed idea that weakens validation, compile reliability, or model
  clarity is deferred.

## Open Evidence Gaps

- IFC5 final structure may differ from current IFCx alpha examples.
- IFCx unit semantics are not fully documented in the read examples.
- The long-term mapping between IFCx transform matrices and IFC placement is
  not stable enough for this project to rely on.
- Space boundary object mapping to IFC2X3 needs a dedicated experiment.
- First-class type templates need a schema and compiler design before
  becoming Formal BIM JSON.

## Recommendation

Proceed with `bim-json-patch/1.0` as a limited experiment. Treat it as a repair
and audit layer, not as BIM JSON 3.0 itself.
