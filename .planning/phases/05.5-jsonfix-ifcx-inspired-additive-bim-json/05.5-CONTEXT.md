# 05.5 CONTEXT: jsonfix Decisions and Boundaries

## Purpose

This context file records the decisions needed before planning jsonfix
implementation. It is intentionally conservative: the phase should improve the
JSON repair path without destabilizing the already working BIM JSON 2.0 to
IFC2X3 compiler.

## User Intent

The user wants to study IFCx/IFC5 JSON ideas and use the useful parts to
improve text2IFC's JSON structure.

The important future scenario is:

```text
An IFC2X3 model exists.
One part of the model is missing or removed.
The user describes the missing part in natural language.
The system creates an auditable JSON repair.
The repaired candidate compiles back to IFC2X3.
```

The user specifically does not want this work to drift into Phase 6
fine-tuning or deployment yet.

## Why Phase 5.5

This phase is inserted between Phase 5 and Phase 6.

- Phase 5 proved the Agent can reach formal BIM JSON and compile IFC.
- Phase 4 proved generated IFC needs strict spatial and semantic gates.
- Phase 6 should not train or deploy against a JSON contract that may still be
  missing additive repair semantics.

Therefore jsonfix is a bridge phase: it improves the JSON repair boundary
before broader data/model work.

## IFCx Ideas Worth Borrowing

| IFCx idea | Meaning in IFCx examples | jsonfix adaptation |
|---|---|---|
| Layered files | Multiple `.ifcx` files can add or override facts. | Ordered patch layers with provenance. |
| Repeated path | The same node path can appear in multiple fragments. | Target operations by stable semantic entity IDs and source maps. |
| Composition | Federation, flattening, and composition create the final tree. | Patch validation, composition, formal validation, then IFC compile. |
| `inherits` | Instances reuse type/template facts. | Candidate future `types[]` / `type_ref` decision, not mandatory first implementation. |
| Namespaced attributes | IFC, material, USD, classification, and boundary facts coexist. | Namespaced patch facts may exist, but Formal BIM JSON remains compiler-friendly. |
| Boundary object | Space boundary can be an object-like fact. | Research candidate; IFC2X3 compiler mapping remains required before formal adoption. |

## IFCx Ideas Not Borrowed Now

- IFC5 alpha is not used as the schema authority.
- IFCx `.ifcx` files are not the runtime output format.
- Remote schema resolution is not required for normal validation.
- OpenUSD mesh vertices and face indices are not accepted as normal model
  output.
- Generic 4x4 matrices are not the primary placement contract.
- Raw STEP or IFC implementation objects remain compiler output only.

## Decision Matrix

### D-05.5-01: Patch envelope before BIM JSON 3.0

Decision: Use a separate `bim-json-patch/1.0` envelope first.

Recommendation strength: high.

Reason: BIM JSON 2.0 and its compiler are already working. A separate patch
envelope lets us test additive repair while keeping the Formal schema stable.

Consequence: Phase 5.5 may produce a BIM JSON 3.0 recommendation, but it does
not have to complete a full 3.0 migration.

### D-05.5-02: IFC2X3 remains the validation and output target

Decision: All composed candidates must validate as BIM JSON 2.0 targeting
IFC2X3 before compilation.

Recommendation strength: high.

Reason: The authorized BIMNet source set is IFC2X3, and all current compiler,
knowledge, and quality gates are IFC2X3.

Consequence: IFCx is used as design inspiration only.

### D-05.5-03: Patch operations are semantic, not compiler-level

Decision: Patches may add or set semantic entities, attributes, properties,
materials, relationships, missing facts, and explicit losses. They must not
contain raw IFC/STEP or low-level IFC helper objects.

Recommendation strength: high.

Reason: The language model should speak in building semantics. The compiler
owns IFC implementation resources.

Consequence: Validators must reject `IfcCartesianPoint`, `IfcDirection`,
`IfcOwnerHistory`, STEP IDs, and raw STEP text in patch outputs.

### D-05.5-04: No silent overwrite of source facts

Decision: Patch layers are ordered, but any overwrite must be explicit,
provenance-bearing, and allowed by operation semantics.

Recommendation strength: high.

Reason: Training truth and repair traceability depend on preserving which facts
came from the source IFC and which came from the repair.

Consequence: The composer must report conflicts and produce provenance traces.

### D-05.5-05: Deletion is review-required

Decision: Normal patch operations do not delete source facts. Deletion-like
intent is represented as a tombstone or review-required diagnostic.

Recommendation strength: high.

Reason: In a BIM repair workflow, accidental deletion is more dangerous than
failing loudly.

Consequence: The first version can repair missing facts without supporting
destructive edits.

### D-05.5-06: Target identity uses BIM JSON semantic IDs

Decision: Patch operations target BIM JSON semantic `id` values. Optional
`global_id` and source provenance help audit source mapping. STEP IDs are
forbidden as stable addresses.

Recommendation strength: high.

Reason: STEP line numbers are serialization details and can change. BIM JSON
semantic IDs are the project-level stable handles.

Consequence: The composer must diagnose missing, duplicate, or ambiguous
targets.

### D-05.5-07: Namespace facts remain experimental

Decision: Namespaced patch facts may be represented for research and mapping,
but Formal BIM JSON output must use existing supported structures unless a
validated schema change is made.

Recommendation strength: medium.

Reason: Namespaces are useful for external knowledge and incremental patches,
but the current Formal compiler expects structured attributes, property sets,
materials, and relationships.

Consequence: Namespace facts either map into existing Formal structures or are
reported as explicit unsupported losses.

### D-05.5-08: Type reuse and boundary objects are design outputs unless
compiled safely

Decision: Phase 5.5 may propose `types[]` / `type_ref` and boundary objects,
but they become Formal structures only if schema, validator, compiler, and
tests are implemented.

Recommendation strength: medium.

Reason: These ideas are promising but need careful IFC2X3 mapping.

Consequence: The final decision report must separate implemented contract from
future BIM JSON 3.0 candidates.

## Working Acceptance Artifact

The phase's concrete demo target is:

```text
dataset/processed/jsonfix/missing-piece-repair/output.ifc
```

The demo must also include:

- `input.txt`
- `base.json`
- `patch.json`
- `composed.json`
- `diagnostics.json`
- `metrics.json`
- `report.md`

## Risks

- Patch layers may become a second hidden schema if not constrained.
- A composer could silently overwrite source facts if conflict rules are vague.
- The model may learn to output low-level IFC or mesh facts if patch prompts are
  too close to IFCx examples.
- A missing-piece demo can pass compile/reopen but still fail spatial topology
  unless Phase 4 quality gates are reused.
- Promoting too much into BIM JSON 3.0 at once could destabilize the dataset
  and compiler.
