# Phase 6.4: Feedback Routing Loop MVP and Live DeepSeek Matrix - Specification

## 6.4-09 Addendum: Datum and Stair Geometry

Phase 6.4 acceptance additionally requires the canonical Design Brief,
expected-fact extractor, Generator prompt/few-shot, compiler local placement,
and deterministic IFC Gate to agree on floor slabs, roof slabs, stair flights,
and stair openings. The binding contract and RED/GREEN verification sequence
are defined in `06.4-09-PLAN.md`.

An IFC cannot be accepted when a floor/roof datum is outside tolerance, a
stair does not rise through its confirmed bounds, a stair flight is only a
single ramp despite confirmed step requirements, or its slab opening is not
co-located with the confirmed opening bounds. Audit may interpret these
findings but cannot override them.

## Goal

Turn the current mostly linear text2IFC workflow into a feedback-capable loop
that normalizes failures into structured issues, chooses a bounded route back
to the correct stage, writes matrix artifacts, and proves the implementation
with deterministic TDD plus real DeepSeek live workflow evidence.

## Background

Phase 6.3 already added dynamic gates, gate summaries, route decisions, hash
binding, compact trace, and a no-false-accept complex-building matrix. That
phase correctly treats the hard two-storey case as an honest blocked route
rather than claiming an accepted IFC.

The remaining gap is that the workflow still behaves too much like a linear
pipeline. It can validate, compile, gate, audit, and block, but the feedback
route is not yet a first-class loop contract. Failures from schema validation,
semantic validation, compiler, reopen checks, deterministic gates, Audit,
provider calls, and runtime exceptions are not normalized into one issue model
with one routing vocabulary. As a result, complex-building work can still drift
back into case-specific patching.

This phase introduces the missing feedback routing layer:

```text
Generate
  -> Validate
  -> Compile
  -> Gate
  -> Audit
  -> Normalize Issues
  -> Route Decision
  -> Feedback Target
  -> bounded rerun or explicit stop
```

The first deliverable is not "make one two-storey prompt pass." The first
deliverable is a general mechanism that can say why a run failed, who owns the
next correction, whether retry is allowed, and what artifact proves that
decision. After deterministic TDD passes, the phase must run real DeepSeek
tests through the live CLI/workflow path. Final live acceptance must not depend
on hard-coded clarification transcripts because LLM questions vary between
runs.

## Requirements

1. **Language policy for machine workflow**: New core workflow fields,
   prompts, route names, issue types, structured logs, test names, and artifact
   keys must use English control vocabulary while preserving Chinese user
   input as raw source text.
   - Current: Some user-facing CLI behavior and older artifacts still mix
     Chinese interaction text with internal workflow semantics.
   - Target: New Phase 6.4 control fields and generated artifacts use English
     keys and enum values. Chinese may appear only as raw user input,
     transcript content, human-readable report text, or optional `message_zh`.
   - Acceptance: Focused tests assert that `issues.json`,
     `route-decision.json`, `feedback-rounds.json`, and `case-result.json`
     contain English keys/enums and no Chinese machine-control keys.

2. **Structured Issue model**: Every relevant failure source must normalize
   into one Issue contract.
   - Current: Gate, Audit, validation, provider, and repair failures use
     different local issue shapes and code vocabularies.
   - Target: The workflow can emit `issues.json` with stable fields:
     `issue_id`, `source`, `severity`, `owner`, `issue_type`,
     `expected_fact_ref`, `actual_ref`, `evidence`, `suggested_route`,
     `retryable`, and optional `message_zh`.
   - Acceptance: Unit tests create schema, compiler, gate, audit, provider,
     and runtime failures and verify they normalize into valid Issue objects
     with allowed enum values.

3. **RouteDecision v2 aggregation**: Normalized issues must aggregate into a
   route decision that names the next target stage and prevents false accept.
   - Current: Phase 6.3 route decisions exist, but they are primarily derived
     from gate/audit issue codes and do not consume a unified Issue list.
   - Target: `route-decision.json` contains `final_status`, `route`, `reason`,
     `blocking_issue_ids`, `retry_allowed`, `target_stage`,
     `max_feedback_rounds`, `current_feedback_round`,
     `human_review_required`, and optional `message_zh`.
   - Acceptance: Tests prove blocking Audit issues, deterministic gate
     failures, Draft unresolved paths, provider truncation, and unsupported
     compiler features cannot produce `final_status: "accepted"`.

4. **Failure source normalization**: Schema validation, semantic validation,
   compiler, reopen check, geometry gate, deterministic gate, audit, provider,
   and runtime failures must be converted to Issues before final routing.
   - Current: Some provider and runtime failures return early as broad statuses
     such as `provider_failed` or `draft_or_blocked`.
   - Target: Every terminal non-accept path writes `issues.json`,
     `route-decision.json`, and `case-result.json` unless the process aborts
     before a session directory exists.
   - Acceptance: Regression tests cover at least one failure from each source
     enum and verify a persisted issue plus route artifact.

5. **Bounded feedback loop**: The workflow must support at most two feedback
   rounds and must stop on non-improvement.
   - Current: Selected repair/gate paths are bounded, but there is no unified
     feedback-round artifact across Design Brief, Generator, Repair, provider
     retry, and blocked routes.
   - Target: `feedback-rounds.json` records each round's input stage,
     generation result, validation/gate/audit result, normalized issues,
     route decision, issue-count delta, target stage, and whether another
     attempt was allowed.
   - Acceptance: Tests prove that a route to `generator`, `repair`, or
     `provider` reruns at most two times, and that unchanged or increased
     blocking issue counts stop as `blocked` or `failed` with evidence.

6. **No hard-coded CLI clarification transcript**: Final live validation must
   exercise real CLI/workflow behavior without a prewritten answer file or
   exact expected LLM question text.
   - Current: Scripted stdin and fake/file providers are useful regression
     tools, but they cannot prove that a live provider-driven clarification
     loop works when questions vary.
   - Target: The live DeepSeek UAT uses either a real terminal REPL session or
     an adaptive driver that waits for actual model questions, records the
     exact transcript, and supplies answers based on semantic question intent
     rather than matching fixed strings.
   - Acceptance: Final live evidence is labelled `live_deepseek`; it records
     real response IDs, model, finish reasons, usage, raw output references,
     parsed output, transcript turns, and no `--scripted-stdin` or
     prewritten `answers.json` as acceptance evidence.

7. **Matrix artifacts**: The phase must produce a repeatable matrix that
   summarizes accepted, draft, blocked, provider, and complex-building routes.
   - Current: Phase 6.3 has a matrix for no-false-accept and gate routing, but
     not the new Issue/RouteDecision/feedback-round contract.
   - Target: The matrix writes per-case `issues.json`,
     `route-decision.json`, `feedback-rounds.json`, `case-result.json`, and
     `report.md`, plus root `matrix-result.json` and `matrix-report.md`.
   - Acceptance: Matrix cases cover simple accepted IFC, two-room smoke,
     controlled two-storey, clarification two-storey, ambiguous two-storey,
     provider truncation, unsupported compiler feature, and non-two-storey
     dynamic routing.

8. **DeepSeek live acceptance gate**: After TDD code passes, the phase must run
   real DeepSeek tests through the OpenAI-compatible provider path.
   - Current: DeepSeek has been explored, but live results are not yet the
     acceptance gate for the feedback routing loop.
   - Target: Live DeepSeek verification includes a JSON smoke call, at least
     one accepted IFC-producing workflow run, and at least one non-accept run
     that produces correct Issues, RouteDecision, report, and final status.
   - Acceptance: The final verification report includes redacted DeepSeek
     config status, response IDs, finish reasons not equal to truncation,
     provider label `deepseek-openai-compatible`, artifact secret scan, and
     evidence paths. If DeepSeek credentials or provider behavior fail, the
     phase records a provider issue and stops without claiming live acceptance.

9. **Report as human review entry point**: `report.md` must show the original
   input, Design Brief, candidate BIM JSON or Draft summary, validation,
   compile/reopen, gates, Audit, normalized issues, route decision, feedback
   rounds, final status, and evidence paths.
   - Current: Reports link many sidecars, but the new Issue/RouteDecision loop
     is not yet the central review narrative.
   - Target: A reviewer can understand why a run accepted, drafted, blocked,
     retried, or failed from `report.md` without opening every JSON file.
   - Acceptance: Tests and matrix artifacts verify report sections and links
     for accepted, blocked, Draft, and provider failure outcomes.

10. **Scope control**: This phase must not introduce RAG, fine-tuning,
    deployment changes, large schema redesign, or one-off two-storey hacks.
    - Current: Complex failures make it tempting to patch the current hard
      prompt directly.
    - Target: The implementation changes routing, issue normalization, loop
      behavior, matrix artifacts, and live DeepSeek validation only. If the
      current BIM JSON schema or compiler cannot support a requested fact, the
      route is `blocked_as_unsupported` rather than a silent schema mutation.
    - Acceptance: Code review and tests find no production branch that checks
      for a specific sample prompt, fixed two-storey room names, or hard-coded
      DeepSeek answer transcript.

## 2026-07-11 Bounded Orchestration Bugfix Amendment

**Status:** Approved for implementation

This amendment closes orchestration defects found during code review. It is a
small-scope stability patch: it does not replace BIM JSON Schema, provider
adapters, the session database, compiler architecture, or Agent role
boundaries.

### Locked Decisions

1. A failed deterministic Gate is authoritative. Audit may add semantic
   findings, but an Audit `accept` response cannot suppress Gate feedback or
   prevent routing to the responsible stage.
2. Geometry, containment, host, slab, wall, stair, and opening/filling
   corrections route to Generator regeneration. Local Repair remains limited
   to schema-local edits whose allowed JSON paths are supported by evidence.
3. The orchestrator allows at most two Generator regeneration rounds after
   the initial candidate. Each round recompiles, reopens, reruns all applicable
   Gates, and reruns Audit before the next route decision.
4. Every round is append-only evidence. A later Audit, Generator response, or
   route decision must not overwrite an earlier round's prompt, raw response,
   parsed output, metrics, issues, or decision.
5. Expected Facts may normalize or derive values only from explicit Design
   Brief facts. It must not invent a 3000 mm storey height, 150 mm slab, or any
   other required BIM dimension.
6. A deterministic Scaffold may remain available as a diagnostic fallback,
   but its provenance must be explicit and it is ineligible for real-provider
   Generator acceptance.
7. Opening/filling checks compare the opening, filling element, and host wall
   through their placement chain and bounds. A missing or incompatible
   placement relation is a blocking issue, not a skipped check.
8. Multi-storey ordering prefers explicit elevation, then explicit numeric
   storey index, then stable source order. It must not be limited to two
   storeys or guess unknown floor-name semantics.

### Added Acceptance Criteria

- [ ] A geometry Gate failure routes to `regenerate_json` even when the raw
  Audit response incorrectly recommends `accept`.
- [ ] One initial candidate plus at most two Generator regenerations are
  possible; a third regeneration is never called.
- [ ] `feedback-rounds.json` contains all completed rounds in order and each
  round links to independent Generator, Gate, Audit, and route evidence.
- [ ] Missing storey height or slab thickness remains unresolved rather than
  receiving a default numeric value.
- [ ] Scaffold-derived candidates record
  `candidate_origin: deterministic_scaffold_fallback` and cannot satisfy live
  Generator acceptance.
- [ ] Deterministic tests reject an opening whose own bounds exceed its host
  wall and a filling whose placement chain or world bounds disagree with its
  opening.
- [ ] Fixtures with 3, 5, and 10 storeys are ordered by explicit elevation or
  numeric index using the same implementation.
- [ ] Real DeepSeek UAT starts only after the focused deterministic suite,
  relevant regression suite, and compileall pass.

## 2026-07-11 Geometry Truth-Closure Amendment

**Status:** Approved for implementation

The first completed 6.4 feedback loop proved that provider, validation, and
route artifacts can be connected. Manual review of a real DeepSeek two-storey
IFC then proved a different defect: a candidate-derived geometry expectation
can make a visually incorrect IFC appear to pass. This amendment adds a
bounded geometry-truth closure wave. It does not replace BIM JSON, the
provider abstraction, the session DB, or the existing Issue/RouteDecision
contracts.

### Locked Geometry Semantics

1. `IfcBuildingStorey.elevation_mm` means the **top surface elevation of that
   storey's structural floor slab**. If storey 2 has `elevation_mm: 3150` and
   the slab thickness is `150`, its slab occupies `Z=3000..3150`; a 3000 mm
   high storey-1 wall occupies `Z=0..3000` and touches the slab underside.
2. A shared wall segment is the positive-length intersection of two
   axis-aligned space boundaries on the same storey. It is not merely a
   `from`/`to` relationship and it is not a wall endpoint chosen by the
   Generator. For example, `x=2000..4000,y=4000..8000` adjacent to
   `x=4000..6000,y=0..8000` yields exactly
   `x=4000,y=4000..8000`.
3. A point touch, overlap, missing rectangle, or conflicting wall thickness
   does not yield a wall segment. The geometry expectation records it as
   unresolved and the Design Brief must request clarification; no Agent may
   guess an axis, length, or room boundary.
4. A stair requirement must state a footprint, start point/elevation, end
   point/elevation, horizontal run direction, and width direction before a
   complex stair is Formal. A simple straight stair may be generated only when
   those facts are present. Its reopened IFC must rise from start to end in
   global Z.
5. `geometry_success` is never allowed to be proved by an expectation derived
   only from the candidate being checked. Candidate-derived dimensions may be
   retained as diagnostics, but never as a passing hard-Gate oracle.

### Added Requirements

11. **Design-derived geometry truth sidecar**
    - Current: Multi-storey expected facts preserve spaces and some openings,
      but do not materialize shared wall segments, slab vertical bounds, or
      verifiable stair requirements. The candidate can therefore be compared
      against itself.
    - Target: `geometry-expectation.json` is deterministically derived from
      confirmed Design Brief/Expected Facts only. It contains source fact
      references and status for exterior walls, uniquely derivable interior
      walls, structural slabs, roof, stairs, and opening host requirements.
    - Acceptance: A two-storey fixture derives the 4 m landing/corridor wall
      segment and storey-2 slab `Z=3000..3150`; an ambiguous boundary records
      an unresolved expectation and never creates a guessed wall.

12. **Postcompile IFC geometry Gate**
    - Current: `run_candidate_gate_stage` compiles and reopens IFC, but its
      active geometry expectation can fall back to candidate geometry.
    - Target: One postcompile Gate compares reopened IFC bounding boxes and
      relationships against the design-derived sidecar. It emits component
      IDs, expected values, actual values, source facts, and a stable issue
      code in `geometry-feedback.json`.
    - Acceptance: The Gate detects `WALL_SEGMENT_MISMATCH`,
      `VERTICAL_SLAB_WALL_GAP`, `STAIR_RISE_DIRECTION_MISMATCH`,
      `STAIR_FOOTPRINT_MISMATCH`, and IFC-level
      `OPENING_FILLING_BBOX_MISMATCH` from deterministic fixtures. A failed
      postcompile Gate cannot return `geometry_success: true`.

13. **Canonical stair coordinate frame**
    - Current: A horizontal extrusion can map the stair profile's positive
      rise coordinate to negative global Z, producing a flight below the
      building.
    - Target: The compiler uses one documented local frame for stairs:
      profile run coordinate follows the declared horizontal run, profile rise
      coordinate maps to global +Z, and the width axis follows the declared
      width direction.
    - Acceptance: A compiler/reopen test with a stair from `Z=150` to
      `Z=3150` verifies the IFC bbox rises upward and remains inside the
      declared footprint.

14. **Audit receives geometry evidence but cannot waive it**
    - Current: Audit receives broad sidecar paths and a geometry boolean; it
      can be given a false pass when the underlying expectation is circular.
    - Target: Audit renderer inputs contain the original request, Design
      Brief, candidate BIM JSON, one design-derived geometry expectation, and
      structured expected-versus-actual Gate evidence. A deterministic
      geometry failure forces a non-accept outcome regardless of Audit prose.
    - Acceptance: A test with an Audit response of `accept` plus a failed
      `VERTICAL_SLAB_WALL_GAP` still produces a blocked route.

15. **Geometry feedback regeneration loop and progress evidence**
    - Current: Some Gate/Audit failures reach a terminal block or the wrong
      stage instead of supplying precise geometry evidence to Generator.
    - Target: Generator-owned wall, slab, stair, and opening geometry failures
      route to `regenerate_json`. The feedback payload includes issue code,
      entity IDs, expected/actual bounds, source fact references, and all
      prior relevant issues. Design-fact ambiguity routes to
      `revise_design_brief`, not Generator. A run has at most three total
      candidate attempts: initial generation plus two feedback regenerations.
    - Acceptance: Deterministic tests prove geometry issues rerun Generator,
      unavailable source geometry asks for Design Brief clarification, and the
      logger records `derive_geometry`, `compile_reopen`,
      `geometry_gate`, `audit`, `route`, and each regeneration round.

16. **No duplicate geometry artifacts or compilation for one candidate**
    - Current: Candidate and semantic expectations can be written separately,
      and final acceptance can recompile an unchanged candidate.
    - Target: Each candidate has one authoritative
      `geometry-expectation.json` and one `geometry-feedback.json`; the
      compile/reopen result used by Audit is reused for final acceptance when
      candidate hash is unchanged.
    - Acceptance: Tests verify that a successful candidate produces one
      geometry expectation source, and finalization reuses hash-bound compile
      evidence instead of recompiling the same JSON.

17. **Real DeepSeek closure evidence**
    - Current: A real DeepSeek run produced an IFC that was accepted by weak
      gates but failed manual geometric inspection.
    - Target: After deterministic GREEN, a controlled two-storey live run
      uses the real DeepSeek provider and either produces an IFC that passes
      the new Gate or honestly records the first failed geometry issue and its
      `regenerate_json` / `revise_design_brief` route. A live success claim is
      permitted only for the former.
    - Acceptance: The live run's `progress.jsonl`, `report.md`,
      `geometry-expectation.json`, `geometry-feedback.json`, issue/route
      artifacts, and IFC when accepted are present; artifact secret scan has
      zero findings.
