# Phase 6.4 Post-review Addendum: Multi-storey DeepSeek Debug Findings

**Date:** 2026-07-09
**Scope:** post-review investigation after the two-storey residential live/debug runs
**Status:** Investigated with focused TDD fixes; complex accepted IFC remains future work

## Summary

The current system can prove simple accepted IFC paths and honest non-accept
routes, but the hard two-storey residential case is not yet reliably accepted.
The latest investigation separated three different failure layers that were
previously easy to mix together:

1. **Design Brief over-conservatism:** DeepSeek may stop at `draft_required`
   for complex layouts when corridor paths, stair details, or opening
   positions are underspecified.
2. **Routing evidence pollution:** Expected facts and Audit evidence paths had
   two bugs that could misroute a real geometry problem as `ask_user` or
   `missing_route_artifact`.
3. **Generator multi-storey geometry weakness:** In one real generated
   candidate, the Generator omitted second-floor exterior walls, attached
   second-floor windows to first-floor exterior walls, and produced
   insufficient second-floor wall coordinates.

These are not the same problem. Treating them as one issue leads to the wrong
fix.

## Root Cause Analysis

### 1. Why did `expected-facts.json` reverse storeys?

The earlier Design Brief used nested storeys with the field name `elevation`
instead of `elevation_mm`. The expected-facts extractor only sorted nested
storeys by `elevation_mm`.

When the Design Brief object order happened to list `first_floor` before
`ground_floor`, expected facts became:

```json
[
  {"id": "storey-1", "source_key": "first_floor"},
  {"id": "storey-2", "source_key": "ground_floor"}
]
```

That polluted containment and opening expectations. It could make a real
Generator/gate problem look partly like the wrong floor was expected.

Fix:

- `_nested_storeys` now accepts both `elevation_mm` and `elevation`.
- `_storey_records_from_nested` writes the normalized value as
  `elevation_mm`.

### 2. Why did Audit evidence become `ask_user`?

The Audit Agent returned evidence paths such as:

```json
["/geometry-feedback.json", "/gate-summary.json", "/generator/candidate.json"]
```

The files existed relative to the run directory, but the validator treated the
leading slash as a different path. That created
`AUDIT_EVIDENCE_PATH_MISSING`, which was then normalized as a missing user
fact. This was wrong: the user did not need to answer anything; the workflow
needed to keep the geometry/gate evidence and route it to Generator/regenerate
logic.

Fix:

- Audit evidence paths are normalized from root-relative strings to safe
  run-relative paths.
- Absolute paths and `..` traversal remain rejected.

### 3. Why did DeepSeek sometimes output invalid Design Brief `missing_facts`?

In one rerun, DeepSeek produced useful `missing_facts` entries with `id`,
`path`, `message`, `reason`, `blocking`, `evidence_refs`, and `source_turns`,
but omitted the required `code`.

The prompt already required reason/evidence consistency but did not explicitly
name `code` in the self-check section. For complex outputs, the model obeyed
the semantic shape but missed the machine routing field.

Fix:

- `design-brief.v2.1` now explicitly requires every `missing_facts`,
  `ambiguities`, and `unsupported_requests` item to include a non-empty
  uppercase snake-case `code`.
- Prompt registry hash was updated.

### 4. Why did the Generator miss second-floor exterior walls?

This is still an open generation-capability problem, not a fixed bug.

Most likely contributing factors:

- The current Generator prompt/few-shot examples are still dominated by
  single-storey/simple rectangular rooms.
- The BIM JSON Generator receives a Design Brief with semantic room locations,
  but it is not forced by a structured intermediate layout plan to create an
  independent exterior wall shell for every storey.
- Wall identifiers such as `wall-south-exterior` are easy for the model to
  treat as building-global walls instead of storey-scoped walls. Once reused,
  second-floor windows can accidentally attach to first-floor walls.
- Existing geometry feedback records many `WALL_BBOX_MISMATCH` and
  `ROOM_ENCLOSURE_OPEN` issues, but the feedback is not yet rich enough for a
  Generator retry to know exactly which storey needs which wall shell.
- The route loop can classify issues, but full `regenerate_json` execution with
  geometry feedback is not yet strong enough for the hard multi-storey case.

This should not be fixed by directly mutating points or auto-adding walls in a
local normalizer. The correct direction is:

```text
geometry/audit evidence
  -> normalized issues
  -> route = regenerate_json
  -> Generator receives precise storey-scoped failure evidence
  -> regenerated BIM JSON
  -> gates and Audit rerun
```

### 5. Why did the latest diagnosis stop at Draft instead of reaching Generator?

The diagnosis runner currently uses a generic simulated answer for any
clarification question. That answer says, in effect: use existing facts, and if
anything is still missing, keep Draft.

For complex two-storey prompts, DeepSeek then conservatively kept these
blocking facts:

- ground-floor transition/corridor relationship;
- second-floor corridor geometry;
- stair detailed geometry;
- some door/window exact horizontal positions;
- roof slab thickness.

Some of these are legitimate missing facts for precise modeling. Others are
over-conservative for the current supported-scope compiler because centered or
best-effort opening placement could be produced only when explicitly allowed by
the product boundary. Phase 6.4 should not silently add those defaults.

## What Is Not Fixed Yet

- The hard two-storey residential input does not yet reliably produce an
  accepted IFC.
- The diagnosis runner does not yet provide a controlled adaptive answer set
  that can force the full Generator/gate/Audit path without relying on exact
  question text.
- Geometry feedback for `WALL_BBOX_MISMATCH` and `ROOM_ENCLOSURE_OPEN` is not
  yet precise enough for robust storey-scoped regeneration.
- The route loop can identify `regenerate_json` in controlled cases, but the
  full live Generator rerun for hard multi-storey geometry still needs stronger
  feedback payloads and acceptance evidence.

## Recommended Next Step

Do not rewrite the BIM JSON schema or keep expanding prompts blindly.

The next focused step should be:

1. Improve the multistorey diagnosis runner so controlled two-storey UAT can
   provide semantic answers to actual questions without exact string matching.
2. Ensure Draft stops are reported as Draft/ask-user with missing-fact issues,
   not `missing_route_artifact`.
3. Enrich geometry/audit feedback for storey-scoped failures:
   - expected storey;
   - affected room or wall id;
   - actual host wall and its storey;
   - expected host wall/storey;
   - actual bbox versus expected bbox when available.
4. Route true multi-storey geometry failures to `regenerate_json` with this
   evidence and rerun Generator within the bounded loop.
5. Only after the route/regeneration evidence is stable, retry the hard
   two-storey and then add a three-storey controlled case.

## Pending Design Question: Evidence Selection Strictness

During follow-up review, the user pointed out that the current evidence
selection and validation layer may be too hard-gated for long-term agent
behavior.

Current behavior:

- `context_selection` deterministically selects schema fragments, IFC capability
  evidence, and few-shots before the Design Brief call.
- The Design Brief validator rejects any `evidence_refs` or
  `selected_evidence_ids` that were not supplied in that selected evidence
  catalog.
- This is useful for traceability and anti-hallucination, but it can also fail
  when the selector misses an obviously relevant capability such as
  `IfcBuildingStorey`.

User concern:

- The selector/evidence catalog should possibly be treated as a reference or
  confidence source rather than an absolute product boundary in every case.
- A future validator could distinguish between hard schema violations,
  unsupported generation capability, selector coverage gaps, and recoverable
  evidence-reference warnings.
- The system should surface these details explicitly to the user instead of
  hiding them behind a generic validation failure.

Decision status:

- No architecture change in the current fix.
- Keep the strict validator for now to preserve traceability.
- Revisit after the multi-storey route loop is proven with live DeepSeek runs.

## Pending Design Question: Hard-coded Issue Normalization

During follow-up review, the user pointed out that the current
`issue_normalizers.py` code-to-owner/route mapping is fragile if it remains the
main long-term attribution mechanism.

Current behavior:

- raw diagnostics from schema validation, geometry gates, deterministic gates,
  Audit findings, provider errors, compiler errors, and runtime errors are
  normalized into `Issue` records;
- many ownership and route decisions are currently derived from hard-coded
  string/code heuristics such as `UNSUPPORTED`, `MISSING`, `STOREY`,
  `RELATIONSHIP`, `HOST`, `SCHEMA`, and `JSON`;
- this is useful for early deterministic behavior and testability, but it can
  misclassify new issue classes or encourage prompt/code drift when the system
  grows.

Important current finding:

- For the multi-storey geometry case, the high-level route decision is broadly
  correct: issues such as second-storey wall bbox mismatch, room enclosure
  failure, missing storey containment, and wrong host relationships should
  route to `regenerate_json`.
- The bug is not mainly that routing selected the wrong destination. The bug is
  that the execution/orchestration layer does not yet dispatch
  `regenerate_json` into a true second Generator call with structured feedback.
  It currently falls back into the repair path for this class of Audit/gate
  failures.

Future improvement direction:

- keep normalizers as transparent first-pass classifiers, but do not let
  brittle string matching become the only attribution authority;
- add an explicit issue taxonomy with stable codes, owners, retry policy,
  expected evidence fields, and allowed next stages;
- require each gate/Audit finding to carry enough structured evidence for the
  target stage, not just a free-text message;
- use Audit or a supervisor only to interpret semantic ambiguity, while
  deterministic gates continue to provide machine-checkable evidence;
- make the dispatcher obey the normalized route:

  ```text
  repair_json -> BIM JSON Agent / Repair Mode
  regenerate_json -> BIM JSON Agent / Generate Mode with feedback
  revise_design_brief -> Design Brief Agent with feedback
  ask_user -> CLI/user clarification
  ```

Decision status:

- No code change in this note.
- Treat this as a Phase 6.4 follow-up design debt before expanding to more
  complex buildings.

## Follow-up Patch: StairFlight + Audit Quality Checks

**Date:** 2026-07-10
**Scope:** two focused patches requested after manual IFC review

Two minimal patches were implemented and tested:

1. **Medium stair support.**

   BIM JSON and compiler support now allow an `IfcStair` semantic parent to be
   decomposed into an `IfcStairFlight` child through `IfcRelAggregates`.
   `IfcRelAggregates.RelatedObjects` is now accepted as an array endpoint, and
   an aggregate parent `IfcStair` may omit its own solid `Representation` when
   the visible geometry is carried by child stair flights.

   The Generator prompt now states that a supported simple straight stair should
   not be represented only as one opaque mass. It should output an `IfcStair`
   parent plus at least one `IfcStairFlight`; a stepped polygon flight is
   preferred when rise/run facts are available. If the current context cannot
   represent a real stair flight, the Generator should return Draft instead of
   silently degrading to a single block.

2. **Audit quality checks.**

   Audit v2 now explicitly checks:

   - `OPENING_FILLING_ORIENTATION_MISMATCH`: an opening and its door/window
     filling must align in the host wall local direction, and the finding must
     name the host wall, opening, filling, and placement/bbox evidence.
   - `VERTICAL_SLAB_WALL_GAP`: wall or space tops must close against the slab
     or roof underside under the selected vertical datum convention, and the
     finding must include the affected lower wall/space, upper slab, z values,
     and gap size.

## Follow-up Patch: Generator Regeneration Dispatcher

**Date:** 2026-07-10
**Scope:** connect route decision to actual Generator re-execution

Root cause confirmed:

- The route layer could produce `route = regenerate_json` and
  `target_stage = generator`.
- The execution/orchestration layer did not obey that route. After Audit
  blocked a geometry/gate failure, it called Repair Mode instead of a second
  Generator Generate Mode call.

Implemented behavior:

```text
Audit blocked
  -> normalize gate + Audit findings into Issues
  -> write route-decision / feedback-rounds
  -> if route == regenerate_json and retry_allowed
  -> call Generator-02 with GENERATION_FEEDBACK
  -> promote regenerated candidate
  -> rerun semantic coverage
  -> rerun deterministic gates
  -> rerun Audit-02
```

The Generator prompt now receives a structured `GENERATION_FEEDBACK` object.
For `regenerate_json`, the prompt explicitly says the model is in BIM JSON
Agent / Generate Mode, not Repair Mode, and must regenerate a complete Formal
BIM JSON 2.0 or canonical Draft rather than output a local patch.

## Follow-up Patch: Controlled Input + Draft Contract + Stair Schema Repair

**Date:** 2026-07-10
**Scope:** respond to the latest hard two-storey DeepSeek diagnosis failures

### Problem

After the Generator-regeneration dispatcher was connected, the hard
two-storey diagnosis still had two earlier blockers:

1. Design Brief/Draft could still stop before Generator because the controlled
   input omitted roof thickness, corridor/transition rectangles, default
   opening placement rules, and stair width.
2. When the Generator did reach Formal BIM JSON, DeepSeek sometimes produced
   stair-related schema errors:
   - `IfcStair` without `ObjectPlacement`;
   - `IfcStairFlight.attributes.NumberOfRisers`, which is not currently
     accepted by the BIM JSON 2.0/IFC2X3 schema contract.

These are distinct. The first is a controlled benchmark input problem. The
second is a schema-contract and repair-routing problem.

### Fix

The controlled two-storey input generator now adds:

- roof slab thickness;
- explicit ground-floor corridor/transition rectangle;
- explicit second-floor corridor and stair-landing rectangles;
- a rule that unspecified doors/windows are centered on their host wall
  segment;
- stair width.

The Generator prompt now also states that:

- `IfcStair` must include a full parent-relative `ObjectPlacement`, even when
  decomposed into flights;
- `IfcStairFlight` must include its own `ObjectPlacement`;
- stair-flight quantities such as `NumberOfRisers`, `NumberOfTreads`,
  `RiserHeight`, and `TreadLength` must not be emitted unless the Formal Schema
  explicitly allows them;
- useful stair-step detail should be encoded in supported
  `Representation.profile.points` instead of unsupported IFC attributes.

Draft path rules were strengthened so Draft records must use addressable JSON
Pointer paths under the Draft envelope. Pseudo paths such as
`/entities/ifc_class/door/placement` are now explicitly forbidden.

Repair eligibility now treats `MISSING_OBJECT_PLACEMENT` and
`INVALID_IFC_ATTRIBUTE` as repairable schema-contract errors when known facts
are available. This does not silently invent BIM facts; it only permits the
Repair Agent to remove unsupported attributes or add required placement fields
from existing context.

| Design Brief | Retains storey elevations, floor/roof thickness, space rectangles, and stair elevation endpoints; it does not preserve explicit interior wall segments. | Preserve or deterministically derive shared wall segments from the supplied space rectangles. |
| Expected facts | Does not materialize the available floor/roof facts into slab top/bottom expectations, and has no wall-segment expectations. | Derive these deterministic expectations without inventing user facts. |
| Generator | Guesses short/wrong-axis interior walls and places an upper floor slab at the new storey's base rather than immediately below its elevation. | Add a controlled multi-storey wall/slab contract and corresponding few-shot. |
| Compiler | Reverses the vertical axis of a stair profile when the solid is extruded horizontally. | Define one canonical stair coordinate frame and verify reopened IFC bbox direction. |
| Gate/Audit | Candidate geometry expectation had `walls: {}` and was sourced from the candidate itself; Audit therefore received a passed gate bundle before IFC compilation and accepted. | Gate must compare against Design Brief-derived geometry; post-compile IFC geometry evidence must precede final audit acceptance. |

### Required acceptance rules

- A run with a slab/wall gap, a wall outside its derived shared segment, a
  stair whose top elevation is below its start elevation, or a stair outside
  its declared footprint must never be reported as final `accepted`.
- Audit must receive the original request, Design Brief, candidate BIM JSON,
  deterministic precompile gates, compiler/reopen result, and postcompile IFC
  geometry gates. It may add semantic findings but cannot override a failed
  deterministic gate.
- A failed postcompile geometry gate routes to `regenerate_json` with the
  component IDs, expected and actual bounds, and a precise failure code.
- The next controlled two-storey input removes `door-stairwell-utility` and
  explicitly states the stair start point, end point, horizontal run direction,
  width direction, footprint, and elevation range.
