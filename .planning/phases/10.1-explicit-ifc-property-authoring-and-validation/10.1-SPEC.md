# Phase 10.1: Explicit IFC Property Authoring and Validation - Specification

**Created:** 2026-07-23
**Ambiguity score:** 0.08 (gate: <= 0.20)
**Requirements:** 10 locked
**Roadmap requirements:** PROP-01, PROP-02, PROP-03, PROP-04, PROP-05

## Goal

Given a Window request that explicitly names an IFC Pset, property and scalar
value, the public IFC-plus-text pipeline creates or updates exactly that typed
property at the authorized occurrence or confirmed Type scope and publishes an
IFC only after reopen, L1 and requested-property L2 pass.

## Background

Phase 10 already proves damaged IFC plus text through Stage 1, deterministic
target/Type resolution, Stage 2, one bound ChangeSet, atomic IFC authoring,
reopen, Production/private L1/L2 and publication. `RepairIntent 0.1` carries
generic `attribute_intents`, and Phase 10's semantic assignment dispatcher can
write occurrence `IfcPropertySingleValue` facts, but there is no complete
public contract that distinguishes Pset name, property name, value type, unit,
scope, standard/custom status and confirmation. Consequently an explicit user
request such as `Pset_WindowCommon.FireRating = EI30` is not yet guaranteed to
be validated, authorized, authored and dynamically required by L2.

The repository already contains an offline, manifest-checked IFC2X3 registry
with 317 official Psets, exact applicable classes, property template types,
IFC data types and unit types. Phase 10.1 uses only exact lookup against that
registry and exact current-model facts. Natural-language aliases, semantic
candidate search, embeddings, vector retrieval and RAG remain Phase 10.2.

## Requirements

1. **Versioned exact-property intent**: Stage 1 preserves every explicitly
   named property as a structured, provenance-bearing intent.
   - Current: `RepairIntent 0.1` stores `intent_kind`, one flattened `name`, a
     scalar `value` and source, with no explicit Pset/property split, scope,
     type, unit or confirmation identity.
   - Target: A versioned intent records `set_name`, `property_name`, scalar
     `value`, optional requested `value_type`/`unit`, requested scope, and exact
     user provenance without permitting Provider-authored authorization fields.
   - Acceptance: Schema/model/prompt tests round-trip exact standard and custom
     examples, reject missing path/value/provenance and prove 0.1 artifacts
     remain readable by their original version.

2. **Exact standard-property resolution**: Exact official properties resolve
   deterministically from the checked-in IFC2X3 registry.
   - Current: `IfcKnowledgeRegistry` exposes exact Pset records, but the repair
     pipeline does not bind explicit property intents to it.
   - Target: Exact case-sensitive Pset/property lookup checks applicable IFC
     class, `TypePropertySingleValue`, IFC data type and required unit family;
     a case mismatch or absent property is not silently normalized.
   - Acceptance: `Pset_WindowCommon.FireRating` resolves to `IfcLabel` for
     `IfcWindow`; an inapplicable class, non-single-value template, unknown
     exact path or registry hash drift produces a stable non-authorized result.

3. **Custom-property confirmation**: Every property not exactly resolved as an
   applicable IFC2X3 standard property requires durable user confirmation.
   - Current: Unknown names can appear as free-form attribute intents but have
     no standard/custom classification or confirmation contract.
   - Target: The system presents exact Pset/property, value, selected IFC value
     type, unit, scope and target; only an answer bound to that preview hash can
     authorize the custom property.
   - Acceptance: Missing, stale, altered or negative confirmation prevents
     ChangeSet binding and publication; affirmative confirmation authorizes
     only the displayed property tuple.

4. **Occurrence-safe default scope**: A property request affects only the
   target occurrence unless shared Type scope is explicitly requested and
   confirmed.
   - Current: Type and occurrence evidence are separated, but property intent
     has no mutation-scope field or shared-impact gate.
   - Target: Omitted scope resolves to `occurrence_direct`. `type_owned` is
     legal only when the user explicitly requests the Type, receives a preview
     containing the resolved Type and every affected occurrence, and confirms
     that exact impact set.
   - Acceptance: An occurrence request leaves all other same-Type Windows and
     the Type unchanged; a Type request cannot execute without a matching
     impact confirmation and detects a changed affected set before apply.

5. **Typed scalar and unit safety**: Every authorized value has a valid IFC2X3
   scalar type and unambiguous unit semantics.
   - Current: semantic assignments carry types, but Stage 1 property requests
     do not reliably determine them.
   - Target: Standard properties use registry type/unit metadata; updates may
     reuse an exact existing property's type; confirmed custom text/boolean/
     integer values use `IfcLabel`/`IfcBoolean`/`IfcInteger`; decimal or
     measured custom values require an explicit type and, when applicable,
     unit clarification before authorization.
   - Acceptance: Type-compatible values bind; incompatible values, non-finite
     numbers, ambiguous measured decimals and unit-family mismatches fail or
     enter clarification without writing an IFC.

6. **Deterministic create/update behavior**: Pset authoring has one stable
   merge policy and never creates ambiguous duplicate direct sets.
   - Current: the generic authorer can create occurrence Psets for Phase 10
     assignments but has no user-facing exact-property merge contract.
   - Target: One matching direct Pset is reused; one matching property is
     updated or a missing property is appended; an inherited-only Pset receives
     an occurrence override without mutating the Type; multiple conflicting
     direct Psets or properties fail closed before mutation.
   - Acceptance: create, add-to-existing, update, inherited-override and
     duplicate-conflict fixtures reopen with exactly the expected direct
     relationship/property counts and unchanged non-target facts.

7. **Binder-only authorization**: Provider output remains a draft and cannot
   promote arbitrary property facts into executable assignments.
   - Current: Phase 10 Binder expands an immutable semantic manifest, but
     explicit dynamic property resolution/confirmation is not a first-class
     manifest input.
   - Target: New exact semantic-manifest and bound-ChangeSet versions represent
     `occurrence_direct`, existing `type_inherited` and confirmed `type_direct`
     ownership without changing historical 0.1/0.2 meanings. A deterministic
     resolver and Binder add a requested property only after exact validation/
     confirmation, source hash, target, scope and model fingerprint checks;
     Stage 2 receives only bounded references/summary and cannot change value
     or scope.
   - Acceptance: Provider-added, modified, stale, cross-target, private-Gold or
     unconfirmed property assignments are rejected with no executable
     ChangeSet.

8. **Atomic property authoring**: Property writes participate in the existing
   all-or-nothing ChangeSet transaction.
   - Current: Phase 10 atomicity covers registered semantic assignments but the
     exact-property request path is not wired end to end.
   - Target: Every authorized create/update is applied within the existing
     transaction and the candidate is reopened; resolution, authoring, reopen
     or postcondition failure publishes no successful IFC and leaves source
     bytes unchanged.
   - Acceptance: Failure injection before and after Pset creation/update proves
     rollback, unchanged source SHA-256, diagnostic evidence and absence of a
     successful artifact.

9. **Requested-property L2 gate**: Every authorized user property becomes a
   mandatory dynamic L2 fact for that operation.
   - Current: Window policy 0.2 checks a frozen core/conditional allowlist but
     an arbitrary explicit Pset is not automatically a mandatory check.
   - Target: The same bound property fact feeds Production expected evidence;
     independent reopened extraction must match exact Pset/property, typed
     value, unit and ownership before publication.
   - Acceptance: Correct create/update passes; missing, mismatched, inherited-
     when-direct-was-requested, wrong-scope or wrong-type facts fail L2 and
     suppress `successful_ifc`.

10. **Window end-to-end acceptance and reusable seam**: The exact-property path
    is proven on LargeBuilding Window requests without coupling common code to
    Window or introducing RAG.
    - Current: LargeBuilding publishes the Phase 10 core Window but its live
      acceptance does not request an extra exact standard/custom Pset.
    - Target: Offline and opt-in DeepSeek cases cover an exact standard
      occurrence property and a custom property confirmation; operation-neutral
      intent/resolution/binding interfaces remain consumable by later Door,
      Opening, Beam, Column, Wall and Space operations.
    - Acceptance: Offline Production/private L1/L2 pass, live successful cases
      contain real Stage 1/2 traces and reopened requested properties, failures
      remain honest, and no alias/vector/RAG code is required for success.

## Boundaries

**In scope:**

- Exact, structured Pset/property/value requests for scalar
  `IfcPropertySingleValue` authoring.
- Exact offline IFC2X3 standard-property lookup using the existing checked-in
  official registry and exact current-model property evidence.
- Standard/custom classification and mandatory confirmation for every custom
  property.
- Occurrence-default scope plus explicit, impact-confirmed Type scope.
- Deterministic type/unit validation, direct Pset create/update/override and
  duplicate-conflict handling.
- Manifest/Binder integration, atomic application, reopen and mandatory
  requested-property L2.
- Window LargeBuilding offline and opt-in real DeepSeek acceptance.
- Operation-neutral interfaces for later entity-family adapters.

**Out of scope:**

- Alias, fuzzy, multilingual semantic, embedding, vector or RAG property
  retrieval - Phase 10.2 owns non-exact candidate discovery.
- Automatic selection of an unknown/custom property without confirmation - it
  would create schema drift from a typo or model invention.
- `IfcPropertyEnumeratedValue`, list, bounded, table, reference and complex
  property templates - the first authoring slice is scalar single values.
- Arbitrary Quantity, Material or Classification request redesign - Phase 10
  already supports its frozen Window semantics; later phases can add explicit
  contracts separately.
- Door, opening-only, Beam, Column, Wall-body or Space mutation - Phases 11/12
  and later operations consume the generic property seam.
- Automatic same-Type/neighbor copying, L3 identity reconstruction, curved
  walls and the 128k context experiment.

## Constraints

- IFC output remains IFC2X3 and uses IfcOpenShell authoring, never Provider-
  authored STEP.
- Exact standard lookup is case-sensitive and offline; a near match is a
  clarification candidate, not automatic authorization.
- Source IFC and historical intent/ChangeSet/evaluation versions remain
  immutable; new behavior uses new exact versions.
- One run owns one unified, all-or-nothing ChangeSet.
- Every custom property confirmation is bound to request, target, property
  tuple, selected type/unit, scope, model fingerprint and impact-set hash.
- Occurrence scope is the default. Shared Type mutation is never inferred from
  the presence of a Type or an inherited Pset.
- The full property knowledge base is not sent to the Provider; prompts remain
  bounded by the current 65,536-token configuration.
- Private benchmark Ground Truth enters only after production application.
- Behavioral code follows RED/GREEN/REFACTOR and fail-closed publication.

## Acceptance Criteria

- [ ] RepairIntent exact-property schema/model separates Pset and property
  names and preserves value, optional type/unit, scope and provenance.
- [ ] Historical RepairIntent 0.1 and ChangeSet evidence remain readable by
  their original versions.
- [ ] Exact `Pset_WindowCommon.FireRating=EI30` resolves offline as an
  applicable `IfcLabel` single-value Window property.
- [ ] Inapplicable, non-single-value, case-mismatched and registry-drift paths
  cannot become authorized standard properties.
- [ ] Every custom property requires a hash-bound confirmation containing
  exact name, value, type, unit, scope and target.
- [ ] Omitted scope changes only the target occurrence; confirmed Type scope
  verifies the complete affected occurrence set.
- [ ] Create, append, update and inherited-override paths reopen without
  duplicate direct Psets/properties; conflicts fail atomically.
- [ ] Every authorized property appears as a mandatory dynamic L2 fact and a
  mismatch prevents successful IFC publication.
- [ ] LargeBuilding offline standard/custom cases pass Production and private
  benchmark L1/L2 with no Gold in public inputs.
- [ ] Opt-in real DeepSeek exact-property UAT uses real Provider traces, has no
  synthetic fallback and records honest failures.
- [ ] Focused/full repair tests, knowledge registry tests, compileall, private-
  canary scan and `git diff --check` pass.
