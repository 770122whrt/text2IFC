# Phase 10.1 Research: Exact IFC Property Authoring

**Researched:** 2026-07-23
**Scope:** Codebase-grounded implementation research; no external sources or RAG

## Executive conclusion

Phase 10.1 does not require a new knowledge base. The repository already ships
an offline IFC2X3 official Pset registry generated from PSD sources. The phase
should add a strict exact-property contract and resolution/confirmation layer
in front of Phase 10's typed semantic assignments, then reuse the existing
Binder, transaction, reopened extraction and Evaluation 0.2 publication gate.

The safest minimum is scalar `IfcPropertySingleValue`. Exact official entries
derive applicable class, IFC type and unit family from the registry. Everything
else is custom and requires a hash-bound confirmation. This creates the stable
output contract that Phase 10.2 retrieval/RAG can later target.

## Current architecture findings

| Capability | Existing asset | Gap for 10.1 |
|---|---|---|
| Public property claim | `repair_intent.AttributeIntent` | flattened name; no scope/type/unit/confirmation |
| Official IFC2X3 Psets | `schemas/ifc/generated/IFC2X3/property_sets.json` | not connected to repair intents |
| Runtime exact lookup | `text2ifc_knowledge.registry.IfcKnowledgeRegistry` | no applicability/template/value binding result |
| Durable clarification | `resolution_flow.py`, `run_store.py` | no property/custom/type-impact question kind |

| Pset write | `set_occurrence_pset` dispatcher | merge/duplicate behavior not frozen as public contract |
| Independent actual fact | `semantic_facts.extract_ifc_semantic_facts` | dynamic requested fact not always mandatory in L2 |
| Publication | `orchestrator.py` Evaluation 0.2 gate | no end-to-end exact-property path |

## Official registry evidence

The checked-in IFC2X3 registry contains 317 Psets. For example,
`Pset_WindowCommon` applies to `IfcWindow`; `FireRating` is
`TypePropertySingleValue` with `IfcLabel`, while `ThermalTransmittance` is
`IfcThermalTransmittanceMeasure` with `THERMALTRANSMITTANCEUNIT`. This is enough
for exact validation without search or model memory. Registry hashes are
already checked by `check_registry_files()`.

## Recommended data flow

```text
exact user text
  -> Stage 1 ExactPropertyIntent (claim only)
  -> deterministic exact registry/current-model resolution
  -> standard result OR custom confirmation preview
  -> scope/type-impact confirmation when required
  -> AuthorizedPropertyFact + immutable hash
  -> Phase 10 semantic manifest and Binder
  -> one bound ChangeSet
  -> atomic create/update
  -> reopen IFC
  -> independent dynamic requested-property L2
  -> publish or fail closed
```

Phase 10.2 inserts only before `ExactPropertyIntent`: it maps a non-exact phrase
to candidate exact Pset/property tuples. It must not replace any downstream
authorization step.

## Merge and ownership rules

1. Default `occurrence_direct` never edits `IfcWindowStyle`.
2. One direct Pset with exact name is reusable.
3. One exact property is updated; absent property is appended.
4. An inherited-only path gets a direct occurrence override.
5. Multiple direct exact-name sets/properties are ambiguous and block.
6. `type_owned` requires explicit request, sorted impact preview/hash,
   confirmation and immediate pre-apply impact revalidation.

Because Phase 10's manifest 0.1 and bound ChangeSet 0.2 encode only
`occurrence_direct` and `type_inherited`, direct Type mutation must use new
semantic-manifest 0.2 / bound ChangeSet 0.3 contracts with `type_direct` and
`set_type_pset`. Historical readers and evidence remain exact-versioned.

## Scalar value rules

- Standard single value: official data type and unit family are authoritative.
- Existing exact custom property: its direct value type is useful evidence but
  the custom tuple still requires confirmation.
- Custom string/boolean/integer: safe defaults are `IfcLabel`, `IfcBoolean` and
  `IfcInteger`, shown in the preview.
- Custom decimal or measured value: require an explicit IFC type and applicable
  unit clarification; do not silently choose length, area, ratio or real.
- Enumerated/list/table/reference/complex templates are out of scope.

## Validation Architecture

### Fast deterministic tests

- JSON Schema/model versioning and prompt parsing.
- Exact official lookup, applicability, template and registry-drift failures.
- Custom and Type-impact preview/hash/answer binding.
- Value type/unit conversion matrix and invalid/non-finite rejection.
- Direct Pset create/update/override/duplicate-conflict reopen fixtures.
- Binder tamper/Gold/cross-target tests.
- Dynamic L2 matched/missing/mismatch/wrong-ownership tests.

### Integration tests

- LargeBuilding damaged IFC plus text with standard FireRating.
- LargeBuilding custom AssetCode requiring feedback confirmation.
- Occurrence edit proves all surviving same-Type Windows and Type hashes are
  unchanged.
- Failure injection proves atomic rollback and no successful artifact.

### Live UAT

- Exact standard occurrence property, complete request.
- Custom property followed by feedback confirmation.
- No synthetic fallback; real Stage 1/2 calls and honest terminal statuses.

## Security and failure risks

| Risk | Severity | Required mitigation |
|---|---|---|
| Provider invents an executable property | critical | claim-only Stage 1 plus Binder-only authorization |
| Typo creates a custom schema silently | high | every custom property requires exact preview confirmation |
| Occurrence request edits shared Type | critical | occurrence default; Type impact confirmation/hash |
| Stale Type impact set misses affected objects | high | recompute immediately before application |
| Duplicate direct Psets hide conflicting values | high | fail closed before mutation |
| Wrong numeric type/unit corrupts semantics | high | official metadata or explicit clarification |
| Gold leaks into expected facts | critical | production signatures/canaries remain Gold-free |
| Applicator reports success without reopened fact | critical | independent reopened L2 is publication authority |

## Planning recommendation

Use four sequential plans: contract/resolver; clarification/scope safety;
authoring/Binder/L2; LargeBuilding offline/live evidence. This keeps schema and
authority stable before mutating IFC and gives Phase 10.2 one exact downstream
contract.
