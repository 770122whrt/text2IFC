# Phase 10.1: Explicit IFC Property Authoring and Validation - Context

**Gathered:** 2026-07-23
**Status:** Ready for planning
**Source:** User discussion plus codebase inspection

<domain>
## Phase Boundary

Build the no-RAG exact-property path for the already proven Window pipeline.
The user explicitly supplies Pset, property and value; deterministic code
resolves standard metadata or requests custom confirmation, binds a typed fact,
authors it atomically and makes it mandatory in reopened L2. The phase proves
the generic seam on Window only and does not implement property discovery or
later entity operations.

</domain>

<decisions>
## Implementation Decisions

### Contract and versioning

- **D-01:** Add a new exact-property intent version rather than changing the
  meaning of `RepairIntent 0.1`; retain exact readers/tests for 0.1.
- **D-02:** Represent a Pset request with structured `set_name`,
  `property_name`, scalar `value`, optional `requested_value_type`, optional
  `requested_unit`, `scope` and public provenance. Do not rely on splitting one
  dotted string after validation.
- **D-03:** Stage 1 may extract user claims only. It cannot declare a property
  standard, applicable, confirmed or authorized.

### Exact resolution and custom classification

- **D-04:** Resolve standard properties by exact case-sensitive lookup through
  `load_ifc2x3_registry()` and verify registry manifest drift before use.
- **D-05:** A standard candidate must match applicable IFC class and
  `TypePropertySingleValue`; other template types are unsupported in 10.1.
- **D-06:** If exact official resolution fails, classify the intent as custom;
  do not auto-correct spelling or select a nearby official property.
- **D-07:** Every custom property, including a property already seen only in
  project IFC data, requires user confirmation of the complete normalized
  tuple before authorization.

### Type, unit and value safety

- **D-08:** Standard properties use official registry data type/unit metadata;
  an exact existing direct property may corroborate but cannot override it.
- **D-09:** Confirmed custom strings, booleans and integers default to
  `IfcLabel`, `IfcBoolean` and `IfcInteger`. Decimal/measured values require an
  explicit IFC type and applicable unit when deterministic evidence cannot
  disambiguate them.
- **D-10:** Reject null, non-finite numeric, container/object and incompatible
  enum/template values in the scalar 10.1 contract.

### Scope and Type inheritance

- **D-11:** Missing scope means `occurrence_direct`; inherited Type evidence
  never changes this default.
- **D-12:** Existing Type reuse is optional and never hard-coded. An exact
  unique GUID/name resolves directly; an ambiguous or selection-required Type
  asks the user using the existing durable Prototype flow; no Type intent
  creates a new dedicated `IfcWindowStyle` from versioned deterministic Window
  template 0.1. Remove the current silent same-size
  `_find_compatible_window_type()` fallback. An explicit `type_owned` property-
  mutation request remains deferred and writes nothing.
- **D-13:** For an authorized existing Type, an exact matching inherited
  Pset/property/value satisfies the request without a direct duplicate unless
  the user explicitly asks for an occurrence override. Missing or differing
  values create an occurrence-direct property; they never mutate or detach the
  Type Pset.

### Merge, authorization and evaluation

- **D-14:** Reuse one direct matching Pset, update one matching property or add
  the missing property. Multiple direct Psets/properties with the same exact
  name are an ambiguity error, not a merge heuristic.
- **D-15:** Resolution/confirmation emits a normalized authorized occurrence
  property fact using semantic-manifest 0.1 and bound ChangeSet 0.2:
  `occurrence_direct` may be authored and existing `type_inherited` facts may
  satisfy exact requests. A deterministic-policy `relationship:type`
  assignment may reference the precomputed ID of a new system-template Type,
  but no `type_direct`/`set_type_pset` contract is added. The Binder copies the
  fact into the one bound ChangeSet; Provider drafts cannot add or modify it.
- **D-16:** Bind confirmation to source-request hash, model fingerprint,
  target occurrence, exact tuple and occurrence scope.
- **D-17:** Each authorized property creates a dynamic mandatory L2 fact with
  allowed ownership: `type_inherited` for an exact reused-Type match or
  `occurrence_direct` for a create/update/override. Independent reopened
  extraction, not applicator return data, supplies actual evidence.
- **D-18:** Any resolve, confirm, bind, apply, reopen or L2 failure follows the
  existing fail-closed terminal state and cannot expose `successful_ifc`.

### Acceptance and forward compatibility

- **D-19:** Prove occurrence standard `Pset_WindowCommon.FireRating=EI30` and a
  confirmed custom `Custom_Asset.AssetCode=W-007` on the LargeBuilding Window
  chain. Explicit Type-mutation-deferred and negative custom cases are
  deterministic fixtures.
- **D-20:** The live DeepSeek runner has no synthetic fallback and records real
  Stage 1/2 counts, clarification/confirmation transitions, ChangeSet, reopen,
  Production L1/L2 and published IFC status.
- **D-21:** Keep intent resolution, normalized property facts and dynamic L2
  extension operation-neutral. Window owns only applicability/target-role
  adaptation so later Door/Opening/Beam/Column/Wall/Space adapters can reuse it.
- **D-22:** Phase 10.2 may return property candidates, but can authorize nothing;
  its successful output must be the exact Phase 10.1 contract.

### the agent's Discretion

- Internal Python class/module names and exact stable error-code suffixes.
- Exact generated Window Type display-name format, provided its GlobalId and
  template inputs are deterministic, it is dedicated to the new occurrence,
  and no project-specific Type/Pset/material/classification value is invented.
- Whether prompt examples use quoted JSON-like notation or Chinese prose, as
  long as both normalize to the same structured intent.
- Evidence artifact filenames, provided hashes and lifecycle states remain
  immutable and indexed in the run manifest.

</decisions>

<code_context>
## Existing Code Insights

### Reusable assets

- `IfcKnowledgeRegistry.property_set(name)` already returns immutable exact
  official metadata; `check_registry_files()` detects generated-registry drift.
- `AttributeIntent` already preserves public provenance and scalar values,
  providing a migration seam to a richer exact-property intent version.
- `SemanticAssignment` already carries fact key, value/type/unit, ownership,
  applicability, source/provenance and authoring action.
- `apply_semantic_assignments()` already creates occurrence Psets and reuses
  the Phase 10 all-or-nothing transaction.
- `extract_ifc_semantic_facts()` already distinguishes direct from inherited
  properties and supplies independent L2 evidence.
- Dynamic policy extensions already have focused tests for explicit request
  facts such as `Pset_WindowCommon.FireRating`.

### Missing capability

- No structured Pset/property/scope/type/unit Stage 1 contract.
- No deterministic exact standard/custom resolver in the repair pipeline.
- No custom-property preview/hash/confirmation lifecycle.
- No stable fail-closed result for direct shared-Type property mutation.
- Current Window application may silently select a same-size existing Type when
  no bound Type exists, and has no deterministic dedicated-template Type path.
- No explicit direct-Pset duplicate conflict contract.
- No end-to-end dynamic requested-property L2 acceptance.

</code_context>
