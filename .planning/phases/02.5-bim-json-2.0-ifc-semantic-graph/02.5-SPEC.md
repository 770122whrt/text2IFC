# Phase 2.5: BIM JSON 2.0 IFC Semantic Graph - Specification

**Created:** 2026-06-11
**Ambiguity score:** 0.10 (gate: <= 0.20)
**Requirements:** 15 locked

## Goal

Replace the fixed BIM JSON 1.0 element vocabulary with a validated,
IFC2X3-aligned semantic entity graph that can be deterministically extracted
from authorized IFC sources and compiled for an explicit architectural
generation profile without fabricating or silently discarding source facts.

## Background

BIM JSON 1.0 and the Phase 2 compiler support nine project-specific element
kinds, hierarchy, basic dimensions, and selected properties. A 35-file audit
found that the contract omits local placement, 189 spaces, 845 openings, 732
filling relations, additional architectural classes, and most IFC properties
and representation forms.

The existing fixed vocabulary also cannot express a direct semantic result
such as `ifc_class: "IfcWall"`. Phase 2.5 is therefore a breaking contract
revision. It introduces official-source schema knowledge, explicit IFC class
identity, spatial truth, bounded semantic geometry, formal-versus-Draft
semantics, deterministic IFC extraction, and compiler capability checks before
Phase 3 creates Text-to-JSON training pairs.

## Requirements

1. **Breaking versioned contract**: Define a new canonical
   `bim-json/2.0` JSON Schema without modifying BIM JSON 1.0.
   - Current: `bim-json/1.0` uses a fixed `elements[].kind` vocabulary.
   - Target: `bim-json/2.0` is a separately versioned IFC semantic graph whose
     JSON Schema is its only structural truth.
   - Acceptance: The 1.0 schema and fixtures remain byte-stable; 2.0 documents
     identify `schema_version: "bim-json/2.0"` and validate only against the
     new schema.

2. **Official IFC2X3 knowledge manifest**: Record and verify every canonical
   source used to build IFC knowledge.
   - Current: The repository contains official EXPRESS but no complete
     machine-readable source manifest or PSD acquisition record.
   - Target: A manifest records official buildingSMART URLs, retrieval dates,
     SHA-256 hashes, source roles, and local/generated artifact paths for
     IFC2X3 EXPRESS, XSD, HTML documentation, and PSD definitions.
   - Acceptance: A repeatable check proves the local EXPRESS hash matches the
     official file and rejects a changed or unlisted source artifact.

3. **Deterministic IFC declaration registry**: Generate a registry from
   official IFC2X3 EXPRESS rather than a hand-authored class list.
   - Current: The contract and compiler maintain a nine-kind mapping.
   - Target: The registry represents all IFC2X3 declarations needed for class,
     inheritance, attribute, select, enumeration, and relationship checks,
     including all 653 entity declarations reported by IfcOpenShell 0.8.5.
   - Acceptance: Registry generation is deterministic, resolves
     `IfcWall`, `IfcSpace`, `IfcOpeningElement`, `IfcRelVoidsElement`, and
     `IfcRelFillsElement` with correct inheritance and attributes, and a drift
     check fails after a generated record is altered.

4. **Official property-set registry**: Generate standard property knowledge
   from official IFC2X3 PSD definitions.
   - Current: Phase 2 writes selected property sets but has no complete
     standard property registry.
   - Target: The registry preserves exact property-set and property names,
     applicability, value types, units or enumerations when declared, and
     source provenance.
   - Acceptance: The generated registry contains 317 official property-set
     templates and validates representative properties from
     `Pset_WallCommon`, `Pset_SpaceCommon`, and
     `Pset_OpeningElementCommon` against the official PSD package.

5. **Explicit IFC semantic entities**: Represent user-meaningful objects with
   stable identity and an explicit validated IFC class.
   - Current: Elements use project-specific `kind` strings and separate
     top-level family assumptions.
   - Target: Semantic objects live in `entities`, each with stable `id`,
     `ifc_class`, typed native IFC attributes, provenance, and optional source
     `GlobalId`.
   - Acceptance: A wall is represented as `IfcWall`; an unknown class is
     rejected; a valid inherited attribute is accepted; an attribute not
     available on that IFC2X3 class is rejected with a field-level diagnostic.

6. **Explicit semantic relationships**: Represent user-meaningful IFC
   relations separately from compiler bookkeeping.
   - Current: BIM JSON 1.0 has containment references but no IFC relationship
     records.
   - Target: `relationships` records use explicit IFC2X3 relationship classes
     and canonical relating/related attribute names. Deterministic aggregation,
     containment, property attachment, and owner-history relations may be
     generated from unambiguous semantic references.
   - Acceptance: Valid void/fill chains pass; unresolved endpoints, endpoint
     class mismatches, duplicate relation IDs, and invalid relation classes
     fail before IFC output.

7. **Capability-gated class universe**: Separate schema recognition,
   extraction, generation, and compiler-only implementation behavior.
   - Current: Anything outside nine classes is unsupported by the contract.
   - Target: Every relevant IFC2X3 entity has an explicit capability state;
     formal compilation accepts only `generate` classes, Draft extraction may
     preserve `extract-only` classes, and low-level implementation classes are
     `compiler-only`.
   - Acceptance: A recognized extract-only class remains in a Draft with an
     explicit capability diagnostic, while the formal compiler rejects it
     without creating output.

8. **Initial architectural generation profile**: Compile the Phase 2 classes
   plus the main architectural classes observed in BIMNet.
   - Current: The compiler generates nine classes.
   - Target: The generation profile also covers `IfcSpace`,
     `IfcOpeningElement`, `IfcPlate`, `IfcCovering`, `IfcCurtainWall`,
     `IfcMember`, and `IfcRailing`, with project, site, building, and storey
     hierarchy support.
   - Acceptance: A complete fixture containing every profile class compiles
     to reopenable IFC2X3 with exact per-class counts and no generated
     `IfcBuildingElementProxy` fallback.

9. **Parent-relative placement truth**: Preserve IFC-like local placement and
   orientation without requiring low-level placement entities in model output.
   - Current: BIM JSON 1.0 has no element coordinates and Phase 2 uses
     synthetic placement.
   - Target: Each placed semantic entity provides a finite parent-relative
     origin, axis, reference direction, and resolvable parent; derived world
     transforms are deterministic.
   - Acceptance: Nested placements round-trip within 1 mm and a defined
     angular tolerance; zero vectors, non-orthogonal bases, cycles, missing
     parents, and non-finite values are rejected.

10. **Bounded semantic geometry**: Preserve only geometry forms that the
    deterministic compiler can regenerate faithfully.
    - Current: Required dimensions compile to synthetic rectangular
      envelopes, while source IFC includes extrusions, BReps, mapped items,
      surface models, and boolean results.
    - Target: Formal geometry uses declared semantic profile/extrusion forms.
      Unsupported representation forms remain Draft content with explicit
      source loss records and are never silently approximated as boxes.
    - Acceptance: Supported profile extrusions preserve placement and
      measurable dimensions; each unsupported representation item contributes
      a machine-readable loss entry tied to its source entity.

11. **Typed attributes and property sets**: Preserve IFC2X3 native attributes,
    official properties, and explicit custom properties without coercion.
    - Current: BIM JSON 1.0 exposes three selected common properties.
    - Target: Values are checked against registry-derived types,
      enumerations, applicability, and units. Custom property sets are
      namespaced and never mislabeled as official buildingSMART definitions.
    - Acceptance: Representative Boolean, label, identifier, enumeration,
      length, area, and count values round-trip with type fidelity; invalid
      standard properties produce field-level diagnostics.

12. **Formal and Draft separation**: Keep compiler-ready truth separate from
    incomplete or unsupported records.
    - Current: Migration either converts or rejects a whole BIM JSON 1.0
      document.
    - Target: A formal `bim-json/2.0` document is complete for its generation
      profile. A separately versioned Draft Envelope contains partial content,
      missing-fact entries, losses, provenance, and clarification targets.
    - Acceptance: Formal validation rejects every missing required fact;
      Draft validation requires every omission or unsupported construct to be
      listed and addressable; the compiler never accepts a Draft Envelope.

13. **Lossless-by-accounting IFC extraction**: Extract authorized IFC2X3 into
    formal BIM JSON 2.0 or an explicit Draft without silent source loss.
    - Current: No canonical IFC-to-BIM-JSON extractor exists.
    - Target: Extraction preserves supported semantic entities,
      relationships, placement, geometry, attributes, properties, source
      `GlobalId`, file hash, and schema provenance; every unsupported source
      object or construct is counted and linked to a Draft/loss entry.
    - Acceptance: For each of the 25 authorized BIMNet files, source inventory
      equals represented plus explicitly reported content for entities,
      relationships, properties, and representation items.

14. **BIM JSON 1.0 migration to Draft**: Preserve known 1.0 facts while
    explicitly declaring spatial uncertainty.
    - Current: 1.0 lacks local placement, spaces, openings, and relationship
      records.
    - Target: Migration emits a Draft Envelope containing mapped 2.0 entities,
      original IDs and values, per-entity missing placement fields, and an
      explicit unknown-space-coverage entry.
    - Acceptance: Migration never invents positions or spaces, never discards
      a 1.0 element, and reports the same stable missing-fact set on repeated
      runs.

15. **Compiler and verifier compatibility**: Preserve completed Phase 2
    guarantees while adding semantic graph support.
    - Current: The compiler accepts only formal BIM JSON 1.0.
    - Target: The compiler also accepts formal BIM JSON 2.0 generation-profile
      documents, expands low-level IFC objects deterministically, writes
      atomically, and verifies reopened IFC2X3.
    - Acceptance: Existing 1.0 regression tests remain green; a complete 2.0
      fixture compiles and passes IfcOpenShell validation; invalid or Draft
      input leaves an existing destination unchanged.

## Boundaries

**In scope:**

- Canonical BIM JSON 2.0 and Draft Envelope schemas
- Official-source IFC2X3 declaration and property-set registries
- Source provenance, hash verification, and deterministic registry generation
- IFC-aligned entities, relationships, attributes, properties, and identity
- Parent-relative placement and bounded semantic extrusion/profile geometry
- BIMNet main architectural generation profile
- Deterministic IFC2X3 extraction with complete loss accounting
- BIM JSON 1.0 to Draft migration
- Compiler and verifier support for formal 2.0 generation-profile documents

**Out of scope:**

- IFC4 or IFC4X3 registry and output - the authorized primary dataset is
  IFC2X3 and multi-schema support would weaken the first contract
- Raw low-level IFC object graphs - implementation entities are deterministic
  compiler output, not natural-language intent
- Arbitrary BRep, mapped, tessellated, surface, boolean, and presentation
  geometry generation - deferred to Phase 4 fidelity work
- Material layers, type-object reuse, and general connection topology -
  deferred to Phase 4
- Broad furnishing, structural-analysis, and MEP generation - recognized by
  the registry but deferred beyond the initial architectural profile
- Vector RAG as a correctness dependency - it may be evaluated later but
  cannot override deterministic schema knowledge
- Runtime user questioning - Draft fields prepare clarification targets;
  multi-turn interaction remains Phase 5
- Fine-tuning and deployment - Phase 6

## Constraints

- JSON Schema Draft 2020-12 remains the only structural truth for each
  versioned JSON contract.
- IFC2X3 structure comes from official buildingSMART EXPRESS; standard
  property metadata comes from official PSD XML.
- Every downloaded or generated knowledge artifact is provenance-addressed
  and reproducible.
- IfcOpenShell 0.8.5 is the schema introspection, compiler, and verification
  runtime adapter.
- Official APIs or documents may fill missing schema metadata only. They must
  not invent project-specific facts.
- Formal compiler input must be complete, finite, internally referentially
  valid, and within the generation capability profile.
- Existing BIM JSON 1.0 and Phase 2 behavior remains supported and regression
  tested.
- Dataset splitting remains by Matterport scene family before Phase 3 creates
  text pairs.
- Every implementation behavior follows a recorded RED-GREEN-REFACTOR TDD
  cycle.

## Acceptance Criteria

- [ ] Official IFC2X3 source manifest and hash checks pass.
- [ ] The checked-in EXPRESS hash equals the official buildingSMART file.
- [ ] Deterministic declaration and PSD registry generation passes drift
  checks.
- [ ] BIM JSON 2.0 validates explicit IFC classes, inherited attributes, and
  relationship endpoints from registry knowledge.
- [ ] Unknown classes and invalid class attributes fail with field-level
  diagnostics.
- [ ] Formal and Draft schemas are separate; the compiler rejects Drafts.
- [ ] Parent-relative placement and derived world transforms pass round-trip
  tests.
- [ ] Every initial architectural generation-profile class compiles with exact
  reopened IFC counts.
- [ ] Supported semantic geometry round-trips without box substitution for
  unsupported source geometry.
- [ ] Standard and custom property values preserve names, types, and values.
- [ ] All 25 BIMNet files satisfy represented-plus-reported inventory
  accounting.
- [ ] BIM JSON 1.0 migration creates stable Drafts with explicit spatial and
  space-coverage gaps.
- [ ] Existing Phase 1 and Phase 2 regression tests remain green.
- [ ] A complete BIM JSON 2.0 fixture produces atomic, reopenable, schema-valid
  IFC2X3.
