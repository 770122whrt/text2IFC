# Phase 2.5 Discussion Log

**Date:** 2026-06-11
**Phase:** BIM JSON 2.0 IFC Semantic Graph

## IFC Class Boundary

**Options discussed:** fixed project kinds; unrestricted IFC strings; raw
low-level IFC JSON graph; registry-validated IFC semantic graph.

**Decision:** Use explicit `ifc_class` values and IFC2X3 naming/inheritance,
but keep low-level placement, geometry-resource, owner-history, and STEP
objects inside the deterministic compiler.

## Knowledge Layer

**Options discussed:** no knowledge layer; vector RAG as truth; deterministic
registry with optional retrieval.

**Decision:** Build the required registry from official buildingSMART
IFC2X3 EXPRESS and PSD sources. RAG is optional later and cannot override
schema validation.

## Schema and Contract Version

**Options discussed:** additive BIM JSON 1.1; breaking BIM JSON 2.0; direct IFC
object serialization.

**Decision:** Use the breaking version `bim-json/2.0`. All semantic objects use
`entities`; semantic relations use `relationships`.

## Generation Coverage

**Options discussed:** retain nine classes; BIMNet main architectural classes;
all IFC2X3 classes immediately.

**Decision:** Generate the Phase 2 classes plus spaces, openings, plates,
coverings, curtain walls, members, and railings. Register all schema classes
with explicit capability states; do not pretend every class is generatable.

## Geometry and Placement

**Options discussed:** dimensions only; semantic generatable geometry; raw
BRep/mesh graph. Flat world coordinates; parent-relative placement.

**Decision:** Use bounded semantic profile/extrusion geometry and
parent-relative placement as truth. Unsupported geometry remains Draft/loss,
not a silent box approximation.

## Attributes, Properties, and Relationships

**Options discussed:** generic key/value bags; typed IFC attributes and
property sets. Explicit all relations; implicit all relations; semantic
relations explicit with compiler bookkeeping generated.

**Decision:** Preserve typed native IFC attributes and exact property-set
names. Users/source data express semantic relations; the compiler creates
unambiguous aggregation, containment, property attachment, and owner history.

## Formal and Draft Semantics

**Options discussed:** permissive incomplete formal documents; formal documents
complete plus a separate Draft Envelope.

**Decision:** Formal BIM JSON 2.0 is complete and compiler-ready. Missing,
ambiguous, extract-only, or unsupported content uses a versioned Draft
Envelope with explicit missing facts, losses, provenance, and future
clarification targets.

## Migration and Identity

**Options discussed:** invent defaults; reject all 1.0; migrate to Draft.
STEP IDs; source-only GlobalIds; stable semantic IDs plus source identity.

**Decision:** Migrate 1.0 to Draft, preserve every known value, enumerate
missing placement and unknown space coverage, and invent nothing. Use stable
semantic IDs, preserve source GlobalIds, and never use STEP line numbers as
identity.

## Official-Source Clarification

The user required that unknown structures must be obtained from official IFC
sources or APIs and must never be invented. Research confirmed:

- buildingSMART IFC2X3 TC1 EXPRESS is the structural authority.
- The official distribution contains 317 IFC2X3 PSD XML definitions.
- IfcOpenShell 0.8.5 exposes 980 declarations, 653 entity declarations, and a
  generated 317-template property-set adapter.
- buildingSMART states that bSDD is not the complete IFC schema and currently
  exposes IFC4.3 semantic dictionary content, so it is not the IFC2X3 source
  of truth.
- Official sources may fill schema metadata, never unknown facts about a
  particular building or user request.

## Deferred Ideas

- Vector RAG evaluation
- Full IFC4/IFC4X3 registry and output
- Arbitrary BRep, mapped, tessellated, surface, and boolean generation
- Materials, type reuse, broad connection topology, furnishing, and MEP
- Runtime multi-turn clarification and Draft completion

## Wave 4 Real-IFC Contract Adjustment

**Date:** 2026-06-12

Representative BIMNet inspection found that its walls are authored as exact
`IfcWallStandardCase` entities: 34 in `hxp.ifc`, 22 in `i5n.ifc`, and 30 in
`vt2_1.ifc`. Treating that class as unsupported would remove the primary
architectural class from training labels.

`IfcExtrudedAreaSolid` also carries its own `Position` relative to the product
placement. Folding that transform into `ObjectPlacement` would conflate
product position with representation position and would not round trip.

**User-approved decision:**

- Preserve exact `ifc_class: "IfcWallStandardCase"` and set its capability to
  `generate`.
- Add optional `Representation.position` with local `origin`, `axis`, and
  `ref_direction`, but no `relative_to`.
- Keep mapped, BRep, surface, boolean, and other unsupported representations
  as explicit Draft losses; do not substitute a box or rename the source
  class.
