# Phase 2.5 Validation Strategy

## Validation Principle

Every public transformation, validator, extractor, and compiler behavior starts
with a failing behavioral test. Normal tests run offline against checked-in
schemas and generated registries; explicit acquisition tests are isolated from
the default suite.

## Test Infrastructure

| Property | Value |
|---|---|
| Framework | pytest |
| Config | repository `pytest.ini` and project-local dependency path |
| Quick command | `python -m pytest tests/knowledge tests/contract_v2 -q` |
| Full command | `python -m pytest tests -q` |
| Expected final runtime | under 420 seconds on the current machine |

## Sampling Rate

- After every RED commit: run the new focused test and record the expected
  behavioral failure.
- After every GREEN or REFACTOR commit: run focused tests plus the affected
  package suite.
- After each wave: run `python -m pytest tests -q`.
- Before phase verification: run registry drift checks, all-25 extraction
  accounting, generated documentation checks, `compileall`, and the full suite.
- No three consecutive implementation commits may occur without an automated
  test command.

## Required Negative Proofs

- Changed source hash is rejected before parsing.
- Unsafe ZIP paths and oversized archives are rejected.
- PSD XML external entities and network resolution are disabled.
- Unknown IFC class and invalid inherited attribute are rejected.
- Extract-only and compiler-only classes cannot enter formal compilation.
- Formal documents reject missing required facts.
- Drafts reject unlisted omissions and cannot enter the compiler.
- Placement cycles, unresolved parents, invalid bases, and non-finite values are
  rejected.
- Invalid void/fill endpoint classes are rejected.
- Unsupported source representation creates a loss entry, not box geometry.
- Migration does not create source positions or spaces.
- Invalid or Draft compilation leaves a pre-existing IFC destination unchanged.
