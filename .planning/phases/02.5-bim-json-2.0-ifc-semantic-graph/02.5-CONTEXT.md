# Phase 2.5: BIM JSON 2.0 IFC Semantic Graph - Context

**Gathered:** 2026-06-11
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 2.5 replaces the fixed nine-kind learning target with a breaking
`bim-json/2.0` contract that represents IFC2X3 semantic entities and
relationships explicitly. It builds a deterministic knowledge registry from
official buildingSMART sources, extracts authorized IFC ground truth without
silent loss, and extends the compiler for the initial BIMNet architectural
generation profile.

The language model expresses user-meaningful IFC classes, attributes,
placements, geometry, properties, and relationships. The deterministic
compiler creates low-level IFC implementation objects and bookkeeping.
</domain>

<spec_lock>
## Locked Requirements

The requirements, boundaries, and acceptance criteria in `02.5-SPEC.md` are
locked. Planning must not narrow the official-source, no-fabrication, Draft
Envelope, or explicit-loss requirements.
</spec_lock>

<decisions>
## Implementation Decisions

### IFC-aligned semantic graph

- **D-01:** The version is `bim-json/2.0`; this is a breaking major contract,
  not an additive BIM JSON 1.1 revision.
- **D-02:** User-semantic IFC objects live in `entities`; semantic IFC
  relationships live in `relationships`.
- **D-03:** Each record has a validated explicit `ifc_class`, such as
  `IfcWall`, and uses canonical IFC2X3 class, attribute, relationship,
  property-set, and property names.
- **D-04:** IFC naming and inheritance semantics follow IFC2X3, while values
  such as placement and representation use bounded semantic payloads rather
  than a raw low-level IFC object graph.
- **D-05:** The model does not generate `IfcCartesianPoint`, `IfcDirection`,
  `IfcOwnerHistory`, STEP line numbers, serializer timestamps, or equivalent
  implementation objects. The compiler generates them deterministically.

### Official knowledge and capability registry

- **D-06:** IFC2X3 TC1 is the only complete schema target in Phase 2.5.
- **D-07:** EXPRESS is the structural authority. Official PSD XML is the
  standard property-set authority. XSD and official HTML are supporting
  references. IfcOpenShell introspection is a runtime adapter and generated
  cache, not a competing source of truth.
- **D-08:** Every fetched source records its official URL, retrieval date,
  SHA-256, and role. Missing schema facts are never invented.
- **D-09:** bSDD is optional enrichment only. It cannot replace IFC2X3
  EXPRESS/PSD and cannot fill project-specific facts.
- **D-10:** The registry covers the complete IFC2X3 declaration universe and
  tags each entity with an explicit capability such as `generate`,
  `extract-only`, `compiler-only`, or `unsupported`.
- **D-11:** An unknown class string is invalid. A known but non-generatable
  class cannot pass the formal compiler gate and cannot be silently dropped.

### Initial generation profile

- **D-12:** Preserve the Phase 2 generation classes and add BIMNet's main
  architectural classes: `IfcSpace`, `IfcOpeningElement`, `IfcPlate`,
  `IfcCovering`, `IfcCurtainWall`, `IfcMember`, and `IfcRailing`.
- **D-13:** Rare observed `IfcBuildingElementProxy` and
  `IfcFurnishingElement` content is initially extract-only unless research
  proves a deterministic semantic geometry profile.
- **D-14:** Geometry is semantic and generatable. The formal profile supports
  declared extrusion/profile forms; arbitrary BRep, mapped, surface, boolean,
  tessellated, or presentation geometry remains explicit Draft/loss content.

### Placement, properties, and relationships

- **D-15:** Parent-relative placement is canonical truth. World transforms are
  derived and may be cached only as reproducible verification output.
- **D-16:** Preserve stable semantic `id`; preserve source IFC `GlobalId` when
  present; never use STEP line numbers as identity.
- **D-17:** Native IFC attributes and standard property sets retain their
  IFC2X3 names and typed values. Custom property sets remain explicitly
  custom and are not presented as buildingSMART definitions.
- **D-18:** User-meaningful relationships such as voiding and filling are
  explicit `relationships`. Aggregation, containment, property attachment,
  owner history, and other compiler bookkeeping are generated from semantic
  references when their meaning is already unambiguous.

### Formal documents, Drafts, and migration

- **D-19:** A formal `bim-json/2.0` document is complete and compiler-ready for
  the declared generation profile.
- **D-20:** Incomplete, extract-only, unsupported, or ambiguous content uses a
  separate versioned Draft Envelope. Every missing fact, unsupported source
  construct, and clarification target is machine-readable.
- **D-21:** BIM JSON 1.0 migration produces a Draft Envelope. It preserves
  original facts, lists missing placement fields per affected entity, and
  records that space coverage is unknown because 1.0 had no space inventory.
  It does not fabricate positions or spaces.
- **D-22:** Official sources may supply schema definitions, allowed
  attributes, enumerations, and property metadata. They may never supply
  unknown coordinates, dimensions, materials, relationships, or other facts
  about a particular source model or user request.

### the agent's Discretion

- Exact generated registry file partitioning and cache format.
- Exact module names and internal adapter boundaries.
- Exact ordering of deterministic registry output.
- Which official descriptions are cached locally, provided provenance and
  copyright constraints are respected.
</decisions>

<specifics>
## Specific Ideas

- Text input containing "wall" or "墙" should ultimately produce an entity
  whose class is explicitly `IfcWall`, not a project-specific `kind: wall`.
- IFC-native attribute names may contain bounded semantic values. For example,
  `ObjectPlacement` may hold a parent-relative semantic placement payload
  without requiring the model to emit `IfcLocalPlacement`,
  `IfcAxis2Placement3D`, `IfcCartesianPoint`, and `IfcDirection` objects.
- The deterministic registry is required for correctness. Vector RAG may be
  evaluated later for class or property retrieval, but retrieved text never
  overrides schema validation.
</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets

- `text2ifc_contract`: diagnostic shape, schema loading, semantic validation,
  and deterministic migration audit patterns.
- `text2ifc_compiler`: atomic output, stable GlobalId derivation, IfcOpenShell
  hierarchy, geometry, property, and reopened verification helpers.
- IfcOpenShell 0.8.5: `schema_by_name("IFC2X3")` exposes 980 declarations and
  653 entity declarations without opening an IFC file.
- IfcOpenShell `PsetQto("IFC2X3")`: exposes 317 buildingSMART property-set
  templates and 1850 property templates.

### Established Patterns

- JSON Schema remains the only structural truth for a BIM JSON contract.
- Semantic checks layer on top of schema validation and return stable
  field-level diagnostics.
- New behavior follows recorded RED, GREEN, and optional REFACTOR commits.
- Verification inspects serialized and reopened IFC rather than compiler-only
  bookkeeping.

### Integration Points

- BIM JSON 2.0 lives beside, not over, `schemas/bim-json/1.0/`.
- The knowledge registry feeds contract generation, semantic validation,
  extraction, compiler capability checks, and later Text-to-JSON constrained
  decoding.
- Phase 3 consumes only formal BIM JSON 2.0 examples or explicitly labeled
  Draft examples; it does not invent another target shape.
</code_context>
