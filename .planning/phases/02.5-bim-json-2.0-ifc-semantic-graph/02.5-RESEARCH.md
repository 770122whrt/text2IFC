# Phase 2.5 Research: BIM JSON 2.0 IFC Semantic Graph

**Researched:** 2026-06-11
**Runtime verified:** IfcOpenShell 0.8.5
**Status:** Ready for planning

## Research Question

How should text2IFC build a reproducible IFC2X3 knowledge layer and use it to
define, extract, validate, and compile BIM JSON 2.0 without asking a language
model to generate the low-level IFC object graph?

## Verified Official Sources

buildingSMART's schema index lists IFC2X3 TC1 version 2.3.0.1 as official and
publishes separate links for EXPRESS, XSD, HTML/PSD distribution, and PSD
support files.

buildingSMART's bSDD documentation states that bSDD is not the complete IFC
schema and that the IFC dictionary currently published there is IFC4.3. bSDD
therefore cannot be the IFC2X3 structural source of truth.

## Verified IfcOpenShell Capabilities

`ifcopenshell.schema_by_name("IFC2X3")` exposes a compiled schema without
opening a model:

- 980 declarations
- 653 entity declarations
- 90 `IfcProduct` descendants including `IfcProduct`
- 50 `IfcRelationship` descendants including `IfcRelationship`
- expected inherited attributes for representative products, spaces,
  openings, and void/fill relationships

`ifcopenshell.express.parse("schemas/ifc/IFC2X3_TC1.exp")` successfully creates
a late-bound schema from the local official EXPRESS file. On the current
Windows machine, initial parsing takes about 90 seconds, so it belongs in
registry generation, not request-time validation.

IfcOpenShell's IFC2X3 property-template adapter contains:

- 317 `IfcPropertySetTemplate` records
- 1850 `IfcSimplePropertyTemplate` records
- representative `Pset_WallCommon`, `Pset_SpaceCommon`, and
  `Pset_OpeningElementCommon` templates

Its generation code consumes the same official IFC2X3 HTML/PSD distribution.
The text2IFC registry should parse PSD XML directly for source provenance and
use IfcOpenShell's adapter as an independent runtime cross-check.

Recommended files:

```text
schemas/ifc/

  generate_registry.py
  check_registry.py

```

The source manifest is human-reviewed and records official URLs, expected
hashes, roles, and retrieval policy. Raw XSD/HTML/PSD downloads go to an
ignored local cache, not Git. Generated normalized registries are checked in
and contain only schema facts required by the product, not copied narrative
documentation.

Normal validation is offline:

```text
checked-in source manifest
  + checked-in official EXPRESS
  + checked-in generated registries
  + project-authored capability overlay
  -> deterministic runtime knowledge API
```

An explicit acquisition/regeneration command may use the network:

```text
official URL
  -> bounded download
  -> SHA-256 verification
  -> safe archive inventory/extraction
  -> EXPRESS/PSD parsing
  -> canonical JSON generation
  -> drift comparison
```

## Registry Design

### Official declaration registry

Each declaration record should include:

- name and declaration kind
- entity abstractness
- direct supertype and full supertype chain
- declared and inherited attributes in schema order
- optionality and derived status
- inverse attributes
- attribute type expression
- select alternatives and enumeration values where applicable
- source schema and source hash

The registry is generated, sorted deterministically, and never edited by hand.

### Official property registry

Each property-set record should include:

- exact set name
- applicable IFC classes
- property names
- template/value kind
- primary data type or reference type
- enumeration items where declared
- unit metadata where declared
- source PSD path and source distribution hash

Do not copy descriptions unless redistribution and attribution are explicitly
reviewed. Names, applicability, and type metadata are enough for validation.

### Project-authored capability overlay

Capabilities must remain separate from official schema facts:

- `generate`: allowed in formal compiler input
- `extract-only`: may be preserved in a Draft but not compiled
- `compiler-only`: low-level implementation entity created deterministically
- `unsupported`: recognized but not semantically represented in this phase

The initial generation profile includes the Phase 2 classes plus
`IfcSpace`, `IfcOpeningElement`, `IfcPlate`, `IfcCovering`,
`IfcCurtainWall`, `IfcMember`, and `IfcRailing`. The overlay should also tag
semantic relationship classes and the hierarchy classes required by the
compiler.

## BIM JSON 2.0 Shape

Recommended top-level shape:

```json
{
  "schema_version": "bim-json/2.0",
  "ifc_schema": "IFC2X3",
  "units": {"length": "MILLIMETRE"},
  "entities": [],
  "relationships": [],
  "provenance": {}
}
```

An entity uses exact IFC names but bounded semantic values:

```json
{
  "id": "wall-001",
  "ifc_class": "IfcWall",
  "global_id": "optional-source-global-id",
  "attributes": {
    "Name": "North wall",
    "ObjectPlacement": {
      "relative_to": "storey-001",
      "origin": [1200.0, 3500.0, 0.0],
      "axis": [0.0, 0.0, 1.0],
      "ref_direction": [1.0, 0.0, 0.0]
    },
    "Representation": {
      "kind": "extruded_profile",
      "profile": {"kind": "rectangle", "x": 5000.0, "y": 200.0},
      "depth": 2800.0,
      "direction": [0.0, 0.0, 1.0]
    }
  },
  "property_sets": {
    "Pset_WallCommon": {"IsExternal": true}
  },
  "provenance": {}
}
```

`ObjectPlacement` and `Representation` retain the native IFC attribute names,
but their values are semantic compiler inputs. They are not serialized
`IfcLocalPlacement`, `IfcAxis2Placement3D`, or representation-resource graphs.

Relationship records use exact IFC relationship and endpoint names. For
example, `IfcRelVoidsElement` refers to a wall ID through
`RelatingBuildingElement` and an opening ID through `RelatedOpeningElement`.

## Formal and Draft Validation

Use separate schemas:

- `bim-json/2.0`: complete and compiler-ready for `generate` capabilities.
- `bim-json-draft/1.0`: wraps partial 2.0-shaped content with explicit
  `missing_facts`, `losses`, `clarification_targets`, and provenance.

The Draft Envelope must not weaken the formal schema or share the compiler
entry point. A draft may contain extract-only entities, but every unsupported
or missing fact remains addressable by stable entity ID and JSON path.

BIM JSON 1.0 migration maps every known hierarchy, element, dimension,
property, and ID into Draft content. It records missing `ObjectPlacement`
fields and an unknown `IfcSpace` coverage gap. It does not create placeholder
spaces or synthetic source coordinates.

## Placement and Geometry

Parent-relative placement mirrors IFC meaning and avoids duplicating world
coordinates as truth. Validate:

- finite coordinates
- non-zero axis and reference direction
- normalization or deterministic normalization policy
- orthogonality within a documented tolerance
- resolvable parent IDs
- acyclic parent chains
- allowed parent classes

Compute world transforms through one tested matrix composition helper.

The initial formal geometry profile should support rectangular and closed
polygon extrusion forms needed by the architectural generation profile.
Unsupported BRep, mapped, surface, boolean, and tessellated source
representations produce Draft/loss entries. The extractor must not substitute a
box and call it lossless.

## Extraction Architecture

Recommended package:

```text
src/text2ifc_extractor/
  extractor.py
  inventory.py
  identity.py
  placement.py
  geometry.py
  properties.py
  relationships.py
  losses.py
  verification.py
```

Extraction first inventories source IFC content, then represents or reports
each inventory item. The final accounting invariant is:

```text
source inventory = represented content + explicit losses
```

Run the invariant independently for:

- semantic entities
- relationships
- property assignments and individual properties
- representation items
- material/type/connection structures deferred to Phase 4

When any required fact is unsupported, output a Draft Envelope. A formal
document is emitted only when every included entity is complete and
generatable and no source content has been silently omitted.

## Compiler Architecture

Keep the Phase 2 atomic compiler boundary and add a version dispatch:

```text
formal BIM JSON 2.0
  -> structural and semantic validation
  -> capability gate
  -> hierarchy and identity
  -> parent-relative placements
  -> semantic geometry adapters
  -> explicit semantic relationships
  -> compiler-generated IFC bookkeeping
  -> in-memory verification
  -> temporary STEP
  -> reopen and verify
  -> atomic replace
```

The compiler creates `IfcOwnerHistory`, placement-resource entities, geometric
resource entities, aggregation, containment, and property attachment. It must
not accept a Draft Envelope or downgrade an unsupported class to
`IfcBuildingElementProxy`.

## Security and Reliability Risks

1. **Source substitution:** verify HTTPS source URLs and exact SHA-256 before
   parsing.
2. **Archive traversal:** reject absolute paths, `..` segments, alternate data
   streams, symlinks, excessive entry counts, and excessive uncompressed size.
3. **XML entity expansion:** parse PSD XML with network access and entity
   resolution disabled.
4. **Unbounded schema/data input:** cap file sizes, entity counts, placement
   depth, relationship counts, and diagnostic volume.
5. **Formal/Draft confusion:** separate schema IDs, loaders, result types, and
   compiler entry points.
6. **Capability bypass:** validate class capabilities after structural
   validation and before any IFC creation.
7. **Geometry bombs:** bound profile points, coordinate magnitude, extrusion
   size, and tessellation work.
8. **Cycle and reference abuse:** use bounded graph traversal with stable
   cycle diagnostics.
9. **Partial output replacement:** retain Phase 2 temporary-file and reopen
   verification guarantees.
10. **Source fact fabrication:** tests must prove migration/extraction never
    inserts missing coordinates, spaces, relations, or values.

## Planning Consequences

1. Build and verify official-source acquisition and registries first.
2. Build the formal/Draft contract and capability gate on those registries.
3. Add placement, semantic geometry, spaces, and relationship validation.
4. Implement extractor and compiler in parallel only after the contract is
   stable.
5. Finish with all-25-file accounting, generated documentation, full
   regression, security review, and requirement coverage.
