# Phase 6.5-06: Real DeepSeek Stability Campaign and Final Verification

**Goal:** Demonstrate stable text-to-IFC generation for canonical two- and three-storey buildings with real DeepSeek evidence.

## Decision Amendment (2026-07-16)

The repeated-run requirement below is retained as historical context but is
superseded. Phase 6.5 now uses coverage-oriented acceptance: one frozen Easy,
one frozen Medium, and one frozen Difficult input must each pass one complete
real-provider Text2IFC run. Repeating the same prompt three times is not the
current completion gate and must not be reported as stronger evidence than
cross-case coverage.

The standard input pool is `tests/text2ifc_basic_test_inputs.md`. The primary
three-case gate and the remaining expansion cases are defined in
`06.5-STANDARD-INPUT-ACCEPTANCE.md`. Failures are recorded first in
`06.5-ISSUE-REGISTER.md`; observing a failure does not authorize an immediate
TDD/code-fix cycle.

## Task 1: Live UAT harness without scripted model answers

**Files:**
- Create: `scripts/agent/run_phase6_5_live_stability.py`
- Create: `tests/agent/test_phase6_5_live_harness.py`

1. RED: require `--case`, `--runs`, `--env-file`, `--output-root`, timeout,
   trace level, and check-config controls; model answers cannot be loaded from
   prewritten response files.
2. GREEN: run independent sessions, stream stage/package/revision progress, and
   append matrix results without exposing credentials.
3. A user clarification may be answered interactively or by an explicitly
   labelled Codex-as-user UAT turn; hidden canned answers cannot count.

## Task 2: Two-storey campaign

1. Run the canonical Chinese two-storey request with staged generation.
2. Inspect every Design Brief, package, ChangeSet, Gate, Audit, and IFC result.
3. Continue independent runs until three consecutive accepted sessions exist
   or a genuine blocker appears. Do not cherry-pick non-consecutive successes.
4. If blocked, classify whether the defect belongs to prompt/example, provider,
   ChangeSet contract/scope, compiler, Gate, or unsupported capability before
   changing code. Use TDD for any code fix and restart the consecutive count.

## Task 3: Three-storey campaign

1. Run a distinct Chinese three-storey request with two vertical connections,
   intermediate slabs, roof, spaces, walls, doors, windows, and stairs.
2. Apply the same three-consecutive-run rule and failure ownership discipline.
3. Do not weaken a Gate or add case-specific production coordinates/names.

## Task 4: Final evidence and human review handoff

1. Generate `stability-matrix.json` and `stability-report.md` from actual runs.
2. Verify six accepted sessions, real response IDs/usage, preservation 1.0,
   bounded rounds, schema/compile/reopen/geometry/Audit success, report links,
   and zero secret findings.
3. Reopen every final IFC with IfcOpenShell and run the full deterministic
   regression after the last live-driven fix.
4. Select one two-storey and one three-storey IFC for user visual review. Label
   visual review as a separate manual result, not a substitute for Gates.
5. Write `06.5-06-SUMMARY.md`, `06.5-VERIFICATION.md`, code review, security
   review, requirement coverage, and update ROADMAP/STATE with verified facts.
6. Commit atomically and push `origin/multiagent-design`.

## Completion Gate

Phase 6.5 coverage-based stability is complete only when the frozen Easy,
Medium, and Difficult primary cases each have one accepted real-provider run
with complete machine-readable and human-review evidence. A failure is first
added to the unified issue register and classified; implementation work starts
only after a separate triage decision. Partial success is not reported as
cross-case stability, and this gate does not claim a statistical success rate.
