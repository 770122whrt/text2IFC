# Phase 6.5: Component-scoped ChangeSets and Multi-storey Stability - Specification

**Created:** 2026-07-12
**Ambiguity score:** 0.10 (gate: <= 0.20)
**Requirements:** 12 locked

## Goal

Replace full-document BIM JSON regeneration after Generator-owned failures with
schema-validated, ID-addressed ChangeSets, then reuse the same composition
mechanism to produce stable two- and three-storey BIM JSON 2.0 and reopenable
IFC2X3 outputs from real Chinese text and real DeepSeek calls.

## Background

Phase 6.4 proved that Design Brief, Generator, deterministic Gates, Audit, route
selection, and bounded feedback can form a real DeepSeek loop. It also exposed
the remaining architectural defect: a `regenerate_json` round asks the model to
return an entire Formal BIM JSON document. A correction to one stair, opening,
or slab can therefore alter walls, windows, placements, or relationships that
already passed. `fact_delta.py` can detect some unrelated changes after the
fact, but no executable scope contract prevents them.

Phase 6.5 borrows the stable identity, composition, and incremental-change
ideas being explored by IFC5. It does not adopt IFC5 or change the IFC2X3
delivery target. BIM JSON 2.0 remains the only formal model contract.

## Requirements

1. **ChangeSet contract**: Define one versioned sidecar contract for Generator-authored BIM JSON changes.
   - Current: Regeneration returns a complete Formal BIM JSON or Draft.
   - Target: Feedback rounds return either `text2ifc/bim-json-changeset/1.0` or a canonical Draft. Operations address entities and relationships by stable ID, never by array index.
   - Acceptance: Contract tests accept valid add/update/remove operations and reject unknown operations, duplicate targets, missing evidence, missing base hashes, and undeclared paths.

2. **Immutable revision binding**: Every ChangeSet is bound to the exact candidate and evidence revision it edits.
   - Current: Route evidence is hash-bound, but a regenerated full document replaces the candidate wholesale.
   - Target: Each ChangeSet records `base_candidate_hash`, `expected_facts_hash`, source issue IDs, and a monotonically increasing revision number; stale bindings are rejected before application.
   - Acceptance: Applying a ChangeSet to any candidate other than its declared base fails without writing a promoted candidate.

3. **Deterministic patch application**: Apply accepted ChangeSets to a copy of the prior candidate and produce a new complete candidate revision.
   - Current: LLM output is promoted directly as the next complete candidate.
   - Target: A deterministic applicator resolves stable IDs, checks preconditions, applies operations, sorts canonical collections, and validates the composed BIM JSON 2.0 document before promotion.
   - Acceptance: Unit tests prove deterministic output hashes and prove the prior candidate remains byte-for-byte unchanged.

4. **Scope and dependency lock**: Limit each feedback round to named failed components plus an explicit dependency closure.
   - Current: Prompt text asks the model to preserve unrelated components but cannot enforce it.
   - Target: Route preparation derives allowed entity IDs, relationship IDs, and field paths from Issues, host/filling/containment links, and expected facts. Any operation outside that set is blocked as `CHANGESET_SCOPE_VIOLATION`.
   - Acceptance: A stair correction may change its flights, landings, stair opening, and declared relations, but a simultaneous unrelated wall or window change is rejected.

5. **No silent semantic invention**: A ChangeSet may only use existing user, Design Brief, schema, capability, expected-fact, or deterministic Gate evidence.
   - Current: `fact_delta.py` checks evidence paths after full regeneration.
   - Target: Every operation cites one or more source issue/evidence references before application. Missing user facts route to Draft; unsupported capability routes to blocked, not fabricated geometry.
   - Acceptance: Tests reject operations supported only by supervisor-authored text, aborted evidence, or guessed dimensions.

6. **Scoped feedback loop**: Connect Audit/Gate `regenerate_json` decisions to ChangeSet generation and repeated local/global verification.
   - Current: `_attempt_generator_regeneration_after_audit` requests and promotes a full candidate.
   - Target: Generator receives the prior candidate index, allowed scope, exact expected/actual evidence, and ChangeSet schema; successful application reruns semantic coverage, relevant local Gates, all global integrity Gates, IFC compile/reopen, postcompile geometry Gates, and Audit.
   - Acceptance: A deterministic integration test executes `Audit blocked -> ChangeSet -> apply -> Gates -> Audit accepted`, and a non-improving loop stops within three ChangeSet rounds with evidence.

7. **Unchanged-component preservation**: Make preservation of passing components machine-verifiable.
   - Current: Preservation is a prompt instruction and post-hoc leaf comparison.
   - Target: Every revision records per-entity and per-relationship semantic hashes. Objects outside the dependency closure must retain identical hashes.
   - Acceptance: Accepted feedback rounds report `unrelated_component_preservation_rate = 1.0`; any lower value blocks acceptance.

8. **Multi-storey staged composition**: Build complex initial candidates in bounded scopes without changing the final BIM JSON schema.
   - Current: One Generator call attempts the entire multi-storey document.
   - Target: Orchestration composes a building/storey skeleton, one package per storey, and one cross-storey package for stairs, slabs, roofs, and vertical relationships. Packages are ChangeSets applied to an internal composition workspace; only the final composition may be promoted as Formal BIM JSON 2.0.
   - Acceptance: Tests cover two and three storeys with dynamically discovered storey IDs; production code contains no fixed two-storey or three-storey counts.

9. **Cross-package ownership rules**: Give every generated component one unambiguous package owner.
   - Current: Multi-storey output can duplicate walls, attach windows to another storey, or drift stair/slab ownership.
   - Target: Storey-local walls, spaces, doors, windows, and openings belong to one storey package. Stairs, inter-storey slabs, roofs, and their openings belong to the cross-storey package while referencing explicit storeys.
   - Acceptance: Composition rejects duplicate IDs, cross-storey host mismatches, orphan openings/fillings, and undeclared cross-package references.

10. **Human-readable revision evidence**: Report each local modification without requiring the reviewer to open every JSON sidecar.
    - Current: `report.md` shows route evidence but full regeneration diffs are noisy.
    - Target: The generated report contains revision number, source Issues, allowed scope, operations, affected dependency closure, unchanged hash result, Gate/Audit results, provider IDs, timings, and final IFC path.
    - Acceptance: Report tests derive all sections from actual trace/revision artifacts and reject a hard-coded report.

11. **Real DeepSeek graded acceptance campaign**: Prove the mechanism with live provider behavior, not fake/file/replay evidence.
    - Current: The simple two-storey case has one real accepted IFC, but a live review exposed cross-storey display-name drift that existing Gates did not detect.
    - Target: Easy, Medium, and Hard canonical cases each complete one real DeepSeek run to accepted IFC, using at most three ChangeSet repair rounds. Easy is the current simple two-storey case. Medium is a two-storey L-shaped building with more spaces, interior partitions, wall junctions, doors, windows, and one vertical connection. Hard has comparable per-storey topology across three storeys with two vertical connections.
    - Acceptance: A machine-readable matrix contains one accepted live session per difficulty, real provider response IDs and usage, zero scope violations, preservation rate 1.0, compile/reopen success, geometry success, Audit accepted, and zero secret findings. This proves canonical-case acceptance, not statistical stability across repeated samples.

13. **Storey-name semantic consistency**: Prevent a component from carrying a display name that explicitly names a different storey.
    - Current: The accepted Easy IFC correctly contains second-storey components under storey 2, while their `Name` values incorrectly say `首层`.
    - Target: The Generator must derive display names from the current storey package. A deterministic Gate compares explicit storey labels in component names with the owning storey from placement/expected facts. Neutral names such as `南墙` remain valid.
    - Acceptance: TDD rejects an entity owned by storey 2 whose `Name` explicitly contains the configured name of storey 1, while accepting neutral or correctly labelled names. The compiler remains a faithful serializer and does not rewrite names.

14. **Segmented L-shaped enclosure**: Exercise irregular envelopes without introducing a bent-wall schema extension.
    - Current: Easy uses four straight exterior walls around a rectangular footprint.
    - Target: Medium and Hard represent an L-shaped exterior envelope as multiple independent straight `IfcWall` entities whose endpoints meet at 90-degree corners. Slabs, roofs, and spaces may use supported polygon profiles.
    - Acceptance: Deterministic expectations verify exterior segment count, endpoint continuity, no unintended gaps/crossings, interior partition connectivity, room enclosure, and correct opening hosts. A single polyline or bent `IfcWall` is out of scope.

12. **Text2IFC boundary preservation**: Keep this phase focused on generating new IFC from text.
    - Current: Existing IFC import/edit is a future design idea.
    - Target: Phase 6.5 leaves extension points for a future imported base revision but accepts only text-derived composition baselines in production and UAT.
    - Acceptance: No Phase 6.5 acceptance case starts from an imported or damaged IFC, and no IFC5 runtime/schema dependency is added.

## Locked ChangeSet Shape

The exact JSON Schema is implemented in Wave 0, but the following semantic
fields and operation vocabulary are locked by this SPEC:

```json
{
  "schema_version": "text2ifc/bim-json-changeset/1.0",
  "changeset_id": "changeset-revision-01",
  "base_revision_id": "revision-00",
  "base_candidate_hash": "sha256:...",
  "expected_facts_hash": "sha256:...",
  "source_issue_ids": ["issue-geometry-001"],
  "scope_id": "scope-revision-01",
  "operations": [
    {
      "operation_id": "operation-001",
      "op": "update_entity",
      "target_id": "stair-storey-1-to-2",
      "target_component_hash": "sha256:...",
      "changes": {
        "/attributes/Representation/depth": 3000
      },
      "evidence_refs": ["issue-geometry-001:/expected"]
    }
  ]
}
```

Allowed operations are `add_entity`, `update_entity`, `remove_entity`,
`add_relationship`, `update_relationship`, and `remove_relationship`. Update
paths are relative to the already identified semantic record. Raw collection
indexes, implicit cascade deletion, whole-document replacement, and generic
`move`/`copy` operations are forbidden.

## Locked Route Semantics

| Existing route | Phase 6.5 execution |
|---|---|
| `regenerate_json` | Generator produces a scoped ChangeSet; it does not return a complete replacement candidate. |
| `repair_json` | Existing syntax/schema repair remains separate and may only repair a malformed candidate within evidence-authorized paths. |
| `revise_design_brief` | Design Brief is revised first; prior candidate revision is not patched until a new ready brief and expected facts are bound. |
| `ask_user` | Conversation remains Draft until the user provides facts or explicitly leaves them unknown. |
| `blocked_as_unsupported` | No ChangeSet is attempted. |
| `gate_issue` | Human/developer Gate review; the model cannot patch around a disputed Gate. |

## Boundaries

**In scope:**

- BIM JSON ChangeSet schema and validator sidecar.
- Stable-ID candidate index, revision hashes, scope derivation, and dependency closure.
- Deterministic ChangeSet application to BIM JSON 2.0 candidates.
- ChangeSet-based repair/regeneration loop with local and global Gates.
- Staged initial composition for building/storey and cross-storey packages.
- Generated revision evidence in `report.md` and a stability matrix.
- Deterministic TDD followed by real DeepSeek two- and three-storey UAT.

**Out of scope:**

- Migrating to IFC5 or emitting IFC5/IFCX - IFC2X3 remains the delivery format.
- Importing, damaging, or editing an existing IFC - reserved for a later phase using the same revision interface.
- RAG, fine-tuning, service/API packaging, or provider replacement.
- Expanding BIM JSON to unsupported IFC classes solely to satisfy a benchmark.
- Silent geometric auto-correction such as closing polygons by copying points.
- Exact STEP IDs or byte-identical IFC comparison across runs.
- Removing Phase 6.4 full trace artifacts before the compact trace contract is proven equivalent.

## Constraints

- JSON Schema remains the single structural truth for Formal BIM JSON 2.0.
- ChangeSet and composition contracts are workflow sidecars, not alternative BIM models.
- Initial generation may use staged partial workspaces, but only a complete schema-valid document is called Formal or compiled.
- All machine-control keys and enum values use English; Chinese user content is preserved as evidence.
- Default maximum is three ChangeSet repair rounds after the initial candidate.
- Every live claim requires real DeepSeek response evidence loaded from environment variables; secrets and private provider URLs are excluded from artifacts and Git.
- Work remains in the C-drive `multiagent-design` worktree.

## Acceptance Criteria

- [ ] Valid and invalid ChangeSet contract behavior is covered by TDD.
- [ ] Stale, out-of-scope, unsupported, and evidence-free ChangeSets cannot be promoted.
- [ ] Unchanged entity and relationship hashes remain identical after every accepted patch.
- [ ] The existing Phase 6.4 deterministic and live-route regressions still pass.
- [ ] A two-storey and a three-storey staged composition produce valid BIM JSON 2.0 without fixed storey counts.
- [ ] Local and global Gates, IFC compile/reopen, geometry checks, and Audit run after each promoted revision.
- [ ] Easy, Medium, and Hard each produce one accepted real DeepSeek IFC with no unrelated component drift; reports do not claim statistical stability from these single runs.
- [ ] Every accepted run writes a reopenable IFC2X3, generated `report.md`, revision manifest, ChangeSet history, timing data, and secret-scan result.
- [ ] Existing IFC editing and IFC5 runtime adoption remain absent from Phase 6.5 implementation and acceptance claims.
