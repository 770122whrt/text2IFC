# Phase 6.5 Context

## Locked Product Direction

Phase 6.5 improves the current Text -> Design Brief -> BIM JSON -> IFC chain.
It is not an IFC editor. IFC5 is architectural inspiration for stable identity,
composition, and incremental changes, not a schema/runtime migration.

## Current Baseline

- `interactive_cli_flow.py::_attempt_generator_regeneration_after_audit`
  builds precise feedback but invokes `run_generator_stage`, which returns a
  complete replacement candidate.
- `fact_delta.py` detects unauthorized leaf changes after a full-document
  response; it does not prevent or safely merge them.
- Phase 6.4 already supplies normalized Issues, RouteDecision v2, bounded
  rounds, expected/actual geometry evidence, hash-bound Gate/Audit artifacts,
  stage progress, DeepSeek provider evidence, and generated reports.
- Strict stair, slab, roof, opening, filling, host-wall, storey, and geometry
  checks now expose genuine model drift. They must remain authoritative.

## Design Decisions

1. The first Generator candidate may remain full-document during the first
   ChangeSet milestone. Failed Generator-owned revisions must become patches.
2. After the patch loop is proven, initial multi-storey generation is staged
   into skeleton, storey-local, and cross-storey packages using the same
   ChangeSet applicator.
3. ChangeSets address stable semantic IDs. Raw JSON array indexes are forbidden.
4. Applying a ChangeSet creates a new immutable revision and never mutates the
   prior candidate.
5. Local Gates accelerate feedback, but a candidate cannot be accepted until
   all global Gates, IFC compile/reopen, postcompile geometry Gates, and Audit
   have passed for the composed revision.
6. Audit judges semantic intent and issue ownership. Deterministic code derives
   scope, validates hashes, applies operations, and blocks unauthorized changes.
7. A future IFC import/edit phase may provide a different base revision, but it
   must use the same ChangeSet interface rather than changing this contract.

## Canonical Data Flow

```text
Chinese user text
  -> Design Brief
  -> Expected Facts and stable ID contract
  -> initial candidate or staged composition workspace
  -> Formal BIM JSON 2.0 revision R0
  -> deterministic Gates + IFC compile/reopen + geometry Gates + Audit
  -> structured Issues and RouteDecision
  -> allowed scope and dependency closure
  -> DeepSeek ChangeSet or canonical Draft
  -> deterministic ChangeSet Gate and applicator
  -> Formal BIM JSON 2.0 revision R1
  -> local Gates + complete global verification
  -> accepted IFC2X3 or another bounded ChangeSet round
```

## Package Ownership

| Package | Owns | May reference |
|---|---|---|
| Skeleton | project/site/building/storeys and hierarchy | none outside skeleton |
| Storey package | spaces, storey-local walls, doors, windows, openings, containment | its storey and explicitly declared hosts |
| Cross-storey package | stairs/flights/landings, inter-storey slabs, roofs, stair openings, vertical relations | participating storeys and package entities |

## Safety Invariants

- No ChangeSet without an exact base candidate hash.
- No operation without source issue/evidence references.
- No path or ID outside the deterministic allowed scope.
- No implicit cascade deletion.
- No silent guessed dimension, placement, host, storey, or relationship.
- No accepted revision with unrelated hash drift.
- No Audit override of deterministic failure.
- No partial composition is described as Formal or compiled.

## Primary Acceptance Cases

- Canonical two-storey residence based on the Phase 6.4 controlled input.
- A distinct three-storey mixed room-layout case that exercises dynamic storey
  discovery, two vertical connections, intermediate slabs, and a top roof.
- Each case runs three independent real DeepSeek sessions. Scripted stdin may
  support deterministic regression but cannot satisfy live acceptance.

## Execution-time Uncertainties

These are engineering hypotheses to measure, not unresolved product decisions:

1. Dependency closure may need refinement for compound stair/slab/opening and
   wall/opening/filling failures. The safe fallback is to block a scope that
   cannot be derived, never to authorize the whole document.
2. One package per storey may still be too large for a dense storey. Phase 6.5
   records package size and latency; zone/subsystem subdivision is considered
   only if the canonical three-storey case proves storey packages insufficient.
3. Three consecutive live successes are intentionally strict and may require
   more than six total calls/runs. A failed run resets that case's consecutive
   counter after any code or prompt change.
4. `remove_*` operations are required to delete model-invented extras, but no
   dependency is removed implicitly. The ChangeSet must name every dependent
   removal and the scope planner must authorize it.
