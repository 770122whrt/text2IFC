# Phase 6.2 AI Design Contract

## 1. System Classification

**System Type:** Hybrid conversational multi-agent structured-output system.

**Description:** A Chinese-first CLI coordinates multiple role-isolated Mimo
agent calls. The system converts natural language and user clarification turns
into a Design Brief, Formal BIM JSON 2.0 or canonical Draft, deterministic IFC
generation evidence, Audit output, metrics, and a generated report.

**Critical Failure Modes:**

1. Claiming a live workflow passed when a semantic role used fake/file/replay
   output.
2. Letting a framework hide provider response IDs, finish reasons, usage, raw
   output, prompt hashes, or parsed outputs.
3. Inventing missing dimensions, relationships, placements, openings, rooms, or
   properties instead of asking or returning Draft.
4. Compiling Draft or invalid BIM JSON to IFC.
5. Persisting API keys, provider headers, private URLs, or `.env` content.

## 1b. Domain Context

**Industry Vertical:** BIM / AEC design automation.

**User Population:** A developer or BIM researcher using a local CLI to test
natural-language-to-IFC workflows.

**Stakes Level:** Medium for research; high if downstream IFC is treated as
engineering truth.

**Output Consequence:** The generated IFC may be opened in BIM viewers and used
to judge model quality. Incorrect geometry, missing walls, wrong openings, or
fabricated properties can mislead evaluation and training data decisions.

### What Domain Experts Evaluate Against

| Dimension | Good | Bad | Stakes |
|---|---|---|---|
| Intent coverage | User-requested spaces, dimensions, openings, and host walls are represented or explicitly Drafted | User facts are dropped or changed silently | Generated model may look plausible but be wrong |
| Spatial correctness | Walls close, openings sit on host walls, rooms/spaces are coherent under gates | Walls disconnect, openings float, coordinate frames contradict prompt | Visual and training evidence becomes unreliable |
| IFC validity | IFC reopens as IFC2X3 and preserves supported classes/relationships | Raw STEP or invalid IFC is accepted | Downstream tools fail |
| Traceability | Every model output links to prompt, raw response, parsed JSON, gates, and report | Only final IFC exists with no evidence | Debugging and prompt iteration become guesswork |
| Clarification quality | Agent asks 1-3 necessary Chinese questions | Agent asks irrelevant IFC-style details or uses hidden defaults | User trust and data quality degrade |

### Known Domain Failure Modes

- Schema-valid JSON that is spatially wrong.
- Complete-looking room models with missing enclosing walls.
- Model asks for optional IFC style details that are not needed for the current
  supported generation profile.
- Model invents plausible IFC schema names or Draft versions.
- Repair or supervision mutates user intent instead of routing to Draft.

### Regulatory / Compliance Context

No formal building-code compliance is claimed. Generated IFC is a research
artifact and must not be represented as a code-compliant construction document.

## 2. Framework Decision

**Selected Framework:** Conditional. Start with native text2IFC orchestrator +
OpenAI Python SDK provider. Use OpenAI Agents SDK only after Wave 0 proves it
works with Mimo Chat Completions and preserves evidence.

**Version:** `openai-agents==0.17.6` in `requirements-phase6.2.txt`; OpenAI
Python SDK comes from that environment.

**Rationale:**

- Mimo OpenAI-compatible Chat Completions is verified locally.
- Mimo Responses API returned 404, so any SDK feature depending on Responses
  API cannot be assumed.
- text2IFC already owns prompt registry, schemas, deterministic gates, compiler,
  report generation, and secret scan. These remain mandatory.
- The SDK may reduce boilerplate for agent roles or handoffs, but only if it
  does not hide required evidence.

**Alternatives Considered:**

| Framework | Decision |
|---|---|
| OpenAI Agents SDK | Candidate; must pass compatibility and trace evidence gates |
| LangGraph | Deferred; stronger state model but more migration work than needed for first CLI |
| CrewAI | Deferred; role abstraction is simple but trace/gate integration would still be custom |
| Raw OpenAI SDK only | Accepted fallback and likely first implementation path |

**Vendor Lock-In Accepted:** Partial. Phase 6.2 uses Mimo provider behavior, but
keeps provider abstraction and deterministic text2IFC gates outside the SDK.

```python
client = OpenAI(base_url=base_url, api_key=api_key)
response = client.chat.completions.create(
    model=model,
    messages=[
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": user_prompt},
    ],
    max_completion_tokens=max_tokens,
    temperature=0,
)
```

### Key Abstractions

| Concept | What It Is | Phase 6.2 Use |
|---|---|---|
| Provider call | One Mimo chat-completion request/response | Preserve raw evidence and parsed text |
| Agent role | Design Brief, Generator, Repair, Audit | Keep role-specific contexts isolated |
| Session | User transcript plus stage state | Persist CLI state and artifacts |
| Gate | Deterministic validation/compile/reopen/report/secret check | Cannot be overridden by model or SDK |
| Report | Generated human review entry point | Summarize all material inputs/outputs |

### Common Pitfalls

1. Assuming Responses API availability because a framework supports it.
2. Treating SDK tracing as enough while losing project-required sidecars.
3. Passing one giant conversation to every role instead of role-specific inputs.
4. Letting structured-output helpers bypass canonical BIM JSON schemas.
5. Printing secrets or private base URLs during CLI diagnostics.

## 4. Implementation Guidance

**Model Configuration:**

- Model from `TEXT2IFC_MIMO_MODEL`.
- API key from `API_KEY`, `MIMO_API_KEY`, or compatible env names.
- Base URL from `OpenAI_BASE_URL` / `OPENAI_BASE_URL`.
- Reject `finish_reason: length` for semantic acceptance.
- Use high enough `max_completion_tokens` for schema-sized responses; record
  exact values in redacted request metadata.

**Core Pattern:**

1. CLI collects initial user request.
2. Session appends a user turn and event.
3. Design Brief call receives original request plus transcript.
4. If questions exist, CLI prints 1-3 questions and appends user answers.
5. Ready Design Brief routes to Generator.
6. Formal candidate passes schema/semantic gates before IFC.
7. Audit receives terminal deterministic state.
8. Report generator builds `report.md` from sidecars.

**State Management:**

- Persist conversation as append-only JSON.
- Persist events as JSONL.
- Persist session summary as `session.json`.
- Persist one trace directory per provider role/attempt.
- Never persist raw `.env` or request headers with credential values.

**Context Window Strategy:**

- Do not pass the full repository to the model.
- Render prompt inputs from structured sidecars: request, transcript, schemas,
  capabilities, examples, and prior diagnostics.
- Preserve renderer input paths/hashes so prompt changes are reviewable.

## 4b. AI Systems Best Practices

### Structured Outputs

The model may be asked for exact JSON, but canonical validators remain the
authority. Parser behavior is bounded: one whole-response outer fence may be
normalized with a diagnostic; arbitrary brace extraction is rejected.

### Prompt Engineering Discipline

Prompt changes require prompt ID/hash changes, live or replay evidence, parsed
outputs, metrics, and report diffs. Examples guide behavior but must not encode
hidden global defaults.

### Async and Streaming

Phase 6.2 may use synchronous CLI calls for simplicity. Streaming can be added
only if events and final response reconstruction remain exact.

### Cost and Latency Budget

Mimo token cost is acceptable for live validation; the project should spend
small live calls to resolve provider uncertainty. Human/assistant context cost
is higher, so report and state summaries should be concise and link to sidecars.

## 5. Evaluation Strategy

| Dimension | Rubric | Measurement |
|---|---|---|
| CLI session correctness | Transcript/events append in order and resume/status are accurate | Code tests |
| Live provider truthfulness | Every live semantic role has response ID, model, finish reason, usage, raw output | Code tests + live smoke |
| Clarification quality | 1-3 Chinese questions, evidence-linked, no hidden defaults | Code tests + human review |
| Schema/contract validity | Formal/Draft discriminators exact; invalid/truncated output blocked | Code tests |
| IFC correctness | Formal output compiles/reopens and passes geometry gates | Code tests + final demo |
| Report completeness | `report.md` links all required sidecars and artifacts | Code tests |
| Secret safety | No keys, provider headers, private URLs, or `.env` content in artifacts | Secret scan |

**Primary Tooling:** pytest plus project artifact verifiers and secret scan.

**Reference Dataset:** Start with 3 CLI scenarios: complete room, clarified
room, unknown-answer Draft. Add more only after the CLI loop is stable.

## 6. Guardrails

| Guardrail | Trigger | Intervention |
|---|---|---|
| Missing live provider evidence | Role lacks response ID/finish reason/raw output | Block live claim |
| Truncated output | `finish_reason == "length"` | Block parse/semantic acceptance |
| Invalid BIM JSON | `validate_v2_document` fails | Route repair/Draft/block; never compile |
| Draft output | Canonical Draft | Write report; no IFC |
| Secret finding | Artifact scan finds credential/private URL | Block completion and remove artifact from acceptance |
| SDK evidence loss | SDK hides required metadata | Reject SDK for acceptance path |

## 7. Production Monitoring

Phase 6.2 is local CLI, not production deployment. It still records:

- live role call counts;
- response finish reasons;
- parse/schema/geometry/report pass rates;
- clarification turns;
- repair route;
- secret-scan results;
- total runtime and token usage when available.
