# Phase 6.2 Specification: Interactive CLI with OpenAI-Compatible Mimo Agent Orchestration

## 1. Purpose

Phase 6.1 proved that real Mimo calls can drive the Design Brief, Generator,
Audit, validation, IFC compilation, geometry gates, and generated report. The
remaining user-facing gap is interaction: the clarification loop still depends
on scripted answer files rather than a human typing in a terminal.

Phase 6.2 turns the Phase 6.1 live pipeline into an observable interactive CLI:

```text
user enters a Chinese building request
  -> CLI starts a durable session
  -> Design Brief Agent asks 1-3 Chinese questions when needed
  -> user answers in the terminal
  -> session transcript and agent contexts are persisted
  -> Generator emits Formal BIM JSON 2.0 or canonical Draft
  -> deterministic gates validate, compile, reopen, and check geometry
  -> Audit Agent reviews without overriding gates
  -> output.ifc, report.md, conversation.json, events.jsonl, and trace sidecars are written
```

The phase also performs a bounded OpenAI Agents SDK feasibility checkpoint
against Mimo's OpenAI-compatible Chat Completions API. The SDK is adopted only
where it preserves trace evidence, prompt registry discipline, and deterministic
gates. If it hides required evidence or relies on unsupported APIs, Phase 6.2
keeps the native orchestrator and OpenAI Python SDK provider path.

## 2. Problem Statement

The current project can run live Mimo workflows, but the user cannot yet
participate naturally:

1. Phase 6.1 accepts scripted answers before the run, so it does not exercise
   a real terminal conversation.
2. The current live runner is case-oriented rather than session-oriented; it
   records traces, but it is not designed for pause/resume or human review of a
   conversation session.
3. Multi-agent context is logically separated, but the CLI boundary does not
   yet make agent inputs, outputs, and handoffs easy for a user to inspect.
4. Mimo's OpenAI-compatible API is reachable, but `POST /v1/responses` returned
   404 in the local smoke test. Any framework that assumes Responses API
   availability must be proven before adoption.
5. A successful SDK call is not enough. The system must retain provider
   response IDs, finish reasons, usage, raw text, parsed JSON, prompt hashes,
   event logs, deterministic gate results, report generation evidence, and
   secret-scan results.

## 3. Goal

Build a Chinese-first interactive CLI that lets a user participate in the
multi-turn text2IFC workflow, persists every material input/output, and produces
a real IFC2X3 artifact and generated run report from a real Mimo-backed
session.

## 4. Requirements

### R1. OpenAI-compatible Mimo compatibility checkpoint

- **Current:** `docs/reference/mimo-openai-api.md` records that raw HTTP and
  the OpenAI Python SDK can call Mimo Chat Completions, while `/v1/responses`
  returned 404. `openai-agents` is installed only in the local `.venv`.
- **Target:** Phase 6.2 has an explicit compatibility result for OpenAI SDK and
  OpenAI Agents SDK paths, including chat completions, streaming or
  non-streaming behavior, tool/function or structured-output support when
  relevant, finish-reason mapping, and trace metadata availability.
- **Acceptance:** A machine-readable compatibility report states
  `adopt_agents_sdk`, `use_native_orchestrator`, or `blocked`, with exact
  redacted evidence. A framework path is not used for live acceptance unless it
  preserves required trace evidence.

### R2. Durable interactive CLI session

- **Current:** Live Phase 6.1 runs are invoked as fixed cases and can consume
  scripted answer files.
- **Target:** A CLI command starts a session, reads request and answer turns
  from stdin, prints stage progress, supports safe `help`, `status`, and
  `quit` commands, and persists transcript, events, session state, and artifact
  paths as append-only records.
- **Acceptance:** Focused tests cover session creation, transcript append,
  status reporting, quit behavior, event ordering, and artifact path handling.
  A scripted-stdin smoke can reproduce the same CLI path without bypassing CLI
  logic.

### R3. Chinese-first Design Brief interaction

- **Current:** Phase 6.1 can ask real Mimo clarification questions, but the
  human answers are prewritten in sidecars.
- **Target:** The Design Brief Agent receives the current transcript and writes
  known facts, missing facts, ambiguities, unsupported intent, readiness status,
  and one to three Chinese clarification questions. The user answers in the
  CLI, and each answer triggers a new real Design Brief call with full history.
- **Acceptance:** A live or scripted-stdin run demonstrates at least one
  clarification turn. The trace shows the original request, question, user
  answer, rerendered Design Brief prompt/request/raw response/parsed output,
  and final `ready` or canonical Draft status.

### R4. Isolated multi-agent orchestration to IFC

- **Current:** Agent roles and deterministic gates exist, but Phase 6.2 has no
  CLI entry that executes them as a user-facing session.
- **Target:** Design Brief, Generator, conditional Repair, and Audit use
  isolated role-specific contexts. The Generator emits only Formal BIM JSON 2.0
  or canonical Draft. Formal output must pass `validate_v2_document` before IFC
  compilation; Draft never compiles.
- **Acceptance:** The accepted Formal CLI demo validates BIM JSON 2.0, compiles
  IFC2X3, reopens the file, passes supported geometry/relationship/structure
  gates, and writes `dataset/processed/agent-demo/phase6.2-interactive-cli/output.ifc`.

### R5. Generated one-file human review report

- **Current:** Phase 6.1 report generation exists for live case directories.
- **Target:** Every Phase 6.2 CLI run writes `report.md` generated from actual
  trace sidecars. It is the human-review entry point and includes original
  input, transcript, Design Brief, prompt references, raw response references,
  parsed BIM JSON or Draft, validation feedback, geometry feedback,
  failure/repair route, Audit result, metrics, provider metadata, and final
  artifact paths.
- **Acceptance:** Report completeness tests fail if a required section or link
  is missing. Hand-written or hard-coded reports do not count.

### R6. Truthful live evidence and safety boundary

- **Current:** Phase 6.1 already forbids fake-provider acceptance, but Phase
  6.2 adds SDK/framework and CLI interaction claims.
- **Target:** Real-provider claims require real Mimo response IDs, finish
  reasons, usage, and raw output evidence. Fake/file/replay providers remain
  unit-test tools only. Credentials, provider URLs, headers, and `.env`
  contents never enter prompts, traces, reports, commits, or final answers.
- **Acceptance:** The final verification includes artifact secret scan, fake vs
  live evidence classification, finish-reason blocking for truncated responses,
  and a requirement coverage check for CLI-01 through CLI-06.

## 5. Boundaries

### In scope

- Local `.venv` usage for Phase 6.2-only dependencies.
- OpenAI-compatible Mimo provider path using environment variables.
- OpenAI Agents SDK feasibility testing and a documented adoption/rejection
  decision.
- Interactive terminal CLI for Chinese-first clarification.
- Session persistence: transcript, events, state, trace manifest, artifact
  paths, and prompt/provider evidence.
- Role-isolated Design Brief, Generator, conditional Repair, and Audit calls.
- Deterministic validation, compiler, reopen, geometry, report, and secret
  gates.
- Final CLI demo artifacts under
  `dataset/processed/agent-demo/phase6.2-interactive-cli/`.

### Out of scope

- Public API service or web UI; these remain later deployment ergonomics.
- Fine-tuning, RAG expansion, or broad data generation.
- Source-equivalent BIMNet geometry fidelity beyond the already-supported
  Phase 4 gates.
- Full fallback/default policy for every unknown answer. Phase 6.2 records
  Draft behavior where facts are unknown, but its priority is the observable
  live CLI happy path and one unknown-answer route.
- Letting a framework agent bypass text2IFC prompt registry, schemas, compiler,
  gates, artifact report, or secret scan.

## 7. Acceptance Scenarios

### A. Interactive clarified room to IFC

The user enters an incomplete Chinese room request. The Design Brief Agent asks
one to three Chinese questions. The user answers wall thickness or another
needed fact in the CLI. The session reaches Formal BIM JSON 2.0, compiles and
reopens IFC2X3, passes geometry gates, runs Audit, and writes final artifacts.

### B. Complete room with no clarification

A sufficiently complete request completes without extra questions. The trace
records `no_clarification_needed`, isolated role calls, deterministic gates,
and final `output.ifc`.

### C. Unknown answer to Draft

When the user says they do not know a required fact, the CLI reaches canonical
Draft, writes report and trace evidence, and writes no IFC.

### D. SDK incompatibility is not workflow failure

If OpenAI Agents SDK cannot preserve trace metadata or depends on unsupported
Responses API behavior, the compatibility report records rejection and the
native OpenAI SDK orchestrator remains the implementation path.

### E. Truncated or malformed provider output blocks

A provider response with `finish_reason: length`, unknown discriminator,
multiple JSON objects, prose outside a whole-response fence, or missing raw
metadata is blocked before semantic acceptance.
