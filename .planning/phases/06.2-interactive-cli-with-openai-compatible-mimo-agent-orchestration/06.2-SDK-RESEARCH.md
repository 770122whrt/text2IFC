# Phase 6.2 SDK Research: OpenAI Agents SDK with Mimo

Status: pre-implementation checkpoint
Date: 2026-06-24
Installed package: `openai-agents==0.17.6`, `openai==2.43.0`

## Purpose

This document is written before live Phase 6.2 compatibility interpretation.
It defines what the OpenAI Agents SDK can help with, what text2IFC must still
own, and what evidence is required before the SDK can be used in the accepted
interactive CLI path.

## Confirmed SDK Surface

The installed package exposes these relevant objects:

- `Agent`
- `Runner`
- `RunConfig`
- `ModelSettings`
- `OpenAIProvider`
- `OpenAIChatCompletionsModel`
- `OpenAIResponsesModel`
- `SQLiteSession`

The official documentation describes the SDK as a framework for multi-agent
workflows with agents, handoffs, tools, guardrails, sessions, tracing, and
streaming. The SDK supports both OpenAI Responses and Chat Completions model
paths. The docs recommend Responses for most OpenAI-only apps, but explicitly
document `OpenAIChatCompletionsModel` for Chat Completions endpoints.

## Fit for text2IFC

### Useful SDK Concepts

| SDK concept | Possible Phase 6.2 use | Acceptance caveat |
|---|---|---|
| Agent | Represent Design Brief, Generator, Repair, and Audit roles | Role prompts must still come from text2IFC prompt registry |
| Handoffs | Possible later abstraction for role transfer | Phase 6.2 already has deterministic routing and should not let the model choose compiler gates |
| Guardrails | Possible wrapper for output contract checks | Canonical JSON Schema validators remain the authority |
| Sessions | Inspiration for conversational memory | text2IFC requires its own shared SQLite DB with `session_id` / `session_hash` and query/export APIs |
| Tracing | Useful debugging surface | SDK tracing cannot replace project DB rows, raw provider evidence, report generation, or secret scan |
| Streaming | Useful if complete metadata is preserved | Non-streaming is acceptable for Phase 6.2 if metadata is complete |

### What text2IFC Must Still Own

- Prompt registry IDs and hashes.
- Renderer inputs and prompt templates.
- Shared Phase 6.2 session DB.
- Mimo request/response evidence capture.
- Response ID, model, finish reason, usage, raw text, parsed JSON, and
  evidence-class labels.
- Formal BIM JSON 2.0 and Draft validation.
- IFC compilation, reopen checks, geometry gates, and relationship gates.
- Generated `report.md` from DB records plus linked artifacts.
- Artifact secret scan.

## Mimo Compatibility Risks

Mimo OpenAI-compatible Chat Completions is locally documented and previously
smoked. Raw `/v1/responses` returned 404, so any SDK path requiring Responses
API cannot be accepted for Phase 6.2.

The SDK can be configured to use Chat Completions through:

- `set_default_openai_api("chat_completions")`, or
- `OpenAIProvider(use_responses=False, ...)`, or
- a direct `OpenAIChatCompletionsModel(model=..., openai_client=AsyncOpenAI(...))`.

However, local source inspection of `OpenAIChatCompletionsModel.get_response`
shows an important evidence gap:

- It reads `response.id` and attaches it to output item provider data.
- It returns `ModelResponse(response_id=None)` for the Chat Completions path.
- It records usage in the SDK `Usage` object.
- It does not expose `choices[0].finish_reason` as a first-class final result.

Therefore, even if the SDK can call Mimo successfully, Phase 6.2 still needs a
native OpenAI-compatible provider adapter to capture exact response ID,
finish reason, raw response, and request metadata for acceptance evidence.

## Adoption Criteria

The SDK may be used in the accepted CLI path only if live or replay evidence
proves all of the following:

1. It calls Mimo through Chat Completions, not through an unavailable Responses
   endpoint.
2. It preserves or lets text2IFC recover response ID, model, finish reason,
   usage, raw text, and redacted request metadata.
3. It does not export traces containing secrets, private provider URLs, or raw
   `.env` values.
4. It does not bypass prompt registry rendering.
5. It does not bypass BIM JSON schema validation, Draft routing, compiler,
   reopen, geometry, report, or secret gates.

## Limited-use Criteria

Use `limited_sdk` when the SDK can successfully call Mimo and represent
role-level concepts, but cannot provide all acceptance evidence directly. In
that case:

- text2IFC keeps the native OpenAI-compatible provider as the acceptance call
  path;
- SDK usage, if any, is limited to non-acceptance experiments or future
  abstractions;
- the compatibility report must state which metadata the SDK hides or rewrites.

## Rejection Criteria

Use `native_orchestrator` when any of these are true:

- SDK call requires `/v1/responses`.
- SDK call fails against the documented Mimo Chat Completions endpoint.
- SDK output hides finish reason or response ID in a way text2IFC cannot
  recover reliably.
- SDK tracing or logging risks leaking secrets.
- SDK structured-output or tool features diverge from Mimo behavior.

## Initial Recommendation Before Live Smoke

Start Wave 0 implementation with a native `openai_compat.py` provider adapter
that directly calls `client.chat.completions.create(...)` and records exact
redacted evidence. Run an Agents SDK feasibility smoke separately and classify
the SDK as `adopt_agents_sdk`, `limited_sdk`, or `native_orchestrator`.

Based on documentation and local source inspection, the likely decision is
`limited_sdk` or `native_orchestrator`, not full adoption, unless the live smoke
proves an evidence-complete path.
