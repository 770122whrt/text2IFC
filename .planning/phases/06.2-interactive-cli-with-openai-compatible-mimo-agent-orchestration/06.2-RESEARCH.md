## Confirmed Local Facts

- Mimo OpenAI-compatible `POST /v1/chat/completions` succeeded with HTTP 200.
- The response shape follows OpenAI chat completions:
  `id`, `object: chat.completion`, `model`, `choices[].finish_reason`,
  `choices[].message.content`, and `usage`.
- The OpenAI Python SDK can call Mimo with `OpenAI(base_url=..., api_key=...)`
  and `client.chat.completions.create(...)`.
- A too-small token budget produced `finish_reason: length`, proving that
  finish-reason gating is required.
- Raw HTTP `POST /v1/responses` returned 404, so Responses API availability is
  not assumed.
- `openai-agents==0.17.6` is installed in the local `.venv` for this worktree.
  It is not a project runtime dependency yet.

## Architecture Implications

### 1. Native orchestrator remains the safe baseline

The existing text2IFC pipeline already has prompt registry, schema validators,
Formal/Draft routing, compiler, geometry gates, report generation, and secret
scan. Any framework must plug into those contracts rather than replacing them.

### 2. Agents SDK is a checkpoint, not a conclusion

OpenAI Agents SDK may help represent agent roles and handoffs, but Phase 6.2
cannot adopt it on reputation alone. The checkpoint must prove:

- it can use Mimo's OpenAI-compatible Chat Completions path;
- it does not require `/v1/responses` for the needed flow;
- it exposes response IDs, finish reasons, usage, and raw text;
- it can coexist with project-side prompt IDs/hashes, shared session DB rows,
  and report artifact references.

If any of those fail, the decision is to use the native orchestrator plus
OpenAI SDK provider calls.

### 3. SDK research must happen before SDK adoption

Wave 0 must produce `06.2-SDK-RESEARCH.md` before compatibility results are
interpreted. That research should answer:

- Which OpenAI Agents SDK primitives matter for text2IFC: agents, handoffs,
  guardrails, tracing, structured output, streaming, and model settings.
- Whether those primitives can run against Mimo's OpenAI-compatible Chat
  Completions path rather than assuming Responses API support.
- Whether the SDK exposes enough raw response evidence for provider IDs,
  finish reasons, usage, raw text, parsed output, and generated reports.
- What text2IFC must continue to own regardless of SDK adoption: prompt
  registry, BIM JSON schemas, deterministic gates, IFC compiler, geometry
  checks, report generation, evidence classes, and secret scan.

The research doc is not the adoption decision. It defines what must be tested
and what evidence is required before the decision.

### 4. CLI requires shared session-store design

The main new system object is not another agent. It is a shared session store
containing many sessions. Each session has `session_id` and `session_hash` and
contains:

- original request;
- user turns;
- agent questions;
- provider calls;
- deterministic gate results;
- output artifacts;
- state transitions.

The shared DB enables history queries, evaluation metrics, resume, and future
API routes. Per-session files should be exports or large payloads linked from
the DB, not the primary evidence store.

### 5. Scripted stdin is necessary for TDD, not sufficient for final UAT

A fully manual CLI is hard to verify in automated tests. Phase 6.2 should build
the CLI so stdin can come from a human or a scripted input stream. The scripted
path must exercise the same code as live interaction; it cannot be a backdoor
that writes `answers.json` before the run.

The final acceptance should additionally include a real-time UAT where Codex
acts as the user and Mimo is the Agent provider. That UAT proves the human
interaction loop, while scripted stdin preserves repeatable regression coverage.

## Recommended Design

```text
run_interactive_cli.py
  -> load Mimo OpenAI-compatible config
  -> start session directory
  -> read request from stdin or --prompt
  -> call Design Brief role
  -> while clarification_required:
       print 1-3 questions
       read answer(s)
       append transcript
       call Design Brief role again
  -> if draft_required:
       write Draft report and stop
  -> call Generator role
  -> deterministic gates
  -> optional one repair attempt if eligible
  -> deterministic gates again
  -> call Audit role
  -> write DB-backed session rows
  -> generate report.md from DB rows and artifact refs
  -> print final artifact paths
```

## Open Risks

- OpenAI Agents SDK may not expose enough raw response metadata for acceptance
  evidence.
- Mimo may support function calling or structured output differently from
  OpenAI. This must be verified before use.
- Unicode handling must preserve Chinese user input through stdin, traces, and
  prompts.
- Long schema prompts may need higher token budgets than simple smoke tests.
- Interactive sessions can be interrupted; the first implementation should
  preserve partial trace state even on user quit.
- SQLite schema design must avoid mixing turns, agent calls, and artifacts
  across session hashes.

## Research Conclusion

Phase 6.2 should first prove provider/framework compatibility, then build a
shared DB-backed CLI on the existing Phase 6.1 live pipeline. The product win is
not a new model or a new framework; it is making the user part of a queryable,
resumable, exportable multi-agent loop while keeping every claim evidence-backed.
