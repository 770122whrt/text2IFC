# IFC Repair 对比实验：指标与独立评分规范

> 更新：2026-09-29｜版本：v0.2｜文档类型：评测参考与实现合同。
> 范围：20 个 IFC／20 个任务／四组，其中 2–4 个任务需要澄清。总体运行见[实验计划](plan.md)。
> 同步状态：2026-09-28 已合并至仓库原路径；指标仍为实施合同，不是已实现评分器或真实成绩。
> 本文是指标定义的唯一维护位置，不重定义生产 Evaluation 或历史 Proof。

2026-09-29 [代码核对](development-readiness.md)确认：现有 benchmark 依赖 ChangeSet／application record；生产 IFC validator 的通过含义为相对 D 无新增诊断，且 `express_rules=False`。后续独立评分须另建入口与固定规则检查，不能直接复用其 `passed` 作为本文最终成绩。可复用原语与基本自检建议见该核对文档；本次不改指标公式、历史 policy 或正式分母。

同日题包审阅补充：开发与正式输入D的制题准入要求本地schema＋EXPRESS零诊断，不能仅“无新增错误”。报告按S1单目标、S2双目标及S3三目标起的规模分层，另列同类／混合组合；这些是输入分组，不改变构件／关系分母。普通门的可选开向不自动成为必要澄清事实；优先使用位置、楼层、不可推导必需尺寸等真实缺项，当前门开发题不计入澄清分母。

## 1. 指标体系

数量、完整构件、应修关系和整项任务分别评价；IFC 校验与非目标保全检查可交付性，token 与耗时描述代价。各指标不加权混成一个总分。

| 指标 | 字段 | 问题 |
|---|---|---|
| 数量完成率 | `quantity_completion` | 需要补回的各类构件在数量上补了多少？ |
| 构件修复完成率 | `component_completion` | 多少目标构件完整满足实际修复要求？ |
| 关系修复完成率 | `relation_completion` | 应该修复的关系中，多少正确恢复？ |
| 严格任务成功率 | `task_success` | 最终修复产物是否满足全部任务和保持条件？ |
| IFC 校验通过率 | `ifc_validation_pass` | 文件是否通过固定校验器与规则设置？ |
| 附带错误 | `collateral_changes` | 是否出现不允许的额外修改、删除或新增？ |
| 资源 | `usage`、时间字段、`cost` | 整个任务含失败、重试和继续的代价是多少？ |
| 澄清过程 | `clarification` | 是否取得必要事实、用了多少交互、之后是否完成？ |

关系指标严格采用“正确修复的关系／应该修复的关系”，不新增 Precision／Recall／F1 为主指标。推理记录用于事后分析，不直接作为正确性分数。

v0.2 保留 v0.1 的产物主指标含义，另列澄清行为和完整交互结果：不得悄悄把“没问但碰巧做对”记成澄清成功，也不得把“问对但没修好”记成修复成功。

## 2. 输入、任务真值与人工审查

### 2.1 三种模型角色

`G_i` 是第 i 题事前认可的参考状态，`D_i` 是冻结的损坏输入，`R_ia` 是方法 a 的唯一正式提交。`TaskSpec_i` 是事前编写、人工认可的评分合同，不是模型自生成的 RepairIntent 或 ChangeSet。

被测系统可以修改它自己的 `model.ifc` 工作副本；冻结 D 始终保留在实验端。评分不能拿已修改的副本当 D，否则实际变化会被抹掉。

| 被测运行侧 | 人工答复侧 | 独立评估／任务审查侧 |
|---|---|---|
| 中性请求、工作副本、普通工具与对本题问题的回答 | 经人工认可的有限用户事实、实际问题和回答 | G、冻结 D、损坏记录、评分合同、最终 R、真实审查记录 |

答复侧不在运行后通过 G／删除脚本推导答案；仅按事前确认的用户意图和公开可确认信息回复被问到的内容。未问到的补充事实不提前送入模型。

### 2.2 必须先人工确认的内容

全部 20 题都要审查 G、D、公开请求和损坏说明，确认目标、受损关系分母、意外损坏、允许连带变化、可接受结果及原有问题。澄清题还应证明初始信息不足且不能从当前 IFC 唯一补齐，并审核用户答复卡。

程序生成的任务默认 `pending_human_review`；自动校验通过不能替代人工接受。任务发生影响目标、分母或答复事实的修订后，受影响任务要重新审查，不能沿用旧接受状态。

### 2.3 评分独立性

评分器读取实际 IFC，不能采用被测模型自报成功、它选出的目标集合或自报数量作为真值。四组使用相同的 TaskSpec、匹配规则、单位、容差和检查器；B 原生报告仅供诊断。

可以复用现有几何、语义、关系和保全 helper，但外部组不需要提交本项目 ChangeSet、application record 或 Proof schema。公共实验评分不能把 B 原生拒绝发布的文件改称正式发布。

## 3. 构件计数与对象匹配

### 3.1 主目标是什么

主目标是用户要求修复的工程对象，如门、窗、梁、柱或明确作为目标的洞口。不能将坐标点、形状表示、Placement、OwnerHistory 等底层实体当成多个构件；类型定义也不计作构件实例。

补一扇窗及其必要洞口，默认以窗作为主目标，洞口与连接进入完整构件的检查；只有用户明确把洞口列为独立目标时才另计。纯属性题以被修改的现存实例作为目标，不以每个字段增加构件数量。

### 3.2 一对一匹配

存活对象优先按稳定 GlobalId 对应；新增对象按事前固定的角色、类别、粗目标区域及位置规则作一对一对应。该步骤只决定“哪一个输出对象接受哪项检查”，不能为了得高分而选择最接近待评分属性的对象。

粗候选区域与严格几何容差分开。被评分的关系、尺寸和属性不得作为事后挑选最有利匹配的依据；位置参与定位时应记录匹配距离，并用单独的严格位置检查评价。可互换目标必须预先定义等价组。

匹配歧义、一个对象匹配多个目标、重复新增都要记录。新 GUID 不使合法新增对象失败；原存对象无理由整体重建／换身份由保全另行评价。

无几何的新增 occurrence 可以计入纯数量，但不能当作完整几何构件。无法匹配的应修关系不算恢复，不能因为它缺少对象就缩小关系分母。

## 4. 数量完成率

对第 i 题、方法 a、应补类别 k，`n_ik` 为要求补回数，`a_iak` 为从冻结 D 到 R 中实际新建的该类实例数。按类型分别封顶：

```text
Q_ia = sum_k min(a_iak, n_ik) / sum_k n_ik
```

要求 2 扇窗、1 扇门，实际新建 3 扇窗、没有门，则 Q＝2/3。要求 3 扇窗且新增 3 个窗实例，数量可以为 3/3，即使某扇位置或关系有错；质量由其他指标反映。

保存 `required_by_class`、`added_by_class`、`credited_by_class`、`excess_by_class`，重复 GUID 不重复计数并进入异常检查。不要只用全楼净数量差：删旧窗又造新窗可能掩盖附带破坏。

纯属性或关系修改且没有新增要求时，该指标事前标记不适用，分母为零、值为 null，不记满分。超额构件和原存对象删除不会被数量封顶规则“豁免”，仍影响附带错误和整项任务。

## 5. 构件修复完成率

令 `Req_it` 为目标构件 t 的必需检查，包括任务实际要求的类别、几何／位置、属性、支撑对象及关系。没有要求的隐藏材料或性能属性不能事后加入义务。

```text
complete_iat = 1，当且仅当目标唯一匹配且 Req_it 全部通过；否则为 0
C_ia = sum_t complete_iat / number_of_target_components_i
```

要求 3 扇窗，2 扇完整正确、1 扇宽度错误，则 C＝2/3。对同一门恢复 3 个字段，其中 2 个正确，则该门尚未完整完成，C＝0/1；字段细节保留在检查记录中。

必需检查不可评估时，不得认定完整构件成功。先区分是提交内容无法满足要求，还是评分器出错；后者按 §10 处理，不直接计成模型写错。

关系指标与构件完整性会重合：前者解释结构关系方面的缺项，后者评价单个工程对象是否完整修好；二者不相加。

## 6. 关系修复完成率

### 6.1 分母与规范化

`E_i_required` 是人工审查并通过 G–D 核对的必需关系修复集合，包括受损、删除或随补回目标必须重新建立的连接。原本正确、无需修复的整栋关系不加入该分母。

```text
Rel_ia = 正确恢复的必需关系数 / |E_i_required|
```

关系按语义连接计数，不按 IFC 关系记录条数计数。同一 containment 实体关联三个构件，应视为三个“构件属于楼层”的连接，避免序列化组织方式改变分数。

示例规范化连接：

```text
(window_1, fills, opening_1)
(opening_1, voids, host_wall_1)
(window_1, contained_in, storey_2)
(window_1, typed_by, reference_type_1)
```

最后一条仅在本题要求且确有恢复义务时计入。关系类型、方向、两端及作用域均正确才得分；几何上贴着墙不代替真实宿主关系。

### 6.2 缺失、额外连接与不适用

应恢复 6 条，正确恢复 4 条，就是 4/6。错误连接不能充当正确连接；重复记录不能重复加分。所有必需连接正确但多建非法连接时，关系完成可以为 100%，但额外错误仍阻断整任务成功。

保存 required、restored、missing_or_wrong、extra_invalid、duplicate 的具体连接。没有关系修复义务则不适用；某方法没有输出不会改变题目原有义务，不得把其分母删掉。

## 7. IFC 校验通过率

### 7.1 重开与规则检查的分工

这里评价“最终文件是否通过固定 IFC 规则检查”，不只评价解析器能否打开。记录从磁盘重开、IFC2X3 Schema、数据约束验证与所选择 EXPRESS 规则的实际结果；几何生成和任务要求检查另行执行。

v0.1 引用的 IfcOpenShell 命令形态如下，实施者必须在锁定版本上验证参数、错误输出和退出行为；本轮没有执行该命令：

```bash
python -m ifcopenshell.validate output/repaired.ifc --rules --json
```

输出路径按实际提交改写。不要仅凭退出码、空 stdout 或 `open()` 成功判定全部检查通过。官方资料入口保留在 §16，当前版本行为由实现时核对。

### 7.2 通过条件

`ifc_validation_pass=true` 要求：正式文件存在、解析完成、正确 Schema、约定验证过程执行完整且无阻断错误。warning 与 error 分开登记；任何规则例外在运行前固定并对四组一致应用。

无正式提交或提交因内容错误不可解析时，校验不通过。评分器程序、依赖或规则引擎异常应标为不可评估，不与正常的校验失败混淆。

尽量选择在相同规则下通过的 G。原有问题和 D 的预期损坏先登记，不要求被测系统顺带解决未声明的全部历史缺陷。标准规则通过不等于满足用户项目要求，也不写成完整 IFC 标准认证。

需要具备形状的目标构件还应实际生成几何并核对位置／尺寸等，属于构件与整任务评价；单独 validator 通过不为无几何目标加满分。

## 8. 非目标保全与附带错误

每题定义允许变化的对象和字段、必要支撑对象、宿主几何及关系变化。对整个源模型，范围外可检查的身份、几何、属性及语义关系按保全合同检查，不只检查目标附近。

给墙增洞允许对应开孔变化，不等于允许随意更改整墙厚度、位置和材料。无语义影响的 STEP 重排或合法新增 GUID 不属于破坏；源对象的非授权删除、重建、属性漂移及多余对象则要检查。

对象级受影响数量取并集，事实／关系级错误另列，避免一个对象三处变化算成三个对象。报告“有已确认附带错误的任务数／20”时，同时报告“保全可评估提交数／20”，不能让无产物任务看起来已经保全。

目标错宿主是目标修复错误；若同时破坏无关对象或关系，另记附带错误。归因可以区分，整任务不因此通过。

保全覆盖、排除规则和不可评估对象须保留。必需保全项目不可评估时不得声称全局保全通过；不能以很高的全楼保留比例隐藏误删一个关键对象。

## 9. 严格任务成功与交互成功

### 9.1 保持原产物主指标

设 F 为预算与提交协议内的正式结果，V 为 IFC 校验通过，C_all 为全部目标构件完整完成，Rel_all 为全部适用关系恢复，P 为非目标保全及无非法额外变化，Gates 为其他事前认可的必需检查：

```text
S_ia = F_ia AND V_ia AND C_all_ia AND Rel_all_ia AND P_ia AND Gates_ia
TaskSuccessRate_a = sum_i S_ia / 20
```

没有关系修复要求时 Rel_all 不额外增加义务，关系指标仍显示不适用。外部 F 不要求本项目内部 schema；B 仍只能提交原生正式发布的结果。

本指标表示最终修复结果成功，不把提问本身强塞进所有任务的成功定义。与用户补充选择相关的目标以事前意图及被认可的答复事实为准，不能在看到结果后选择一个有利参考。

### 9.2 澄清案例单列完整交互

对于事前定义的 2–4 个澄清题，另记录 `clarification_success` 与 `interactive_success`：

```text
interactive_success = clarification_success AND task_success
```

没问而碰巧猜对，可以如实获得产物分，但 clarification_success 为 false，不能宣称“成功澄清”。问到必要信息但修复失败，clarification_success 可以 true，interactive_success 仍 false。

同时报告信息充分题与澄清题切片，不把仅在实际提问的任务上取分母，掩盖本应提问却没有提问的情况。样本仅 2–4 题，适合逐案展示，不据此宣称一般交互优势。

## 10. 等待、失败、不适用与不可评估

适用性事前定义，各指标保存 numerator、denominator、value、status。等待用户是中间状态，不是无输出失败。

| 情况 | 适用的数量／构件／关系 | IFC 校验 | 任务 | 保全 |
|---|---|---|---|---|
| 正式提交，可解析 | 按实际计算 | 实际检查 | 按 §9 | 实际检查 |
| `awaiting_user`，交互未关闭 | `pending`，不先填 0 | `pending` | `pending` | `pending` |
| 澄清后继续 | 延续同题，最终再评分 | 最终检查 | 一个任务单元 | 最终检查 |
| 正式结束但无提交、预算耗尽、取消或预定等待到期 | 0／原适用分母 | 不通过，注明无提交 | false | 不可评估 |
| IFC 因内容错误无法解析 | 0／原适用分母 | false | false | 不可评估 |
| 可解析但规则失败 | 仍计算可得部分完成 | false | false | 可算项照常 |
| 指标事前不适用 | null，不纳入该指标适用题均值 | 不影响其他项 | 按其他要求 | 按合同 |
| 评分程序／依赖异常 | null，`not_evaluable` | 未确认通过 | null | 不可评估 |
| 尚未执行 | `not_run` | `not_run` | `not_run` | `not_run` |

所有任务和方法行保留。存在 pending 或评分故障时，不把未完成表伪装成完整的成功率排名；可报告“已确认成功 x/20，另有 y 个待完成／不可评估”。

超时遗留文件、B 的 staging 候选等可用于另列诊断，不选择最佳者代替唯一正式结果。评分代码修复后重算冻结结果；计分语义变化时所有组使用同版重算。

## 11. 澄清的记录与判定

### 11.1 制题时冻结必要事实

每个澄清题定义 `required_user_facts`，说明缺失项为什么必要、为什么当前 IFC 无法唯一提供，以及哪些问题可以取得这些事实。它们来自预先用户意图，不从最终模型表现倒推。

所有 20 题均有普通问答通道，不给公开包添加 `clarification_required` 标签。文件、工具反馈、启动语句不得提示哪题必须问；该标签只存在制题／评估侧。

### 11.2 按卡回答，不帮模型解题

问题由被测系统提出。人工按答复卡只回复所问事实，相同事实对四组相同。不能额外附加修复步骤、代码、隐藏对象身份或私有比较结果。适配器只转换消息／原生候选格式，不能自主补问题或代用户选目标。

泛泛请求“请把全部缺失信息都给我”不等于命中所有必要事实；由事前答复规则说明允许返回的信息粒度。规则在四组间一致，不因某组问得笼统就给它全套答案。

### 11.3 最少需要的交互字段

| 字段 | 含义 |
|---|---|
| `required_fact_count` | 本题必要用户事实数 |
| `requested_required_fact_ids` | 实际问到哪些必要事实 |
| `answered_fact_ids` | 实际提供了哪些被问到的事实 |
| `turns` | 往返轮次，同一问题多事实仍按实际交互记 |
| `unnecessary_questions` | 对已有明确事实的重复或无关问题，保留依据 |
| `clarification_success` | 必要信息已由合格交互取得，而非私有答案自动注入 |
| `unconfirmed_commitments` | 没获得所需事实前已作出的关键选择及证据 |
| `task_success`、`interactive_success` | 产物成功与完整交互成功，分别保存 |

“不必要问题”和“未确认就做出决定”的判定用原请求、D、问答和操作轨迹，而不是只看推理自述。已建立推理记录可辅助定位，不是行为事实的替代。

## 12. Token、动态预算、时间与费用

### 12.1 整个任务累计

```text
TotalTokens_ia = sum_j (InputTokens_j + OutputTokens_j)
```

j 包含本题全部根调用、子 Agent、摘要、纠正及实际计费用量的失败／重试。保留原始 usage，再规范为 input、output、cached_input、reasoning_output 等；缓存和 reasoning 若是总数的子集，不二次相加。

区分 per_request 与 cumulative 用量，按可核对请求 ID 去重。SDK 通知、原生日志和账本反复出现同一请求只记一次；真正重试是新的请求。没有返回 usage 的请求记未知，不自动为零。

`usage_coverage` 为 complete／partial／unavailable，并说明缺失来源。推理文本缺失不等于 token 为零，输出 token 中可能有未展示部分；严格依实际 Provider 的用量语义处理。

### 12.2 任务预算记录

每题保存 budget_profile、初始 token／活动时间上限、增加规则、每次增加的触发理由与最大累计额度。四组同题规则一致，不同题可以不同。调整不得读取私有评分或根据某组胜负；具体数值在正式输出揭示前确定。

澄清后的新 turn、运行时重启和路径变化均不重置本题账本。任务上限不是模型上下文窗口，也不是每次请求 max_tokens；不得混为一个参数。

### 12.3 时间分解

| 字段 | 定义 |
|---|---|
| `prepare_s` | 创建工作副本、准备环境等，不含被测方法执行 |
| `active_elapsed_s` | 实际活动执行区间之和，含方法启动、索引、API 等待、工具、自检和摘要 |
| `human_wait_s` | 已明确暂停执行、等待人工回复的区间之和 |
| `wall_elapsed_s` | 从被测方法开始到终止／冻结的总历时，包含人工等待 |
| `evaluation_s` | 最终外部评分耗时 |

等待期间有子进程继续工作或请求模型时，该活动不能从计时和用量里消失。建议统一调度停止活动后再计纯人工等待，并在异常情况下保存重叠区间而非强行做错误减法。

主效率表使用全部任务的累计 token 和活动耗时，人工等待和总历时另列。成功子集效率可补充，不能只挑成功案例计算代价。

费用保留货币、实际账单／估计标识、价格版本和可观察覆盖；不同模型 token 更少不自动等于费用更低。开发调用、正式任务及重跑基础设施开销分别登记，均不抹掉。

## 13. DeepSeek 返回推理的保存与分析

保存接口实际返回的推理字段／块、最终文本、工具调用、结果及必要协议元数据。A/B/D 中的 DeepSeek 调用都核对，包括能获得的失败、重试、压缩与子 Agent；不只截取成功最后一轮。

建议字段：request_id、run_id、native_session_id、parent_session_id、stage、attempt、model_requested、model_observed、wire_protocol、reasoning_ref、reasoning_status、finish_reason、usage、时间戳。原始载荷与规范化摘要建立引用，避免重复存几份完整内容。

reasoning_status 为 available、empty、not_returned、truncated、redacted；状态本身不能改变模型分数。必要的工具往返推理字段按实际协议保留，日志脱敏副本不能反向破坏在线上下文。

不在任务增加“请展示完整思考”，不尝试恢复隐藏状态，不把后写的解释当原始推理。原始记录在受控分析区保存，公开报告只选必要且脱敏的片段；认证信息不保留。禁止跨题、跨组复用这些轨迹作为经验。

分析时把推理、动作与实际 IFC 对齐。模型说“已经连好宿主”不能证明关系正确；推理文本描述一个原因也不能单独证明它导致失败。

## 14. 汇总与不确定性

Q/C/Rel 先按题计算，再对事前适用题取宏平均；适用但无正式产物仍为零。总分子／总分母作为辅助微平均，不能替换宏平均或把一个批量题当作多个独立模型。

主表任务和 IFC 校验分母为 20，显示 x/20 和百分比。信息充分与澄清切片另列，交互成功以事前确定的澄清任务数为分母。pending／评分故障按 §10 说明，不丢行。

保存 B–A、C–A、B–D 的逐题配对和共同成功／共同失败／单方成功。按真实场景族解释独立性，不把同建筑导出版本当独立样本。

沿用 v0.1 的不确定性报告安排：独立场景假设合理时可报告任务成功率的 Wilson 95% 区间，配对差异使用按场景族重采样的区间；参数在评分前固定。20 题且每方法一次运行不能估计重复运行可靠性，不因区间计算而扩大结论。

## 15. 评分程序基本自检与容差

### 15.1 基本自检不替代 20 题人审

复用 1–2 个非正式样例和已有测试，构造必要正负输出检查计分程序。不要再建 20 个人工修复结果或第二套大型 benchmark。

| 控制情形 | 应检出的行为 |
|---|---|
| 未修 D | 不因可打开而判成功，受损目标反映缺失 |
| 已核对正确结果 | 适用目标与保持条件通过 |
| 数量齐但尺寸错 | 数量可满、构件部分完成、任务失败 |
| 错宿主／漏连接 | 对应必需关系不记恢复 |
| 值正确但写错实例／字段 | 构件和任务不通过 |
| 目标完成但误删他处 | 保全和任务失败 |
| 重复补建 | 数量封顶、额外变化被检出 |
| 无必需几何 | 数量可得分、构件不能完整完成 |
| 合法新 GUID／STEP 重排 | 不因序列化差异直接拒绝 |
| 等待用户 | 保持 pending，不立即算无输出失败 |
| 问对但没修好／未问碰巧修好 | 交互与产物结果分别记录 |
| 评分器异常 | 标记不可评估，不伪装正常模型失败 |

### 15.2 数值规则先核对再冻结

长度、位置、角度、尺寸、形状比较的单位、算法和容差从适用 Repair 合同核对。既往 IFC2Text 墙体往返的 0.1 mm 不能自动推广为所有 Repair 对象阈值。需要新阈值时用非正式开发样例给出依据再审阅，不根据正式结果放宽。

尚未定义必需阈值的任务不能正式冻结；这属于实施前缺口，不通过“看着差不多”临时评分。
