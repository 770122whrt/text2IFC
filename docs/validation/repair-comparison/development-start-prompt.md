## 4. 已锁定的实验要求：不得自行改回

### 4.1 四组与规模

A：DeepSeek Flash API＋中性通用执行器。
B：同底座 DeepSeek＋本项目现有 Repair Harness。
C：用户指定的 GPT API（当前目标 GPT‑6 Sol）＋与 A 相同的通用执行器；不是日常完整 Codex。
D：按 DeepSeek 官方 Harness 调研和接入；ZCode 只作尚未启用备选，不增加第五组。

20 个源 IFC，每个一个修复任务；四组完整运行共 80 个任务单元。调用、子 Agent、澄清和继续不增加任务数。用户已经确认这些方向，不再询问是否用 API、是否做 20 题、是否使用关系完成比例。

### 4.2 A/C 不提示解题方法

初始用户内容仅为：中性操作句＋四组共用公开请求＋IFC 文件。

不要添加“使用 IfcOpenShell”“先索引”“生成 ChangeSet”“按某个审计流程操作”“你是 BIM 专家”，不附赠 API 教程、few-shot、修复脚本、目标答案、专用 Schema 或私有评分代码。

A/C 可以自行调用 IfcOpenShell、写普通脚本、用 Shell、搜索替换或直接编辑 STEP。可预装固定依赖并允许其自行检查环境，但不通过初始提示主动指路。不要只给 run_python 而禁止直接文本编辑；也不要让它只能一次输出完整 IFC。

工具名称、参数、权限、路径和提交方式可以提供，必须中性、A/C 一致，不夹带修复步骤。B/D 自身固有 Prompt 与工具属于方法，不为了统一输入将其删除。

根目录或生产文档中“不由模型直接写 STEP”的要求仍约束 B；本实验明确允许的 A/C 直接编辑只发生在隔离基线路径，不改 B 的生产合同。

### 4.3 冻结 D 与可写副本分离

被测系统可以编辑当前题可写 IFC 副本。实验端保存未修改的 D，评分比较冻结 D 与最终 R。G、损坏记录、删除 GUID、其他组结果和开发仓库不能进入 A/C/D。

允许最终提交被修改副本或显式另存文件，按中性提交协议选定一个结果。不能使用“已被修改的 model.ifc”充当修复前 D，也不能私自从多个产物挑一个得分最高的。

### 4.4 20 题全部人工审查

每题准备 G、D、共同请求、损坏说明、目标构件／应修关系分母、已有问题、合法替代与保全条件；澄清题另准备受控答复卡。全部 20 题由用户逐一审阅，程序生成材料始终默认 pending_human_review。

评分器是运行后的计分程序，不是另一名修复 Agent。“评分程序基本自检”使用少量已知对错的开发结果检验计分逻辑，不替代 20 题人审，也不要求用户另手修 20 个模型。

### 4.5 20 题内 2–4 个澄清案例

先按 3 个准备，即建议 17 个信息充分＋3 个信息不足；它们包含在 20 题中，与门／窗／梁／柱等操作分类正交。缺少的信息必须必要且无法从当前 IFC 唯一得到，不能把不知道 API 用法当作缺少用户意图。

所有题、所有组均有普通提问渠道；不在公开 prompt、文件名或工具 metadata 中泄露“本题必须澄清”。问题由被测模型提出，适配器只转接；不替模型生成问题。

回答依据事前人工认可的用户答复卡，同事实各组一致，只回答问到的内容，不临时从 G／删除映射找答案，也不顺带教修复方法。B 的候选 token 等仅机械绑定当前公开候选，不从隐藏真值替用户选项。

awaiting_user 是同一任务中间状态。等待、回答、继续保留任务身份、文件、会话和累计用量；不能将 SDK 单轮结束当作任务结束。

### 4.6 DeepSeek 推理保留

A/B/D 保留接口实际返回的推理内容，与 content、工具调用、工具结果、usage 分开，覆盖可获取的失败、重试、摘要和子 Agent。记录 request_id、父会话、阶段、attempt、model、wire protocol、reasoning_ref/status、时间和终态。

不要求额外展示思考，不恢复未返回的隐藏内容，不以推理字数当真实 token；缺失、空、截断和脱敏分别标记。工具调用需要的推理历史字段按实际协议保留，日志整理不能破坏在线上下文。

推理仅用于事后分析，不进入下一题或其他组；密钥与认证头不写入公开记录。

### 4.7 预算按任务动态分配

不再统一固定 128k／900 秒。按模型规模、目标数、操作与几何复杂度等建立任务预算；同题四组上限和增加规则相同，不同题可以不同。

增加预算的触发条件、额度与总上限在正式输出揭示前确定，不依据私有评分或某组快成功而单独加额。澄清和重启不清零用量。

区分 active_elapsed_s、human_wait_s、wall_elapsed_s。只有实际暂停活动等待人工的区间才暂停活动计时；后台仍运行就继续记录。真实开发／正式费用上限需单独授权；旧 IFC2Text 额度不得继承。

### 4.8 指标不改变

保留数量完成率、构件修复完成率、关系修复完成率、严格任务成功率、IFC 校验通过率、附带错误、全任务 token／时间。关系为“正确修复数／应修数”，不用 F1 取代。

独立评分从最终 IFC 与人工认可合同计算；不要求 A/C/D 生成我们的 ChangeSet／application record；不能用 B 自己解析的请求当四组真值。IFC 重开不代替固定规则校验；标准规则不代替几何、关系和用户要求。

澄清行为与产物成绩分开：未问碰巧修对不算澄清成功；问对但没修好不算任务成功。完整交互成功另列。待人工回复不立即计零；最终无输出仍保留原分母。

## 5. 有目的地检查代码和环境

- 是否已经有人实现 A/C 公共工具、DSH 接入、任务预算或实验骨架；有则复用，不平行重写。

环境只读确认 Python／IfcOpenShell、Docker／WSL／可用服务器入口和磁盘；不要输出凭据、安装软件或改系统服务。环境检查失败不重复重试几十次，记录确切错误并继续不受阻的文档工作。

## 7. 开发建议应具体到能执行

优先给出一个范围小的首批里程碑，而不是“一次实现完整 80 次实验”。建议首批围绕任务合同、冻结 D／工作副本、人审卡／答复卡、按任务预算和离线记录骨架；A/C 中性工具与评分基本自检可按依赖安排，DSH 先独立只读调研。
