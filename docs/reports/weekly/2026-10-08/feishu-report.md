## 一、Repair 的技术思路：确定目标、局部修改、核验结果

我们的 Repair 方法分为三个 Part，始终围绕同一个修复目标推进。

**Part A：把用户要求与当前模型对应起来。** 从公开 IFC 中查找目标墙体、保留洞口或参照门窗，核对位置、尺寸和可用属性。需要补充的事实，例如洞底高度，向用户澄清；不根据损伤前模型替用户猜答案。

**Part B：把明确要求转成一组受约束的修改。** 模型提出修改方案，执行系统核对对象与参数后，在 IFC 副本上整体应用。门窗的名义尺寸、洞口几何尺寸、安装位置、类型和材料等分别处理；涉及多个目标时，不能把只完成其中一个的结果当作整个请求完成。

**Part C：以实际 IFC 判断是否完成。** 重新打开结果，检查构件是否存在、位置和尺寸是否正确、墙—洞口—门窗关系是否成立、类型及材料／外观是否符合要求，以及范围外对象是否保持。内部检查决定能否发布；实验再用各组共用的独立评分器评估正式产物。

## 三、四组对比：分别观察模型与执行方式的影响

|组别|请求模型与协议|模型负责什么|Harness 负责什么|
|---|---|---|---|
|A|`deepseek-v4-flash`；Chat Completions|自主读 IFC、选择工具、编写脚本或直接编辑、提问和提交|中性通用工具循环，不替模型选择修复方法|
|B|`deepseek-v4-flash`；Chat Completions|理解需求，结合公共场景查询定位，必要时解析属性，输出 ChangeSet|项目 Repair Harness：精简场景／查询、确定性参数绑定、受约束的原子应用与核验发布|
|C|`gpt-6-sol`；Chat Completions|与 A 相同的自主修复任务|与 A 相同的通用执行器，通过 GPT API 运行；不使用日常 Codex 完整环境或个人技能|
|D|`deepseek-v4-flash`；Messages|在官方原生工具与会话中自主修复|官方完整 DSH `sdk` profile，保留文件／Shell、子 Agent 和压缩；SDK／runtime 固定为 `0.2.0rc1`|

DeepSeek 用于 A、B、D，只有 D 使用官方 DSH；B 是我们的领域 Harness。A–B 比较通用与领域执行方式，A–C 比较相同执行器下的模型差异，B–D 比较两套完整系统。A/B 显式启用 `thinking`，C/D 设置 `reasoning_effort=high`；不同协议参数不视为严格等价，同名服务别名也不能冒充固定权重快照。请求型号、实际返回标识、协议与执行版本分别记录。

同题四组使用相同损坏 IFC、相同自然语言要求和同题预算，在独立工作副本中运行。A/C 不额外获得修复教程，B/D 保留原生方法。发生澄清时继续同一任务，预算和调用累计；正式 IFC 提交后由共用评分器检查。无输出、预算停止和运行错误均保留，不从实验记录中删除。

### 已确定的评审指标

**指标定义已确定，核心独立评分已实现。** 主指标为严格任务成功率，其他指标用于解释结果，不加权合成总分。

|指标|评审含义|
|---|---|
|严格任务成功率|正式提交且全部目标、必需关系、IFC 格式与范围外保全均通过；完整实验每组报告成功题数／20|
|数量完成率|新增门／窗按各类要求分别封顶，再除以应补总数；数量齐全不等于修复正确|
|构件修复完成率|类别、尺寸、实际几何、位置、公开参照／外观及关系全部满足的目标数／应修目标数|
|关系修复完成率|正确恢复的必需语义连接数／冻结的应修关系数；不按 IFC 记录条数计分|
|IFC 校验通过率|结果可重开、schema 正确且固定版 schema＋EXPRESS 检查通过|
|保全与附带错误|非授权修改、删除、重建、多余对象／关系，以及受影响对象数；无产物时保全不可评估|
|澄清与交互成功|3 道澄清题检查必要事实是否问到并获答复；交互成功还要求修复成功，所有题另记问答次数|
|资源代价|整题输入／输出 token、模型调用、工具往返、活动时间、人工等待及总历时；包括可获取的失败、重试、压缩和子 Agent 用量|

尺寸／位置使用冻结的 **1 mm 容差**；0.5 m 仅用于粗匹配。外观由公共参照几何和部件样式见证，无法证明等价的差异待审；角度字段目前未独立测量。终止无输出的任务，适用完成率记零；等待、未运行及评分器故障单列，不冒充模型失败。

最终数量／构件／关系先报告逐题宏平均，再补充合并目标分母的微平均；当前自动汇总已有微平均，宏平均与不确定性分析仍需在报告层补齐，费用也需账单或价格依据。005 离线重放的共享几何保全误报尚待评估侧修正并用保留产物同版重算，原真实失败不改写。

### 单题预算与循环限制

下表额度已在运行前冻结，每个“题目 × 组别”分别适用，同题四组相同。

|规模|题数|累计 token 上限|模型调用上限|活动执行时间|单次实验命令工具时限|
|---|---:|---:|---:|---:|---:|
|S1：1 个目标|7|1,250,000|48 次|30 分钟|120 秒|
|S2：2 个目标|8|1,750,000|64 次|40 分钟|120 秒|
|S3：3 个目标|5|2,500,000|80 次|50 分钟|120 秒|

整题模型调用、阶段循环和工具次数不能混为一谈。一次响应可含多个工具操作。A/C 采用同一通用循环；D 保留原生循环，子 Agent、压缩和重试调用累计到同题，其原生工具内部时限保留自身语义，整题仍受活动时间约束。

B 场景定位一次执行最多 **8 轮响应**，查询与核验反馈共同占额度；这不是整题仅能调用 8 次模型。ChangeSet 生成与需要模型参与的属性解析各最多 2 次尝试。最终应用／核验失败后，B 当前没有自主无限重修循环，而是保留终态。

四组单次最大输出均为 **65,536 token**；B 另有 65,536 的估算输入保护阈值。它们不是整题预算，也不表示各模型实际上下文容量相同。网关用“请求字节数＋最大输出”保守预留下一次调用额度，可能在账面 token 尚未耗尽时停止；预留量不当作实际消耗。用量缺失记 unknown，reasoning 已计入输出时不重复相加。

本批没有自动扩额规则。澄清恢复不清零 token、调用或活动时间；确认后台模型与工具都停止后才计纯人工等待，准备和独立评分耗时另列。用户批准的 **20M 是总用量目标，超出无需再次审批，未设为硬停止线**。80 项上限加总为 141M，这是额度上限之和而非预计用量；原批次 16:35 快照已有约 42.75M 已知 token、2 次用量未知。两 demo 的原开发额度为每任务 2.5M／100 次／90 分钟，与正式额度及后续 B 开发复验分别记账。

### 运行流程与比较方式

每题依次完成输入／条件冻结、四个独立会话、修复与必要澄清、唯一产物／终态冻结、独立评分。同一时刻只安排一个活动任务，按题轮换 A→B→C→D、B→C→D→A、C→D→A→B、D→A→B→C，不用私有评分帮助模型返工，也不重开挑最好答案。

最终按 S1／S2／S3、门／窗／混合、信息充分／澄清分层，保存 B–A、C–A、B–D 的逐题配对。原批次、已见题目的 B 开发复验与零模型调用的离线重放分别报告；共享来源族、不同运行版本和每题仅一次运行的限制一起披露，不合成未见测试成功率。本次补充未刷新下方 16:35 的进度表与图片。

## 四、从失败中定位问题：本周修复了哪些共性机制

多项 B 组任务已找到正确墙体和公开参照，后续却在尺寸解释、安装或核验阶段被拒绝。本周将问题归为三类，针对一般机制修复。

|问题|为什么影响修复|本周调整|
|---|---|---|
|尺寸与语义混淆|门窗名义尺寸未必等于洞口尺寸；单位或属性含义错误会让几何看似正确、语义仍不合格|分别处理构件与洞口尺寸，保持单位及长度属性一致；按明确的宿主和精确参照确定属性|
|公开参照没有被完整保留|类型相同不等于安装相同；用整个包围盒判断进深，还可能误拒合法窗台板或五金外伸|保留已核验公开实例的安装与完整几何，分别核对门框位置、部件外伸及映射基底|
|几何应用与格式规则不一致|墙轴不一定在墙厚中心，可能只切掉半面墙；复用完整门实体可能破坏 IFC 表示关系；未定义开向也可能触发多余澄清|按实际墙体位置生成贯通洞口，合法复用完整门实体；精确类型已有的未定义开向保持原事实|

修复不依赖题号，也没有修改原请求、降低评分要求或向模型补入私有答案。对缺乏合法公共依据、存在关系歧义或模型输出错误的情况，仍保留拒绝和失败。

相关验证已有 **285 项回归通过**；后续开向分支的 **87 项相关回归通过**，两者覆盖有交集，不简单相加。最新 Linux 公共链路测试 **7 项通过**，覆盖正常修复、问答恢复、错误尺寸拒绝、完整墙开洞及未授权适配拒绝等场景。这里使用假模型响应，验证的是运行与执行链路，不计入真实模型成绩。
