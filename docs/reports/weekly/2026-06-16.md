# text2IFC 周报 / 2026-06-16

## 1. 本周结论

本周 text2IFC 从“能把结构化 JSON 编译成 IFC”推进到了“自然语言到 BIM JSON 2.0，再到可打开、可审查 IFC2X3”的端到端闭环。

当前最重要的结论是：

1. **BIM JSON 2.0 已成为项目的结构化中间表示。** 它可以表达 IFC 类、父子放置、空间、开口、门窗填充关系、基础几何、属性、材料层、类型复用和连接拓扑。
2. **25 个授权 BIMNet IFC2X3 文件已进入本地数据管线。** 数据集按 Matterport scene family 做了 train/validation/test 分离，避免同一场景泄漏到不同 split。
3. **Text-to-JSON 数据集和基线已跑通。** 当前有 25 个 formal supported-scope 目标、100 条确定性 text/BIM JSON pair，以及 provider-independent evaluation harness。
4. **中文多轮 Agent 已跑通 simple-room demo。** Agent 能在信息缺失时提问，回答完整后输出 Formal BIM JSON 2.0，并编译出 IFC2X3。
5. **Phase 4 完成了生成 IFC 的质量门禁。** `simple-room-fixed` 和 `two-room-suite` 均有 text、prompt、raw output、BIM JSON、IFC、diagnostics、metrics 和 report，可供人工审查。
6. **Phase 6 可以开始规划，但边界必须清楚。** 可以做 supported-scope 训练、评估和部署；不能宣称完整复原 BIMNet 的复杂几何、BRep、tessellation 或全部材料/类型样式。

## 2. 一条完整链路：自然语言到 IFC

本周最值得作为人工核验样例的是 Phase 4 的 `two-room-suite`：

```text
自然语言输入
  -> provider prompt
  -> raw provider output
  -> BIM JSON 2.0 candidate
  -> validate_v2_document 校验
  -> IFC2X3 compiler
  -> output.ifc
  -> IfcOpenShell reopen
  -> generated IFC quality gate
  -> diagnostics / metrics / report
```

对应文件：

| 环节 | 文件 |
|---|---|
| 自然语言输入 | `dataset/processed/agent-demo/geometry-gate/two-room-suite/input.txt` |
| 使用的 prompt | `dataset/processed/agent-demo/geometry-gate/two-room-suite/prompt-used.md` |
| provider 原始输出 | `dataset/processed/agent-demo/geometry-gate/two-room-suite/raw-response.txt` |
| BIM JSON 2.0 | `dataset/processed/agent-demo/geometry-gate/two-room-suite/candidate.json` |
| 编译后的 IFC | `dataset/processed/agent-demo/geometry-gate/two-room-suite/output.ifc` |
| 自动诊断 | `dataset/processed/agent-demo/geometry-gate/two-room-suite/diagnostics.json` |
| 指标 | `dataset/processed/agent-demo/geometry-gate/two-room-suite/metrics.json` |
| 人类报告 | `dataset/processed/agent-demo/geometry-gate/two-room-suite/report.md` |

该样例的输入是：

```text
请创建一个单层双房间套间，总长 8 米、宽 4 米、高 3 米；
中间在 x=4 米处设置分隔墙，分隔墙中间有门，东墙中间有窗。
```

实际 IFC 中包含：

- 2 个 `IfcSpace`：`West Room` 和 `East Room`
- 5 面 `IfcWall`：南、北、西、东、中间分隔墙
- 1 个 `IfcDoor`：位于中间分隔墙
- 1 个 `IfcWindow`：位于东墙
- 2 个 `IfcOpeningElement`
- 2 个 `IfcRelVoidsElement`
- 2 个 `IfcRelFillsElement`

本周人工核验时发现一个有价值的教训：查看器可能造成视觉误判；自动检查也不能只看 IFC 是否能打开。我们进一步确认了墙体边界、门窗位置和空间关系，结论是当前 demo 大体正确，但 report 还不够详细，后续应把“自然语言需求覆盖表”纳入审核报告。

## 3. Phase 2.5：BIM JSON 2.0 与 IFC 语义图

Phase 2.5 是本周前半段的关键补课：BIM JSON 1.0 不含可靠的 source placement、space 和 IFC 语义关系，无法承担训练数据的结构真相。因此项目插入 BIM JSON 2.0。

完成内容：

- 下载并验证官方 IFC2X3 TC1 EXPRESS schema。
- 构建 IFC2X3 knowledge registry：
  - 980 个 declaration
  - 653 个 entity
  - 317 个 property set
  - 1850 个 simple property
- 定义 Formal BIM JSON 2.0 和 Draft Envelope。
- 为所有 653 个 IFC2X3 entity 标记 capability state。
- 支持 parent-relative placement、`IfcSpace`、`IfcOpeningElement`、`IfcRelVoidsElement`、`IfcRelFillsElement`。
- 实现 IFC2X3 -> BIM JSON 2.0/Draft extraction。
- 实现 BIM JSON 2.0 -> IFC2X3 compiler。
- 对 25 个授权 BIMNet IFC2X3 文件做 provenance 和 extraction accounting。

关键决策：

- JSON Schema 仍然是 BIM JSON 的唯一结构真相。
- 低层 IFC helper object，例如 `IfcCartesianPoint`、`IfcDirection`、`IfcOwnerHistory`，由 compiler 生成，不要求语言模型输出。
- 不支持或不完整的信息必须进入 Draft/loss，不允许静默补全或伪造。

## 7. 本周发现的问题和经验

### 7.1 IFC 能打开不等于 BIM 语义正确

Phase 5 live Mimo 实验已经能生成 reopenable IFC，但最初房间墙体方向有问题。Phase 4 因此引入 generated IFC quality gate，把空间关系和可视化几何作为一等验证对象。

### 7.2 自动报告还需要更接近人工审查

当前 `two-room-suite` 的 `report.md` 过于简略，虽然 `diagnostics.json` 有墙体 bbox，但人类更需要看到：

- 原始自然语言需求
- BIM JSON 实体数量
- IFC 实际实体数量
- 需求覆盖表
- 门窗/空间/墙体拓扑表
- 未覆盖或未要求的信息

这应进入 Phase 6 的质量改进项。

### 7.3 专家 Agent 润色是合理的，但必须受控

专家 Agent 不应该把用户没说的信息偷偷变成默认事实。更合理的角色是：

- 把自然语言改写成“设计简报”
- 明确哪些是用户显式事实
- 明确哪些是系统建议假设
- 对关键缺失信息提出 1-3 个问题
- 在 demo 模式下可以给出默认假设，但必须写入 artifact

这样可以提高 text -> JSON 的稳定性，又不会破坏项目“不静默补充必要数据”的原则。

## 8. Phase 6 建议补充内容

Phase 6 原目标是数据扩展、fine-tuning 和部署。本周之后，建议把它拆成更明确的几条主线。

### 8.1 专家 Agent / 需求规范化层

建议加入一个前置层：

```text
用户自然语言
  -> 专家 Agent 生成设计简报
  -> 缺失信息问题或显式假设
  -> BIM JSON Agent
  -> BIM JSON 2.0 validation
  -> IFC compiler
  -> generated IFC quality gate
```

验收重点：

- 专家 Agent 输出不是 IFC，也不是低层 helper entity。
- 输出必须区分 `explicit_user_facts`、`assumptions`、`questions`。
- 必要事实缺失时进入 Draft，不进入 Formal。
- demo 模式的默认假设必须可追溯。

### 8.2 训练数据版本化和 loss sidecar

Phase 6 训练数据必须继续使用 Phase 3 的 scene-family split，不能使用原始 BIMNet train/test 文件夹。

建议数据包包含：

- prompt/input
- design brief
- target BIM JSON 2.0
- source provenance
- split
- loss sidecar
- projection omissions
- generated IFC quality metrics

### 8.3 Fine-tune 与 RAG 的对比实验

建议至少比较三种路线：

1. **Structured prompt baseline**：作为最低成本基线。
2. **RAG + structured output**：用于 IFC class、property、capability、prompt examples 检索。
3. **Fine-tuned model**：只在 evaluation 明确优于 baseline/RAG 时推进。

不能只看 JSON validity，还要看：

- schema valid rate
- semantic valid rate
- missing required facts rate
- compile success rate
- reopen success rate
- generated IFC quality gate pass rate
- clarification question count
- unsupported/forbidden output rate

### 8.4 部署服务边界

Phase 6 部署不应直接开放“模型输出 IFC”。建议服务链路为：

```text
API / UI
  -> Agent session
  -> design brief / Draft state
  -> BIM JSON 2.0 candidate
  -> validator
  -> compiler
  -> IFC quality gate
  -> artifacts + report
```

生产服务应保留：

- session transcript
- candidate JSON
- validation diagnostics
- generated IFC
- human-readable report
- machine-readable metrics

### 8.5 Report 与人工审核升级

Phase 6 应把 report 从“pass/fail 摘要”升级为审查报告。

建议新增：

- 自然语言需求覆盖表
- 设计简报覆盖表
- JSON 实体统计
- IFC 实体统计
- 墙、空间、门窗、开口关系表
- 未覆盖项和 Draft 项
- viewer 检查建议

## 9. 下周建议目标

优先级：

1. 先定义 Phase 6 的 supported-scope 边界和验收指标。

4. 定义 RAG、fine-tune、baseline 的对比实验。
5. 再决定是否启动真实 fine-tuning。
