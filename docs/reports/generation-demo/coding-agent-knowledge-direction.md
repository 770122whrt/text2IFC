**建议研究的问题：怎样给 Coding Agent 合适的建模接口与任务知识，使它以可控成本生成满足空间要求的 IFC？**

这比“我们有一个生成 IFC 的 Agent loop”更具体。Generation 是当前主任务；独立 IFC Repair 可作为以后检验知识复用与修改保全的第二任务，不能仅因两者都有反馈循环就宣布算法已经统一。

## 1. IFC 生成与代码生成是什么关系

IFC 建模属于领域化的程序生成与结构化数据生成问题。它和 coding 有大量共同点，不宜宣称普通 coding 没有语义、依赖、复杂约束或不完整需求。

需要先区分三个层次：

- **IFC：** 建筑对象、属性和关系的数据模式，以及遵循该模式的模型实例；STEP 是一种交换表示。IFC 本身不是通用编程语言，也不是完整知识库。[buildingSMART 官方说明](https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/content/introduction.html)
- **本项目 BIM JSON：** 项目定义的建模中间表示，经编译器生成 IFC；不能直接等同于任意标准 IFC JSON 序列化。
- **Python + IfcOpenShell：** 另一种可执行建模入口；Agent 完全可以写代码、运行、检查和修改，得到同一类 IFC 产物。

| 比较点 | 与普通 Coding 的共同点 | IFC 场景中的具体难点 |
| --- | --- | --- |
| 类型和结构 | 都需遵循接口与类型约束 | 对象类型、关系端点、属性适用范围、空间包含关系共同约束模型 |
| 正确性 | 运行成功都不等于满足需求 | 文件可打开、对象可见、几何正确、关系正确、用户要求完成是不同事实 |
| 非局部依赖 | 修改代码也可能影响其他模块 | 窗、洞口、宿主墙、位置与相关关系可能必须一起成立 |
| 表达形式 | 高层函数和抽象可减少重复工作 | 绝对坐标、相对位置、重复构件、楼层复用的表达能力影响生成难度 |
| 评价方式 | 都需要独立测试，而非仅检查语法 | 应检查最终 IFC 的几何、关系和约定后续任务，允许多种合理设计 |

例如“在这面墙上加一扇窗”，模型中出现一个窗对象只是部分结果。还需要在适用的模型约定下检查宿主、洞口、填充关系和几何位置。具体要求必须事先定义，不能将所有可选 IFC 关系都一律判为必需。

生成与修复可以共享领域知识，但任务条件不同：生成从需求构造新模型；修复从既有模型和问题出发，同时考虑目标变化与未受影响内容的保全。代码生成与代码修复也有这种区别。独立 Repair 的知识检索实现，不能未经接线核实就算成 Generation 已部署能力。

## 2. 如何讲“自然语言到空间”的故事

建议把问题说成：**语言模型能写建模代码，但完成空间任务需要同时处理设计意图、领域规则和模型状态。text2IFC 探索如何通过可执行接口与按任务提供的知识连接这三者。**

流程可以概括为：自然语言要求 → 可检查的设计要求 → 建模表示与操作 → IFC → 独立检查与必要反馈。现有 Brief、BIM JSON、编译和检查可承担其中一些环节；流程图本身不是方法创新。

“IFC 是独立 coding knowledgebase”建议改成：**IFC 建模具有结构化的领域知识体系，可以研究如何将这些知识交给 Coding Agent 使用。** 知识体系至少要区分以下四类。

| 知识或信息 | 例子 | 建议放置方式 |
| --- | --- | --- |
| 标准事实 | 类型、继承、属性类型、关系端点 | 权威注册表与可查询文档；按任务提供必要部分 |
| 可执行建模规则 | 受支持的构件构造与关系应用逻辑 | 编译器或工具接口，明确其保证与限制 |
| 当前任务事实 | 用户要求的数量、尺寸、位置，已有 IFC 中的真实对象 | 需求与模型状态；未知事实需澄清或获得设计授权 |
| 经验与示例 | 典型建模代码、JSON 例子、失败模式 | 按操作和任务选取，避免将例子中的值当作本次答案 |

知识库可以回答窗与洞口的关系类型，不能回答用户没有指定的窗宽。官方知识、项目能力范围和具体设计事实不应混在一起。项目已有 [IFC2X3 知识来源约定](../../reference/ifc2x3-knowledge-sources.md) 对此作了区分。

对未来 coding 的意义是一个可检验的问题：**同一个模型的表现，有多少来自模型本身，有多少来自接口抽象和知识组织？** 仅在 IFC 上取得结果，仍不能据此声称改进了通用 Coding Agent。

## 3. Token 压缩与知识利用应成为同一条研究线

建议目标是：**在满足同一组任务要求的前提下，减少完成任务的总成本。** 不以输入越短、生成越少或更早拒绝任务作为单独成功标准。

JSON 不天然比代码省 token。Python 可以通过循环、函数和相对位置表达重复构件；逐对象展开的 JSON 反而可能更长。需要比较表示的抽象能力，不能只比较括号、字段名或输出后缀。[CodeAct](https://proceedings.mlr.press/v235/wang24h.html) 已研究可执行代码作为 Agent 行动空间及其组合能力，因此“Agent 能写代码并迭代执行”已有直接先例。

### 已有实现与直接观察

[context_selection.py](../../../src/text2ifc_agent/context_selection.py) 已按关键词选择类别、能力信息和示例；选择门窗时会加入洞口及相关关系类别。这是现有基础，不应再包装为首次引入关系知识。

2026-09-15 的只读探查调用 `select_design_brief_context(user_request='Create a wall with one window.', conversation=[], schema_version='bim-json/2.3')`，用 `json.dumps(..., ensure_ascii=False, separators=(',', ':'))` 计算字符数，得到 context 共 17,676 字符。其中根 schema 7,477 字符，包含 `$defs`；若干定义又作为独立证据项出现。这是定位冗余的线索，**不是 token 测量，也不是可直接删除这些证据项的证明**；引用和校验依赖仍需保留。

现有光庭案例的成功流程还提供了一份真实成本账本，来源是 run `ce8116ce095acdcf` 的三个 stage metrics：

| 阶段 | 输入 token | completion token | 总 token |
| --- | ---: | ---: | ---: |
| [Brief](../../../dataset/processed/proof/generation/phase6.6/courtyard-library-20260912/evidence/v2/rerun-03/live-run/runs/ce8116ce095acdcf/design-brief/metrics.json) | 26,041 | 49,984 | 76,025 |
| [Generator](../../../dataset/processed/proof/generation/phase6.6/courtyard-library-20260912/evidence/v2/rerun-03/live-run/runs/ce8116ce095acdcf/generator/metrics.json) | 59,377 | 59,334 | 118,711 |
| [Audit](../../../dataset/processed/proof/generation/phase6.6/courtyard-library-20260912/evidence/v2/rerun-03/live-run/runs/ce8116ce095acdcf/audit/metrics.json) | 110,763 | 12,034 | 122,797 |
| 合计 | 196,181 | 121,352 | 317,533 |

这是一个成功 run 的三次调用，不含该案例此前失败尝试，不能代表平均成本。completion 中已经包含 reasoning，不能再次相加；输入含缓存命中，token 总量不等于实际计费金额。当前人类验收状态以 [案例 REPORT](../../../dataset/processed/proof/generation/phase6.6/courtyard-library-20260912/open-court-v2/REPORT.md) 为准，不能用冻结的早期报告标题覆盖后续验收。

它支持优先调查三处成本：Brief 的推理与输出；生成表示及上下文；Audit 重复读取的大量内容。仅压缩最终 JSON 可能漏掉主要成本来源，但本轮没有验证具体节省比例。

### 值得补强的机制候选：按建模义务提供知识

比“检索最相似的几段文本”更具体的方案是：

1. 从请求和当前状态中识别本次需要完成、需要检查的建模义务。例如窗的放置和适用的宿主/洞口关系。
2. 明确哪些义务已经由编译器保证，哪些仍需 Agent 决策。编译器负责的底层细节不必逐次完整注入，但接口用法和必要前提仍需提供。
3. 为 Agent 负责的义务选择成组知识，保留完成操作所需的依赖；在预算内压缩重复内容和无关示例。
4. 反馈出现缺口时，补充对应义务的知识；预算不足或事实未知时，分阶段处理或澄清，不静默丢弃必要要求。

这个方案尚未实现成通用策略。现有门窗规则已覆盖其中一个简单情形，首版可用明确规则和覆盖算法探索，不必先训练模型。**依赖扩展、集合覆盖或检索循环本身也不构成新算法。**

相关先例已经较强：[RepoCoder](https://aclanthology.org/2023.emnlp-main.151/) 使用迭代检索与生成；[Repoformer](https://proceedings.mlr.press/v235/wu24a.html) 研究何时需要检索。因此，潜在差异应落实到“编译器保证、任务义务、知识覆盖和最终空间结果”的具体建模与实验，不能仅声称按需 RAG 或更少 token。

## 4. Coding Baseline 应如何设置

主要对照必须是真正能查文档、写代码、执行和调试的 Agent。直接逐行生成 STEP 可以作为补充，但不适合成为唯一或最强 baseline。

| 设置 | Agent 可以使用什么 | 主要回答的问题 |
| --- | --- | --- |
| B1 通用 Coding Agent + IfcOpenShell | Python、官方 API 文档、执行工具、公开检查反馈 | 专门系统相对合理的通用建模方案有什么价值？ |
| B2 同一 Coding Agent + 本项目编译器 | 同一 BIM JSON 合约、编译器、可用知识和检查工具 | 优势究竟来自编译器，还是额外 Agent 机制？ |
| B3 B2 + 候选知识选择 | 控制器不变，仅替换上下文选择方式 | 知识选择本身是否带来收益？ |
| B4 完整 text2IFC | 完整 Brief、生成、审核及适用的候选修订流程 | 实际系统完成任务的成本与效果如何？ |

**B2 最关键。** 如果通用 Agent 拿到我们的编译器后表现就相同，应把贡献归于接口/编译抽象与系统使用价值，不能继续将结果归因于独有推理能力。

比较 B1 与 B2 时，两者接口和内置知识不同，不能把差值全部算成语言模型能力变化。再单独固定表示，比较完整上下文、当前关键词选择、普通 top-k 和候选义务选择；知识来源集合、模型、工具反馈和预算应尽量一致。完整上下文放不下时需如实报告，不能用任意截断构造弱对照。

[IFC-Copilot](https://show2instruct.github.io/ifc-copilot/) 已提供 IFC 原生工具与代码执行路线，是值得纳入的领域近邻。Text2MBL 则应在双方都支持的模块化布局任务上比较；任务和后端不一致时，只做方法与协议层面的对照，不强行排列分数。

评测需同时保留两种设置：端到端从同一自然语言请求开始；控制实验从同一冻结任务说明开始。最终评分以独立要求和生成 IFC 为准，不以某个系统自己生成的 Brief 或 JSON 是否匹配作为唯一答案。

## 5. 能借鉴 Text2MBL 什么

可以借鉴研究结构：**明确任务 → 设计合适的建模抽象 → 建立数据和评价 → 比较与消融。** Text2MBL 针对模块化建筑的 modules、units、rooms 设计代码架构，微调模型生成操作序列；它的价值不限于“LLM 写了 Revit 代码”。[NeurIPS 2025 官方论文页](https://proceedings.neurips.cc/paper_files/paper/2025/hash/61a3e68eb9059ccacdde0bb84870b80e-Abstract-Conference.html)

它还比较了代码与坐标表示，但两者涉及相对布局操作等抽象差异，因此不应将结果简单解释为代码语法优于坐标语法。其几何指标也有边界，不能等同于完整建筑可用性证明。[原文与 Table 2](https://arxiv.org/html/2509.23713v1)

“我们更 solid”需要拆开判断：当前仓库的编译、检查、证据保存以及独立修复工作，提供了较丰富的系统基础；Text2MBL 在定义清楚的任务、配对数据和方法比较上提供了论文证据。系统范围更大、工程检查更多，不等于研究贡献更强。当前没有同任务公平实验，不能声称 text2IFC 已优于它。

现阶段不建议为模仿 Text2MBL 立即启动微调。先确定表示和知识机制是否确有优势；若已有强通用模型加接口即可完成，微调可能增加数据工作却不回答核心问题。后续若能形成高质量、按建筑家族隔离的数据，再研究知识选择或操作策略的学习。

## 6. 三项贡献如何围绕一条主线组织

以下是候选表述，投稿时需按实验证据改写，不能直接作为已证实的创新声明：

1. **面向空间建模的可执行接口。** 将自然语言设计要求落到可检查的构件与关系表示，再生成 IFC。现有编译器是基础，贡献强度取决于接口抽象和对照证据，不在于使用 JSON。
2. **按建模任务提供领域知识。** 区分编译器保证与 Agent 需要决定的内容，在预算内提供必要的规则、依赖和示例。它是当前最值得小规模补强的技术候选，尚不能声称已比现有检索方法有效。
3. **交互系统与可复用的空间任务评价。** 展示需求、建模结果和检查，并用强 Coding Agent 对照同时衡量任务完成与总成本。实验结果到位后再填写效果，不预先写“显著提升”。

这三项分别是接口、机制、系统与证据；不是三项互不关联的新算法。若第二项只获得机械去重的收益，适合写成系统优化，不能硬撑方法创新。

Demo 故事候选：**text2IFC 通过可执行的建模知识与按任务提供的上下文，让用户把自然语言要求转成可检查的 IFC 模型。**

英文工作标题：*text2IFC: Interactive Building Generation with Executable Domain Knowledge*。标题可用于讨论，不能据此宣称当前所有交互或知识调度均已实现。

## 7. 下一步先做什么

| 顺序 | 范围 | 产出与下一步判断 |
| --- | --- | --- |
| 1. 成本与失败诊断 | 先分析已有记录；区分需求、知识缺口、表示冗长、编译缺陷和审核开销 | 确定该压缩哪一阶段，是否存在知识选择问题 |
| 2. 强对照小试 | 在当前支持的任务上，先比较 B1、B2 与当前系统；可从约 12 个开发任务起步 | 找到增益来自接口还是流程；开发任务不冒充正式盲测 |
| 3. 一项机制补强 | 固定表示与控制器，比较当前选择、top-k 与候选义务选择 | 检验必要知识覆盖、任务成功和成本的关系 |
| 4. Demo 证据 | 保留按建筑/任务家族隔离的未见测试；展示正常生成、反馈修订及澄清/不支持情形 | 形成可交互 Demo 和有边界的结果，再决定是否扩展方法论文 |

核心结果应报告：满足预设要求的成功率；几何与关系检查的分项结果；全部尝试的 token、费用、时间和重试；澄清/拒绝比例。必要知识覆盖率可用于解释原因，不能替代最终 IFC 的任务结果。失败必须保留在分母中，不能只比较成功样本的成本。

对知识机制最好观察多个预算下的成功率与成本曲线，而非只给一个“压缩率”。正式实验的规模应结合任务差异、初步方差与可用预算确定；不把探索集数量当作统计保证。

如候选知识选择没有胜过普通检索，应保留负结果，转向接口与表示的解释；如主要瓶颈是联动修订，则回到 [此前的关系与修订方向讨论](https://github.com/770122whrt/text2IFC/blob/09e8e9311f0b8c3ffc022dc42a12a48165ed7aa1/docs/reports/generation-demo/research-direction-discussion.md)。当前建议先诊断接口与知识供给，不再预设修订范围策略优先。

本轮工作为代码与已有记录只读核实、原始文献核实及方向文档整理。没有运行新的 LLM/Provider 实验、改动生成逻辑或变更既有证据。后续真实实验按 [Agent 能力评测协议](../../validation/agent-capability-evaluation.md) 执行。
