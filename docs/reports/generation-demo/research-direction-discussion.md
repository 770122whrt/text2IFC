## 1. 对旧三点的调整

旧版的可核验流程、写入所有权和版本绑定，适合作为系统实现依据。继续给这些模块换名字，不能解决创新性问题。

Demo 应先回答：用户今天能够通过这个系统完成什么有价值、且相关系统尚未充分展示和验证的事情？随后再解释关键技术与证据。

建议的产品主线是：**通过自然语言生成具有正确构件关系、能够继续使用和修改的 IFC 建筑模型。** 这是应用目标，仍需限定建筑类型与支持关系，不将“完整”理解为覆盖全部建筑专业。

## 2. 三个值得比较的方向

| 方向 | 具体研究问题 | 可以演示什么 | 必须补的内容 | 主要风险 |
| --- | --- | --- | --- | --- |
| A. 关系感知的建筑生成 | 模型能生成构件，为什么没有生成正确的整体关系？将关系依赖纳入生成计划是否有效？ | 空间属于正确楼层；门窗、洞口和宿主相互一致；模型支持相应查询与操作 | 明确关系义务与生成单元的映射，验证其对计划的实际影响 | 换成图或 JSON 本身不新；若只是编译器漏写关系，应修 Bug |
| B. 能联动、也能保留的迭代生成 | 固定局部范围可能修不动，完整重写可能改坏其他部分；Agent 如何选择必要的联动范围？ | 用户修改一项要求，系统显示必要关联变化和仍然满足的旧要求 | 在既有 ChangeSet 之上增加范围选择/扩大决策，以及语义影响检查 | 依赖排序和局部修复已有先例；仅加邻居遍历仍主要是工程 |
| C. 面向后续使用的生成验证 | 文件通过检查后，是否真的能完成约定的查询、计量和局部操作？ | 生成后立即执行公开的后续任务，暴露“看起来正确但用不了”的结果 | 独立需求标注、可执行任务与公平对照 | 若只有更多检查，没有新任务设置或发现，难成为单独方法贡献 |

**当前建议：B 优先做小型可行性诊断，A 是重要替代方向，C 为两者提供证据。** 排序依据是与现有实现的距离，不是已经证明 B 最有创新性。若现有失败主要是初次遗漏，应转向 A，不要为了使用 ownership 机制强行解释成迭代回退。

另两个可保留但暂不展开的方向是：按收益选择澄清问题，以及学习下一步生成/修订策略。它们可能更偏 AI，但分别需要意图交互评价或训练数据，当前 Demo 阶段的工作量更大。多 Agent、RAG、更多工具或更大模型可作为手段，不单独列为创新。

## 3. 将 B 说具体：保护语义要求，而不是锁住所有字节

设想一个示意场景：用户调整一个房间的尺寸，这可能要求邻接墙体与门洞一起变化；其他楼层的房间数量和用途仍应保持。固定只允许改房间对象，可能无法完成；放开全部模型，又可能无意改变其他楼层。这个例子用于说明问题，不代表当前实现已覆盖任意空间重规划。

候选机制需要回答四件事：

1. 当前哪些要求仍有效，哪些已被用户明确替代？
2. 哪些对象和关系共同决定这次修改能否成立？
3. 小范围修订失败后，依据什么证据扩大范围，何时应停止或澄清？
4. 如何独立检查新要求完成、仍有效的旧要求保留，避免靠删对象使错误数下降？

已有所有权、版本检查和原子应用可承担执行约束。需要研究的是它们上面的决策：**这一步应该改什么、为什么需要一起改、是否值得继续扩大。** 它可以先是明确的算法，不必为了“像 AI”而训练新网络。

仍需面对直接先例。[ATLAS v3](https://arxiv.org/html/2510.25890v3) 已包含局部诊断、修补、依赖排序和人工介入。因此，“用依赖图指导修复”不是足够的区别。值得检验的更具体问题是 IFC 的几何与关系依赖下，范围选择能否兼顾完成与保全；是否超出已有方法，须做方法级比较。

若最终仅得到“锁得更严，所以拒绝更多修改”，不能据此宣称生成更可靠。

## 4. 如果这条路线成立，论文贡献怎样写

先围绕一个能力组织三项贡献，避免把三个基础模块当成三个算法：

1. **任务贡献：** 把生成后的交互修订定义为同时满足新要求、保持仍有效旧要求的建筑建模任务，明确必要联动与无关破坏的区别。
2. **技术贡献候选：** 用构件关系和验证反馈选择修订范围，在局部操作与必要联动之间做决策。具体算法和差异尚需原型与对照支持。
3. **系统与证据贡献：** 提供可交互的 text2IFC 演示，以及独立检查需求满足、关系正确和修改影响的可复用任务。

这是一种论文组织方式。任务设置是否足够新、技术是否有效、系统是否比直接近邻更有用，都仍有待证明。若诊断支持 A，第二项应改为关系依赖驱动的构造规划，不能两条路线都写成已完成。

Demo 的一句话候选：**text2IFC 让用户在自然语言生成建筑模型后继续修改设计，并查看哪些关联部分需要变化、哪些已有要求得到保留。**

英文工作标题候选：*text2IFC: Interactive Building Generation with Relation-Aware Revision*。题目中的交互界面与关系决策均须在演示前真正实现和测试。

## 5. 最先做什么，才能避免继续空想

### 第一步：先用已有产物区分失败原因

从现有 Generation 失败记录中，区分需求遗漏、初次关系缺失、编译实现错误、修订回退、范围过窄和不可满足要求。保留失败的阶段与中间模型。现有材料若没有足够的跨场景案例，就明确证据不足，不从一个成功光庭案例推导能力。

目的是决定 A 与 B 哪个问题值得优先解决。这个诊断不需要先训练模型，也不要求先跑大批新生成。

### 第二步：准备小型探索集，先看矛盾是否存在

可先设计约 12 个开发任务，覆盖三类情形：范围内可完成；必须联动其他部分；要求相互冲突或不受支持。任务数是探索规模建议，不是统计功效保证。

对同一失败候选比较：完整重写、提示要求局部修改、固定强制范围。若这三种做法没有显示值得解决的完成/保全矛盾，就暂停 B 的机制开发。若有，再增加关系感知范围策略作为候选。

同一个探索集不能在据其修改方法后充当盲测集。正式比较需保留按建筑/任务家族隔离的未见样本，并固定模型、可用信息、预算和评分器。

### 第三步：看联合结果，而不是只看一个通过率

| 指标 | 它回答什么 |
| --- | --- |
| 新要求完成率 | 这次请求是否完成？ |
| 仍有效要求的保留情况 | 是否无意破坏其他要求？ |
| 联合成功率 | 新要求完成且保全满足，是否同时成立？ |
| 关系正确性与后续任务 | 生成 IFC 是否支持约定的实际使用？ |
| 拒绝/澄清及成本 | 是否靠不执行任务保全；是否消耗更多调用、时间和 token？ |

必要联动不计为破坏；用户已替代的旧要求不再作为保全目标。不能用该次生成的 Brief 独自充当原始需求的完整答案，也不能把冻结数据结构的 hash 不变等同于完整语义保全。

这些是下一步实验设计建议，本轮没有执行新 Provider 调用。执行时仍需满足 [Agent 能力评测与真实调用协议](../../validation/agent-capability-evaluation.md) 的适用准入要求。

## 6. Demo 应展示的过程

建议最终演示包含一条正常生成、一条需要关联修订的请求，以及一条明确冲突/不支持的请求。观众应能看到需求、模型、具体变化及检查结果，而不是只观看事先挑选的视频。

例如：生成一栋支持范围内的两层建筑，提出一次会影响关联构件的修改，显示必要变化与保留要求，再执行一个针对真实 IFC 的查询或后续操作。具体建筑与操作应在当前能力核实后确定；这里没有新增功能承诺。

## 7. 投稿判断

**WWW 2027 Demo：** 适合围绕一个可交互系统说明技术与使用价值。官方上限 4 页含参考文献，截止 2026-11-16 AoE；录入 Companion Proceedings，不能与研究主会论文混称。[官方征稿](https://www2027.thewebconf.org/demos/)

其主题适配仍需认真处理。开放 IFC、Web 展示和自然语言输入是可能的背景，真正需要解释的是 Web 环境中的结构化数据生成、交互或复用问题。仅添加网页界面不足以证明适配。

**AI Demo：** 若核心是 Agent 在复杂设计任务中的决策与可观察行为，主题可能更直接；具体届次需按最新征稿核实。没有必要为了 WWW 标签，把当前范围扩大成完整协同平台。

**后续方法论文：** 只有在范围决策或关系规划的对照结果成立后，再扩大任务分布、模型覆盖与方法比较。Demo 可成为研究起点，但后续论文需要实质新增贡献与充分披露已有发表内容，不能仅扩写文字。
