## 1. 当前结论

已有研究足以说明自然语言能够驱动 BIM 建模、IFC 工具操作和验证反馈。它们并未共同证明一般建筑的 IFC 生成已经可靠：任务范围、输出表示、验证对象和成功标准存在明显差异。

因此，两个极端判断都不成立：既不能说“别人只做了演示，所以这些能力都算我们的创新”，也不能说“别人分别做过这些组件，所以我们没有研究空间”。有价值的贡献应落在一个尚未充分解决的任务或决策问题上，并给出对应证据。

上一版三点——可核验流程、写入边界、版本绑定——描述了实现基础。它们为研究提供条件，尚不足以回答为什么这套系统有新的能力、为什么比简单做法更好。

## 2. 比较文献时，先对齐任务

| 比较维度 | 必须分开的情况 | 对本项目的影响 |
| --- | --- | --- |
| 输入 | 一次性完整需求、开放设计意图、多轮修改、既有 IFC | 多轮编辑成功不能替代从零生成结果 |
| 输出 | 图像、场景网格、Revit/Vectorworks 代码、原生 IFC | 可视化合理不能代替 IFC 对象与关系正确 |
| 尺度 | 构件、房间布局、专用桥梁、多层建筑 | 多层并不自动意味着语义完整；大文件也不等于复杂设计 |
| 验证 | 执行成功、规则符合、文本符合、关系正确、实际后续操作 | 需要明确每个分数究竟测了什么 |
| 迭代 | 重试、完整重写、局部修订、用户改变需求 | 需要区分修复旧错误与实现新要求 |
| 证据 | 案例、固定任务集、跨模型重复、消融、人工评估 | 一个成功案例证明可行性；更广结论需要相应分母 |

这里的“完整建筑”应具体列出支持的楼层、空间、构件和关系，而不是声称覆盖施工级 BIM 的全部专业和用途。

## 3. 直接相关工作

### 3.1 Text2BIM：完整建模工作流的直接先例

**方法与证据。** 多 Agent 将需求变成建模代码，调用 Vectorworks，导出 IFC 后进行规则检查和迭代优化。它有重复实验，并非只展示一张成功图片。[正式论文](https://doi.org/10.1061/JCCEE5.CPENG-6386)

**版本必须分开。** arXiv v1 使用 10 个提示、3 个模型、每组 5 次，保存 391 份含中间产物的 IFC；v2 改为 25 个提示、3 个模型、每组 3 次，保存 534 份。v2.1 调查部分段落仍沿用 391 的叙述，不能拿它否定后一个版本。中间 IFC 数也不是独立建筑数。[v1 实验](https://arxiv.org/html/2408.08054v1)、[v2 实验](https://arxiv.org/html/2408.08054v2)

**研究启发。** v1 描述过优化时重写代码造成重复/冲突，以及删除墙后问题数下降但结构受损。这给“修订造成回退”提供了实例依据；是否在我们的任务中稳定出现、是否是主要瓶颈，仍需测量。不能把该版本的现象概括成所有当前系统都存在同等程度的问题。

### 3.2 Text2MBL：领域表示、学习任务与配对数据相互配合

**方法与证据。** 该工作将模块、住宅单元和房间组织成层次化动作/代码，利用 Revit API 实例化 BIM，并微调语言模型。其贡献同时包括任务表示、配对数据和学习实验，不能简化成“用了一个 Agent”。[NeurIPS 2025 官方论文](https://proceedings.neurips.cc/paper_files/paper/2025/hash/61a3e68eb9059ccacdde0bb84870b80e-Abstract-Conference.html)

**实验边界。** 198 个设计对应 396 对文本与代码，设计级划分为 138/20/40；评估涉及可执行性、语义和几何。模块化住宅布局是有意义且明确的任务范围，范围有限本身不构成不严谨。[方法与实验](https://arxiv.org/html/2509.23713v1)

**对我们的要求。** “分层表示”和“文本到 BIM 代码”已不足以作为创新。如果探索关系优先生成，需要说明 IFC 中哪类跨对象依赖没有被已有表示解决，以及新表示实际改善了哪种推理。

### 3.3 MCP4IFC / IFC-Copilot：最接近原生 IFC 的系统路线

**方法与证据。** MCP4IFC 提供 IFC 查询、创建、修改和动态代码工具；后续 IFC-Copilot 项目提供 52 个工具及操作评估。其公开演进说明原生 IFC 与工具循环已经有直接先例。[MCP4IFC v1](https://arxiv.org/html/2511.05533v1)、[IFC-Copilot 项目](https://show2instruct.github.io/ifc-copilot/)

**具体边界。** MCP4IFC §4.2 展示了复杂结构生成，但明确说明这些生成/编辑实验不是综合基准。对生成文件的检查发现，某些结果缺少正确洞口、IfcSpace、材质、属性或空间归属。这是具体文件的语义缺陷证据，不能用来断言所有工具或新版本都无法处理这些关系。

**重要区别。** 后续项目的 100 条自定义任务包含查询、创建和编辑，其操作准确率不能直接理解为整栋从零生成成功率。复现时还须固定代码和论文版本，避免混用新旧接口及成绩。

### 3.4 Self-Verification：已直接覆盖“需求先变成检查要求”

**方法与证据。** 生成前构造 IDS 与非 IDS 规范，再用验证器和修改 Agent 迭代。两页论文展示一个住宅案例和五轮修订，部分要求逐步满足；最终仍有空间与楼层关系问题。作者明确将其定位为概念验证，并提出需要更完整的评估。[EC3 2026 原文](https://ec-3.org/wp-content/uploads/2026/08/EC32026_444.pdf)

**能说明什么。** 这足以否定“我们首次从需求派生验证规范”。但它不能支持一般建筑可靠性的广泛结论。同样，单案例边界不能被直接改写成该工作“不严谨”。

**我们的潜在区别。** 需要独立检查原始需求是否遗漏、关系问题能否定位，以及跨案例的修订收益。增加验证器数量本身不构成方法创新。

### 3.5 Trestle-Bridge：不能忽略领域约束下的分阶段生成

**方法与证据。** 该工作用需求、规划和执行角色完成 Revit 栈桥参数化建模，并报告 200 个案例及纠错分析。它提供了工程约束、依赖组织和反馈修订的直接先例。[原文](https://link.springer.com/article/10.1186/s44147-026-01130-3)

**范围与比较。** 栈桥的参数化设计空间与一般建筑不同，不能直接混用成功率。若我们扩大到多类建筑，就需要证明这些新增关系和自由度得到了处理；“范围更广”只有在结果成立时才有贡献。

### 3.6 BIMgent：长流程能力不能由单步能力代替

**方法与证据。** BIMgent 用多模态 Agent 操作 BIM 软件 GUI，包含规划、定位和监督。v2 在 25 个建筑任务上报告 32% 端到端成功率，并进行子任务及消融分析。[原文](https://arxiv.org/html/2506.07217v2)

**启发与限制。** 单步表现较好仍可能无法完成整套建模流程，这支持研究组合任务。但 GUI 定位和执行错误占有重要位置，不能直接把其失败归因为 IFC 关系推理。我们也不应拿原生 API 系统与 GUI 系统的原始数字直接比较。

### 3.7 BIM-Edit 与 BIBIMBAP：评价方法近邻，任务并不相同

**BIM-Edit。** 324 条自然语言编辑任务，分别检查几何、语义和拓扑。它提供了局部修改的任务及产物评价依据；输入/参考 IFC 的变体数量不是独立建筑数量。[论文](https://arxiv.org/html/2606.20146v3)、[任务集](https://huggingface.co/datasets/BIM-Edit/BIM-Edit-Tasks)

**BIBIMBAP。** 100 个原子 CRUD 任务，用可执行测试判断操作结果。它可以支撑操作级诊断，但不能代替整栋生成的长流程评估。[原文](https://ec-3.org/wp-content/uploads/2026/08/EC32026_271.pdf)

**作者项目线需要继续跟踪。** MCP4IFC、IFC-Copilot、Self-Verification 和这些评估工作之间存在作者或工具联系；Self-Verification 原文明示使用 MCP4IFC 工具。应记录具体依赖和版本，不能把不同项目名都视为独立系统基线，也不能因此把各自贡献合并成一个已完成的系统。

### 3.8 Capability-based Evaluation：可靠性与复杂度已有专门研究

**已核实内容。** 2026 年这篇 Automation in Construction 论文研究了 31 个构件、组合和系统级任务，记录 238 个错误，并给出六类能力和十类错误分析。其公开正文片段明确讨论复杂度升高时可靠性下降。[出版商页面](https://www.sciencedirect.com/science/article/pii/S0926580526001512)

**阅读边界。** 本轮核查了出版商摘要及方法/结果公开片段，未获得全部评测代码并复现。因此不判断其每个任务是否覆盖我们的目标关系。

**对选题的约束。** “建筑越复杂，LLM 越容易失败”已经不是足够新的发现。若做评测贡献，应进一步区分对象数量、依赖密度、信息遗漏和迭代回退，并通过控制变量说明原因。

## 4. AI 与结构化生成近邻

| 工作 | 已核实内容 | 对选题的实际影响 |
| --- | --- | --- |
| [SceneCraft，ICML 2024](https://proceedings.mlr.press/v235/hu24g.html) | 通过 LLM Agent 合成 Blender 场景代码 | 3D 场景规划与代码生成已有 AI 主会先例；新瓶颈要具体到目标表示和关系 |
| [MANSION，CVPR 2026](https://openaccess.thecvf.com/content/CVPR2026/html/Che_MANSION_Multi-floor_lANguage-to-3D_Scene_generatIOn_for_loNg-horizon_tasks_CVPR_2026_paper.html) | 官方摘要描述多楼层语言生成、可导航环境与任务编辑，并发布超过 1,000 个建筑场景 | “完整建筑规模”“任务导向生成”本身并不新；具身场景的目标与 IFC 数据语义不同，不能直接宣称谁更完整 |
| [ATLAS v3，原 PRISM](https://arxiv.org/html/2510.25890v3) | 类型表示、分层约束、验证、局部修订及依赖排序；实验限于 AUTOSAR | 不能把关系约束、验证驱动修订或依赖排序换到 IFC 后直接称为通用新算法 |
| [细粒度模型访问控制](https://doi.org/10.1007/s10270-017-0631-8)、[ChronoSphere](https://doi.org/10.1007/s10270-019-00725-0) | 模型权限与版本/事务机制 | 当前 ownership、freeze、revision 是可复用基础机制 |
| [CodeMEM](https://aclanthology.org/2026.findings-acl.834/) | 迭代代码生成中的上下文维护与错误重现 | 回退现象并非首次发现；应解释本项目中的具体关系机制与方法效果 |

ATLAS 是本轮补充的版本更正：同一 arXiv 记录 v1 名为 PRISM，当前 v3 改名并收窄了表述与实验范围。讨论最新版时使用 v3，不将 v1/v2 的全部强主张自动延续为当前结论。

v2.1 还收录了 NADIA、AutoBIM、BIMVLM、IFC-Agent、模型切片、Event-B Agent 等线索。它们保留在原调查中；本页不将其统一升级为“本轮全文复核”。当我们选择具体方法后，再针对最接近的几篇做方法级比较。

## 5. v2.1 中最需要修正的一步推理

调查将 Text2BIM 的重写破坏、MCP4IFC 的语义缺失和 Self-Verification 的未解决关系，一并用于支持状态隔离方向。这些现象都值得研究，**但它们不是同一种失败原因**。

| 观察到的现象 | 可能发生在哪一阶段 | 优先检验的解释 |
| --- | --- | --- |
| 用户要求的空间根本没出现 | 需求理解或初次生成 | Brief 是否漏要求；生成计划是否遗漏对象 |
| 门窗有几何，却没有正确宿主/洞口关系 | 表示、编译或初次生成 | 关系能否表达；编译器是否建立了正确关系 |
| 先前正确的关系在后续修订后失效 | 迭代修订 | 实际写入与语义影响是否超出目标 |
| 范围内补丁反复失败 | 范围约束或任务不可满足 | 是否必须联动其他对象；是否存在相互矛盾要求 |

仅仅增加写入隔离，不能补回从未生成的关系；锁住一个检查不充分的状态，还可能保留错误。反过来，某些跨区域修改是完成新需求的必要步骤。由此更值得研究的是：**在当前有效需求下，怎样选择生成与修改的单元，并判断何时必须联动。**

这也是当前不直接确定最终三项创新点的原因。应先用现有失败产物定位主要矛盾，再选方法。

## 6. Demo 与方法论文分别需要什么

WWW 2027 Demo 的官方要求是已实现、经过测试、有创新性和意义的系统，鼓励参与者直接交互；论文最多 4 页，含参考文献，截止 2026-11-16 AoE，录入 Companion Proceedings。内部文献调研不受这 4 页限制。[官方征稿](https://www2027.thewebconf.org/demos/)

我们的判断是：可以围绕一个清楚的新系统能力组织贡献，不必寻找三个全新基础算法。但需明确它超出直接相关系统的哪项已展示能力，并给出可操作演示和适度对照。

WWW Demo 仍要求 Web 主题相关性。浏览器只是展示方式，不能单独完成这项论证。若选择该目标，应具体说明开放结构化建筑数据的生成、交互与复用为什么对 Web 用户有价值。若系统贡献主要是 AI 建模决策，AI Demo 的主题可能更直接。AAAI-26 Demo 征稿可以作为系统技术、意义与演示要求的往届参考，不代表已核实下一届的日程。[AAAI 往届要求](https://aaai.org/conference/aaai/aaai-26/demonstration-call/)

方法论文则需要把某项决策或表示定义清楚，证明其收益能超出固定模板、简单分包或普通验证循环。代码完整和检查严格是实验条件；它们不能替代方法比较。
