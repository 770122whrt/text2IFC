### 1. 本文负责什么

本文集中维护研究问题、动机、贡献措辞、近邻攻击的结论，以及实验设计／记录／效果。文献原文依据在 [literature](repair-literature-matrix-20260921.md)，方法思路、闭环及 Demo 案例在 [展示版 Method](../../architecture/ifc-repair-pipeline-status-and-roadmap.md)。不再为每轮讨论新建一份平行方案。

IFC-SemRepair 是论文暂定名，不修改 text2IFC 仓库身份。研究主线是已有 IFC 的语义修复。本轮重点回应完整任务组合：局部修改、失败不部分提交、语义变更追溯及结果核验。不能因为其中每个基础机制都有先例，就跳到“整个系统没有贡献”；同样不能因为还没找到完全相同系统，就宣布所有组成部分首次提出。RAMC 与 Self-Verification 分别作为变更表示近邻和 IFC 验证闭环近邻，不冒充已经完成同一任务的两套直接替代系统。

### 2. 研究问题与动机

**研究问题**： 给定已有 IFC2X3 中受支持的局部缺失／错误，以及自然语言修复要求，如何把要求落实到正确的当前实例、标准属性和关系，并返回可核对的实际修复结果？

研究对象是“语言表达的修改如何在已有工程模型中准确实现”。定位目标、区分 Pset 与根 Attribute、区分 occurrence 与共享 Type、保证新增构件的宿主／楼层关系，这些构成具体语义负担；不是泛泛的“让 Agent 更安全”。当前没有承诺自主发现整个建筑所有缺陷，也没有承诺在缺少公开信息时猜回隐藏原值。

应区别：普通修改是改变已有状态；恢复是把事先确认的错误修到任务参考状态；生成是从要求建立新模型。三类可能共用工具，但任务与评测分母不能混用。

技术主文档中的 Repair Loop 包括用户澄清与恢复、阶段内有限输出纠正、产物核验和用户明确发起的下一轮请求。当前没有从最终 IFC 核验失败自动返回 Stage 1 的通用循环，因此不将其写成自主迭代修复或自学习的贡献。私有 G／损坏记录只在修复后进入独立评价，不作为生产纠正反馈。

### 3. 当前主张：已有 IFC 的局部、可回滚、可追溯语义修复

暂定标题保留：

**IFC-SemRepair: Schema-Grounded Repair of Existing IFC Models with Semantic ChangeSets**

**核心 Claim**： 我们展示一个直接面向已有 IFC2X3 的自然语言语义修复系统，将当前模型和标准知识中的语义依据落实为实例绑定的局部 ChangeSet，以请求级事务完成修改，并将来源、实际变更与 L0／L1／L2 证据相连；失败不提交部分修复，成功结果可按具体语义事实核对。

“语义 ChangeSet”是内部表示，不是新的 buildingSMART 开放标准。“可回滚”目前指失败事务不提交，不能未经实现核实扩成成功后任意选择性 Undo。“可追溯”指事实、操作和产物检查之间的对应，不仅是聊天日志。

| 贡献候选 | 相连的技术内容 | 相比只列功能，多回答了什么 | 当前证据边界 |
|---|---|---|---|
| C1 当前模型依据驱动的局部语义修复 | 目标实例、标准属性、值类型、单位、occurrence／Type 来源进入统一修改意图与 Manifest | 用户的要求怎样在真实 IFC 中变成正确字段与关系，而不只是检索一个词或生成完整模型 | 已有解析、来源与受支持操作；不宣称通用新 grounding 算法 |
| C2 请求级事务化 IFC 修改 | 语义范围与关联对象进入同一 ChangeSet，在候选状态原子执行，失败不部分提交 | 多项修改怎样作为一件完整修复处理；如何避免把未完成的一半当成果 | 已有 staging、原子写入、失败路径与历史测试定义；本轮未新跑，成功后任意撤销未确认 |
| C3 贯通的语义追溯与分层核验 | 同一 operation／fact 的来源、写入动作、实际对象、expected／actual 和检查证据相连 | 能说明“为什么改这个、究竟改了什么、哪一项证据证明完成或失败” | 有 SemanticAssignment、application records、终态证据与三级检查；完整统一 UI 和全链覆盖效果仍需核对 |

三个候选的价值在配合关系，不在单独发明检索、事务或日志。C1 提供具体待改语义，C2 将其作为完整修改提交，C3 检查该修改的真实结果并保留来由。已有某个组件不等于已有这套面向原生 IFC 的完整修复系统；但系统组合本身也必须有实际任务价值，不能只把熟悉组件排列成新图。

效率作为横向目标保留：当前有局部模型输出、索引、有界候选与验证缓存／调度实现，但整体速度和 token 优势待测，不放进已经证实的效果 Claim。请求级回滚和追溯见技术文档 §3.2，效率边界见 §6。

这是一组有实现依据、仍待最接近系统完整核查的 Demo 贡献候选。暂不宣称所有原子模块首次、已优于所有 Agent，或已经建立新的通用算法理论。

### 4. RAMC：对方具体做了什么、碰到我们哪里？

原始依据为《Software Model Evolution with Large Language Models: Experiments on Simulated, Public, and Industrial Datasets》，作者 PDF §III–IV、图 2–3。[R]

RAMC 的起点是当前编辑相对前一模型版本的差异；它从历史变更检索样例，序列化 Simple Change Graph 后由 LLM 补全，再解析成模型补全建议。它并不只新增节点，也能表达删除及属性变化。

**重合**： “不重写整个模型，而是表示并生成局部变更”已存在。因此不能把 JSON 替代图、给变更绑定实例，单独视为新方法。

**差别**： 我们从自然语言修复要求与当前 IFC 出发，依靠标准记录、当前实例和受支持操作实现修改；不是从软件版本历史预测下一步编辑。该差别说明任务不相同，但不自动证明算法新颖。

**保留问题**： IFC 的属性身份、来源及关系约束是否要求一种超出现有变更表示的机制？当前尚未给出这种机制的证明，不靠增加字段名或另造 IR 文件补足。

### 5. Self-Verification：有真正的 IFC 检查，不是模型口头自评

原始依据为《A Self-Verification Framework Toward Reliable Text-to-BIM Generation》，EC³ 2026 两页正文、图 1–2。[S]

其 Specifier 在首轮形成 IDS／非 IDS 规格；Modifier 生成和修改 IFC；IfcTester 执行 IDS 检查，Verifier 生成并执行补充代码，两类反馈用于后续迭代。论文有一个住宅五轮示例，并说明初始规格遗漏会影响后续验证。

**重合**： 自然语言要求、结构化规格、修改 IFC、检查并反馈的链条已有，不能把它说成“只生成、不修改”或“只让 LLM 看结果”。

**差别**： 其展示围绕从设计要求迭代生成模型；我们的当前 Repair 聚焦已有 IFC 的局部问题，使用注册操作、实例化变更及操作级结果检查。它的 IDS／非 IDS 两类验证不是我们 L0／L1／L2 的同一分层维度，不能比较层数宣称优越。

**保留问题**： 固定操作 policy 与请求特定事实结合，是否比其工具／动态检查路径在明确任务上有增量？当前只登记问题，不把论文的单例失败当成其系统能力上限，也不立即设计大规模对照。

### 6. 对这两篇的比较结论

| 维度 | RAMC | Self-Verification | 本项目当前定位 |
|---|---|---|---|
| 主要问题 | 已有软件模型的编辑补全 | 文本生成 BIM 的规格满足与迭代改进 | 已有 IFC 的自然语言局部修复 |
| 输入重点 | 当前差异和历史变更 | 设计要求及后续反馈 | 当前模型、用户修复要求和必要的公开补充 |
| 表示／执行组织 | 变更图与模型补全建议 | IDS／非 IDS、工具和动态 IFC 代码 | RepairIntent、标准／实例解析、Manifest、Bound ChangeSet |
| 对我们最直接的挑战 | 显式、局部变更不是新思想 | 规格—修改—验证闭环不是新思想 | 不能仅以领域更换或模块重命名回应 |
| 尚可主张的任务化增量 | 非历史补全任务 | 非从零生成任务 | 面向当前 IFC 状态的语义修复系统与可检查结果；效果未知 |
| 原生 IFC 操作 | 论文实现围绕软件模型补全，不是 IFC2X3 修复服务 | 确实生成和修改 IFC，不能说它不碰真实 IFC | 从已有 IFC 接续局部修复，不要求先经过本系统生成 |
| 局部表示与效率动机 | §IV.B 已用模型切片／变更图降低上下文负担 | 论文没有给与本项目可直接比较的耗时／token 结果 | 局部输出、有界上下文与验证加速代码存在，优势未测 |
| 请求级失败回滚 | 所读正文未建立针对 IFC 请求事务的放行与回滚合同 | 两页论文未定义或验证一整组请求级原子回滚合同 | 候选隔离、失败不部分提交；不是成功后任意 Undo |
| 追溯内容 | 以历史变更为检索与补全依据，不能说没有历史信息 | 有规格、检查反馈及迭代过程，不能说没有过程记录 | 明确到 fact／operation／actual entity／check 的语义来源链；全覆盖质量待核 |
| 整体等价性 | 是编辑表示的机制近邻，不是同任务替代 | 是 IFC 检查与修订近邻，不是已证实的相同产品合同 | 两篇的局部重合不能合并成一套已存在的完整本项目 |

“RAMC + Self-Verification 已覆盖所有工作”也不成立：两篇共享部分机制，不代表它们已实现本项目的所有 IFC 语义、操作合同与用户交互。正确判断是：宽泛机制首创不能保留，具体任务化贡献仍可讨论；这不等于已经确认存在独立新方法。

其他近邻如 IFC-Agent、MCP4IFC、Wu、CADIR、ATLAS 等继续保留在文献矩阵；本轮没有因为只重点谈两篇就忽略其余攻击。

#### 6.1 为什么这不是只换一种领域文件

我们应该证明的不是“把 UML 换成 IFC”，而是同一个修复意图怎样跨越几种不同对象保持含义：用户说的对象、当前 occurrence、共享 Type、标准 Pset、宿主／包含关系、执行中新建的实体以及最终检查的实际对象。来源和作用域在这些步骤间丢失，就可能出现“值对但写错地方”或“构件补了但关系不对”。C1–C3 的关联正针对这些具体问题。

因此，局部事务与语义追溯可以作为论文的实质设计贡献来写，不必因其不属于新的模型训练算法就排除。更强的独立方法首创仍需额外论证；效率则属于需要数字支撑的效果，而非仅凭局部变更结构推定。

#### 6.2 尚不能忽略的直接近邻

IFC-Agent §6.3 明确承认修改后模型一致性验证不足，这支持具体的结果核验差异；但 Wu 2026 已有构件改动与重评价，仍需核对它的完整执行、回滚和追溯合同。不能用 RAMC 不是 IFC 就避开真正的 IFC 编辑系统。

IfcOpenShell 官方 `file` API 已列出 transaction、discard、undo 与 redo。它说明基础事务／撤销不是新的 IFC 能力；并不说明每个调用 IfcOpenShell 的 LLM Agent 都已把一次自然语言请求的全部语义修改封装成同样事务。本项目读取到的回滚实现采用候选隔离，不据底层工具能力推断已提供成功后的完整 Undo 功能。[T]

### 9. 实验设计登记：目前暂停，不排规模

核心评测原则是：对预先保存的原始 G 做受控损坏得到 D，运行 Repair 得到 R，最终按 G–D、D–R、G–R 核对真实损坏、实际变更和目标恢复。L0／L1／L2 已有，不另起一套替代门槛。

G 和损坏真值仅用于独立评测，不进入生产 Prompt、检索或重试反馈。对于缺少公开恢复依据的任务，不能要求猜回隐藏值；澄清成功与修复产物成功分开。仍存对象优先保持身份，被删除后新建对象按冻结角色对应；不要求 STEP 文本逐字相同。

以下只登记需要以后讨论的事项，不提供任务数、重复数或调用预算：目标事实／保持条件的边界；公开请求与补充信息的来源；比较器对当前操作的覆盖；一个足以展示语义问题的最小案例；是否需要对照及如何避免工具能力不匹配。

| 设计项 | 状态 | 执行许可 |
|---|---|---|
| v0.3 的 48 任务／288 次运行方案 | 规模被用户认为偏大，转为未批准历史草案 | 不执行，也不作为默认计划 |
| 单案例 G–D–R 演示建议 | 仅建议，待 Claim 范围确认后再讨论 | 未新增真实调用授权 |
| Stage 2 确定性 Draft 对照 | 待定问题 | 不改生产代码、不执行消融 |
| 新数据集与新实验批次 | 尚未冻结 | 不启动 |

#### 9.1 从旧稿保留的评测设计要点

以下内容从 v0.3 研究草案和三方比较协议收拢，供以后确定实验时使用。它们保持设计草案身份，不表示新实验已经批准、实现或执行；48／288 的旧规模不恢复为计划。

| 设计问题 | 保留的具体要求 |
|---|---|
| 参考与损坏是否成立 | G 事先满足本任务的目标事实；G–D 必须证明至少一个目标事实被破坏。源模型原有问题预先记录，不算作此次新错误。普通设计变更另设预先确认的目标，不能强迫结果等于旧 G。 |
| 公开信息从哪里来 | 请求及澄清回答来自独立任务要求或公开模型依据，先于输出冻结；不能让评测器读取私有 G 后为系统生成回答。明确给值、模型参照辅助、信息不足三类任务分别报告。 |
| 如何匹配补回构件 | 存活对象优先按稳定身份匹配；新对象按预先固定的角色、位置、几何和宿主一对一对应，不用“待评分属性刚好正确”选择最有利匹配。重复补建、匹配歧义和读取失败不能通过严格成功检查。 |
| 如何规范化差异 | 数值先统一单位，几何容差和必需身份规则在运行前确定；忽略无语义影响的 STEP 排序，不能因此忽略属性来源、共享关系或任务要求的身份。 |
| 如何计算恢复与成功 | 恢复率只以实际损坏的目标事实为分母，逐案例报告并按类别汇总；严格成功要求正式产物、目标事实、保持条件和适用检查全部成立，且没有范围外实质改动。 |
| 失败与保持怎样计入 | 所有冻结尝试及重试成本保留，超时、解析失败、无输出不得从分母删除。无产物的恢复计 0、产物保持记 N/A；另报首轮与澄清后完成情况、被额外改变的事实／对象和检查覆盖。 |
| 比较器如何自检 | 用未修的 D、参考 G、错字段／错对象、目标恢复但误改其他对象、错宿主／楼层、重复补建、仅 STEP 重排及合法新身份作正负控制；这些自检不计入模型成绩。 |
| 划分与公平对照 | 同源模型的损坏与措辞变体留在同一划分，按源模型分组报告；工具 Agent、同操作能力直接输出与完整系统采用可比的模型、公开信息、工具及预算，同一独立评测器计分。不得弱化基本合法性检查来制造弱基线。 |
| 阶段对照与效果解释 | 确定性草案与 LLM 草案仅为待讨论对照；若复用冻结上游输出，只解释下游差异。完成率、错误发布和成本一起报告，不能把筛掉更多产物直接称为修复能力提升。 |
