# IFC-SemRepair：原始—损坏—修复三方比较协议

> **历史设计参考，不再持续维护**： 当前比较实现与 L0／L1／L2 的关系见 [技术主文档](../../../architecture/ifc-repair-pipeline-status-and-roadmap.md)；评测原则、后续设计、批准状态及实际结果统一进入 [Claim 与实验](../claims-and-experiments.md)。本文不构成新的实验执行指令。

> 日期：2026-09-21｜版本：v0.3｜状态：实验设计，尚未执行本协议的新实验。
> 目的：用独立参考证明目标被恢复，同时区分意图理解、实际执行与非目标保持。
> 范围：已有 IFC2X3 中受支持的属性修正与构件补全；不把普通字段编辑扩称为完整工程性能修复。

### 1. 直接回答

是的，主评测就采用用户提出的链条：原始 IFC → 受控损坏 → 运行 Repair → Compare。

关键不是额外增加一个复杂评测框架，而是让三个文件各自承担不同角色：原始文件 G 是预先存在的参考；损坏文件 D 是系统真正看到的输入；修复文件 R 是系统实际写出的结果。比较程序读取真实 IFC，不接受 Agent 的“完成”声明作为答案。

```text
评测准备：原始 IFC G ──受控损坏──> 损坏 IFC D

生产修复：D + 公开请求 q + 允许的公开资料
                         ↓
                     Repair 系统
                         ↓
                     修复 IFC R

独立评测：已保存的 G + D + R
                         ↓
三方 Compare：G–D（损坏核验）+ D–R（修改核验）+ G–R（恢复核验）
```

G、私有损坏记录和参考答案不进入生产 Repair，也不进入其检索库、Prompt、澄清回答生成器或自动重试反馈。它们在预测产物保存后供私有比较器使用。公开请求可以包含合法的用户要求，但不能从删除脚本机械复制被删 GUID、完整几何或 gold ChangeSet。

### 2. 三次比较分别证明什么

| 比较 | 要回答的问题 | 不能替代什么 |
|---|---|---|
| G → D | 计划损坏的目标真的坏了吗？是否顺带破坏了其他内容？ | 不能仅凭损坏脚本返回成功就确认损坏有效 |
| D → R | 系统实际改了哪些实例、属性、关系或几何？ | 有差异不等于差异正确 |
| G → R | 目标是否恢复到预先定义的参考语义？还剩哪些差异？ | 不能用文件字节或全模型相似度替代具体事实 |

对于恢复实验，令参考修复变化为 Δ* = Diff(D,G)，预测变化为 Δhat = Diff(D,R)。比较的是经身份对齐和语义规范化后的变化，而不是要求二者的 STEP 行号、序列化文本或低层操作序列相同。

BIM-Edit v3 附录 D–E 已使用输入、参考、预测三种模型和对应变化集合，明确避免未变化结构主导评分。因此三方比较是合适的证明方法，而不是本项目的独立首创。[S1]

### 3. 先明确“原始模型就是正确答案”的条件

G 必须先满足本次目标事实和当前生产入口所需条件，并且公开任务 q 与 G 中被评测的目标一致。它不必被夸称为整个工程的绝对无错误模型。

如果用户真正要求的是一个新的设计值，而不是恢复原状态，参考答案应是预先人工确认的新目标模型 G* 或目标谓词，不能强迫 R 等于旧 G。本协议的主实验只做与原始参考一致的受控恢复，普通设计修改另列。

如果原模型本就存在未解决问题，应在运行前记录。不得把这些原有问题计成此次修复新引入的错误，也不能在看到结果后临时放宽生产门禁；会阻断当前入口的源模型应在冻结测试集前排除或作为单独问题集。

### 4. 如何获得公开请求，而不把问题变成“猜丢失的信息”

#### 4.1 推荐主设定：有用户要求的语义恢复

例如，预先确认的设计要求是“二层走廊的这扇门耐火等级为 EI60”。G 中对应值是 EI60，损坏程序将其改为另一合法标签；公开请求用自然语言要求恢复到 EI60，但不提供标准 Pset 路径、被删身份或参考补丁。

这不是无提示恢复隐蔽历史值，而是在检验：能否理解要求、定位当前实例、选择正确 IFC 字段、写入并恢复相关状态。论文应准确称为“自然语言引导的修复”，不是自主发现全部缺陷。

请求建议由独立的工程任务清单/公开设计说明编写，并在损坏方案及输出出现前或独立于损坏执行冻结；第二人检查它与参考模型是否一致。若请求本身明确给了目标值，它会降低值推断难度，但不等于应隐瞒它已提供了答案的一部分。

#### 4.2 上下文辅助设定：必须有公开证据

例如用户明确要求沿用当前模型中某个已存在、已确认的 Type，或者保留的 Opening 提供了定位与几何依据。只允许使用生产系统在 D 与公开资料中确实能访问的事实；“旁边看起来相似”不自动证明应复制其属性。

这类实验单列，不与信息更充分的任务混成一个成绩。

#### 4.3 信息不足设定：澄清，不评分为猜中隐藏值

删除了耐火标签，D 中没有设计要求，用户只说“修好”，那么原值可能有多种，系统不能从信息上唯一恢复。正确动作应是询问；预先准备的回答由独立用户规格提供，而不是比较器读取 G 后现编。

主修复完成率只在信息足够、能力范围明确的任务上定义；澄清集另报正确询问、回答后完成率及轮数。不要把一次询问立即计为已修好。

### 5. 推荐先做哪些损坏

| 组别 | 受控损坏 | 修复重点 | 与当前实现的关系 |
|---|---|---|---|
| P1 单属性缺失 | 移除一个受支持 occurrence 的直接标量属性；其余语义不变 | 找到标准属性并补回值、类型与来源 | 与现有 occurrence 属性操作直接对应 |
| P2 单属性错误 | 将一个已有直接标量值改成同类型但不符合要求的值 | 纠正实际字段，而不是改相近字段或共享 Type | 适合作为最先验证的稳定切片 |
| P3 复合语义损坏 | 同模型中两个目标的直接属性缺失/错误，包含跨 family | 每项要求是否都得到实现，其他属性是否保持 | 使用已有多操作能力，不宣称一般依赖规划 |
| C1 有界构件缺失 | 删除可由当前 add_beam/add_column 表达的简单梁/柱及必要关系 | 受支持几何、楼层、Type 及要求的属性恢复 | 仅选可重建且公开信息充分的模型；先核对比较器覆盖 |

诱饵不是另外制造不可修的坏数据：例如原模型同时含 Tag 与 Reference、多个同名构件或多个 occurrence 共享 Type；损坏只针对当前可修的字段，用诱饵考察是否理解正确。

不要为了实验人工创建错误共享 Type、复杂列表属性、斜梁或任意几何损坏，再把现有系统本就不支持的任务混进主成功率。这样的任务可作范围外说明，但不是检验受支持能力的主分母。

Door、Window、Opening 的新增/填充有注册实现和历史证据，但不自动获得 R1 的本次新验收资格。窗口/洞口恢复可以作为很直观的展示案例，在独立检查其几何、关系和比较适配后加入；不为凑数量而扩大主实验。

### 6. 一次示例报告应该长什么样

下表是设计示例，所有值均为说明用途，不是本轮实验结果。

| 检查项 | 原始 G | 损坏 D | 修复 R | 判定 |
|---|---|---|---|---|
| 目标 Door 的 FireRating | EI60 | EI30 | EI60 | 被损坏的值恢复 |
| 属性所属路径与值类型 | DoorCommon / IfcLabel | 相同 | 相同 | 写在正确字段 |
| 目标 Door 的其他直接属性 | 原值集合 | 保持 | 保持 | 无额外语义改动 |
| 共享 Type 及其他 Door | 原状态 | 保持 | 保持 | 相关非目标保持 |
| 门的几何与宿主关系 | 原状态 | 保持 | 保持 | 无额外几何/关系改动 |
| 文件重开与适用检查 | 通过 | 通过 | 通过 | 产物可用 |

对于“删掉窗户再补回”的案例，表格换成：目标存在、类为 IfcWindow、几何容差、目标宿主、Opening/void/fill、实际适用的楼层归属、Type 和要求的属性。不能仅凭一个形似窗户的盒子出现就判恢复。

### 7. Compare 不能只按 GUID 或字节相等

#### 7.1 仍然存在的对象

优先按稳定 GlobalId 匹配。属性修改任务中，目标 occurrence 的身份保持可以是明确要求；不能允许删除重建所有对象后只检查最终形状。

#### 7.2 被删除后重新创建的对象

新对象可以有新 GlobalId。评测器需要按冻结的角色/位置/几何/宿主条件进行一对一对应，再读取该对象的真实属性和关系。不得使用“被评测的属性值刚好正确”作为挑选最有利匹配的主要依据，否则错误会被匹配过程隐藏。

原始目标身份与原始角色只在私有比较阶段使用。应用日志中的新对象映射可作为线索，但必须回读 R 验证对象确实存在、角色成立、没有重复补建。匹配歧义或读取失败应记为无法评价/诊断失败，并阻断严格成功，不随意挑一项。

IfcDiff 官方文档明确假设同一对象在前后模型中具有一致 GlobalId。它适合保留对象的差异诊断，但不能独立解决“新 GUID 的补回构件与原始目标是否等价”。[S2]

#### 7.3 规范化和容差

枚举、布尔、标签和标识符按冻结语义规则比对；字符串不默认采用模糊相似度。数值按单位换算到统一量纲再比较。几何容差沿用适用操作的既有冻结标准，新增类型再预先定义，不能看到结果不通过才调整。

STEP 编号、排列顺序等序列化差异不作为语义失败。OwnerHistory 等作者信息不能一律忽略：只有预先声明为本实验非必需的表示差异才排除。共享关系实体的拆分或复制也应比较其承载的语义，而不是只数底层节点变化。

“不要求字节完全相同”不等于允许任意丢失属性、GUID 或关系。

### 8. 指标：先独立报告，不急于加权成一个总分

对案例 i，预先定义：目标所需事实 T_i、允许受本次修复影响的语义范围 A_i、必须保持的检查集合 P_i。

在确认损坏后，定义 B_i 为 G 中成立、D 中已被破坏的目标事实集合。要求 B_i 非空；否则该样本没有真实损坏，不进入修复成功率。

#### 8.1 损坏事实恢复率

```text
恢复率_i = R 中重新成立的 B_i 事实数 / B_i 事实总数
```

它回答“坏掉的部分恢复了多少”。默认逐案例宏平均，避免包含很多事实的大模型支配结果；各损坏类型另外分组。没有正式 R 时该任务恢复率计 0，诊断候选结果单独记录，不以诊断候选代替交付成功。

#### 8.2 严格任务成功率

```text
成功_i = 正式修复产物存在且可重开
         AND 适用的生产检查通过
         AND T_i 中全部必需目标事实成立
         AND P_i 中全部保持要求通过
         AND 没有冻结范围外的实质语义改动
```

成功率的分母包括主集合的全部已冻结尝试：Provider 错误、超时、无输出、解析失败不能删除。若失败纯属基础设施，保留总结果并补充失败原因；不得悄悄换成成功重试覆盖。

没有产物时，保持指标单独标 N/A，并在严格成功中计失败；不把“源文件没被改”算成修复产物保全成功。

#### 8.3 保持与新问题

记录范围外发生改变的事实/对象数量、出现改变的案例数，以及检查过多少对象和类别。保留类别、属性来源、关系、几何分别报告。不能仅用一个接近 100% 的全模型保持率掩盖少量但重要的新错误。

#### 8.4 分层诊断与成本

属性恢复、几何恢复和拓扑恢复独立报告；某类不适用就标 N/A。意图/目标解释正确率是机制诊断，不能代替最终 R 对 G 的判断。

同时记录 first-pass、预先允许的澄清后成功、调用数、实际 token、耗时以及重试/失败成本。仅最终成功提升但成本大幅增加，也必须如实呈现。

### 9. 三方比较如何覆盖“理解错但执行一致”的问题

如果系统把用户要求解释为错误属性，生产写入与检查可能共同采用错误解释。但 G 的独立目标事实已经在运行前冻结，因此 G–R 的任务级核验可以发现没有真正恢复。

所以用户提出的三方链条，正好能补充上一轮对共享 Manifest 的担忧。无需再把“系统能自证理解正确”作为先决条件。

但不能只做“全局 G–R 看起来差不多”：若参考模型和评分器都只读系统自己选中的字段，仍可能循环自证。比较所用的目标、字段身份、单位和保持条件必须预先由任务与参考事实定义。

### 10. 在评测系统前，先检验比较器

| 比较器控制样本 | 预期 |
|---|---|
| 把 D 原样当作 R | 目标恢复必须失败，防止“只要能打开就成功” |
| 把 G 当作 R | 参考自检应通过；仅测试评测器，不记作模型成绩 |
| 值正确但写入错误 Pset 或错误 occurrence | 必须失败 |
| 目标恢复，但另一扇门属性被顺带改变 | 保持检查失败 |
| 构件形状正确，但宿主/楼层错误或多补一份 | 必须失败 |
| 只重排 STEP，必需语义不变 | 不应误报语义失败 |
| 仅被删除目标使用新 GUID、且符合既有身份政策 | 对齐后判定，不因 GUID 本身机械失败 |

这些检查是评测可靠性基础，不是新的 AI 方法。优先复用既有测试，不触发无关全仓库 preflight，也不把测试通过数换成模型能力指标。

### 11. 与现有仓库如何衔接

本轮只读检查得到以下事实，未运行脚本：

| 已有入口 | 本轮核实到的行为 | 接下来的用途 |
|---|---|---|
| `scripts/ifc_repair/compare_ifc_files.py:24–65` | 按 GlobalId 生成通用两文件差异报告，包含 Type、位置、几何指纹和直接属性等；正常流程返回 0 | 生成 G–D、D–R、G–R 辅助诊断；退出码 0 不等于修复成功 |
| `scripts/ifc_repair/compare_ifc.py:36–210` | 封装 IfcDiff、可选跨 GUID mapping、Window occurrence comparison；`--blocking` 针对已生成的 Window occurrence 报告 | 复用适用的 Window 比较；不自动扩称全 family 的严格三方评分器 |
| `src/text2ifc_ifc_repair/benchmark_evaluation.py:51–180` | `BenchmarkEvaluationInputs` 接受私有 original 与 mutation-role mapping；比较角色语义时不要求 GUID 相同；私有 Gold 不能提升失败的生产结果 | 使用已有私有评估边界；逐操作核对抽取器和适用 policy |
| 同文件 `:183–205` | 额外 occurrence 报告有版本和 Window operation 条件 | 新属性/梁柱用例不能只因函数存在就认定此细粒度报告已覆盖 |
| R1 capability manifest `:28–70` | occurrence 标量属性、受限梁柱、澄清及多操作已有不同级别证据 | 冻结任务时按操作范围绑定；注册、历史展示、本次测试三者分开 |

因此不需要从零新写 Compare。最小增量是统一三份差异、独立目标检查、保持检查和每案人读报告，并补齐本次范围内尚缺的映射/检查适配。

历史 R1 中无合法原始参考三元组的案例仍保持 N/A，不能把新评测协议事后套回去制造旧 Gold。新建样本在执行前就保留 G，是合法的受控实验。

### 12. 推荐产物布局

```text
case-XXX/
  public/
    damaged.ifc
    request.txt
    context.json            # 仅允许的公开上下文，可为空
  private/
    original.ifc
    mutation.json           # 隐藏损坏角色、原值与操作日志
    reference-checks.json   # 预先冻结的目标/保持规则
  prediction/
    repaired.ifc            # 真正正式结果；无输出时不伪造
    run-ledger.json
    public-evaluation.json
  evaluation/
    damage-diff.json
    repair-diff.json
    residual-diff.json
    target-and-preservation.json
    REPORT.md
```

这是建议的整理结构，不代表现有机器 Schema 或生产 run 格式；实现时应接现有产物，不重复建立另一套权威。把 private 放到独立目录还不够，生产 Agent 的工具可见范围也不能包含该目录。

展示包可以在评测完成后放出原始—损坏—修复三份模型供人查看；这不等于允许在运行中把原始模型传给 Repair。
