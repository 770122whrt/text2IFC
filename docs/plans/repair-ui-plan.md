## 1. 目标与优先级

用户在三维建筑中选择构件，用自然语言提出局部修改，观察系统理解、澄清、修改和检查的过程，再通过同视角前后切换看清几何变化。

优先级是：**几何变化看得见 → 点选与输入直观 → 产出清楚可读 → 过程可追溯 → 技术详情按需展开**。首个真实用例为“点击墙体→在墙上新增窗户”，第二个为“以选中柱子为参照，在旁边新增柱子”。不能因界面能演示任意新增就宣称后端已经支持所有几何。

Generation 当前不开发，不放空菜单和无效入口；通用三维/对话组件避免不必要的业务耦合即可。UI 不重开四组模型实验，不改写已有成绩、任务审核或 Proof。

## 2. 用户已确认的界面边界

| 项目 | 当前决定 |
|---|---|
| 构件点击 | 高亮并显示实际名称、类别和可得楼层，不自动弹出完整 Property 表 |
| Property | 单独点击“查看属性”后按需读取，优先代码/现有索引，不额外调用 LLM |
| 修改方式 | 三维选中对象＋自然语言＋必要澄清；普通无选择请求也保留 |
| 布局 | 三维为主、右侧对话、底部可展开过程与文件，代码不常驻占据大面积 |
| 代码 | IFC、ChangeSet、差异只读；可查看/复制，不提供手写 STEP 后直接保存执行 |
| 前后切换 | 阶段一必做；同一相机、坐标基准和缩放，明确当前版本 |
| 过程内容 | 可读摘要优先；展开后看真实已产生的中间文件 |
| 复用 | 采用成熟三维、IFC 导入与编辑器组件，复用 RepairAPI，不重新开发 IFC 内核 |

“代码只读”不意味着建筑不能修改。用户输入“在这面墙上加窗”，系统仍正常执行并输出新 IFC；只是代码面板不是另一套绕过 Repair 的编辑执行器。

| Repair/Generation | 均不启动，不调用 LLM，不改实验账本与源 IFC。真实修复前后切换保留在后续阶段，不因目前只测输入加载而制造结果。 |

样本在看结果前登记。LFS 指针只算“内容未恢复”，不能当作 IFC 加载失败；只恢复明确选定路径，不展开整个数据集。完整 IFC2X3 的判定来自文件 Schema 而不是扩展名。文件打开、返回几何、模型可见、构件覆盖/诊断分别记录；有诊断就明确标记，不把“250/250”或截图存在等同标准校验及每个面完全正确。此次为多样例冒烟检查，不是全库/所有 IFC2X3 的全面认证。

### 2.2 本轮执行：打开文件、统一高亮、模型树与可读属性（2026-10-10）

1. “打开 IFC”必须经实际文件选择器验证，保留失败导入不丢原模型/草稿的行为；当前本地打开不称为服务器上传。延续已登记12个IFC2X3样本，存在诊断与缺件如实显示。
2. 用户截图的选中墙斑驳先复现定位。高亮覆盖所选 IFC 构件的所有网格，采用一致颜色；保留深度测试，不透过真实遮挡物，不扩大到其他共面对象，不移动顶点或修改源材质。取消选中恢复原材质、透明度和显示设置。共面竞争用显示层的有界深度偏置处理，不用关闭深度测试冒充修复。
3. 模型树参考用户截图的类别分组（Project/Site/Building/Storey及Elements→IfcClass→对象）；数量全部从当前文件读取，不复制截图中的计数。隐藏、无Body、解析缺网格分别标注；点击无可视网格对象可读属性但不高亮不存在的几何。树节点操作遵循查看/选中提交，目录展开本身不绑定参照。
4. 属性保留原Pset/字段名、数值、布尔false、0、缺省与单位；实例和Type分开，不把层高等推断写成源值。嵌套/复杂值按可读层次显示，未支持表达保留为可展开原始数据。Property读取失败不丢草稿，过期异步结果不能串到别的构件或模型。
5. 验收包含真实文件导入/下载字节一致、类别数量、搜索定位、树/三维联动、读属性、高亮清除/遮挡保留、旋转/右键隐藏回归。开发截图展示完整界面与斑驳修正前后，不新增用户截图管理功能。仍不做测量、剖切、视点保存或Repair接线。

### 2.3 当前决定：中英界面切换，随后接入 Repair（2026-10-10）

用户反馈已人工查看多份 IFC，认为渲染基本合适、效果良好。本记录是用户的显示确认，不替代既有解析诊断，也不推定未记录文件或所有 IFC2X3 已全面认证。版本管理、Git 式分支和共享协作不开发；不因本轮决定删除原有运行证据或开发仓库历史。

先完成中英界面切换：页首提供“中文 / EN”，默认中文并在本浏览器保存选择；存储受限时仍可在当前会话切换。菜单、按钮、模型树辅助文字、属性分组、状态/错误说明、占位符和无障碍标签随语言更新。IFC 名称、类别、GlobalId、Pset/Qto/属性名、源字符串、原始 JSON、用户请求及未来 Provider 原始输出不自动翻译。布尔、缺失值只改变显示标签，不改变值；单位和几何配置不变。

切换仅更新展示，禁止重载 IFC、再次解析几何、重置相机/隐藏列表/主辅参照/草稿/待执行请求/搜索或清空已展开属性。不得触发新的 Repair 或模型调用。保留模型树与属性的展开状态、滚动位置；选择状态与物理颜色不受界面语言影响。英文界面需要检查长文案和常用笔记本屏幕布局。

验收先用字典/占位符/原值保持测试，再在真实 IFC 页面检查双向切换、语言偏好恢复、动态属性/隐藏/错误消息、相机与请求不变、真实文件打开和源下载一致性。不重做整个数据集或全库 preflight。实际记录写回同路径文档，不复制第二套版本。

中英切换完成后下一阶段按现有 RepairAPI 接线：本地 HTTP 上传/输入文件绑定 → 冻结自然语言与可选主辅参照 → 独立执行和真实阶段/澄清 → 接回候选与已发布 IFC → 同坐标同相机前后查看/实际产物下载。先离线完整接口和失败路径，再按适用准入与获准预算验证真实调用；不把本轮界面翻译当成 Repair 已接通，不重开四组比较实验。

本轮实际完成：`i18n.mjs` 提供界面字典、可重绘文案和存储降级；静态入口与查看器/模型树/属性渲染已接入，不改变原型状态机或几何内核。31项查看器Node检查（含7项语言测试）、27项新增真实Edge/WebGL2语言/保全/文件检查、原有18项真实模型交互回归均通过。原始结果与截图在 `ui/ifc-viewer/.artifacts/i18n/candidate-1/`；查看器使用入口仍为4178。下一步开始Repair接线，不继续扩展Viewer工具清单。

## 3. 界面与核心交互

### 3.1 主工作台

三维约占主工作区 65%–72%，右侧对话起始宽度约 320–380 px；比例是设计建议，不固定死。过程条默认紧凑，展开后呈现阶段说明和文件。属性、源码通过按钮打开，关闭后回到几何视图。桌面/笔记本优先，窄屏保持可滚动操作。

保留源材质；选中参照和本次新增使用不同样式及文字图例。高亮是显示覆盖，不改写 IFC 材料。按钮有可读名称、键盘焦点，颜色不是唯一状态提示；减少动画设置应被尊重。

### 3.2 点选、名称和按需属性

三维工具栏提供两个模式，默认“查看”。两者都允许旋转、平移、缩放和按需属性，均不是“新增窗/柱”的动作选择器。

| 模式 | 点构件的作用 | 请求行为 |
|---|---|---|
| 查看 | 只高亮浏览对象、显示名称等简卡 | 不改草稿引用，不发起修复；草稿与原引用保留 |
| 选中提交 | 点选对象作为下一条自然语言需求的参照 | 可移除参照直接描述；不要求先选操作类型 |

浏览对象、草稿引用、已提交请求的引用分别保存。切回查看后点其他对象只改变浏览对象；再次进入选中提交不自动带入刚浏览的对象，只有该模式下的新点击才更换草稿参照。参照标签保留并可明确移除，用户原文不随模式切换丢失。

卡片与图例必须依据实际对象及版本绑定，而不能仅依据当前模式标注“已选为请求参照”。切到选中提交但尚未重新点击时，刚浏览的其他对象仍标为“仅查看此构件”；明确移除引用后同样不得保留“已选为参照”的提示。原引用标签与浏览卡可以对应不同对象，应清楚表达两者各自作用。

拖动不是点击。点选只出简卡，Name 缺失时显示“未命名墙体”等降级标签，不虚构名字。已提交请求冻结原文、参照和基准模型版本；后续浏览、选取和模式切换均不改变它。

右侧只在空会话显示简短引导，有消息后收起宣传文案。示例通过独立“演示案例”入口查看，不常驻“加窗/补柱”模式按钮，不覆盖工作台草稿与消息。核心问题、阶段、结果采用适合桌面阅读的字号和对比度，减少重复小字；一个明确模式标识与按需来源详情保证真实性。

“查看属性”主动触发完整属性读取，区分实例与 Type 继承、单位和缺失值；不能把 null 显示为零或 false。属性读取失败不丢用户草稿或三维选择。轻量名称读取与完整 Pset/Qto 展开不是同一操作；前端按需展示不要求后台关闭生产所需索引。

“查看源码”为独立动作，不在每次点选时强制抢占三维空间。

### 3.2.1 查看模式右键隐藏（2026-10-09 补充）

查看模式下，右键短点命中的构件打开菜单，提供“隐藏此构件”；不能隐藏上一次左键选中的别处对象。右键拖动继续用于平移，拖动结束不弹隐藏菜单。选中提交模式不提供隐藏菜单。增加“撤销上次隐藏”和“显示全部”，始终显示当前版本隐藏数量。

隐藏只改变当前显示版本的可见性，不删除 IFC，不减少 Repair 的输入范围，不清除主/辅助参照。被引用对象被隐藏时，参照标签注明“已隐藏”；显示全部不改变相机、草稿或已提交记录。浏览、隐藏、位置信息预览均不构成模型修改。演示案例与工作台独立保存可见性；正式 IFC 使用解析出的实体映射，不把全部同类型构件当作一个隐藏对象。

### 3.2.2 主参照与辅助参照（2026-10-09 补充）

在选中提交模式，默认点选绑定“定位参照”；点击“添加参考构件”后，下一次有效点选绑定独立的“参考构件”，随后回到普通点选。再次点击辅助按钮或切回查看取消这次拾取，不删除已保存的两个参照。两者分别显示、分别移除，不能以第二次拾取覆盖原定位参照；同一对象不能误填为两个不同角色。

定位参照不等于确定性操作的 target：例如选中柱子可能只是位置基准，而真实 add_column 的 target 仍为楼层。辅助参照可能用于尺寸、类型、材质或空间关系，具体用途来自用户文字和澄清，不因一次点击就自动复制全部属性。不要求每题都选择两个对象；无参照、只有主参照、只有辅助参照的文字请求都保留。

两个引用与模型版本一起随提交冻结，随后浏览、替换、隐藏不改变历史请求。未接后端时只保存原始文字和这两个引用，不声称已经将其送入真实 Repair。对正式数据必须核验两个引用属于请求版本，并维持源文件只读。

### 3.3 选择对象进入 Repair 请求

需要新增/适配 `viewer selection → 公共构件身份 → 自然语言定位` 的连接层，而不只是显示对象名。

提交时冻结用户原文、输入模型版本和选择上下文；之后再点击其他对象只影响下一条草稿，不能改变已提交任务。原文与系统补充定位信息分别保留，不把自动拼接内容伪装成用户逐字输入。

Viewer local ID、STEP ID 与 GlobalId 建立显式映射并绑定模型版本，服务端用当前 IFC 核验。前端提供的名字、尺寸和属性不能直接作为真实几何权威。新字段通过适配层/适用的新接口合同引入，不悄悄修改已注册生产 Schema。

点构件不等于指定新构件落点。鼠标命中位置只有在明确的“在此放置”交互中才成为放置输入，第一版优先对象选择＋文字描述位置。对“右边/旁边”需考虑世界、构件与当前视角的差别；必要时澄清方向与距离，不让后续旋转相机改变已确认的设计方向。查看器居中变换也不能直接当作 IFC 坐标。

点柱新增柱时，选中柱可能只是参照，实际目标仍是对应楼层；点窗新增窗时，窗可能是类型参照，宿主应绑定正确墙体，不能将选中 ID 无条件写入 target。先验证受支持直墙窗洞和直矩形柱，不在 UI 阶段扩成任意建模系统。

### 3.4 澄清

缺必要尺寸、位置或有多个候选时，在对话中提问。输入框改为“回答这个问题”并保持可输入；推荐选项只辅助填写和预览，不代替文字回答。“预览位置/候选”与“发送回答并继续”分开，预览不应用修改。保留原生 clarification ID、状态版本和合法回答形式，过期答复不能套到新 run。

实际后端只接受结构化选择时，提供其合法的补充说明/重新澄清路径，不能伪装任意答案已被接受。设计原型的补柱示例可用明确声明的本地规则解析有限方向与米/毫米距离；不称作 LLM 理解，不把未识别文字悄悄替换为预设距离。

可从当前 IFC 唯一推得的事实不无谓询问，必要用户选择不由前端默认值替代。等待、回答和继续属于同一次任务，文件、上下文和累计用量不重置。

## 4. 阶段一：可展示的三维工作台

| 步骤 | 工作 | 交付/验收 |
|---|---|---|
| U1.0 设计预览 | 布局、点选高亮、简卡、按需属性、输入、过程抽屉和前后按钮 | 可操作原型，所有示意内容标识清楚，供用户审核 |
| U1.1 真实 IFC 加载 | 当前优先现有 dataset 的 IFC2X3 多模型实际加载、显示覆盖和基本交互核对 | 输入文件非 LFS 指针；列清加载结果、缺失及诊断；前后配对放 U1.3 |
| U1.2 对象联动 | 名称/身份映射、选择取消、参照标签、按需属性/源码 | 视觉对象、身份与数据一致，不串模型版本 |
| U1.3 前后对照 | 保持相机与坐标，显示新增对象，支持关闭高亮 | 无假位移；新增对象切回前版本有明确缺失提示 |
| U1.4 展示验收 | 2–3 个代表性真实案例，桌面/笔记本浏览器检查 | 几何变化可辨、信息清楚、无关键交互错误 |

阶段一正式验收必须使用已认可案例的真实输入和输出；不能临时绘制一扇不存在于 IFC 的窗就称为真实修复。需要大文件时仅按明确路径恢复，不展开整个数据集。

本轮 U1.0 可以使用明确标识的示意几何审核交互。它不是 IFC 解析器、真实历史回放或实际 Repair；不能将原型播放写成“阶段一已完成”。阶段一完成须满足 U1.1–U1.4。

未接后端时，工作台“提交需求”只保存本页待执行请求并明确反馈“接口未接入，未执行”，不改变模型、不生成阶段或结果。查看模式的主按钮只切换到选中提交，切换本身不发送；选中提交允许无参照的充分文字描述。

只有独立“演示案例”入口内提供“播放示例”。案例拥有独立请求、过程与展示，不得使用主工作台的任意文字却播放固定结果；退出案例恢复进入前的草稿、引用、消息、模型视角和版本。窗案例展示已知前后结果，柱案例演示位置澄清；均保留示意标签，不冒充历史 IFC 证据。

### 前后切换规则

1. 默认修复前；正式实现中只有实际结果可用才启用修复后。
2. 前后使用同坐标基准，不分别自动居中；相机 position、target、zoom、up 保持。
3. 存活对象可映射时保持选择；新增对象切回前版本提示“该对象在修复前不存在”，不跳到同名其他对象。
4. 切换是查看，不是执行撤销，也不改变下一任务的输入版本。继续修改的基准版本需要明确。
5. 未通过的可读候选单列“候选（未通过）”，不包装成已发布修复后。

## 5. 阶段二：基于现有代码的 Repair 接线详细计划

> 2026-10-10：本节为代码阅读后的实施计划，不是接线完成报告。实施基线采用当前已读取的 `bimnet-ui / codex/ui-development`。原工作树的更新未在本轮核验，不将其能力写为已实现；用户已明确暂缓最终检查后的C返工，因此无需为查找该模块再等待目录权限或额外决策。下文明确区分“已有”“拟新增”和“暂不做”。若后续发现影响现有修复能力的实际版本冲突，再单独报告。

### 5.1 核对结论与真正的接入入口

| 项目 | 当前代码事实 | 本次接入安排 |
|---|---|---|
| 原始入口 | `RepairAPI.start(source_ifc_path, repair_text, run_id=...)`，输入是 IFC 路径与自然语言字符串；不是前端直接发 ChangeSet | 保留该入口。点选数据先生成可读自然语言，再合成 `repair_text` |
| 场景定位 | `RepairAPI(..., scene_grounding=False)` 默认关闭；开启后进入 `generate_scene_repair_intent()` | UI 几何/参照场景显式绑定 `scene_grounding=True`，不把默认配置当作实验认可配置 |
| 用户澄清 | `continue_with_answer()` 已有候选、补充说明、原型授权、属性确认/拒绝和取消合同 | 用后端给出的 `answer_modes` 和 `answer_schema` 驱动控件，不另写自然语言执行器 |
| 自动输出纠错 | 普通 Intent 默认最多2次；ChangeSet最多2次；scene grounding最多8轮，包含查询和纠错 | 展示真实 attempt/round，不都命名为“修复了模型一次” |
| 最终检查 | `apply_and_evaluate()` 应用一次、重开、Evaluation，然后发布或终止 | 完整保留检查和发布规则；检查后不自动返工，仅留默认关闭的任务层扩展点，见§5.6 |
| 过程记录 | `RunStore` 有 state、transitions；Intent、查询、Draft、绑定、终端检查均有文件 | 增加只读过程投影、文件目录和少量动作观察事件 |
| HTTP/UI | 当前服务只允许GET/HEAD；前端请求只记为 `pending_backend` | 新增薄HTTP服务与独立执行器，不重写渲染/Repair核心 |
| 任意恢复 | `resume()` 仅支持特定边界；`clarification_required` 返回等待，`intent_ready`可继续，其余拒绝 | 刷新恢复查看与进程崩溃后恢复执行分开，不承诺任意阶段无损续跑 |

代码定位：`src/text2ifc_ifc_repair/api.py:146–285,287–524,526–872`；`scene_grounding.py:25–151`；`request_stage.py:118–295`；`provider_stage.py:63–84,184–336`；`orchestrator.py:153–339`；`ui/ifc-viewer/serve.mjs:24–40`。行号是本轮阅读定位，后续以函数名为准。

前端主路径应成为：

```text
当前实际 IFC + 用户原文 + 可选主/辅点选
  → 核对所选对象属于该 IFC
  → 把点选转为 Name/楼层/方位/必要坐标的自然语言补充
  → 用户可查看实际提交文本

  → Apply → 重开/Evaluation → 正式结果或明确失败
  → 读取实际输出 IFC → 同坐标前后查看/下载
```

### 5.2 点选转换为自然语言：不绕开原系统

#### 5.2.1 数据怎样传递

前端保留已有 `reference`、`auxReference`，新增服务端 `input_id` 与准备好的请求编号。提交准备接口接收：原始用户文本、输入文件身份、主/辅参照的版本和实体身份、请求文本语言；显示用名称/位置不能由浏览器自报后直接认作事实。服务端从该输入IFC重新读取对象，核对STEP ID/GlobalId以及当前文件，产生自然语言描述。

送给Repair的主输入仍只有同一IFC路径和完整自然语言。结构化点选快照仅用于核对、追踪和界面显示，不直接替模型生成RepairIntent，不把选中柱子无条件当作 add_column 的执行target。绑定和Audit仍走原流程。

建议用确定性模板生成点选描述，不额外调用LLM。名称、楼层、几何信息可复用 `readModelIndex` 的显示摘要与后端 `PublicScene`/IFC索引，但后端以当前IFC复核的数据为准。若准备阶段与Repair各建索引，首轮可以先接受小规模重复读取；需优化时按同一输入绑定缓存，不能未经核对复用前端174样例缓存。

#### 5.2.2 人读文本的组织

以下是说明格式的示例，不是174模型实测几何事实：

```text
用户要求：
在这面墙上加一扇窗，尺寸和参考窗一致，窗台离本层地面900毫米。

点选定位补充（由界面依据当前IFC生成）：
“这面墙”对应楼层“Level 1”中的 IfcWallStandardCase，
Name为“<源文件真实名称>”，位于本建筑模型X正向一侧。
<必要时补充：该对象在IFC世界坐标中的几何范围/定位中心。>

点选参考补充（由界面依据当前IFC生成）：
“参考窗”对应楼层“Level 1”中的 IfcWindow，
Name为“<源文件真实名称>”，位于上述墙体上。
仅按用户要求参考其尺寸；位置仍需按照用户要求确定。
```

`user_text`、`selection_context_text`、`effective_repair_text`分别保存。界面原消息不伪装为系统扩写后的原话；增加可展开的“本次定位补充/实际提交内容”，不新增操作菜单。用户修改草稿或参照后，旧的准备结果失效；最终开始时冻结同一个准备结果。中文/EN界面切换不重写已经准备/提交的文本。

默认描述顺序为实际Name＋IfcClass＋实际楼层名＋可核实的空间位置；重名时再加世界坐标范围、同宿主或相对关系，不单靠Name。保留技术实体身份在侧车记录中，先不强制把GUID堆进用户正文；描述仍不能唯一区分时必须澄清，不因点击过就允许解析成另一对象。

另拟新增“点选语义回读检查”：原生模型完成理解/解析后，核对用户明确说“这面墙/参考窗”的引用，是否与解析出的宿主/参照对应。不是简单要求所有operation.target都等于主点选（新增柱的执行target可能为楼层）。若不一致则在应用前要求澄清或停止，不能偷偷覆盖模型产出的目标，也不能执行后才忽略错对象。这是新的接线合同/检查点，当前API没有完整现成入口；必须在U2.1/3单独实现并验证，不能把被动进度observer兼作隐藏的修改路由。未表达明确用途的辅助参照不强制当成复制全部特性的授权。

#### 5.2.3 不能让方位描述制造歧义

- `Name`必须是原Name，不把“二层东侧墙”这样的生成描述塞进精确Name字段。`Level 0/1/2`保留源楼层名称，不擅自翻成建筑实际层数。
- 墙的“位于东侧”与墙轴“朝北/南”不是一件事。当前 `PublicScene.overview()` 把IFC世界X/Y说明为东/北约定；它不是地理真北认证。正文优先写“模型X正向一侧/模型Y负向”，需要东/北时附明采用的模型坐标约定。
- 方位来自固定IFC/建筑坐标，不由页面旋转后的左右直接推断。用户明确使用“画面右侧”且无法转换成唯一设计方向时，追问方向/距离，不静默猜测。
- Viewer `(x,z,-y)`变换和居中位移不作为IFC世界坐标发送。描述位置统一来自后端源IFC；定位中心明确为几何定位信息，不解释为新增构件放置点。
- 参考对象只是参考对象。用户说“同尺寸”不默认授权复制所有材质、属性和性能；点柱新增柱时真实执行target可为楼层；点窗作为参考时新增窗宿主仍须正确定位墙体。
- 用户要求与选择上下文冲突，显示冲突并澄清，不由服务端决定哪一项优先。无选择的完整请求正常提交；没有必需尺寸时不填默认值。
- 当前输入预算为UTF-8 16KiB（`RepairIntentLimits.max_request_bytes`）；合成文本及后续补充都纳入检查。先压缩系统生成的重复描述，不静默裁剪用户要求。

已知相关证据：`docs/validation/repair-comparison/demo-results.md:49–51`曾记录楼层名称、方位与精确Name混淆；后续scene路径见该文档开头。`scene_context.py:53–151`提供源世界坐标/楼层/宿主/Type/查询覆盖；`scene_grounding.py:124–148`可保留参照安装信息。

DeepSeek只保存实际接口返回的reasoning/response/usage；`live-attempt-*.json`等现有记录可关联到对应attempt。原始技术记录保留在开发详情，缺失/截断注明；不为显示过程额外调用LLM，不把推理自述当作IFC检查结果。终端evidence可投影应用摘要，不再复制成多份平行权威。

### 5.4 真实进度：现有状态还需要动作观察层

当前公共API确实写入created/source_validated/index_ready/intent_ready/targets_resolved/changeset_ready和澄清/终态。但是`APPLICATION_READY`、`EVALUATED`虽在枚举中存在，`api.py:842–872`仍把`apply_and_evaluate()`作为一次同步调用，之后直接提交终态。不能仅因枚举有名字就给前端画成已逐步上报。

接线分两层：

1. **业务状态权威**保持RunStore与RunResult。公开的 `state_version`只用于状态冲突/澄清校验，不用前端计时器推进。
2. **展示观察事件（拟新增）**由实际代码边界发出：阶段开始/结束、Provider attempt开始/完成、查询返回、纠错开始、应用写完、重开结束、Evaluation结束、澄清等待/已答、终端产物可用。观察器不做路由决策、不改变结果、不给模型附加指令。

首版使用HTTP轮询事件增量即可，约1秒一次；不同时搭SSE/WebSocket。事件持久化为单份JSONL或任务DB事件表（二选一），`event_seq`与原生`state_version`分开。GET读取不能启动/恢复任务；显示服务器已知事件，而不是在每次轮询重复计算全部几何或全量读取所有大文件。轮询频率在实现时验证I/O，不固定成高频忙轮询。

拟议事件字段：`task_id/run_id/event_seq/stage/action/status/attempt/state_version/occurred_at/summary_key/summary_args/artifact_ids/issue_refs`。无真实开始事件的历史记录，只显示已完成边界；当前动作不明确时显示“应用与检查中”，不编造百分比或持续时间。

前端六张阶段卡保持：读取模型→理解请求→定位与确认→形成修改→应用修改→检查与结果。每卡可展开该阶段的所有真实尝试；新事件不抢走用户正在阅读的旧文件。Intent/Draft阶段不产生新的IFC，三维仍显示原模型；存在候选且完整写入/可解析时才提供明确标记的预览。

### 5.5 澄清与前端的完整闭环

`start()`和`continue_with_answer()`都可能返回`clarification_required`，这是等待用户，不是失败，也不另开任务。

| 后端允许的answer.kind | 前端交互 | 后端继续方式 |
|---|---|---|
| `add_detail` | 输入框切成“回答此问题”，保留问题上下文；提交detail原文 | 同run追加补充说明，再执行Intent/scene理解，保存resume快照 |
| `select_candidate`（对象） | 候选名称/楼层/位置；点击先定位高亮，明确“选用此候选”才回答 | 发原候选token；服务端核对被提供候选，重做解析/后续步骤 |
| `select_candidate`（属性） | 属性路径、定义等卡片，不假装能定位三维网格 | 发原属性candidate_token，并保留operation/claim绑定 |
| `authorize_prototype` | 显示真实Type/参照与影响，按钮明确“确认使用该原型” | 发candidate_token和authorized=true，不把普通预览算成授权 |
| `confirm_property`/`reject_property` | 展示对应属性预览和接受/拒绝 | 发原preview_hash，不能前端重算或替换；不存在add_detail模式时不假装可任意回答 |
| `cancel`（需要时保留eof兼容） | 取消当前等待中的任务 | 原生取消路径；不是关闭网页就默认取消 |

回答请求必须包含当前 `run_id`、`clarification_id`、`expected_state_version`和answer。服务端还需执行每run单一写入租约及answer幂等，原因是当前API可能在最终状态提交之前已经调用Provider；不能只依赖提交时的版本冲突来避免重复收费。过期回复返回冲突并刷新问题，不把旧答案移植到新问题。

当前限制须诚实处理：

- scene阶段的clarification在`scene_grounding.py`验证candidate_ids，但返回给API的主要是scene_question；`_parameter_clarification`当前不能据此自动得到完整三维候选卡。首版如原生结果只给add_detail/cancel，就显示问题和文本回答，不从提问句子猜候选。若要丰富此分支，作为明确的后端公共信息投影补充单独测试。
- Type候选可能是IfcTypeObject而非可直接绘制的occurrence；只能基于已有实例映射做关联展示，映射没有时显示文字，不假定位。属性候选的public_id也不是构件GUID。
- 批量property confirmation的当前public preview有汇总信息，不保证已有每项旧/新值。前端要么按实际信息展示，要么从同次public确认记录补齐投影，不能编造字段明细。
- 一次答复仍缺事实时继续等待下一问；不设置“只准一次澄清”。CLI循环里的8轮上限不是Web任务默认无限预算授权；Web需共享任务级预算，等待用户不消耗运行超时，答复不清零费用/轮次。
- 运行中不把随手点别的构件改为当前答复。浏览、原请求引用、候选预览和已确认回答分开保存；等待时发出的文字只进入当前澄清通道。

### 5.6 已有纠错照常保留；最终检查后返工暂不做

**用户已确认（2026-10-10）：当前没有接通的C检查后返工模块先不开发，只留最小扩展位置，不再作为接线前置条件，也不再要求确认C的入口。** 这是范围决定，不代表删除最终检查、原生纠错或用户澄清。

#### 5.6.1 这次继续接入的两类回路

普通Intent最多2次；ChangeSet最多2次；scene grounding最多8轮，其中正常场景查询不是错误。格式、合同或绑定问题仍由原生VALIDATION_FEEDBACK处理，前端展示真实attempt及诊断，不降低或额外扩大现有重试预算，也不把它们叫作最终IFC返工。底层HTTP重试另外记账。

用户澄清仍使用同一个run和冻结源模型。`add_detail`重新理解累计自然语言，候选/属性/原型确认进入各自原生路径；不清零任务预算、不另写清空重跑机制。

#### 5.6.2 当前最终检查后的确定行为

| 实际结果 | 本轮处理 |
|---|---|
| 检查通过且原生结果允许发布 | 展示正式IFC，启用修复后查看和对应下载 |
| 检查未通过，存在完整可读取候选 | 展示失败原因，可查看“候选（未通过）”；任务结束，不自动重新调用模型 |
| 应用或Provider提前失败，没有候选 | 保留输入模型、诊断和已产生的材料；任务结束，不伪造IFC |
| 需要用户澄清 | 按§5.5等待并继续同run，不当作最终失败或C返工 |

`apply_and_evaluate()`、Evaluation及发布规则原样保留。不得因暂缓返工而跳过检查、把未通过候选发布为成功，或从原生失败终态直接调用`resume()`倒退执行。Generation的BIM JSON返工循环不移植到本次IFC接线。

#### 5.6.3 只预留一个内部扩展点，不搭建返工框架

接线开发时，把原生运行结果的接收与投影集中在任务层的结果处理入口（例如`handle_run_result`），不要分散到前端点击回调。任务层可以保留一个可选的`rework_policy`参数，**当前固定为`None`**；现阶段若有人尝试配置非空策略，明确报“尚未支持”，不能偷偷启用自动重跑。这是拟实现的内部接口约定，本次文档更新没有增加运行代码。

| 扩展边界 | 最小约定 |
|---|---|
| 位置 | Web任务编排/结果处理层；不改变`RepairAPI.start/continue_with_answer`的现有业务输入 |
| 将来可提供给策略的数据 | 当前task/run身份、原生RunResult、公开Evaluation和该run的artifact引用，均按只读数据处理 |
| 当前默认行为 | 不调用任何返工策略，不生成新run、不改源IFC、不追加模型调用或费用；直接保留原生终态 |
| 前端 | 不加无效的“自动返工”按钮，不虚构reworking阶段；已有真实事件和文件列表保持可扩展即可 |
| HTTP与文件 | 本轮不增加`/rework`端点、返工Schema、独立控制器文件或第二份计划；只在现有任务层留接口位置 |
| 将来启用条件 | 另行确认反馈输入、作用范围、次数/费用上限、停止条件和验收；旧失败run和已发布结果不能被覆盖 |

本次仅新增“默认不触发返工”的聚焦验收要求：最终检查失败不引发额外Provider调用或新run，同时原生Intent/Draft纠错和澄清继续仍然可用。不开发自动合并、版本分支或完整多轮编排系统。

### 5.7 结果怎样返回并在三维中展示

1. 任务结束后以`RunResult.successful_artifact_publishable`及`artifacts`判定结果，不以HTTP200、LLM“完成了”或staging有文件判成功。公开Evaluation进一步展开几何/关系/语义/保全等实际项。
2. 成功时读取正式IFC字节并解析；检查不通过但有可读candidate时单列“候选（未通过）”；无候选时仍显示输入模型与错误，不保留上一任务的结果下载按钮。
3. 当前`loadIfc()`会初始化相机、清空请求状态并分别居中模型，不能原样用于结果切换。需拆出“解析得到模型数据”和“切换显示对象”，任务对话不跟随结果载入清空。
4. 前后使用相同IFC世界坐标→Three坐标变换和输入基准的居中位移，不分别以自己的包围盒居中；切换保持position/target/up/zoom。IFC几何和材质只从对应文件解析，不根据ChangeSet画替代窗/柱。
5. 174的IfcOpenShell缓存只绑定174源文件，不能套用到repaired.ifc。首版普通输入/输出配对可都用已实测的web-ifc路径；如选用原生路径，则对任意输入/输出分别生成同配置、独立绑定的网格后比较。引擎选择固定在同一任务，不能无提示切换。
6. 点选身份按当前显示IFC的GlobalId/STEP映射处理。旧对象能匹配则保持定位；新增对象切回输入时显示不存在，不借同名对象代替。点击“查看修复前”仅改变视图，不把下一条任务基准切回旧文件。
7. 变化摘要先从实际application `operations[].changes`及独立解析出的对象取得新增/修改ID；过滤低层关系/几何实体，不把它们数成几十个建筑构件。需要对照时复用现有compare能力，不能用私有评估材料补生产说明。
8. 结果卡显示“新增了什么、位于哪里、参数来源、检查结论”，对象名可定位。下载入口通过artifact_id取得与画面版本一致的源IFC；重开后才启用正式结果查看，Viewer解析异常与Repair检查异常分别显示。
9. 继续修改是明确以当前已发布IFC为输入的新任务，不是Git分支功能。原输入/候选/正式输出仍保留以支持单次修复核对。

### 5.8 HTTP接口与执行模型（均为拟新增）

不改变现有前端技术栈。本轮不迁Vue、不建立协作账户平台。新增Python薄HTTP层与任务执行器，复用现有RepairAPI、RunStore和模型Provider配置；同源提供Viewer和API，避免让用户维护两个可见地址。现有Node静态服务保留为只读开发入口，默认启动器切换时必须先检查端口占用和服务身份。具体HTTP框架安装另在实现前核对本地依赖；不是为了接线重写整个后端。

| 接口草案 | 请求/返回重点 | 不能做的事 |
|---|---|---|
| `POST /api/ifc-inputs` | 上传当前IFC字节，返回input_id、schema、source_name、对象可用性摘要 | 接受任意服务器文件路径；读取dataset私有G |
| `POST /api/repair-requests/prepare` | input_id＋user_text＋主/辅引用→prepared_request_id、可读点选补充、effective_repair_text | 发模型请求或直接生成ChangeSet |
| `POST /api/repair-tasks` | prepared_request_id＋client_request_id→task_id/run_id，202 | 在HTTP请求里同步等整个Repair；重复点击重开任务 |
| `GET /api/repair-tasks/{id}` | 原生状态投影、执行是否在途、当前问题、结果角色、事件游标 | 读取即调用resume或把等待判失败 |
| `GET /api/repair-tasks/{id}/events?after=N` | 增量且有序的真实阶段/attempt/文件事件 | 伪造历史过程、返回半个文件 |
| `POST /api/repair-tasks/{id}/answers` | clarification_id、expected_state_version、answer、client_answer_id | 接受未提供候选、过期问题、重复触发付费 |
| `GET /api/repair-tasks/{id}/artifacts` | 当前任务已完成材料的artifact_id/角色/阶段/大小/可读摘要 | 任意目录浏览或泄露密钥 |
| `GET /api/repair-tasks/{id}/artifacts/{artifact_id}` | 只读JSON/文本或真实IFC下载 | 用模型提供的字符串拼服务器路径 |

前端刷新通过task_id重新查询；同一task/run的start/answer互斥。长任务放独立进程，模型密钥仅服务端；第一版单任务队列即可，不加Redis/Celery等平台。浏览器断开不杀进程；进程退出但原生未终态则标“中断”，只在既有合法边界恢复，不自动重新提交。运行中取消目前无完整公共接口，不先放“随时取消”按钮；等待澄清时用现有cancel。

Web侧只保存必要的input映射、请求侧车、幂等记录和观察事件。原生run是过程/成功权威；不要把同一结果在两处独立决定。文件名与模型文本均当数据处理；本机服务只监听本机，后续公开部署再定义身份与上传安全边界。本次不扩展多人版本平台。
