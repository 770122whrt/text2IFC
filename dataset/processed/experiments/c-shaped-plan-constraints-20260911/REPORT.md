## 为什么以前没有修到

旧案例与测试主要覆盖合法表示、部件身份、楼梯聚合关系和明确坐标的忠实编译。C 型凹角进一步暴露了两个不同边界：自由文字中的“墙在轮廓内、连续且不重叠”没有成为执行检查；Generator 的非法字段改名又可能退回完整 JSON 返工，丢掉本来正确的关系。

此前 Brief 与 Expected Facts 来自同一个模型结果，后续编译可以忠实实现一个错误的派生墙界。因此，“输出与 Brief 一致”不能证明它满足用户原始几何要求。原始失败与独立检查均保留在[上次报告](../c-shaped-wall-join-20260911/REPORT.md)，没有修改评价器来迁就候选。

## 本次通用机制

- 显式选择 Brief2.4：用 `plan_constraints` 表达已明确的轮廓内墙带约束，引用真实轮廓、楼层、墙厚和用户轮次。无该要求时为空，旧合同与默认生成策略保持。

- 只允许一次模型校正发生错误楼层中声明为派生值的墙界；用户明确墙界、轮廓、墙厚、门窗、楼梯、宿主、身份和材料均无写权限。剩余错误或越权使整个校正失败；明确事实冲突不能通过移动别的墙掩盖。
- 旧字段修复已改为受限 ChangeSet：唯一合法枚举字段可被提供给模型确认，原值和所有关系必须保留；本轮继续验证该路径。
- 原始响应、校正响应和检查分别保存。最终仍须独立重开 IFC 检查，不接受模型自报覆盖率作为正确值证明。

## 真实运行后发现的名称误报：修复前记录

本次完整 loop 已编译并通过独立485项检查，但第一次 Audit 因三条 `STOREY_NAME_CONFLICT` 阻断，随后 ChangeSet 只改三处 Name 才通过。这是旧名称 gate 的误报，不把改名作为系统修复。原修复后的候选、初次 gate 与 Audit 均冻结在 `live-run/runs/defec36086974f4b/evaluation-rounds/round-01/`。

H1：检查错误地要求跨层楼梯名称必须逐字包含出发层正式名称；“一层”不等于楼层记录的“首层”，尽管实际关系和冻结端点正确。预测改用已冻结端点作为可提及楼层集合后，任意语言的出发层简称均不再误报。H2：楼板洞口没有继承其明确服务楼梯的跨层语境，预测仅对唯一冻结洞口/宿主及唯一对应楼梯开放该语境可以消除误报，普通墙门窗仍不可任意提及别层。H3：实际归属/关系错误，预测独立关系和几何检查失败；若如此不得更改名称 gate 掩盖它。本次几何检查通过，现存修改仅为名称，支持前两项。

本小步限定名称启发式的适用边界：楼层实体关系优先；已冻结连接中的出发/到达层都可能合法出现在楼梯名称中，只有目的层名称也不能独立证明归属错误。此前“destination_only 必须失败”的测试是过强语义假设，应作为明确合同修正记录，不添加“一层=首层”等别名表。楼梯洞口语境要求冻结洞口身份、唯一实际 void 宿主、宿主楼层以及唯一冻结楼梯的到达层和洞口平面范围共同对应；不通过候选 Name 或 ID 字符串猜测。缺少/重复/错误宿主或端点、普通构件、无证据的第三层提及仍拒绝。开发族覆盖三种楼层命名、单端点措辞、父/子楼梯、洞口、错误和歧义负例，保全候选字节；同时用同一修复后检查重评冻结初始和最终候选。最终 IFC 检查器不变，不据此报告系统成功率。

结果：冻结名称族修复前15失败/26通过；修复后相关99项检查通过，含两种策略公共编译/独立IFC检查。见 [红测试](validation/name-context-red.xml) 与 [最终回归](validation/name-context-final.xml)。同一名称检查重评初次及最终候选，初次3条误报→0，最终0→0；其他动态gate状态和候选/最终IFC字节均保留，见 [旧检查](name-baseline.json)、[新检查](name-candidate.json)。仅可声明本类已知误报修复及回归通过，不能声明未知任务成功率提升。
