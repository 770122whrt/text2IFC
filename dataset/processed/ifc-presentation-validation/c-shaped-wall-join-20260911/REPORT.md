## 1. 原因是什么

新普通 Brief Prompt v2.12 从同一请求和真实澄清重新执行，没有承接上次的错误候选。凸角墙边界较上次改变，但凹口西墙仍落在开敞缺口里：Brief 给出 X=4800～5000、Y=4800～12000 mm，而 C 形实体在该段位于 X≤4800 一侧。可见只增加 Prompt 说明，尚不能保证轮廓内的墙接合正确；这属于模型派生几何错误，不是用户批准扩大轮廓。

本次更早发生的实际阻断在字段修复路径：

1. Generator 的9个空间使用非法属性名 `InteriorOrExternalSpace`。本仓库 IFC2X3 registry 的合法名为 `InteriorOrExteriorSpace`，编译合同正确拒绝非法名。
2. 原候选111个实体、60条关系；两个 IfcStair 已通过 IfcRelAggregates 连接各自梯段，父楼梯无需自身 Representation。
3. 旧局部字段恢复只支持 terminal-s 拼写配对，这类错误退回整份 JSON Repair。模型改正属性时又漏掉两条聚合关系，输出变成111个实体、58条关系。
4. 两个父楼梯因此失去表示来源，校验报 MISSING_REPRESENTATION，公共流程以 `draft_or_blocked` 停止。这不是旧楼梯要求重新出现，也不是应当放宽校验的误报；是完整 JSON 返工丢失无关关系。

真实证据：run [`916d8afe752160e3`](live-run/runs/916d8afe752160e3/case-result.json)、[原字段反馈](live-run/runs/916d8afe752160e3/generator/validation.json)、[Repair 路由](live-run/runs/916d8afe752160e3/repair/route.json)。[逐项诊断](diagnosis.json)列出丢失关系、前后合法性及实际 usage。

## 2. 已修什么，为什么这样修

新增早期字段恢复合同1.1 / ChangeSet Prompt v1.8：对于非法字段，如果原字符串值精确匹配当前 IFC 类唯一的可编写枚举字段，且目标不存在，则只提供旧字段和该目标字段的修改权限。模型仍需结合请求/Brief 判断含义，不能确认时返回 Draft；机器不自动改名或代选语义值。

原值必须保留，其他字段、几何、材料、实体、全部关系均无写权限。多个字段匹配、目标冲突、未知枚举、自由数值/文字、反馈不实或额外几何错误继续阻断；部分修复和越界写入整组回滚。保留既有非法枚举值纠错路径，不修改旧注册 Prompt/Schema、默认生成策略或 Repair IFC 几何。

这样直接减少完整 JSON 返工的机会，并由执行器保证范围外保全，不仅依靠“不要漏关系”的提示。它只证明受限结构修改成立；唯一枚举匹配不等于自然语言含义证明，更不代替最终 IFC 语义检查。

本案例的**手写离线诊断 ChangeSet**修正9个字段后，合同校验通过、60条关系逐ID完整保留、范围外组件哈希和原候选字节未变。没有调用 Provider、没有把该副本编译为交付 IFC；不能把此结果当作真实模型修复成功或 C 完成。
